# AGENTS.md — правила работы агента в этом проекте

> Этот файл читается **автоматически в начале каждого нового чата**. Он задаёт
> обязательный процесс, запреты и чек-лист старта сессии. Дополняет системные
> инструкции; по вопросам процесса и домена приоритет у этого файла.

## 1. Язык

Всё на русском: артефакты, спеки, отчёты, summary, комментарии в коде, тексты
коммитов. Не переводить: имена файлов, пути, идентификаторы capability
(kebab-case), код, команды, флаги CLI. Полные правила — `openspec/config.yaml`.

## 2. Обязательный процесс: всё через OpenSpec (автоматически)

**Полная программа в ветке `concept/intelligent-lead-research` (решение пользователя 2026-10-15):** весь объём [36 требований](docs/intelligent-lead-platform-roadmap.md) и применение изученной информации обязательны к реализации. Change — `intelligent-lead-research`; связь пожеланий, исследований и задач — `docs/concepts/intelligent-lead-research/implementation-coverage.json`. R1–R4 задают начальную последовательность и не снимают международные рынки, собственный поиск/краулер, browser/OCR, формы, inbound email и ответы. Исходные ответы CL-00…CL-13 и их происхождение сохранены в общем реестре: Crawlee/SearXNG/RU–GB/unit пилота — предложения ассистента, ручной режим форм — старый pending-план, а не окончательные решения пользователя. Ограничения существующего demo ниже сохраняют его путь; они не урезают отдельно запрошенную пользователем полную программу. Реализация и закрытие задач требуют apply/verify и реальных доказательств.

**Актуальный приоритет demo scope:** `customer-demo-request-to-emails` — существующая
регистрация/profile approval → заявка с отдельными offer и desired leads → approve
заявки → реальный crawl → тематические письма, видимые оператору на существующем
экране. Отправка и отдельное approve/reject писем не блокируют результат. Следовать
ограниченному плану `docs/e2e-plan.md`; сначала ручной реальный crawl через UI, затем
исправлять только наблюдаемые блокеры. Не расширять scope до whole v2, recovery/
hardening, SMTP, отдельного crawl mode, editorial capability/CAS, PG upgrade/replay
hardening или полного no-action-approved sweep.

- **Любое** изменение поведения, кода, домена, спеки, каталога или инфраструктуры
  выполняется **только через изменение OpenSpec** (schema `spec-driven`):
  change → proposal → specs → design → tasks → apply → verify → archive.
- Агент **сам** инициирует этот процесс, не дожидаясь напоминания: сопоставляет
  запрос пользователя с существующим change или создаёт новый
  (`openspec new change "<name>"`), затем ведёт по артефактам.
- Каталоги под `openspec/changes/` **вручную не создавать** — только через CLI
  (нужны метаданные `.openspec.yaml`).
- **Перед правкой кода:** убедиться, что существует change и задача под эту
  правку. Нет — сначала OpenSpec, потом код.
- Использовать навыки `.agents/skills/openspec-*` (`new`/`continue`/`apply`/
  `verify`/`archive`/`sync`/`update`).
- Статус задачи меняется (`- [ ]` → `- [x]`) **только** при выполнении её
  критерия «верификация». Завершение — `verify`, затем `archive`.
- **Перед началом работы над запросом** сообщить пользователю план в терминах
  OpenSpec (какой change, какие артефакты), и только затем писать код.

## 3. Заглушки запрещены как результат

**Определение.** *Заглушка* — реализация порта, которая не выполняет реальную
функцию, а возвращает фиксированный/усечённый результат или отказ
(`deterministic`, `unavailable`, `fake`, `noop`), поставленная на путь
продуктовой или пользовательской функции.

**Правило:**

- Заглушка SHALL NOT использоваться как реализация функции и SHALL NOT выдаваться
  за работающую интеграцию.
- Изменение, задача или контур **не считается выполненным**, пока на его пути
  стоит заглушка. Нельзя закрывать задачу, чей критерий требует реальной
  интеграции, оставляя заглушку в коде или конфигурации.
- Нет внешней системы (провайдера, БД, сервиса) — задача **остаётся открытой**;
  заглушка её не закрывает.
- В интерфейсе и логах заглушка **не маскируется** под успех.
- Конкретный перечень заглушек к незамедлительному исправлению (P0) —
  `docs/implementation-matrix.md`, раздел «0. Заглушки к незамедлительному
  исправлению». Он — очередь приоритета; на каждый пункт создаётся OpenSpec change.

**Допустимые исключения (не «заглушка как результат»):**

- честный `unavailable`-отказ в **нереализованном** контуре — допустим как явное
  состояние, но означает нереализованность и держит change незакрытым;
- тестовые двойники (`fake`/`deterministic`) — **только** в тестах и dev-контуре,
  никогда как поставка;
- `deterministic` — только если детерминизм и есть требование, а не подмена
  внешнего движка.

## 4. Гейт приёмки

Перед отметкой любой задачи или change выполненным:

- `make check` (build / test / vet / importlint / archlint / openspec) — зелёный;
- `go -C tools/archlint run .` — код 0;
- `openspec validate <change> --strict` — valid;
- на пути задачи нет заглушек (§3).

Нарушение архитектурной границы или заглушка **не отмечается** выполненным.

## 5. Доменная архитектура

- Канонические границы — `architecture/domain-catalog.yaml`; объяснение —
  `docs/domain-model.md`.
- **Context-first:** код, данные и контракты относятся к bounded context; чужая
  доменная модель напрямую не импортируется.
- Change, меняющий capability, агрегат, владение или связь, обязан обновить
  каталог, `docs/domain-model.md` и затронутые диаграммы **в том же change**.
- Не смешивать: bounded context (модель) / сервис (единица деплоя) / роль (режим
  запуска) / BRD-движок (функция).

## 6. Старт сессии — чек-лист

1. Прочитай этот файл (`AGENTS.md`).
2. `docs/progress-log.md` — **сначала строка «Фокус сейчас»** (активный change),
   затем «где остановились», решения, предупреждения.
3. `docs/core-roadmap.md` — план, этапы, точка подхвата.
4. `docs/implementation-matrix.md` — что реально реализовано (уровни A/B/C).
5. `openspec list` — активные изменения и их статус.
6. Определи change для запроса (§2); если его нет — создай.
7. Сообщи план пользователю в терминах OpenSpec.

**Не начинать правки кода до шага 6.**

## 7. Источники истины

| Артефакт | Что задаёт |
|---|---|
| `architecture/domain-catalog.yaml` | контексты, агрегаты, capability, связи |
| `docs/system-map.md` | карта исполнения |
| `docs/architecture.md` | архитектурные решения, механизмы, стек |
| `docs/domain-model.md` | доменная модель и владение |
| `docs/business-requirements.md` | функциональный бэклог (BRD) |
| `docs/implementation-matrix.md` | факт по слоям: что реализовано, где заглушка |
| `deploy/services.yaml` | группы процессов и роли запуска |
| `openspec/specs/`, `openspec/changes/` | требования продукта |
| `docs/progress-log.md` | журнал решений и точка подхвата |

При расхождении: рамка → спеки → архитектура (§1–10) → карта. Документ правится,
а не спорит.

## 8. Прочее

- Не коммитить и не создавать ветки без явной просьбы пользователя.
- Не удалять и не переписывать изменения, сделанные не тобой.
- Правило архивации дельт: изменение с `## MODIFIED`/`## REMOVED` архивируется
  **после** изменения, создавшего затронутую capability.
- Документы правятся в том же change, что меняет их содержание.
- Итоговые сообщения и отчёты — на русском, со ссылками на файлы
  (project-relative пути).
