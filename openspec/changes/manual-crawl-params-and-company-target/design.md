## Context

Задание поиска обслуживает примитив `backend/platform/jobs` (не доменный агрегат): `Store` хранит состояние `queued → running → done/failed`, `Runner` в потоке воркера вызывает `RunSearch.Handle`. `RunSearch.Handle` декодирует непрозрачный `SearchJobPayload`, строит бюджетную задачу Firecrawl, планирует цели (`LLM.Plan` либо дословный план из payload) и для каждой цели делает `Search`, а затем `Crawl` по каждому результату; найденные компании копятся в `companyIDs` по нормализованному домену (`processPage`).

Ограничения, определяющие подход:

- Обход сейчас **обязан** нести `MaxDepth > 0` и `MaxTimeSeconds > 0` (`crawlURL` их требует), а бюджетная обёртка `guard.Crawl` отклоняет вызов без явного `max_pages`. Это зафиксировано требованием `firecrawl-credit-budget`.
- Счётчик найденных компаний уже существует в `RunSearch.handle`, но используется только для прогресса, а не для остановки.
- Планирование (`LLM.Plan`) работает по интерфейсу `llm.Port` и не поддерживает пагинацию поиска; порт `search` тоже не поддерживает страницы.
- Прогресс — `ports.SearchJobProgress`; фазы — константы `Phase*` в `app/progress.go`. Доменной модели задание поиска не касается: в `architecture/domain-catalog.yaml` нет агрегата поискового задания.

Мотивация — см. `proposal.md`; требования — дельты спек `company-quota-search`, `search-strategy`, `search-job-progress`, `firecrawl-credit-budget`.

## Goals / Non-Goals

**Goals:**

- Оператор задаёт целевое число компаний; задание останавливается по достижении цели.
- Задание добирает цели, пока цель не достигнута или не наступит условие остановки.
- Оператор задаёт цели вручную (seed-запросы и/или стартовые URL) и лимит числа результатов поиска.
- Обход может идти без обязательной глубины, времени и внутреннего предела страниц.
- Единственный денежный тормоз — опциональный кредитный бюджет; без него граница — подтверждённый остаток аккаунта.

**Non-Goals:**

- Не строим автономного фонового агента: задание по-прежнему запускается явным действием оператора.
- Не добавляем пагинацию в контракты `search`/`crawl` (добор идёт перепланированием целей).
- Не меняем доменную модель: не вводим агрегатов, сущностей, value objects и domain events. Новая capability `company-quota-search` регистрируется у владельца `lead-management` в каталоге и в capability matrix, но модель не добавляет; межконтекстные контракты не меняются.
- Не меняем машину состояний `jobs` (`queued/running/done/failed/cancelled`): достижение цели — это `done`.

## Decisions

### D1. Целевое число компаний — условие остановки в прикладном слое

`targetCompanies` входит в `SearchJobPayload`, а условие остановки проверяется в `RunSearch.handle` между страницами обхода и между целями. Счётчик — существующий `len(companyIDs)`.

*Owning context:* `lead-management`. Агрегата нет: поисковое задание — операционный примитив `jobs`, а не доменная сущность, поэтому новых сущностей, доменных событий и политик не появляется. Это осознанное решение: заводить агрегат «поисковая сессия» ради счётчика — избыточно и размывает границу домена.

*Альтернатива:* доменный агрегат с инвариантами квоты — отклонено (противоречит природе задания как операционного процесса).

### D2. Добор целей — повторное планирование с дедупликацией

Когда цели исчерпаны, а `len(companyIDs) < targetCompanies`, прикладной слой вызывает `LLM.Plan` ещё раз, передавая перечень уже использованных целей, чтобы получить новые. Использованные цели ведутся в множестве с нормализацией (поисковый запрос — trim + lower; URL — схема и завершающий слэш отбрасываются). Добор завершается, когда `Plan` не вернул ни одной новой цели, при ошибке `Plan`, при исчерпании бюджета или при достижении предела итераций добора. Без `LLM` (nil) добор невозможен: задание завершается с причиной «цели исчерпаны».

*Альтернатива:* пагинация `search.Port` — требует поддержки постраничного поиска в Firecrawl и межу контракта; отложено. *Альтернатива:* увеличение `MaxResults` без добора — после первого поиска Firecrawl вернёт те же URL, новых целей не появится.

Предел числа итераций добора задаётся конфигурацией (защита от зацикливания).

### D3. Лимиты обхода: обязательность снята, но денежный и страничный тормоза остаются

- `crawlURL` перестаёт требовать `MaxDepth > 0` и `MaxTimeSeconds > 0`: отсутствие значения означает «не ограничивать». Дедлайн времени ставится только при заданном `MaxTimeSeconds`.
- `guard.Crawl` перестаёт требовать явный `max_pages`. Граница страниц на сайт = `min(lead-max-pages, подтверждённый остаток аккаунта, доступный бюджет задачи)`. Резерв = итоговая граница, сверка по факту.
- Бюджет и остаток аккаунта — **денежная** граница, но не число страниц: передавать движку весь бюджет как `limit` нельзя — движок пытается выкачать пол-сайта (тысячи страниц), обход висит и падает по таймауту (`unexpected EOF`). Число страниц на сайт задаёт внутренний предохранитель.
- Внутренний предохранитель `lead-max-pages` — верхний предел страниц на один сайт; значение по умолчанию `50`, `0` — без предела (осознанный риск).
- Адаптер при нулевом лимите не отправляет `limit` в Firecrawl (только при положительном).

**BREAKING** для требования «обход только по явному лимиту»: см. дельту `firecrawl-credit-budget`. Проверка свежего остатка аккаунта перед затратной операцией сохраняется.

### D4. Бюджет ограничивает и добор

Перед каждой итерацией добора прикладной слой проверяет снимок бюджета: если доступного остатка меньше минимальной стоимости следующего шага (поиск + хотя бы одна страница), добор прекращается и задание завершается с причиной «бюджет исчерпан». Без заданного бюджета этой проверки нет — ограничение только через остаток аккаунта в `guard`.

*Альтернатива:* не проверять бюджет на доборе — риск незаметного превышения; отклонено.

### D5. Ручные цели и лимит поиска — расширение payload и формы

`SearchJobPayload` получает `targetCompanies int` и `maxResults int`. Ручные цели уже выражаются существующим `Plan.Targets` (`PlanTarget`), поэтому новая модель не нужна: форма и панель ассистента собирают `[]ports.PlanTarget`, `decodePlanTargets` переиспользуется. `maxResults` доходит до `search.Query.MaxResults` через `CrawlLimits`/`RunSearch`. Оба поля необязательны: отсутствие читается как `0` (цель не задана; лимит — по умолчанию адаптера), что сохраняет совместимость старых заданий.

### D6. Прогресс и причина остановки

`SearchJobProgress` расширяется полями `TargetCompanies`, `TargetReached` и `StopReason`; добавляется фаза `PhaseExpanding` («добор целей»). Причина остановки пишется в снимок прогресса терминального события `EventDone` (новый тип события не вводится). Журнал показывает «найдено X из N». Расширение прогресса требует согласованной правки обоих хранилищ (PostgreSQL и memory).

### D7. UI

- Главная (`dashboard.html`, форма «Новый поиск»): поля «Сколько найти», «Результатов на запрос», textarea «Свои цели» (по строке — запрос или URL); бюджет остаётся. `views.go`/`templates.go` получают соответствующие поля представления.
- Ассистент (`assistant.html`): панель плана становится редактируемой — цели, целевое число и лимит поиска правятся перед «Запустить краулинг»; скрытые поля формы заменяются видимыми.
- Журнал: «найдено X из N» и фаза добора.

### D8. Устойчивость обхода: сбой и таймаут сайта не роняют задание

Сбой обхода одного сайта (`crawl.failed`), исчерпание лимита времени на один сайт и отказ одного поискового запроса (`search.failed`) перестают завершать задание: ошибка логируется и учитывается в метрике, уже добытые страницы проходят разбор и сохраняются, а обработка продолжается со следующей цели. Это ключ к «ничего не упускать»: один проблемный или медленный сайт, либо один неудачный запрос, не должны терять результаты по остальным. Дедлайн времени ставится на один сайт (`crawlCtx`), а не на задание, поэтому его истечение — не отмена. Реальной отменой остаётся только отмена родительского контекста (оператор/остановка процесса). Транзиентные сбои транспорта (обрыв соединения `unexpected EOF`, сброс соединения, сетевой таймаут, ответ 5xx) повторяются в адаптере (`IsTransient`); отмена и дедлайн контекста не повторяются. Прежний код `crawl.failed` остаётся доступным, но штатный сбой отдельного сайта им больше не завершается.

*Альтернатива:* оставить сбой или таймаут сайта фатальным — противоречит цели «ничего не упускать»; отклонено.

## Risks / Trade-offs

- **[Неограниченный расход]** Снятие обязательных лимитов обхода рискует расходом кредитов. → Обход проходит через `guard`: проверка свежего остатка аккаунта, резерв, остановка при 402; денежная граница — остаток аккаунта и бюджет задачи; число страниц на сайт ограничивает внутренний предохранитель; оператор может задать бюджет. Фактический расход виден по ходу.
- **[Добор зациклится или исчерпает LLM]** Повторное планирование может не давать новых целей. → Дедупликация целей, предел итераций добора, остановка при пустом приросте с явной причиной.
- **[Дорогое перепланирование LLM]** Каждая итерация добора — вызов `LLM`. → Ограничено пределом итераций; без ключа LLM добор недоступен и задание останавливается честно.
- **[Повторный обход тех же URL]** Дедупликация компаний есть, но повторный обход URL тратит кредиты. → Вести множество обойдённых URL и пропускать уже обработанные.
- **[Долгое задание занимает воркер]** Без `MaxTimeSeconds` задание может идти долго. → Аренда и согласование осиротевших заданий уже есть; оператор может отменить; время обхода ограничивается, если задано.
- **[Несовместимость с прежним контролем]** Снятие обязательного предела страниц ослабляет прежнюю гарантию полного контроля расхода. → Риск принят осознанно по запросу оператора; фиксируется в изменённом требовании `firecrawl-credit-budget`.

## Migration Plan

- Изменение `SearchJobPayload` обратно совместимо: старые задания без новых полей читаются как «цель не задана», «лимит по умолчанию».
- Снятие обязательных глубины/времени и возврат `lead-max-pages` к значению `50` — точка несовместимости по поведению; откат — возврат прежних проверок в `crawlURL`/`guard.Crawl` и прежнего значения конфигурации.
- Расширение прогресса требует обновления хранилищ (PostgreSQL и memory) в рамках change; конкретный способ (колонки или JSON) сверить с реализацией `search_job` при apply.

## Open Questions

- Поведение Firecrawl при полностью незаданном `limit` обхода (жёсткий дефолт движка или обход всего сайта) — уточнить по движку при реализации; на решение о границе остатка аккаунта это не влияет.
- Значение предела итераций добора по умолчанию — подобрать эмпирически; на структуру артефактов не влияет.
