## Why

Остались два движка без capability, и оба участвуют в workflow (BRD §4.1, вопрос 21):

- **3.10 Цепочки** — шаг 4: подготовка черновиков. Без него каждое касание готовится вручную отдельно, и повторные касания не выполняются вовсе.
- **3.15 Отчётность** — шаг 9 и обратная связь: без него конвейер не замыкается, потому что результат кампании не возвращается в следующую.

Оба движка попадают в одно изменение, потому что образуют замкнутый контур: цепочка порождает касания, отчётность показывает их результат, результат определяет следующую кампанию. По отдельности ни один из них не даёт работающего цикла.

**Цепочки — самое опасное место рамки.** Движок создан для того, чтобы действовать без человека: он ведёт последовательность касаний, ждёт задержки, переходит по условиям. Соблазн добавить автоматическое утверждение по истечении срока огромен — иначе цепочка встанет. Но Решение 1 рамки запрещает исполнение без утверждения, и BRD 3.10 фиксирует прямо: **автоматическое утверждение по истечении срока не выполняется, неутверждённый шаг остаётся неисполненным.** Значит цепочка обязана уметь стоять, а система — сообщать о простое вместо того, чтобы его устранять.

**Отчётность упирается в границу зон.** Пул живёт в контуре клиента (Решения 1 и 6), а отчёт требует агрегатов по этому пулу. Значит отчётность не может просто «читать данные»: она должна собираться там же и отдавать агрегат, не поднимая записи.

## What Changes

- **Добавляются две capability:** `outreach-sequences` (движок 3.10) и `campaign-reporting` (движок 3.15).
- **Цепочка порождает черновики и не отправляет ничего.** Каждый шаг исполняется только после отдельного утверждения оператором.
- **Автоматическое утверждение по истечении срока запрещено.** Неутверждённый шаг остаётся неисполненным; система сообщает о простое и не устраняет его сама.
- **Остановка цепочки автоматическая, возобновление — только человеком.** Приостановка при ответе, остановка при отписке, отказе или попадании в стоп-лист выполняются системой. Обратный переход — решение оператора.
- **Условие открытия отсутствует в языке ветвления.** Как и в сегментации: не помечено нежелательным, а не существует.
- **Отчёты считаются в контуре клиента и возвращаются агрегатами.** Записи пула на платформу не поднимаются.
- **Отчёты отдают агрегат с порогом минимальной группы.** Срез по одному человеку не показывается: агрегат из одной записи раскрывает её.
- **Управленческая отчётность отделена от отчётности по лидам.** Активность менеджеров — сведения о работе сотрудников клиента, а не о лидах.
- **Не входит:** автоматическая отправка любого рода, автоутверждение, A/B-тесты, прогнозные модели, отчёты по открытиям (сигнал не собирается).

## Capabilities

### New Capabilities

- `outreach-sequences`: ведение последовательности касаний. Охватывает: конструктор сценариев с шагами, задержками и условиями; порождение черновиков на каждый шаг; отдельное утверждение каждого шага; запрет автоутверждения по сроку; ветвление по переходам и ответам; приостановку и остановку; ограничение числа касаний; журнал выполнения.
- `campaign-reporting`: аналитика по кампаниям, лидогенерации и воронке. Охватывает: дашборды по кампаниям, источникам, воронке; отчёт по качеству базы; управленческую отчётность; фильтрацию; выгрузку; агрегацию с порогом минимальной группы.

### Modified Capabilities

Нет. `openspec/specs/` пуст. Связь:

| Capability | Связь |
|---|---|
| `outreach-approval` | цепочка ставит черновики в очередь утверждений; это её основной потребитель |
| `read-tracking` | поставщик сигналов перехода и ответа; отчётов по открытиям нет по её требованию |
| `lead-segmentation` | сегмент — цель кампании и срез отчёта |
| `email-verification` | отчёт по качеству базы опирается на статусы адресов |
| `lead-pool-client-side` | отчётность считает по пулу в том же контуре и возвращает агрегаты |

## Impact

**Закрывает пробел покрытия.** Последние два движка из перечня «Движки без capability» (вопрос 21 BRD §8). После этого изменения перечень пуст, и остаётся только вопрос 23 о роли 3.17.

**Соответствует рамке.** Цепочки — прямое применение Решения 3: черновик порождается, утверждение требуется на каждом шаге, автоутверждение запрещено требованием. Отчётность — зелёная зона: агрегаты без записей.

**Главный риск — простой цепочек.** Если оператор не утверждает шаг, цепочка стоит. Это не дефект, а свойство: альтернатива — автоутверждение, запрещённое рамкой. Смягчение: система обязана сообщать о простое, а не устранять его; отчётность показывает объём неутверждённых шагов, чтобы простой был виден.

**Второй риск — агрегат раскрывает запись.** Срез, отфильтрованный до одного человека, показывает его данные. Смягчение: порог минимальной группы и агрегация в контуре клиента.

**Экономика.** Отображать пропускную способность. Отчётность не создаёт ценности напрямую, но без неё нельзя доказать результат, а доказуемость — то, что продукт продаёт.

**Доменная модель.** Изменение затрагивает bounded contexts: outreach-orchestration, analytics, message-delivery, engagement-observation. Owning context capabilities: `outreach-sequences` — `outreach-orchestration` и `campaign-reporting` — `analytics`. Новые сущности принадлежат aggregate `campaign` (aggregate root `campaign`), доменные события — `campaign-state-changed`, `outreach-outcome-recorded`, policies — `outreach-scheduling`, `operator-approval-required`; второй aggregate `campaign-report` (aggregate root `report-snapshot`) даёт доменное событие `report-snapshot-created`, его policy — `anonymized-reporting`. Межконтекстные взаимодействия идут через контракты `campaign-command`, `analytics-event`, `campaign-report`, `outreach-outcome`. Границы, владение и связи не меняются, поэтому `architecture/domain-catalog.yaml`, `docs/domain-model.md` и диаграммы остаются как есть.
