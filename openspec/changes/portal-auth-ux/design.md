## Context

Клиентский портал отдаётся ролью `api` сервиса `platform-governance`
(`backend/contexts/platform-governance/internal/adapters/http`). Анонимные
экраны (`/login`, `/register`, `/reset`, `/register/sent`) собираются тем же
каркасом `frontend/components/templates/layout.html`, что и рабочие экраны:
каркас рисует боковое меню, если у страницы непустой `Page.Sidebar`. Ранее
`portalNav` для анонима возвращал пункты «Вход» и «Регистрация», а в
запущенном контейнере — ещё и рабочие разделы. В результате гость видел меню
рабочей консоли.

Шаблоны вшиты в бинарник через `//go:embed templates/*.html`, поэтому правки
разметки не видны до пересборки образа. Это объясняет, почему изменения не
отражались на фронте.

## Goals / Non-Goals

- **Цель:** анонимные экраны выглядят как обычный сайт: вход — точка входа,
  выбор «Вход | Регистрация», отдельная форма регистрации, поля собраны в
  логические секции и ограничены по ширине.
- **Цель:** рабочее боковое меню показывается только аутентифицированному
  клиенту.
- **Не цель:** менять доменную модель, каталог, маршруты, сценарии
  аутентификации и текст сообщений сверх необходимого.
- **Не цель:** трогать операторскую консоль и её навигацию.

## Decisions

### Решение 1. Пустой `Sidebar` у анонима вместо нового каркаса

Страницы анонимных экранов получают `Sidebar: components.Nav{}` (пустой список
пунктов). `layout.html` уже рендерит `nav` только при непустом `Sidebar.Items`
и не применяет grid-каркас `body:has(> .sidebar)`. Новый layout-шаблон не
вводится: это точечное изменение представления, а не новый слой.

### Решение 2. Сегментированный переключатель «Вход | Регистрация» внутри карточки

Выбор реализуется существующим фрагментом `tabs` (`components.Tabs`), который
уже выглядит как сегментированная капсула. Модель страницы получает поле
`AuthTabs components.Tabs`; шаблон вставляет `{{ template "tabs" .View.AuthTabs }}`
внутри карточки (а не через `Page.Subnav`, который рендерится вне содержимого).
Подписи берутся из каталога сообщений (`text`), не из шаблона.

### Решение 3. Центрированная auth-карточка общим CSS

В `frontend/components/static/console.css` добавляются `.auth-shell` (центровка
и отступ сверху) и `.auth-card` (стеклянная карточка с ограничением ширины:
узкая — для входа/сброса, широкая — для регистрации). Секции формы
(`.form-section`) уже дают две колонки при `min-width: 52rem`; ограничение
ширины карточки убирает «колбасы» на широком экране.

### Решение 4. Границы и один writer

Общий слой `frontend/components` правит один участник; разметка контекста —
`platform-governance`. Доменная модель не меняется.

## Risks / Trade-offs

- **[Устаревшая сборка]** → Изменение шаблонов не видно без пересборки образа;
  в задачах и верификации обязательна пересборка `platform` и живой запрос
  страницы.
- **[Кэш `console.css`]** → Статика раздаётся `FileServerFS` с обычными
  заголовками; при проверке использовать жёсткое обновление/версию. Явного
  cache-busting в этом change не вводится.
- **[Конфликт с presentation в активном change]** → Требование уточняет
  анонимный UX, описанный в `client-account-request-flow` §8; конфликтующий
  пункт о боковом меню у анонима считается заменённым этим change'ом.

## Migration Plan

Миграций данных нет. Порядок: правка общего CSS → разметка и модели контекста →
тесты/золотые рендеры → пересборка контейнера `platform` и живая проверка
`/login` и `/register`.
