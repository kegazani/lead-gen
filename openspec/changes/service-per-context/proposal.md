## Why

Модель и владение уже разрезаны по bounded contexts, а развёртывание — нет: единица деплоя сейчас процесс, и каждый контекст разложен по 2–4 из шести процессов (`api`, `ingest`, `sender`, `worker`, `chains`, `schedule`), а `integration-platform` — по всем шести. Из-за этого границы отказа, масштабирования и выката не совпадают с границей владения: правка одного контекста требует перевыката общего процесса, один пул отказа обслуживает несвязанные жизненные циклы, независимо масштабировать конкретный контекст нельзя. Швы при этом уже прорезаны: `backend/contexts/<ctx>` изолирован, межконтекстных импортов нет (кроме `composition`), спека запрещает распределённый агрегат, а связи описаны как published-language / customer-supplier с видами event/command/query/policy. Контекст уже почти сервис — остаётся сделать его сервисом и по этой границе резать развёртывание.

## What Changes

- **BREAKING:** единица сервиса и развёртывания — bounded context. Каждый из 11 контекстов становится отдельным сервисом с собственной границей отказа, релиза и масштабирования.
- **BREAKING:** `deployed_by` в каталоге заменяется: сервис у контекста один, а `api`/`ingest`/`sender`/`worker`/`chains`/`schedule` перестают быть процессами-владельцами размещения и становятся ролями (режимами) запуска внутри сервиса.
- **BREAKING:** 13 синхронных связей (9 `command`, 4 `query`) становятся сетевыми вызовами между сервисами — с таймаутами, ретраями, идемпотентностью и обработкой частичного отказа на границе. При совмещённом деплое связь MAY выполняться in-process адаптером того же контракта: сетевое разделение остаётся целевым, а семантика контракта (дедлайн, отмена, идемпотентность) сохраняется.
- 15 асинхронных связей (10 `event`, 5 `policy`) сохраняют природу и идут через брокер; вид связи становится обязательным транспортным атрибутом в каталоге.
- Каталог и схема: у контекста появляется сервисная принадлежность и объявленный транспорт контрактов; запрет на чужую модель усиливается с «нет импорта» до «нет импорта и нет прямого доступа к чужому хранилищу».
- `tools/archlint` расширяется проверками сервисной границы: один сервис на контекст, запрет импорта чужого домена, объявленный транспорт у каждой связи, отсутствие прямого доступа к чужой схеме данных.
- `docs/system-map.md` §2 переписывается: проекция «context → process» заменяется на «context → service», процессы становятся ролями сервиса, матрица связей уточняется по транспорту.
- **Целевая модель, а не компромисс.** Физически первый деплой MAY совмещать несколько сервисов в одном образе и конфигурации (как сейчас), но границей сервиса считается контекст: выделение позже не потребует пересмотра модели. Это не «процесс ≈ сервис»: единица владения и модуля остаётся контекстом, совмещён только первый деплой.
- **Роли PostgreSQL — часть сервисной границы.** Bootstrap/admin credential используется только для идемпотентного provision ролей/схем и ownership upgrade явного списка объектов; схему и её объекты владеет `NOLOGIN` owner. Отдельная migration login role может через `SET ROLE` принять только owner своей схемы и запускается одноразовым migration job; runtime role не является владельцем и получает только необходимые права своего контекста после применения миграций. Runtime-процессы не получают bootstrap или migration DSN.
- **Пошаговое включение, без заявления о глобальной изоляции.** `request-fulfillment` — первый пилот с отдельными runtime и migration credentials. Он не завершает задачу schema-per-service: задача 3.10 остаётся открытой до фактической изоляции всех PostgreSQL-контекстов, включая зависимости, секреты и роли каждого процесса.
- **Двухфазный release/activation в scope 3.10.4.h/i.** Tofu сначала готовит candidate, затем отдельный release job выполняет stage и DB jobs, формирует каноническую Ed25519-подписанную attestation, и только после независимой проверки Tofu активирует candidate. Release private key доступен только release job через secure file; Tofu получает public key. Attestation и state не содержат credential values и digest/hash секретов.
- **Удалённый lock и ledger — выбор B (3:0).** Единственный авторитетный lock/ledger volume уникален для пары environment+deployment и фактической Docker daemon identity; runner и Tofu должны использовать точно тот же удалённый daemon. Атомарный lock удерживается от начала candidate release до завершения Tofu activation; локальный flock — только дополнительная защита. Ledger хранит переходы `new → staging → verified → activation_in_progress → activated` либо `failed/recovery_required`, nonce/generation, active generation для rollback и replay/CAS данные. Падение оставляет durable state; автоматическое освобождение stale lock запрещено при неопределённости операций.
- **Compatibility bridge G1.5 (prep/code only; вариант A).** Не считать исходный G1 совместимым с migration set `0005–0009`: его `Verify` требует exact set и завершится отказом. До любого включения protocol v2 нужна отдельная immutable G1.5, сохраняющая v1 поведение, с runtime-only identities и точным образом/digest; manifest выпуска может перестать откладывать 0005–0009 только после доказательства совместимости G1.5. G1.5 — единственная цель rollback; исходный G1 не объявляется rollback target. Не применять compatibility migration к пользовательской БД и не выполнять production deployment в этом change.
- **Lifecycle и предел rollback.** Исходный G1 остаётся текущим до отдельного выпуска G1.5; G2 request protocol v2 не допускается, пока bridge не развернут и release gate не пройден. До первого durable v2 admission/intent rollback ограничен v1 writes и G1.5; после него rollback к v1/G1.5 запрещён, остаются только G2 roll-forward/recovery. Сохранить прежние привилегированные G1 credentials до отдельного retirement и явного окончания rollback window.
- **Подписанное подтверждение и anti-replay.** Generation и release nonce уникальны для deployment и никогда не переиспользуются после abort/activation. Предварительная проверка и CAS удалённого ledger блокируют параллельный запуск и replay. Ed25519 подписывает канонический детерминированный JSON с `keyId`, schema/purpose, deployment/environment, daemon identity, target, generation/nonce, именами bundle-файлов, image digest и временем выпуска/истечения; секреты и их хеши не включаются. Tofu сверяет подпись, активный ключ, поля и ledger до activation. Tofu state и unsigned JSON сами по себе anti-replay не обеспечивают; direct apply без соответствующего активного lock запрещён.

## Capabilities

### New Capabilities

- `service-topology`: правила сервисной границы — сервис как единица развёртывания, соответствие «один контекст — один сервис», допустимый транспорт контрактов (sync для `command`/`query`, async для `event`/`policy`), требования к таймаутам, ретраям, идемпотентности и частичному отказу на границе сервисов, запрет прямого доступа к чужому хранилищу; разделение PostgreSQL provisioning/migration/runtime identities и проверка версии схемы runtime credential без применения миграций.

### Modified Capabilities

- `domain-architecture`: пересматривается различение доменных и эксплуатационных границ — контекст размещается не в нескольких процессах, а в одном сервисе (роли внутри сервиса); требование о единственном владельце модели распространяется на сетевой транспорт; каталог обязан объявлять сервисную принадлежность контекста и транспорт каждой связи.

## Impact

Affected bounded contexts: все 11 — `platform-governance`, `data-governance`, `lead-management`, `audience`, `content-production`, `outreach-orchestration`, `message-delivery`, `engagement-observation`, `analytics`, `integration-platform`, `request-fulfillment`: у каждого меняется единица развёртывания и транспорт его связей. Каноническая доменная модель (агрегаты, сущности, события, policies, направления связей) не меняется — меняются эксплуатационная проекция и транспортные атрибуты связей.

- **Каталог и схема:** `architecture/domain-catalog.yaml`, `architecture/domain-catalog.schema.json` — `deployed_by` → сервис + роли, обязательный транспорт связи.
- **Документация:** `docs/system-map.md` (§2.0, §2.1, §3), `docs/domain-model.md` (capability matrix, колонка процессов), `docs/architecture.md` (§2, §8, §11 — единый образ и его назначение).
- **Диаграммы:** `architecture/diagrams/bounded-context-map.puml` и `context-relationships.puml` — границы сервисов; при необходимости добавляются deployment-диаграммы.
- **Инструменты:** `tools/archlint/` — новые проверки сервисной границы.
- **Код:** `cmd/*` — шесть процессов перестают быть единицей деплоя и становятся ролями внутри сервисов; `backend/contexts/<context-id>` — composition root сервиса, а не процесса; `backend/contexts/<ctx>` сохраняется без изменения границ.
- **PostgreSQL и развёртывание:** provisioner для повторяемого создания ролей/схем, миграционный job отдельно от runtime-групп, ограниченные per-context credentials и secret mounts для Compose, Tofu local и bare-metal; переход существующего Compose volume не зависит от `initdb`-скриптов. Все runtime-группы, включая скрытые зависимости `intake` на `supportGreenDSN`, `consoleauth` и vector storage, получают только нужные runtime credentials.
- **Риски:** 13 синхронных связей получают сетевую стоимость и режимы частичного отказа (нужны таймауты, ретраи, идемпотентность, деградация); 11 сервисных контуров наблюдаемости и релиза тяжелы на раннем продукте; нужно явно решить, как совмещённый первый деплой выражается в конфигурации, чтобы `archlint` и модель не разошлись.
- **Совместимость:** публичного API и production-кода пока нет; миграции данных не требуется.
