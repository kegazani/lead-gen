## Why

Продукт начинается с качества входных данных: без сильного парсера сайтов нет ни лидов, ни персонализации, ни кампаний. **Цель этого среза — крутой краулер**, который превращает сайт в структурированную карточку компании (название, описание, контакты, соцсети) — включая JS-сайты, контакты не на главной странице и LLM-извлечение, а не «тащит всё подряд». Всё остальное (запуск поиска, хранение, консоль) — минимальная обвязка, чтобы запускать краулер и видеть, что он распарсил. **Движок краулинга — Firecrawl** (hosted API, ключ и кредиты): JS-рендеринг, чистый Markdown-выход, ротация IP на стороне провайдера, соблюдение robots.txt. Это зависимость от чужого облака, но граница «пайплайн обогащения ↔ внешний движок» сохраняется: замена движка — правкой адаптера, не ядра. Отправка писем — вне среза MVP (решено: креды позже), но это первый пункт следующего среза: операционный CRM уже определён (см. «Следующий срез» в What Changes), и MVP проектируется так, чтобы следующий срез не потребовал переделки.

## What Changes

- **Краулер — ядро среза**, адаптер за `provider-port` (контекст `integration-platform`). Движок — **Firecrawl** (hosted API): `/search` (поиск с готовым markdown), `/map` (список URL сайта без контента), `/scrape` (страница → markdown/HTML/JSON по схеме), `/crawl` (обход сайта с лимитами и фильтрами путей). JS-рендеринг, SPA и «умное ожидание» динамики — на стороне Firecrawl; ротация IP — на стороне провайдера; robots.txt соблюдается. Наш Go-код — HTTP-клиент API Firecrawl (stdlib) за портом, нормализация результата в модель лида, дедупликация.
- **Навигационный слой — найти страницу с контактом, даже если её нет на базовом эндпоинте:**
  1. **`/crawl` + `includePaths`** (`*contact*`, `*team*`, `*about*`, `*staff*`, `*impressum*`) — обход по релевантным путям, а не по всему сайту; `excludePaths` отсекает нерелевантные разделы (блог, новости, каталог товаров) до обхода; `limit`/`maxDepth` — бюджет;
  2. **`/map` + точечный `/scrape`** — быстрый путь для крупных сайтов: список проиндексированных URL без загрузки контента, затем скрейп только многообещающих страниц.
- **Слой экстракции — от дешёвого к дорогому, с эскалацией на LLM:**
  1. **Firecrawl-рендер → чистый Markdown** (убирает навигацию, футеры, рекламу) + доступные метаданные;
  2. **нормализатор без LLM** — regex email/телефона поверх Markdown, декодирование обфускации Cloudflare (`__cf_email__`), слияние полей из метаданных и текста + **оценка качества результата** (заполнены ли ключевые поля: название, описание, контакты);
  3. **LLM-экстракция по JSON-схеме** (`name`/`email`/`phone`/`role`) через **Firecrawl `extract`** (structured-режим) — **этап эскалации:** подключается **только если предыдущие слои дали плохой результат** (не хватает полей, низкое качество, сложная JS-страница, неоднозначный текст вида «отдел продаж — Иван Петров»). LLM-результат не перетирает сильные сигналы слоёв 1–2: слияние по приоритету, происхождение каждого поля фиксируется.
- **Граница автономности (non-goal среза):** никакой автономной кликательной навигации. Firecrawl умеет интерактив (`/interact`, `/agent`: клики, формы, логин, многошаговые сценарии), но это самая дорогая функция (до 7 кредитов/мин) и остаётся вне MVP — «Показать email» и формы поиска сотрудника закрываются точечными сценариями следующего среза, не этого.
- **Источники поиска** за портом Search: Firecrawl `/search` (поиск с готовым markdown, без отдельного ключа поисковика). AI-планирование (LLM-порт `Plan`, провайдер **DeepSeek** — OpenAI-совместимый `base_url` + `model`): запрос оператора раскладывается в серию поисковых запросов и стартовых URL («рассуждение, куда идти в интернете»).
- **Хранение:** PostgreSQL через `pgx/v5` — распарсенная карточка компании (зелёная зона, schema-per-service) и контакты (красная зона, отдельная БД); у каждого поля — происхождение (источник URL, дата).
- **Минимальная витрина** (по канону `web-frontend-architecture`: экраны в `adapters/http`, `frontend/components`, `html/template` + HTMX): запуск поиска запросом, журнал заданий со статусами, таблица найденного, карточка с полями и источниками. Полноценный CRUD/статусы лидов — позже, минимально: удалить/скрыть запись. **Готовность к следующему срезу:** компоненты отдельно от страниц (заготовка под три вкладки: сегменты / кампании / CRM), журнал заданий — единый job-механизм со статусами (queued/running/done/failed), который позже переиспользует рассылка; схема карточки расширяется миграциями (статусы, кастомные поля, история активности), а не переделкой; адаптер краулера не различает режимы discovery/targeted.
- **Следующий срез (после MVP): операционный CRM-слой поверх пайплайна** — в MVP не входит, но рамка зафиксирована, и MVP строится так, чтобы срез не потребовал переделки:
  1. **Своя CRM-логика в том же приложении, поверх локальной БД** — без внешней CRM (Asana отменена): кастомные поля, статусы, история активности по каждому лиду, права доступа, если операторов несколько;
  2. **Двухфазный краулинг** поверх того же адаптера: discovery crawl (`/crawl` широко → агрегация обнаруженных сегментов по индустрии/гео/типу компании с оценкой объёма лидов) → выбор сегмента пользователем → targeted crawl по нему;
  3. **Три вкладки UI:** разведка сегментов (обнаруженные сегменты с объёмами, выбор), кампании (запуск targeted crawl и рассылки, статусы job'ов), CRM-воронка;
  4. **Статусная модель лида:** `not warmed` → `email sent` → `warming` → `cold` (с полем `snooze_until`, после которого лид автоматически возвращается в пул), канбан с drag-and-drop;
  5. **Рассылка по сегменту** с обязательным исключением bounced/unsubscribed/rejected и логированием статуса доставки на каждого лида (email_log); результаты (ответы/переходы) используются для поведенческой сегментации;
  6. **Шаблоны писем с merge-полями** (название компании, имя контакта, индустрия…) и обязательными fallback-значениями для незаполненных полей;
  7. **Ручное продолжение диалога:** встроенный email-интерфейс (или синхронизация с ящиком), история переписки отображается в карточке лида;
  8. **Сегменты** — динамические условия по полям лида (индустрия, гео, канал, приоритет, статус); пересечение с `lead-segmentation` (приоритет исключающих сегментов) решается ссылкой на неё, а не переопределением.
  Отдельный пункт того же среза: автономная агентная навигация через Firecrawl `/interact`/`/agent` — не входит ни в MVP, ни в список выше.

## Capabilities

### New Capabilities

- `osint-enrichment` — capability объявлена в `architecture/domain-catalog.yaml` (контекст `lead-management`), но спеки в `openspec/specs/` не имеет. Этот change создаёт её первую версию (дельта ADDED в фазе specs) с требованиями в редакции среза.

### Modified Capabilities

Нет.

**Обоснование.** Срез реализует требования `osint-enrichment` (по явному запросу человека, минимизация, без накопления, без обхода защит — robots.txt соблюдается движком) и `provider-agnostic-integrations` (адаптеры за контрактом, смена конфигурацией). Краулер — адаптер за портом, а не новая capability; доменная модель не меняется.

## Impact

- **Affected bounded contexts:** `lead-management` — первичный (карточка компании, задание поиска, витрина); `integration-platform` — порты Search/Crawl/LLM и адаптеры (Firecrawl, DeepSeek). Полный домен `integration-platform` (агрегаты `adapter-registration`, `integration-invocation`) — за change'ем ЭТАПА 0, этим срезом не реализуется.
- **Доменная модель не меняется:** карточка компании — по агрегату `lead-profile` каталога, контакты — по агрегату `contact`; каталог, `docs/domain-model.md`, диаграммы без изменений. Задание поиска — операционная запись app-слоя; если появятся доменные инварианты — отдельное изменение каталога (открытый вопрос design).
- **Код:** модули `backend/contexts/lead-management`, `backend/contexts/integration-platform` (порты+адаптеры), `contracts/integration-platform`; примитивы рендеринга `frontend/components`; оболочка вызова порта `backend/platform`; сборка ролей `api`/`worker` в `backend/cmd/lead-gen`; регистрация в `go.work`.
- **Зависимости:** Go — `github.com/jackc/pgx/v5` (MIT), HTTP-клиент API Firecrawl — stdlib; **Firecrawl** — hosted API (ключ, кредиты) как внешний сервис за портом (поиск, обход и LLM-экстракция); LLM-провайдер — **DeepSeek** (OpenAI-совместимый `base_url` + `model`), нужен только для планирования поиска; HTMX — статический файл. Второй AGPL-компонент не добавляется. Docker для краулера не требуется (движок в облаке); нужен только сетевой доступ к API Firecrawl и PostgreSQL.
- **Проверка:** `make check` зелёный; контрактные suite портов против тестовых адаптеров (fake Firecrawl/поиск/LLM); e2e-сценарий «запрос → поиск → обход → карточки в БД → таблица в консоли».
- **Риски:** качество парсинга на неоднородных сайтах — главный риск (смягчение: навигация по релевантным путям, regex → LLM-эскалация, лог по URL, метрика «доля страниц с извлечёнными полями»); блокировки (смягчение: ротация IP на стороне Firecrawl, лимиты, backoff; robots.txt соблюдается — часть страниц может быть недоступна, принимается как следствие); стоимость и лимиты Firecrawl (кредиты, rate limit) — смягчение бюджетом и лимитами; зависимость от облака и ключа (секрет вне репозитория); если Firecrawl не подойдёт — запасной путь: self-hosted адаптер (Crawl4AI или colly+chromedp) за тем же портом, без правки ядра.
