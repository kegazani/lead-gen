# provider-token-budget Specification

## Purpose

Ограничивает расход токенов на платный LLM-вызов через известную верхнюю оценку входа, явный output cap и резервирование для каждой попытки.

## ADDED Requirements

### Requirement: Стабильный scope платной LLM операции

Каждая опубликованная LLM операция Plan, Suggest, Converse, ConverseStream, Interpret и Assess SHALL принимать caller-provided валидный стабильный технический `OperationScope`/`OperationID` и budget-policy context. Отсутствующее или невалидное значение SHALL приводить к отказу до сети; адаптер SHALL NOT генерировать scope. Повтор той же логической операции, включая Temporal/activity replay, SHALL сохранять scope. Каждая физическая отправка, retry или repair SHALL иметь уникальный attempt ID внутри scope. Scope и attempt ID SHALL NOT содержать PII.

#### Scenario: Scope отсутствует или невалиден

- **WHEN** любая опубликованная LLM операция вызвана без валидного caller-provided scope
- **THEN** операция отклоняется до HTTP-вызова и адаптер не создаёт scope самостоятельно

#### Scenario: Replay той же логической операции

- **WHEN** та же бизнес-операция или Temporal/activity replay повторно вызывает LLM операцию
- **THEN** вызывающая сторона передаёт тот же OperationScope

#### Scenario: Retry и repair в рамках одной операции

- **WHEN** операция выполняет исходную отправку, допустимый retry или JSON repair
- **THEN** все попытки используют один OperationScope, а каждый физический send получает отличный attempt ID

#### Scenario: Разные операции не сталкиваются

- **WHEN** две независимые логические операции выполняются одним потребителем
- **THEN** caller передаёт разные OperationScope, и их reservations/attempts не объединяются

#### Scenario: Идентификатор владельца отсутствует

- **WHEN** callsite не имеет подходящего стабильного технического идентификатора
- **THEN** он предоставляет отдельный idempotency scope либо остаётся заблокированным; PII не используется как scope

### Requirement: Явный ограниченный бюджет вызова

Каждый платный chat completion SHALL иметь конечный бюджет на операцию и передавать провайдеру `max_tokens`, не превышающий зарезервированный output cap. Источник бюджета SHALL быть явным и ограниченным для конкретной модели. Если верхняя оценка prompt/input неизвестна, система SHALL использовать поддерживаемый tokenizer/model-context bound либо отказать до сети; она SHALL NOT называть оценку неизвестного входа жёстким cap. Ограничение не SHALL представляться гарантией полной суммы account billing.

#### Scenario: Неизвестная верхняя граница prompt

- **WHEN** prompt нельзя ограничить поддерживаемым tokenizer/model-context bound
- **THEN** операция отклоняется до HTTP-вызова и не заявляется как ограниченная по токенам

#### Scenario: Output cap передан провайдеру

- **WHEN** вызов chat completion принят бюджетом
- **THEN** JSON body содержит `max_tokens` не больше зарезервированного output cap

### Requirement: Резерв на каждую платную попытку

Система SHALL резервировать верхнюю оценку расхода до каждой отправки платного запроса, включая retry и semantic JSON repair. Следующая попытка SHALL отправляться только при успешном отдельном резерве. Если исход предыдущего вызова неизвестен, его резерв SHALL оставаться занятым, а blind re-send SHALL быть запрещён. Usage SHALL сохраняться как фактические данные только при наличии подтверждённого ответа; usage не SHALL использоваться как гарантия account billing total.

#### Scenario: Retry требует нового резерва

- **WHEN** классифицированный безопасный исход допускает повтор
- **THEN** перед повторной отправкой создаётся дополнительный резерв; нехватка бюджета завершает операцию без сети

#### Scenario: Неизвестный timeout

- **WHEN** запрос мог быть исполнен провайдером, но клиент не получил подтверждённый ответ
- **THEN** резерв удерживается и запрос автоматически не отправляется повторно

#### Scenario: JSON repair

- **WHEN** Assess выполняет единственную семантическую JSON repair попытку
- **THEN** repair потребляет отдельный резерв и ограничивается тем же `max_tokens` правилом

### Requirement: Ограничения модели и подтверждённая usage

Система SHALL учитывать сумму верхних границ input и output в пределах подтверждённого context bound выбранной модели. Provider usage SHALL храниться отдельно от резерва и бюджета и сверяться только при наличии подтверждённого ответа. Синтаксис `max_tokens` у DeepSeek Chat Completion подтверждает только возможность передать output bound; конкретные context limits и pricing SHALL быть проверены для каждой поддерживаемой модели отдельно.

#### Scenario: Context bound превышен

- **WHEN** верхняя граница input вместе с output cap превышает подтверждённый предел модели
- **THEN** вызов отклоняется до отправки

#### Scenario: Usage присутствует в ответе

- **WHEN** провайдер вернул usage
- **THEN** usage записывается как фактическое использование отдельно от зарезервированного и не объявляется account billing total
