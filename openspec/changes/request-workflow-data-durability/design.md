## Context

См. `proposal.md` и delta-спецификации. Используются существующие владельцы: `request-fulfillment` владеет заявкой и черновиками; `lead-management` — карточками, контактами и журналом поисковых заданий; `outreach-orchestration` — кампаниями/утверждением; `message-delivery` — очередью отправки и сообщениями; `integration-platform` — SMTP.

Рабочее дерево уже содержит незакоммиченные изменения во всех затронутых контекстах. Их необходимо сохранять; перед каждой правкой сверять staged и unstaged diff конкретного файла. `request-failure-terminal-state`, `service-per-context` и `provider-resilience-and-budgets` остаются независимыми активными изменениями; этот change не включает полный rollout протокола v2, release activation или полную Temporal history reconciliation.

## Goals / Non-Goals

**Goals:**
- Согласовать переход отмены с текущим Temporal execution и не запускать новые шаги после подтверждённой остановки.
- Сохранять лиды и черновики инкрементально на существующих владельческих PostgreSQL adapters.
- Сделать принятие утверждённого действия durable до положительного ACK и восстановимым после рестарта.
- Для уже переданного Gmail письма различать SMTP acceptance и неизвестный исход; не делать слепой повтор.
- Проверять повторы, отмену и рестарт на изолированных адаптерах и интеграционном сценарии.

**Non-Goals:**
- Автоматически возобновлять внешний Firecrawl crawl с точного URL/frontier checkpoint; сохраняются данные, а незавершённый запуск может быть показан как прерванный.
- Автоматически разрешать неизвестный SMTP исход или гарантировать exactly-once через внешнюю почту.
- Создавать новую доменную capability, менять агрегаты или переводить production deployment на protocol v2.
- Реализовывать глобальное мгновенное распределённое прекращение уже выполняющейся отправки: HTTP показывает отдельно принятую отмену и downstream подтверждение.

## Decisions

1. **Каждый bounded context пишет только в собственное хранилище.** Request, leads, outreach и delivery не используют общую таблицу. Контексты обмениваются отменой и исходами через опубликованные сообщения/контракты; повторная доставка и поздний порядок обрабатываются владельцами.
2. **Использовать существующие PostgreSQL stores и стабильные идентификаторы.** Не создавать новый общий job framework. Результаты добавляются/upsert-ятся по владельческой identity. Ошибка сохранения становится ошибкой этапа, а не логируемым успешным partial.
3. **Сохранять каждый черновик отдельно сразу после генерации.** Текущий batch API `SaveDrafts` остаётся доступным для совместимости; одиночный save реализуется через него с одним элементом, если контрактный suite подтверждает атомарную семантику.
4. **Delivery ACK — после durable записи.** Памятный канал не является подтверждённой очередью. Владелец delivery хранит inbox/команды в PostgreSQL с уникальным idempotency key и atomic claim. Команда с тем же ключом и тем же payload — replay; payload conflict — явная ошибка.
5. **Отмена — идемпотентная команда и durable fence в каждом downstream owner.** Request owner сохраняет свою отмену/outbox; outreach блокирует поздний handoff/approval; delivery блокирует enqueue/claim для отменённой заявки. Уже отправленные сообщения не переписываются в cancelled. Полный запрет до HTTP-ответа возможен только после downstream acknowledgement и явно не подразумевается.
6. **Unknown SMTP outcome не равен retryable failure.** До передачи DATA можно повторять согласно транспортной политике; потеря подтверждения после DATA отмечается unknown и ждёт сверки. Стабильный RFC `Message-ID` помогает сверке, но не считается механизмом идемпотентности Gmail.
7. **Gmail transport использует обязательный STARTTLS на 587.** TLS handshake и проверка сертификата предшествуют AUTH; сетевые операции ограничены общим deadline. Секрет приложения задаётся deployment secret/file config, не хранится в репозитории и не передаётся в argv/logs.
8. **Не менять владение доменом.** Реализуются текущие связи `request-fulfillment → lead-management → outreach-orchestration → message-delivery → integration-platform`; новые агрегаты, события и relationships не добавляются без отдельной необходимости. Если ревью выявит изменение каталожной связи, каталог, `docs/domain-model.md` и диаграммы обновляются в этом change.

## Risks / Trade-offs

- [Риск] Отмена распределена между PostgreSQL контекстов и брокером, поэтому существует короткое окно до downstream fence → сохранять outbox и показывать состояние «отмена ожидает подтверждения»; поздние команды проверяют durable tombstone.
- [Риск] Сбой после SMTP DATA до ответа нельзя разрешить локально → оставлять `unknown`, блокировать автоповтор и предъявлять сверку оператору.
- [Риск] Внешний Gmail, Temporal или Firecrawl недоступен во время приёмки → задачи реальной интеграции остаются открытыми; тестовый сервер не подменяет acceptance.
- [Риск] Текущее рабочее дерево содержит незакоммиченные изменения и несколько файлов имеют staged + unstaged версии → назначить одного владельца на bounded context и применять только узкие diff.
- [Риск] Миграции затрагивают раздельные runtime roles → только additive migration владельца, PG17 acceptance на disposable БД, без пользовательского Compose/DB.

## Migration Plan

1. Добавить совместимые additive migrations только для реально недостающих durable inbox/fence данных; не менять существующие migration checksums.
2. Подключить новый storage за владельческим портом. До готовности БД производственная сборка не подтверждает приём сообщений через память.
3. Развернуть читателей и миграции до включения новых producer contracts; сохранять обратную совместимость wire payloads либо версионировать контракт.
4. Проверить upgrade с существующими заявками/черновиками и restart на изолированной PostgreSQL 17.
5. Включать Gmail путь только при TLS и реальном SMTP конфиге; Mailpit остаётся тестовым адаптером, а не производственной интеграцией.
6. Rollback приложения допустим только пока новая durable запись читается старой версией. После записи несовместимого формата — roll-forward; миграции не удалять.

## Open Questions

- Для Gmail IMAP-сверки нужно проверить, доступен ли IMAP на выделенном аккаунте; отсутствие IMAP оставляет спорный SMTP outcome неизвестным, а не разрешает повтор.
- Фактические credentials Firecrawl/LLM/Gmail не проверялись и задаются владельцем окружения вне репозитория.
