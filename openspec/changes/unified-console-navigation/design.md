## Context

Общая навигация консоли строится `components.ConsoleNavMessagesWithContext` по
каноническому списку `ConsoleSections` и базовым адресам `ConsoleBases`
(конфигурация точки входа). Список содержал только операторские разделы, а
платформенная консоль `platform-governance` имела собственный список
(`consoleNav`), поэтому два админских контура не пересекались: платформенная
показывала обе группы, операторские — только свою.

Активный тенант в консолях определяется через `consolescope.ActiveTenant`
(cookie `active_tenant`); платформенная консоль читала только `?tenant_id`.

## Goals / Non-Goals

- **Цель:** на всех консолях — четырёх операторских (`/intake`, `/lead-console`,
  `/reporting`, `/mailing`) и платформенной (`/admin`) — видны обе группы
  разделов (навигация двусторонняя: операторские консоли несут и платформенные
  разделы); сайдбар не сужается при переходах, тенант и актор сохраняются.
- **Цель:** раздел, требующий тенанта, не отвечает «тенант не задан», а ведёт к
  выбору тенанта.
- **Не цель:** менять домен, права, контракты; переписывать операторские сервисы.

## Decisions

### Решение 1. Один канонический список разделов для всех консолей

Платформенные разделы добавляются в `ConsoleSections` с владельцем
`ConsoleServicePlatform` (`platform-governance`). Все консоли строят сайдбар
через общий `components.ConsoleNavMessagesWithContext` из одного списка; общий
слой остаётся единственным источником структуры разделов, а платформенная
консоль убирает собственный список пунктов (нет дублей).

### Решение 2. Активность по ключу и по пути

Операторские консоли передают в общий слой ключ раздела (`leads`, `reports`,
…), платформенная — путь экрана (`/console/tenant`, `/platform/operations`, …).
Общий слой отмечает активный раздел по ключу и по префиксу адреса; владельца
открытого раздела (`consoleOwner`) определяет по ключу или по пути, поэтому
разделы текущего сервиса остаются относительными, а остальных — абсолютными.

### Решение 3. Тенант из cookie консоли

Вводится `activeTenant(r)`: `tenant_id` из запроса, затем из формы, затем
`consolescope.ActiveTenant(r)`. Все экраны консоли и построение навигации
используют его, поэтому выбранный тенант переносится по ссылкам без ручного
ввода.

### Решение 4. Отсутствие тенанта — переход к выбору

Экран, требующий тенанта, при его отсутствии перенаправляет на
`/console/tenant` (выбор тенанта), а не рисует отказ. Выбор сохраняется в cookie
(`consolescope.SetActiveTenant`, уже реализовано), и разделы открываются.

### Решение 5. Платформенный базовый адрес во всех консолях

Базовый адрес платформенной консоли задаётся одним флагом точки входа
(`-console-platform-base` / `CONSOLE_PLATFORM_BASE_PATH`, по умолчанию `/admin`) и
кладётся в `components.ConsoleBases` под ключом `ConsoleServicePlatform`. Через
`externalConsolePrefixes` он попадает во все пять сервисов как внешний префикс
чужой консоли: `PrefixMiddleware` не переписывает ссылки на платформенные
разделы, поэтому с операторской консоли они ведут на `/admin/...`, а не
дополняются префиксом текущей консоли. Так ссылки двусторонней навигации
остаются в пределах единого origin (`admin-proxy`).

## Risks / Trade-offs

- **[Пустые базовые адреса сервисов]** → Общий слой строит относительные пути,
  если адрес сервиса не задан; это прежнее поведение операторской консоли.
- **[Тесты консоли]** → Тенант-фолбэк расширяет поведение; тесты с явным
  `tenant_id` не меняются, добавлены проверки выбора тенанта и общей навигации.

## Migration Plan

Миграций нет. Порядок: платформенные разделы в общий список и подписи в каталог →
активность по ключу и по пути → платформенный базовый адрес во все сервисы →
убрать собственный список `consoleNav` → тесты и golden → пересборка затронутых
контейнеров и живой прогон.
