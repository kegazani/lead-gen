## Context

Мотивация — `proposal.md`. Точка отказа — `firecrawl.Client.Crawl`
(`backend/contexts/integration-platform/internal/adapters/firecrawl/firecrawl.go`):
асинхронный обход опрашивается в `pollCrawl` до терминального статуса. Ограничитель
цикла — только `ctx` вызывающего: `MaxTimeSeconds` из `crawl.Request` в адаптере не
читается, число итераций не ограничено, интервал опроса постоянный. Потребители
(`SearchLeadsForRequest.crawlSite`, `RunSearch.crawlURL`) ставят контексту
собственный дедлайн, но это защита вызывающего, а не выполнение контракта порта:
при вызове без дедлайна (в частности, через сетевой контракт) обход не завершается,
и activity висит до серверного `StartToCloseTimeout`.

Контракт `crawl.Port` уже объявляет `Request.MaxTimeSeconds` («предельное время
обхода»), то есть требование существовало, но адаптер его не исполнял — это дефект
адаптера, а не новая функциональность.

## Decisions

### Решение 1. Жёсткий дедлайн обхода из `MaxTimeSeconds` и контекста

**Выбор.** В начале `Crawl` вычисляется предельное время обхода: если
`MaxTimeSeconds > 0` — это оно; оно **сужает** дедлайн контекста (берётся меньший).
Дальше все запросы обхода (первичный `POST /v1/crawl`, опрос статуса, остановка)
идут под `context.WithTimeout` с этим пределом.

**Почему.** `MaxTimeSeconds` — часть контракта порта; адаптер обязан его
исполнять, не перекладывая на вызывающего. Ограничение «не шире контекста»
сохраняет приоритет явного дедлайна вызывающего (например, отмены activity).

### Решение 2. Backoff и предел числа итераций опроса

**Выбор.** Интервал опроса растёт от `pollInterval` (500 мс) до потолка (5 с);
число итераций ограничено (`maxPollAttempts`) как последний предохранитель, когда
ни `MaxTimeSeconds`, ни дедлайн контекста не заданы.

**Почему.** Постоянный частый опрос (2 раза/с) лишний и не защищает от
бесконечного цикла. Backoff снижает нагрузку, а предел итераций гарантирует, что
цикл завершится даже в вырожденном случае «нет внешнего дедлайна».

### Решение 3. Нормализованная причина остановки: `ErrTimeout` ≠ `ErrCancelled`

**Выбор.** Новый sentinel контракта `crawl.ErrTimeout` возвращается при истечении
времени (`context.DeadlineExceeded`, свой или контекстный дедлайн);
`crawl.ErrCancelled` — только при явной отмене (`context.Canceled`). В обоих
случаях возвращаются уже собранные страницы.

**Почему.** «Оператор остановил» и «не уложились во время» — разные причины с
разной политикой повтора: таймаут — транзиентный сбой, который потребитель/WORKFLOW
вправе повторить; отмена повтором не воскрешается. Смешение их в `ErrCancelled`
скрывало таймаут и мешало честному решению о повторе. Сохранение частичных
страниц не даёт потерять добытое до остановки.

### Решение 4. Потребители: таймаут обхода — ограниченная остановка сайта

**Выбор.** `SearchLeadsForRequest.crawlSite` и `RunSearch.crawlURL` обрабатывают
`ErrTimeout` наравне с `ErrCancelled`: сохраняют уже добытые страницы (через
кратко-ограниченный отсоединённый контекст) и продолжают, не отменяя шаг/задание.

**Почему.** Продуктовое поведение уже задано: дедлайн одного сайта не отменяет
`lead-search` и не роняет `RunSearch` (спеки `lead-search` «Дедлайн исчерпан»,
`search-job-lifecycle`). Новый sentinel не должен менять это поведение — только
различать причину в логе/метрике и не терять страницы.

### Решение 5. Activity не меняется: heartbeat и таймауты уже есть

**Выбор.** Шаг `SearchLeads` в `request-fulfillment` продолжает использовать
существующий `startHeartbeat`; значения `StartToCloseTimeout`/`HeartbeatTimeout`
задаются политикой исполнения и приходят из флагов `backend/cmd/lead-gen` —
этот файл вне scope и не правится.

**Почему.** Блокирует не отсутствие heartbeat, а неограниченный обход. Правка
адаптера завершает шаг за секунды–минуты, задолго до серверных таймаутов activity.

## Risks / Trade-offs

- **[Потребитель ждал обход дольше `MaxTimeSeconds`]** → обход честно завершится
  `ErrTimeout` с частичными страницами; это и есть объявленная семантика поля.
- **[Потолок итераций при отсутствии дедлайна]** → вырожденный обход всё равно
  завершится `ErrTimeout`; значение выбрано с большим запасом.
- **[Повтор на таймаут]** → повтор остаётся за вызывающим: `lead-search` не
  роняет шаг (сохраняет пул), Temporal повторяет activity по политике. Подмена
  успехом исключена.

## Migration Plan

1. Добавить `crawl.ErrTimeout` в контракт (аддитивно, обратно совместимо).
2. Дедлайн + backoff + нормализация исхода в адаптере Firecrawl.
3. Обработка `ErrTimeout` в `search_leads.go` и `run_search.go`.
4. Тесты: `httptest`-сервер, отдающий незавершающийся `crawl`; проверки возврата
   `ErrTimeout` по дедлайну, `ErrCancelled` по отмене, сохранения частичных страниц.

**Откат.** Реверт правок; `MaxTimeSeconds` снова игнорируется, поведение прежнее.
