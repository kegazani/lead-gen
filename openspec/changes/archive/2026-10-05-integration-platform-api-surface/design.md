## Context

`integration-platform` собран вертикальным срезом (change `integration-platform`):
агрегаты `adapter-registration` и `integration-invocation`, use cases
`RegisterAdapter`/`SelectAdapter`/`InvokeIntegration`, порты и in-memory/PostgreSQL
адаптеры. Роль `api` осталась каркасной. Каталог уже объявляет связь
`integrations-status-for-governance` (владелец `integration-platform` →
потребитель `platform-governance`, запрос, транспорт `http-json`, контракт
`adapter-status`). Источник состояния адаптеров существует как публичная
поверхность корневого пакета (`AdapterStatusSource`) и уже используется точкой
сборки для раздела интеграций консоли — но только in-proc.

## Goals / Non-Goals

**Goals.**

- Реальная HTTP-поверхность роли `api` для уже объявленного контракта
  `adapter-status` и для чтения реестра регистраций.
- Сетевой адаптер контракта, чтобы потребитель мог читать владельца раздельно.
- Честное, явное поведение роли `ingest`.
- Не добавлять внешних зависимостей и не требовать от поверхности внешних ключей.

**Non-Goals.**

- Сетевые поверхности `provider-port` и `vector`: без сконфигурированного
  адаптера поставщика/эмбеддера они были бы всегда недоступны; задача остаётся
  открытой до выбора провайдера.
- Публикация команд `RegisterAdapter`/`SelectAdapter` наружу: потребителя-команды
  нет.
- Аутентификация поверхности: это внутренний адрес сервиса (как у внутренних
  JSON-поверхностей прочих контекстов), отдельные меры доступа — вне среза.

## Decisions

### Решение 1. Что именно отдаёт роль `api`

Отдаём то, что уже объявлено и нужно потребителю: состояние объявленных
адаптеров (контракт `adapter-status`) и реестр зарегистрированных адаптеров.
Оба чтения реальны: состояние — факт конфигурации точки сборки, реестр — чтение
хранилища регистраций. Ни одно не требует внешней системы. Сетевые поверхности
команд `provider-port`/`vector` не выставляем: без адаптера поставщика они не
несут функции, а имитировать интеграцию запрещено (`AGENTS.md` §3).

### Решение 2. Форма контракта `adapter-status`

Контракт публикуется отдельным пакетом
`contracts/integration-platform/adapterstatus` (модуль `contracts/integration-platform`):
DTO `Status{Adapter,State,Reason}`, конверт `Response{Contract,SchemaVersion,Adapters}`,
интерфейс `Port`, ошибка `ErrUnavailable`. Поля — строки закрытых словарей
(up/degraded/down/unknown; коды причин). Свободного текста в контракте нет,
поэтому секреты не переносятся по построению; недоступность владельца отличается
от «адаптеров не объявлено» через ошибку, а не пустой список.

### Решение 3. Транспорт выбирается топологией

Сетевой адаптер `adapterstatus/httpport` реализует `Port` поверх `net/http`
(`GET {base}/adapter-status`). Точка сборки выбирает транспорт по флагу
`-integration-platform-url` (`LEADGEN_INTEGRATION_PLATFORM_URL`): пусто —
источник владельца in-proc (co-location), задан — сетевой адаптер. Форма
контракта от транспорта не зависит — как у прочих синхронных контрактов проекта
(`delivery-target`, `content-version`, `lead-search`).

### Решение 4. Источник состояния один, обёртка одна

Источник состояния адаптеров (`AdapterStatusSource`) остаётся один и тот же — и
для HTTP-поверхности владельца, и для раздела интеграций консоли. Поэтому второй
реестр адаптеров не заводится: точка сборки передаёт один источник обеим
сторонам. Обёртка потребителя (`adapterCatalog`) держит функцию чтения, а не
конкретный тип источника: co-location и сеть подставляются одной обёрткой.

### Решение 5. Веб-адаптер роли `api`

HTTP-поверхность живёт в `internal/adapters/http` контекста и не содержит
доменных правил: роутинг, JSON и нормализация ошибок. Отсутствующий источник —
честный `503`; пустой реестр — пустой список без ошибки. Свободный текст ошибок
не раскрывает технических деталей владельца.

### Решение 6. Поведение `ingest`

У контекста нет объявленного входящего протокола (в каталоге нет ни одной связи
с потреблением). Роль `ingest` не поднимает приёмник и не выдаёт себя за
принимающую: она явно логирует, что входящего протокола нет, и ожидает отмены
контекста. Это допустимое явное состояние нереализованного контура, а не
заглушка под успех.

## Risks / Trade-offs

- **[Открытый внутренний адрес]** → поверхность не аутентифицирована; обосновано
  тем, что это внутренний адрес сервиса, как у прочих JSON-поверхностей. При
  выделении в публичный контур потребуется отдельная мера доступа.
- **[Реестр обычно пуст]** → регистраций адаптеров в срезе пока нет; `GET /adapters`
  отдаёт пустой список. Это реальное состояние, а не недоступность; поверхность
  не выдумывает записи.
- **[Связь `provider-port` остаётся in-proc]** → сетевого транспорта у вызова
  поставщика пока нет; это вне среза (нет провайдера), задача миграции
  `provider-port` на `http-json` остаётся открытой.

## Migration Plan

Совместимо и аддитивно: без заданного `-integration-platform-url` поведение
прежнее (in-proc источник у консоли), роль `api` впервые начинает слушать адрес.
Миграция данных не требуется.

## Open Questions

1. Аутентификация внутренних JSON-поверхностей контекстов — общий вопрос, не
   специфичный для этого изменения.
2. Состав команд `provider-port`, выставляемых по сети, — определяется первым
   бизнес-сценарием потребителя (вне среза).
