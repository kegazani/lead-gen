## Context

Мотивация — `proposal.md`. Текущее состояние: `vectorRecallPort` включает
эмбеддер по `LLM_API_KEY` и делит `LLM_BASE_URL`/`LLM_MODEL` с чат-адаптером
(`integration-platform/internal/adapters/openai`, `NewVectorEmbedder`). Эмбеддинг
оффера вызывается на шаге одобрения заявки (`request-fulfillment`), поэтому
отсутствие эмбеддингов у провайдера ломает одобрение.

## Decisions

### Решение 1. Эмбеддинги — отдельный набор параметров

**Выбор.** `-embedding-base-url`, `-embedding-model`, `-embedding-key`
(ENV `EMBEDDING_*`). `vectorRecallPort` собирается только при непустом
`-embedding-key`; базовый адрес/модель берутся из `EMBEDDING_*`, а при пустых —
дефолты эмбеддера (`text-embedding-3-small`).

**Почему.** Чат и эмбеддинги — разные возможности провайдера; DeepSeek даёт чат,
но не эмбеддинги. Общая конфигурация невыразима.

### Решение 2. Отсутствие эмбеддингов — честная недоступность

**Выбор.** Нет `-embedding-key` → `vectorRecallPort` возвращает nil; семантический
recall честно недоступен. Одобрение заявки при nil-порте проходит (как и раньше
при пустом `LLM_API_KEY`); семантика — дополнительный слой, а не блокер цикла.

**Почему.** Заглушка запрещена; выключенный порт — явное состояние, а не имитация.

### Решение 3. Чат не затронут

`LLM_*` продолжает питать генерацию писем/планирование. Меняется только источник
параметров векторного порта.

## Risks / Trade-offs

- **[Пользователь задал только `LLM_*`]** → семантика выключена; это ожидаемо и
  видно в консоли адаптеров/логах. При необходимости задаются `EMBEDDING_*`.
- **[Разные провайдеры чата и эмбеддингов]** → допустимо: наборы независимы.

## Migration Plan

1. Флаги/ENV `EMBEDDING_*` в `cmd`.
2. `vectorRecallPort` по `-embedding-key`.
3. `compose.yaml`/`.env.example`.
4. Приёмка: одобрение заявки проходит без ключа эмбеддингов; с ключом — recall работает.

**Откат.** Пустой `EMBEDDING_KEY` = прежнее поведение «вектор недоступен».
