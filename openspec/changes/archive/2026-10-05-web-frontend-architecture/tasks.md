# Задачи

Срезы — вертикальные: каждый даёт работающий сценарий оператора, а не слой. **Срез 1 обязателен и замыкает разрыв**: без него workflow застревает в `awaiting-approval`. Остальные срезы крупнее и опираются на уже реализованные экраны, контракты и эндпоинты; код консоли создаётся этими задачами (здесь — только план).

## 1. Срез 1. Замкнуть цикл утверждения результата фулфилмента

Цель среза: оператор видит заявки, чьё исполнение стоит в фазе `awaiting-approval`, и по кнопке утверждает или отклоняет результат, после чего workflow идёт к `fulfilled` (или `cancelled`). Всё живёт в контексте `request-fulfillment` — владельце агрегата `request` и workflow.

- [x] 1.1 Реализовать use case чтения очереди утверждения в `backend/contexts/request-fulfillment/internal/app/query`: заявки в доменном статусе `processing`, чья фаза по `ports.WorkflowStatusReader` равна `awaiting-approval`; строке вернуть идентификатор, тенант, оффер, версию, фазу, найденное число лидов и состояние исполнения. Отсутствие/недоступность читателя фазы — отдельный исход «исполнение недоступно», а не пустая очередь (верификация: unit-тест с заглушкой читателя и с `nil`-читателем)
- [x] 1.2 Реализовать экран очереди `GET` (полная страница): строки заявок, пустое состояние, состояние «исполнение недоступно»; разметка на `frontend/components` (`Layout`, `Nav`, `Page`, `status-badge`), стиль и статика — по образцу существующей консоли (верификация: golden-тест страницы; пустая очередь и недоступный рантайм различаются)
- [x] 1.3 Реализовать решение оператора: `approved`/`rejected` отправляются на выделенные HTML-маршруты `POST /requests/{requestID}/approval/approve|reject` и возвращают POST/redirect/GET на экран; обработчик переиспользует `ports.WorkflowSignaler`; JSON-эндпоинт `POST /requests/{requestID}/workflow/approval-decision` для программных клиентов сохраняется неизменным (верификация: тест обработчика для HTML-формы и для JSON; повторная отправка даёт одно решение)
- [x] 1.4 Показывать статус workflow: фаза, найденное число лидов, состояние исполнения — при открытии экрана и после решения; обновление мягким опросом или HTMX-фрагментом (верификация: golden-тест фрагмента; тест контракта «фрагмент = часть страницы»)
- [x] 1.5 Подключить к экрану сессию оператора и CSRF: изменяющие запросы без валидной сессии и токена отклоняются; cookie `HttpOnly`, `Secure`, `SameSite`; CSP без inline-скриптов через `components.SecurityHeaders` (верификация: тест запроса без токена отклоняется; заголовки присутствуют)
- [x] 1.6 Обеспечить честную деградацию: при `nil`-портах `WorkflowStatus`/`WorkflowSignaler` экран показывает «исполнение недоступно», а действие отвечает 503 — состояние не выдумывается (верификация: тест без рантайма даёт явное состояние и 503)
- [x] 1.7 Реализовать состояния экрана: загрузка, пусто, ошибка, отказ в доступе, недоступность рантайма — общими блоками, без дублирования по страницам (верификация: каждый случай отрисован тестом)
- [x] 1.8 Собрать экран в сервисе: маршруты и шаблоны в `request-fulfillment/internal/adapters/http`, подключение в `Build`/`New`, middleware наблюдаемости, учётные данные сессии из конфигурации точки входа (верификация: сервис поднимается; приложение отдаёт экран очереди; `go build ./...` проходит)
- [x] 1.9 Покрыть инварианты тестами: решение по недоступному исполнению не «успешно»; двойная отправка даёт одно решение; отсутствующая заявка/чужой тенант не раскрываются (верификация: по тесту на инвариант)
- [x] 1.10 Провести сквозной сценарий среза: подача → валидация → одобрение → фаза `awaiting-approval` → утверждение из консоли → `fulfilled`; отказ на паузе → `cancelled` (верификация: тест на заглушке workflow проходит оба исхода; переходы зафиксированы с актором и временем)
