# Дизайн операторской консоли платформы

## Context

Мотивация и объём — в `proposal.md`. Здесь только состояние проекта и ограничения, формирующие подход.

**Что уже реализовано и не перепроектируется.**

- **Стек интерфейса** — HTMX + серверные шаблоны на `html/template`, серверный рендеринг (`docs/architecture.md` §11).
- **Общий слой компонентов** — `frontend/components`: `Layout`, `Nav`, `Page`, `Field`, `Notice`, `Tabs`, `status-badge`, `provenance`, `SecurityHeaders`, модель «полная страница или фрагмент» (`Set.Render` / `Set.RenderFragment`) и разбор ошибок формы.
- **Существующая консоль оператора** — `backend/contexts/lead-management/internal/adapters/http`: вход, серверная сессия и CSRF (`-console-user`/`-console-password`), главная, карточки, лиды, воронка, отправка, библиотека шаблонов, ассистент, форумы. Это образец приёмов (навигация, сессия, PRG, CSP), а не отдельный продукт.
- **Экран валидации заявки** — `backend/contexts/request-fulfillment/internal/adapters/http`: очередь `GET /validation`, экран `GET /requests/{id}/validation`, действия `take`/`offer`/`approve`/`reject`/`call`. Одобрение (`approve`) само запускает workflow фулфилмента.
- **Портал клиента** — `backend/contexts/platform-governance/internal/adapters/http`: `GET/POST /register`, `GET/POST /portal`.
- **Дашборд** — `backend/contexts/analytics/internal/adapters/http`: `GET /dashboard`, `GET /dashboard/stream`.
- **Исполнение заявки (workflow)** — `backend/platform/workflow` (Temporal) и адаптер `request-fulfillment/internal/adapters/workflow`: фазы `starting-processing → searching → awaiting-approval → fulfilling → fulfilled` (отказ на паузе → `cancelled`), сигнал `approval-decision`, query `status`. API: `GET /requests/{id}/workflow`, `POST /requests/{id}/workflow`, `POST /requests/{id}/workflow/approval-decision`.

**Что уже зафиксировано и не пересматривается.**

- Интерфейс — эксплуатационная часть роли **`api`** (внутренний контур), поднимаемой сервисами, а не отдельный процесс и не bounded context (`docs/system-map.md` §2.1). Роль `api` не делает долгих операций.
- **Обязательное утверждение человеком** — центральный инвариант продукта: автоутверждение запрещено, а прямой вызов API без решения оператора не исполняет действие.
- **Терминология** (BRD §3.18): формулировка «адрес существует» запрещена; допустимы «доставляемый», «рискованный», «неизвестно», «недействительный».

**Ограничения, определяющие дизайн.**

- Консоль обязана совпасть с context-first структурой Go-модуля (`migrate-platform-to-go` §2, `service-per-context`): `domain` не импортирует другие слои и контексты, `app` использует только свой `domain`/`ports` и опубликованные контракты, SDK — только в `adapters`; межконтекстная сборка в одном пакете запрещена.
- Экран часто показывает данные нескольких контекстов. Чужие данные приходят только через объявленные синхронные `query`-контракты (`sync`/`http-json`), не импортом чужого контекста.
- Рантайм workflow может быть не подключён: тогда порты `WorkflowStatusReader`/`WorkflowSignaler` равны `nil`, и обработчик обязан честно ответить `503`, а не выдумывать состояние.

**Ключевое напряжение.** Консоль — единственное место, где человек принимает необратимые решения, и одновременно самый дешёвый способ обойти инвариант утверждения (кнопка вместо серверной проверки, «оптимистичный» JavaScript). Дизайн обязан сделать обход невозможным по построению, а не по соглашению. Ровно на этом ломается текущий сценарий: без экрана сигнал `approval-decision` некому подать, и заявка застревает в фазе `awaiting-approval`.

## Goals / Non-Goals

**Goals:**

- **Замкнуть цикл утверждения результата фулфилмента:** показать оператору заявки в фазе `awaiting-approval` и дать утвердить или отклонить результат одной кнопкой, с отображением состояния исполнения.
- Свести экраны консоли в связную навигацию, не создав ни общей доменной модели, ни второго владельца состояния.
- Исключить обход инварианта утверждения через интерфейс: любое необратимое действие проходит серверную проверку.
- Переиспользовать уже готовые экраны, компоненты, эндпоинты и контракты, не дублируя их.
- Дать предсказуемую работу с длительными операциями: команда отделена от результата, прогресс виден.

**Non-Goals (на уровне дизайна):**

- Не проектируем публичные страницы `ingest` — другой контур, без сессии оператора.
- Не проектируем консоль топологии сервисов (change `service-topology-console`) и визуальный стиль.
- Не строим SPA, мобильное приложение и офлайн-режим.
- Не вводим собственные механизмы утверждения, доступа и идемпотентности — используем ядро.

## Decisions

### Решение 1. Консоль — эксплуатационная часть роли `api` внутри сервисов, а не bounded context

Консоль не получает собственного bounded context, агрегатов и состояния. Это способ представить уже существующую модель человеку. Экран принадлежит контексту-владельцу своего основного агрегата и живёт в его `internal/adapters/http`; он читает проекции и отправляет команды прикладным сервисам owning context.

**Почему так:** `docs/system-map.md` §2.0–§2.1 различает контекст (модель и владение) и роль (режим запуска внутри сервиса). Роль `api` не владеет моделью. Экран, показывающий данные нескольких контекстов, принадлежит владельцу основного агрегата и добирает чужие данные по объявленным контрактам. Готовый пример — существующая консоль `lead-management` и экран валидации `request-fulfillment`: оба живут в `adapters/http` своих контекстов.

**Следствие.** Правила видимости, права и решения живут в owning context; сервис-владелец экрана применяет локальный контрактный снимок правила `access-decision` и политики owning context, а не условие в шаблоне. Первый срез живёт в `request-fulfillment`, потому что владелец агрегата `request` и workflow — он.

### Решение 2. Стек: серверный рендеринг на `html/template` + HTMX; SPA отклонён

Экран собирается на сервере: HTML отдаётся целиком при переходе и фрагментом при частичном обновлении. JavaScript ограничен библиотекой HTMX (BSD-2-Clause) и небольшими вспомогательными скриптами; клиент не содержит бизнес-логики.

**Почему так:**

- Консоль — внутренний инструмент оператора, а не публичный продукт с богатым клиентским состоянием. Очередь, карточка и решение — это списки и формы, где выигрыш от клиентского состояния мал, а цена (второй набор правил доступа и валидации) высока.
- Инвариант «ноль исходящих действий без утверждения» дешёвле всего проверяется на сервере в одном месте. Чем меньше логики в браузере, тем меньше способов её обойти.
- `html/template` экранирует вывод по умолчанию и делает XSS-класс ошибок маловероятным.
- Стек уже канонизирован (`architecture.md` §11) и уже используется существующей консолью.

**Рассмотренные альтернативы:**

- **SPA (React/Vue) с JSON API.** Отклонено: требует второго набора проверок доступа и валидации на клиенте, выносит персональные данные шире нужного, усложняет доступность и тестирование, вводит второй стек в проекте, сознательно выбравшем стандартную библиотеку.
- **Отдельный фронтенд-процесс/сервис.** Отклонено: нарушает «один образ, назначение задаётся конфигурацией» (`architecture.md` §8) и создаёт второй контур доступа к данным.
- **Готовая админ-панель или UI Twenty CRM.** Отклонено: не выражает семантику утверждения и правила доступа, требует доступа к красной зоне из чужого UI.

### Решение 3. Слои и место в context-first структуре

```text
backend/cmd/lead-gen/                  # единая точка входа: сервис и роли из deploy/services.yaml
backend/contexts/<context-id>/         # сервисная сборка: composition root сервиса
frontend/components/                   # примитивы без доменных терминов: layout, рендеринг шаблонов,
                                       # поля, уведомления, вкладки, бейдж статуса, происхождение,
                                       # безопасность заголовков, «полная страница или фрагмент»
backend/platform/transport/http/       # синхронный транспорт границы сервиса (пакет transport)
backend/contexts/<context-id>/
  internal/adapters/http/              # обработчики, шаблоны и статика экранов этого контекста
    templates/
  internal/app/                        # вызываемые use cases
  internal/ports/                      # контракты, нужные контексту
```

**Правило зависимостей.** `adapters/http` вызывает только `app` своего контекста (и его `ports`); `domain` не видит представления; `frontend/components` не содержит доменных терминов. Экран, которому нужны данные другого контекста, запрашивает их через объявленный синхронный `query`-контракт владельца (транспорт `sync`/`http-json`, `backend/platform/transport/http`), а не импортом чужого контекста. Межконтекстная сборка в одном пакете запрещена (`service-per-context`).

**Почему так:** сохраняется один владелец модели, а представление остаётся заменяемым. Обработчики и шаблоны экрана живут рядом с use cases своего контекста.

**Следствие.** Проверка границ импортов расширяется правилом: пакет HTTP-адаптера не импортирует `domain` и `app` чужого контекста (проверяемо `go run ./tools/importlint`). Общие приёмы консоли (сессия оператора, CSRF, рамка страницы) выносятся в единое место, чтобы не копироваться по контекстам, но не тянут доменных зависимостей.

### Решение 4. Модель рендеринга: полная страница + гипермедиа-фрагменты, POST/redirect/GET

- Переход по навигации отдаёт полную страницу (layout + содержимое).
- Действие отдаёт **фрагмент** (`hx-*`), который заменяет часть страницы. Тот же обработчик по прямому запросу без заголовка HTMX отдаёт полную страницу — так работает прогрессивное улучшение.
- Изменяющие действия идут только через POST с последующим redirect (PRG), чтобы обновление страницы не повторяло необратимое действие.
- Обновление списков — по явному действию или мягкому опросу; длительные задачи — через опрос статуса (Решение 11).

**Почему так:** PRG убирает самый частый способ случайного дублирования решения — перезагрузку страницы. Возврат полной страницы по прямому запросу делает каждый экран работоспособным без JavaScript и упрощает тестирование. Существующий экран валидации уже реализует эту модель (`validationAction`).

**Следствие.** Шаблон фрагмента и шаблон полной страницы используют общую разметку блока; дублирования разметки не допускается.

### Решение 5. Карта экранов и навигация

Навигация строится вокруг работы оператора, а не вокруг контекстов: контексты — внутренняя граница, пользователь видит задачи. Колонка «Статус» — что уже реализовано и сюда не переписывается.

| Раздел | Экран | Состояние |
|---|---|---|
| **Заявки** | Очередь валидации и экран валидации заявки | реализовано (`request-fulfillment`) |
| **Исполнение** | Очередь `awaiting-approval`, статус workflow, утверждение/отклонение результата | **первый срез этого change'а** |
| **Лиды** | Главная, карточки, лиды, воронка, отправка, шаблоны, ассистент, форумы | реализовано (`lead-management`) |
| **Отчёты** | Дашборд и поток метрик | реализовано (`analytics`) |
| **Рассылки** | Очередь утверждения черновиков и пакетов | API готово (`outreach-orchestration`), экран — отдельный срез |
| **Настройки** | Пользователи и роли, тенант, интеграции, домены, лимиты, аудит | будущий срез |
| **Топология** | Топология сервисов (только администратор) | отдельный change `service-topology-console` |

**Правила навигации.** Разделы и действия, недоступные роли, не показываются, но отсутствие в навигации — не защита: сервис-владелец экрана проверяет право на каждое действие (Решение 9). Видимые разделы строятся по тому же снимку доступа, а не по конфигурации шаблона.

**Единый вход.** Сейчас экраны разных контекстов поднимаются разными сервисами (`deploy/services.yaml`: `lead-management` — группа `demand`, `request-fulfillment` — группа `intake`) и слушают каждый свой `apiAddr`. Объединение их под одним адресом и общей навигацией — отдельный срез (Срез 2), а не условие первого среза: экран исполнения работоспособен и сам по себе, как экран валидации. **Решение (закрывает открытый вопрос 1): внешний маршрутизатор по пути.** Экраны остаются экранами своих сервисов, но публикуются под одним origin; маршрутизатор проксирует путь (`/…`) к сервису-владельцу, поэтому вход и сессия оператора становятся общими, а не по сервису. Общий каркас навигации со ссылками на разные порты отклонён: он не даёт единого входа и дублирует сессию. Введение маршрутизатора — изменение развёртывания (`deploy`/`compose`) и учитывается `deployment-topology`.

### Решение 6. Первый срез — замкнуть цикл утверждения результата фулфилмента

Это ответ на разрыв: без этого экрана workflow не покидает `awaiting-approval`.

**Очередь `awaiting-approval`.** Экран читает заявки, чьё исполнение стоит на человеческой паузе. Источник — use case контекста `request-fulfillment`: заявки в доменном статусе `processing`, фаза которых по `ports.WorkflowStatusReader` равна `awaiting-approval`. Строка показывает: идентификатор заявки, тенант, оффер, версию, текущую фазу, найденное число лидов и состояние исполнения (`execution`). Заявки, чей рантайм workflow недоступен, показываются честно (состояние «недоступно»), а не как пустая очередь.

**Решение.** На экране — утвердить или отклонить. Кнопка шлёт `POST /requests/{requestID}/workflow/approval-decision` и возвращается на экран (PRG). Обработчик переиспользует `ports.WorkflowSignaler`, уже подключённый к API: экранный путь — та же команда, что и программный, отдельного механизма утверждения не вводится. Форма несёт актора из сессии; отказ на паузе переводит заявку в `cancelled`, утверждение — к `fulfilling → fulfilled`.

**Отображение статуса.** После решения и при обычном открытии экран показывает фазу workflow, найденное число лидов и состояние исполнения. Мягкое обновление — опросом или HTMX-фрагментом по образцу существующей консоли.

**Серверная проверка.** Ни решение, ни исполнение не зависят от клиента: сигнал принимает owning context, запись решения и исполнение остаются за ядром. Экран без JavaScript обязан работать (полная страница + форма).

**Почему так:** это единственное место, где консоль обязана замкнуть durable-сценарий человека. Экран — тонкая проекция: он не решает, он показывает состояние и подаёт команду.

**Последующие срезы** (крупнее, см. `tasks.md`): единый вход и навигация; дашборд лидов и отчётность; экран очереди утверждения рассылок `outreach-orchestration` (поведение уже нормировано, маршруты готовы); настройки, доступ, тенант, аудит; длительные операции и DLQ; доступность, локализация и безопасность.

### Решение 7. Состояния, формы и свежесть данных

Каждый экран обязан иметь явные состояния, а не только «повезло»:

- **Загрузка:** индикатор на фрагменте (`hx-indicator`), кнопка действия блокируется на время запроса.
- **Пусто:** осмысленное пустое состояние с подсказкой следующего шага, а не пустая таблица.
- **Ошибка:** серверная ошибка показывается понятным сообщением с возможностью повтора; технические детали без идентификатора корреляции наружу не отдаются.
- **Отказ в доступе:** экран объясняет, что действие недоступно, а не показывает 404 скрытно; факт отказа фиксируется в аудите при значимом действии.
- **Недоступность рантайма:** если workflow недоступен, экран показывает «исполнение недоступно» (watermark), а не пустую очередь и не ноль.
- **Свежесть:** там, где проекция отстаёт, показывается время расчёта; недоступность контура не скрывается под «нулём» (BRD §3.17).
- **Формы:** серверная валидация — источник истины; ошибки возвращаются к форме с сохранением введённого.

### Решение 8. Идемпотентность и утверждения в интерфейсе

- **Защита от двойной отправки.** Кнопка блокируется на время запроса; повторный POST не должен приводить ко второму решению — идентификатор исполнения `fulfillment-<requestID>` уже служит ключом идемпотентности запуска, а путь решения — единственная необратимая операция и должен дедуплицироваться по тому же принципу.
- **CSRF.** Каждый изменяющий запрос несёт токен; проверка на сервере; cookie сессии `HttpOnly`, `Secure`, `SameSite`.
- **Интерфейс не обходит утверждение.** Никакой клиентский путь (кнопка, фрагмент, скрытое поле) не исполняет действие: исполнение возможно только после подачи сигнала owning context, а выпуск результата выполняет workflow.

**Почему так:** консоль — самый вероятный источник дублей и «случайных» необратимых действий. Существующий экран валидации и консоль `lead-management` уже держат сессию и CSRF; первый срез наследует этот приём.

### Решение 9. Доступ и RBAC

- Аутентификация и права — в `platform-governance`; консоль не воспроизводит правила ролей локально.
- **`access-decision` — подписка, а не синхронный запрос.** Связь объявлена как `policy`/`async`: сервис-владелец экрана хранит локальный контрактный снимок правила и применяет его к экранам и действиям. Синхронного запроса решения на каждое действие нет — он сделал бы `platform-governance` общей точкой отказа консоли.
- Роли из BRD §3.16: владелец, менеджер, маркетолог, дизайнер контента, администратор, аналитик. Матрица «роль → раздел → действие» — отображение снимка решений доступа, а не условие в шаблоне.
- **Проверка на сервере для каждого действия.** Навигация скрывает недоступное, но ни одно действие не полагается на скрытие.
- На первом срезе, до подключения полного снимка, экран исполнения применяет ту же сессию оператора, что и существующая консоль (`-console-user`/`-console-password`); переход на матрицу ролей — отдельный срез.

**Почему так:** RBAC на клиенте не является RBAC. Правило, продублированное в шаблоне, разойдётся с серверным и превратится в уязвимость.

### Решение 10. Мультитенантность

- Тенант определяется **на сервере** из сессии и пользователя; он не читается из параметров запроса, пути или скрытых полей формы.
- Изоляция обеспечивается политикой хранилища (row-level security), а не фильтром в представлении; интерфейс полагается на то, что запросы контекста уже ограничены тенантом.
- Переключение тенанта доступно только пользователю, которому разрешён более чем один тенант; факт переключения фиксируется.

**Почему так:** тенант, пришедший из клиента, — классическая уязвимость изоляции; существующий экран валидации уже полагается на фильтр владельца (`ValidationQueue` не отдаёт чужие тенанты).

### Решение 11. Длительные операции через очередь

Консоль никогда не выполняет долгую работу в рамках запроса. Модель единая: действие публикует команду и получает идентификатор задания; экран показывает прогресс (процент, текущий шаг, время начала) и обновляет его мягким опросом или фрагментом; неуспешное задание показывает нормализованную причину; исчерпавшие попытки задания видны администратору (DLQ). Модель применяется к импорту файлов, генерации контента, рендерингу PDF, построению отчётов и сбору данных. Состояние durable-исполнения заявки (фаза, найденное число лидов, исход) читается через `GET /requests/{id}/workflow` и показывается на экране исполнения.

**Почему так:** `architecture.md` §3 разделяет синхронные и асинхронные операции, а §6.2 требует, чтобы потеря задания была невозможна.

**Где живут экраны модели (срез 6).** Модель единая, но экраны — у владельца задания: примитив `platform/jobs` не хранит состояние сам, хранилище задания принадлежит контексту. Единственная реализованная долгая операция на этом примитиве — выгрузка отчёта в `analytics` (`ports.ReportExportStore`); там же живут экран прогресса/результата и экран DLQ. Отдельный центральный экран заданий в `platform-governance` создал бы второго владельца модели или межконтекстный доступ к чужим хранилищам — оба запрещены. Доступ к разделу заданий (DLQ, повтор) — решение о ресурсе `jobs-admin` владельца политики: клиенту он закрыт, администратору открыт; ссылка показывается по тому же снимку доступа, а не условием в шаблоне. Повтор упавшего задания — явное действие оператора (примитив `jobs.RetryJob`), не автоматическая политика.

### Решение 12. i18n и терминология

- Тексты выносятся в каталоги сообщений, а не остаются строковыми литералами в шаблонах; локализуются форматы дат, чисел, валют и часовых поясов.
- **Терминология верификации** следует BRD §3.18: «доставляемый», «рискованный», «неизвестно», «недействительный»; формулировка «адрес существует» запрещена. Дата и источник проверки показываются рядом со статусом.
- **Открытия не показываются.** Метрик открытий в консоли нет; состояние прочтения — `read` / `unknown`.
- **Формулировки инварианта.** Там, где речь о решении оператора, интерфейс говорит «утвердить/отклонить/отложить», а не «отправить»: отправка — следствие утверждения.

### Решение 13. Доступность

- Целевой уровень — WCAG 2.1 AA: семантическая разметка, корректные заголовки и landmarks, текстовые метки у полей.
- Полная клавиатурная доступность: очередь и формы проходятся без мыши; фокус видим.
- При подмене фрагментов HTMX фокус управляется явно; изменения объявляются через `aria-live`.
- Цвет не является единственным носителем смысла (статус, признак риска — с текстом и иконкой).
- Ошибочные формы дают сводку ошибок и связывают её с полями.

### Решение 14. Тестирование консоли

- **Рендеринг-тесты шаблонов:** golden-файлы для фрагментов и ключевых страниц; проверка обязательных элементов (фаза, найденное число, кнопки решения).
- **Интеграционные тесты обработчиков:** `net/http/httptest`, прикладные сервисы и порты workflow подменяются тестовыми реализациями.
- **Тесты контракта фрагментов:** один и тот же обработчик возвращает корректный фрагмент с заголовком HTMX и полную страницу без него.
- **Тесты инвариантов:** решение без сессии отклоняется; повторный POST не даёт второго решения; при `nil`-порте сигналов экран честно показывает недоступность (503), а не выдумывает успех.
- **Проверка границ:** HTTP-адаптер не импортирует `domain` и `app` чужого контекста (`go run ./tools/importlint`); отсутствие новых сущностей и контрактов проверяет `go -C tools/archlint run .`.
- **Сквозной сценарий:** заявка проходит подачу → валидацию → утверждение результата → исполнение; отказ переводит в `cancelled`.

### Решение 15. Ресурсы, безопасность консоли, развёртывание

- HTMX и вспомогательные скрипты поставляются как статические ресурсы; обязательной сборки фронтенда нет.
- Строгая Content-Security-Policy без inline-скриптов; разметка без `unsafe-inline`. Общий приём установки заголовков — `components.SecurityHeaders`.
- `html/template` экранирует вывод по умолчанию; ссылки из пользовательских данных обезвреживаются.
- Секреты интеграций и токены в HTML не попадают.
- Кэширование страниц с персональными данными запрещено; ответы с персональными данными — `Cache-Control: no-store`.
- Ограничение частоты попыток входа и чувствительных действий.

### Решение 16. Доменная привязка

Изменение не вводит сущностей, агрегатов, domain events, policies и межконтекстных контрактов. Первичный источник первого среза — aggregate `request` в `request-fulfillment`; статусная машина и решения заданы спекой `client-request` и `request-validation`; человеческая пауза и сигнал утверждения — уже реализованным workflow. Права и аудит — aggregate `tenant-access` в `platform-governance` (контракт `access-decision`). Консоль читает эти данные и отправляет команды через существующие контракты.

**Следствие:** `architecture/domain-catalog.yaml`, `docs/domain-model.md` и обязательные диаграммы **не меняются**. `go -C tools/archlint run .` должен остаться зелёным: новых capability не добавляется (изменение помечено `skip_specs: true`).

## Risks / Trade-offs

- **Протечка доменных правил в представление.** Самый вероятный способ со временем нарушить context-first: удобно «дописать условие в шаблоне». Компенсация: правило зависимостей, проверка импортов, тесты и явное «шаблон не решает, шаблон показывает».
- **Дублирование сессии и CSRF по контекстам.** Экран `request-fulfillment` и консоль `lead-management` нуждаются в одном и том же. Первый срез обязан вынести общий приём в единое место, иначе разойдётся поведение безопасности. Компенсация: общий компонент/пакет, покрытый тестами.
- **Разрозненность экранов по сервисам.** Разные контексты поднимают свои `apiAddr`; без общего входа оператор ходит по разным адресам. Принято осознанно на первый срез; объединение — отдельный срез.
- **Недоступность рантайма workflow.** Без Temporal экран обязан честно показать недоступность и не притворяться, что очередь пуста. Компенсация: явное состояние и тест на `nil`-порт.
- **Слабая мгновенность отклика.** Опрос и обновления фрагментов уступают SPA по «живости». Принято осознанно ради инварианта утверждения и простоты.

## Migration Plan

Изменение задаёт структуру консоли и создаёт её первый срез; порядок работ — в `tasks.md`:

1. **Первый срез — замкнуть цикл.** Очередь `awaiting-approval`, отображение статуса workflow, утверждение/отклонение через `approval-decision`, сессия и CSRF, тесты. Это проверочный сценарий всего дизайна и единственный обязательный срез.
2. **Единый вход и навигация.** Свести экраны под общий каркас и вход, не переписывая готовые экраны.
3. **Дашборд лидов и отчётность.**
4. **Очередь утверждения рассылок** (`outreach-orchestration`).
5. **Настройки, доступ, тенант, аудит.**
6. **Длительные операции и DLQ.**
7. **Доступность, локализация, безопасность.**
