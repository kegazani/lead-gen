## Context

Change №1 (`client-request-domain`) дал агрегат `request` со статусной машиной и инвариантами (заморозка оффера после `validated`, `processing` только из `validated`). Агрегат `call` живёт в `outreach-orchestration`. Мотивация — в `proposal.md`.

## Goals / Non-Goals

**Goals:**

- Определить, где живёт workflow валидации и решение.
- Связать валидацию со звонком-уточнением через `call`.
- Задать, как правки оффера до `validated` отличаются от замороженного оффера после.

**Non-Goals:**

- Агентный конвейер после `validated` — change №2 и №4.
- Клиентский портал (где клиент подаёт заявку) — change №5.
- Экран оператора детально — общий дизайн интерфейса в `web-frontend-architecture`.

## Decisions

### Решение 1: workflow валидации — application service `request-fulfillment`

Валидация — прикладной use case контекста-владельца заявки, а не отдельный контекст и не Temporal-workflow сам по себе (хотя в change №2 он может стать шагом графа). Команды `take-for-validation`, `approve`, `reject` — application services, выполняющие переходы статусной машины.

### Решение 2: решение валидации — внутри агрегата `request`, не `operator-decision`

`operator-decision` (в `outreach-orchestration`) — аудируемое решение по *черновику действия*. Решение по заявке — другой предмет. Валидационное решение (решение, актор, время, причина) хранится в агрегате `request`, чтобы не размывать границу и не плодить отдельный агрегат.

### Решение 3: звонок-уточнение — переиспользование `call`

Клиенту звонят через существующий агрегат `call` (`outreach-orchestration`). Заявка хранит `call_id` по идентификатору, не владея звонком.

### Решение 4: правки оффера — на месте до `validated`

До `validated` оффер редактируется на месте (валидатор уточняет формулировки). Заморозка и версионирование включаются только после `validated` — это уже инвариант `client-request`, здесь не дублируется.

## Risks / Trade-offs

- **[Размытие границы с `operator-decision`]** → Явно отделено в Решении 2; решение хранится в `request`.
- **[Звонок вне контекста заявки]** → Заявка ссылается на `call_id`, владение звонком остаётся у `outreach-orchestration`.
- **[Правки оффера до/после валидации]** → Чёткая граница `validated`: до — на месте, после — версия (инвариант `client-request`).

## Migration Plan

Новой персистентности не требуется: решение и `call_id` — новые поля агрегата `request`. Миграция БД — добавление колонок (`validation_decision`, `call_id`). Откат: колонки nullable, существующие заявки не затрагиваются.

## Open Questions

- Нужен ли статус «возврат на доработку» (`validating → submitted`) вместо жёсткого `rejected` — решается продуктово; не меняет спек этого change (жёсткое `rejected` покрыто).
