## Контекст

Миграции — SQL-файлы, принадлежащие схеме сервиса (schema-per-service). Загрузчик
`backend/platform/migrate` (`Load`) проверяет директиву принадлежности
`-- schema: <context-id>` до выполнения, но само применение жило в
`applyMigrations` внутри `cmd/lead-gen`: цикл `pool.Exec` без блокировки и без
учёта уже применённого. Из-за этого:

- на чистой базе два процесса одновременно выполняют
  `CREATE SCHEMA IF NOT EXISTS`: PostgreSQL допускает гонку `IF NOT EXISTS` на
  `pg_namespace_nspname_index` → SQLSTATE 23505 и падение контейнера;
- на существующей базе повторный `up` выполняет `0002_access_and_outbox.sql`
  заново, а `UPDATE ... SET roles = ARRAY[role]` ссылается на уже удалённую
  колонку `role`.

## Решение 1. Применение — шаг `migrate.Apply` в `backend/platform/migrate`

Применение переезжает к загрузчику: единая точка `Apply(ctx, pool, dir, owned)`
выполняет `Load`, сериализацию и применение. `cmd/lead-gen` больше не содержит
логики цикла миграций — он вызывает `Apply` (обёртки `supportPool` и
`applyMigrations` сохраняются как тонкие вызовы, чтобы не менять все места
сборки сервисов). Это чинит дублирование и делает применение проверяемым в одном
пакете.

## Решение 2. Межпроцессная блокировка — advisory-lock по имени схемы

На время применения схемы удерживается session-level advisory-блокировка
`pg_advisory_lock(key)`, где `key` — детерминированный хэш (FNV-1a 64) строки
`migrate:<schema>`. Одна блокировка на схему означает:

- общая схема `consoleauth`, применяемая несколькими сервисами, сериализуется
  между процессами — гонка `CREATE SCHEMA` исчезает;
- разные схемы не блокируют друг друга.

Блокировка берётся на **выделенном соединении пула** (`pool.Acquire`) и
удерживается до конца применения: advisory-lock действует в пределах сессии, а
пул выдаёт разные соединения на разные операторы. Освобождение — `defer
pg_advisory_unlock`; при падении процесса блокировка снимается разрывом сессии.
Бюджет ожидания не ограничивается дедлайном вызывающего искусственно: ожидание
блокировки — штатное поведение конкурирующего старта.

## Решение 3. Таблица версий и транзакция на миграцию

Под блокировкой создаются схема (`CREATE SCHEMA IF NOT EXISTS`, имена
квалифицируются через `pgx.Identifier.Sanitize`) и таблица
`<schema>.schema_migrations (version text PRIMARY KEY, applied_at timestamptz)`.
Каждый файл применяется в собственной транзакции: `BEGIN` → SQL файла →
`INSERT INTO schema_migrations(version)` → `COMMIT`. Ошибка откатывает файл
целиком (нет частичного применения), а запись версии и эффект миграции
атомарны. Уже записанные версии пропускаются.

Почему версия — имя файла: порядок применения задаётся именем, а expand/contract
делает переименование файла событием, требующим повторного применения. Таблица
живёт в схеме сервиса: во-первых, она не требует прав на чужую схему; во-вторых,
для раздельных баз (зелёная/красная зоны `lead-management`) она создаётся в
каждой базе отдельно.

## Решение 4. Идемпотентность `0002_access_and_outbox.sql`

Повторное применение на базе, мигрированной прежним кодом (таблицы версий ещё
нет), не должно падать. Причина — `UPDATE`, ссылающийся на колонку `role` после
её удаления. Перенос `role → roles` оборачивается в `DO $$ ... $$` с проверкой
наличия колонки `role` в `information_schema.columns`: на первом применении
перенос выполняется, при повторе — пропускается. Смысл, состав и типы колонок не
меняются, поэтому база остаётся совместимой без новых ALTER-ов.

Остальные миграции проверены: `CREATE SCHEMA/TABLE/INDEX` и `ADD COLUMN` уже
несут `IF NOT EXISTS`/`IF EXISTS`, `INSERT` без конфликта и неидемпотентных
`DROP` нет. Отслеживание версий делает повторное применение безопасным даже для
будущих файлов, идемпотентность `0002` закрывает уже существующие базы.

## Отвергнутые варианты

- **Только таблица версий, без блокировки.** Не чинит гонку `CREATE SCHEMA` на
  чистой базе: две транзакции успевают создать таблицу версий до её появления.
- **Только advisory-lock, без таблицы версий.** Заставляет полагаться на
  идемпотентность каждого файла навсегда; одна неаккуратная миграция вернёт
  найденную проблему.
- **`CREATE SCHEMA` вне блокировки.** Возвращает наблюдаемую гонку
  `pg_namespace_nspname_index`.
- **Единый migrator-процесс/контейнер.** Меняет топологию деплоя и добавляет
  точку отказа; advisory-lock решает задачу в существующей топологии.
