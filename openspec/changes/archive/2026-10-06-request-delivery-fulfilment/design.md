## Context

Мотивация и объём — `proposal.md`. Состояние, определяющее подход:

- Workflow заявки (`request-fulfillment`, `adapters/workflow/fulfillment.go`) после
  передачи писем встаёт на человеческую паузу (`awaitApproval`) и ждёт **сигнал
  консоли заявок** `SignalApprovalDecision`. Достигнув сигнала, он переводит заявку
  `processing → fulfilled`.
- В недоборном контуре оператор утверждает письма в очереди `outreach-orchestration`;
  оттуда уходит `approved-action` → `message-delivery` доставляет письма и публикует
  `delivery-event`. Сигнал в workflow заявки при этом **никто не подаёт** — отсюда
  наблюдаемый дефект: заявка навсегда в `processing`.
- `approved-action` уже несёт кампанию двумя способами: полем `campaign_id` и
  `correlation_id = campaign_id` (`ports/contracts/approved_action.go`). Мост
  `message-delivery` кладёт кампанию в `domain.DeliveryCommand.CorrelationID`, но
  агрегат `message` её не хранит, и `delivery-event` её не несёт.
- Событие доставки уже публикуется через transactional outbox (`delivery-event`,
  MINOR-версионируемый контракт) и уже потребляется другими контекстами; в
  `request-fulfillment` подписки на него нет.
- Передачу писем выполняет `activity HandoffDrafts`; её исход —
  `outreach-handoff.Result{CampaignID, Accepted, Skipped, Repeated}` — в граф
  workflow не поднимается, `campaign_id` заявки не фиксируется.
- Состояние заявки — aggregate root `request`; переход `processing → fulfilled`
  идемпотентен по построению (`applyTransition`: повтор в целевой статус — no-op).
  Граф исполнения версионируется маркерами `workflow.GetVersion`.

## Goals / Non-Goals

**Goals:**
- Замкнуть жизненный цикл: после реальной отправки письма заявка доходит до
  терминального `fulfilled` по наблюдаемому исходу доставки, без ручного сигнала.
- Не выдавать недоставку за успех; не оставлять заявку в ожидании навсегда.
- Остаться в рамках существующих контрактов, расширяя их аддитивно (MINOR).

**Non-Goals:**
- Не менять контур утверждения/отправки `outreach-orchestration`.
- Не вводить автоотправку без человека и не менять контракт `approved-action`.
- Не пересчитывать ретроспективно уже бегущие исполнения (детерминизм Temporal):
  исправление действует на новые запуски.

## Decisions

### Решение 1. Что означает `fulfilled` и наблюдаемый триггер

**Выбор.** Для заявки с недобором `fulfilled` означает: **все письма, переданные
заявкой на утверждение, доставлены** (по каждому получен исход `delivered` от
`message-delivery`). Триггер — событие `delivery-event`. `failed` по отдельному
письму не завершает заявку: недоставка оставляет остаток видимым, а не подменяется
успехом.

**Почему.** `processing → fulfilled` — завершение фульфилмента, а не достижение
цели (цель недостижима и завершается видимым остатком — `request-shortfall`).
Решение оператора в недоборном контуре уже принято в очереди `outreach`
(утверждение черновиков); его наблюдаемое подтверждение — факт доставки, а не
повторный сигнал консоли заявок. «Все доставлены» — минимальное честное условие:
одно доставленное письмо при ещё недоставленных (или отказавших) не должно
закрывать заявку.

**Альтернативы.** (A) Завершать по первому `delivered` — отклонено: ложное
завершение при отказе остальных. (B) Завершать по исходу «все достигли
терминального исхода (delivered|failed)» — отклонено: отказ завершал бы заявку
успехом. (C) Завершать по сигналу консоли заявок (как сейчас) — отклонено: в
недоборном контуре сигнала нет, это и есть дефект.

### Решение 2. Сопоставление события доставки с заявкой — по кампании

**Выбор.** `delivery-event` дополняется непрозрачной ссылкой `campaign_id`
(MINOR), унаследованной от `approved-action`. Контекст `request-fulfillment`
фиксирует `campaign_id` своей заявки при передаче (existing команда `RecordCampaign`)
и сопоставляет событие доставки с заявкой по (`tenant_id`, `campaign_id`).

**Почему.** Одна кампания на заявку, `campaign_id` детерминирован из `request_id`
и уже присутствует в `approved-action`. Это точный ключ, не зависящий от формата
доменных строк, в отличие от корреляции по `recipient_ref` (идентификатор контакта
может встречаться у нескольких заявок — тогда корреляция неоднозначна) или по
разбору `campaign_id = "handoff-" + request_id` (формат не является частью
контракта).

**Расширение аддитивно:** `campaign_id` — необязательное поле (старые издатели без
него совместимы; потребители, не читающие его, не затронуты).

### Решение 3. Где живёт накопление «все доставлены» — в durable workflow

**Выбор.** События доставки не накапливаются в новом хранилище контекста:
подписчик (`delivery-event` → сопоставление по кампании) подаёт бегущему workflow
заявки сигнал `SignalDeliveryOutcome{message_id, delivered}`. Сам workflow
(durable, с детерминированным реплеем) дедуплицирует по `message_id` и завершает
паузу, когда все переданные письма покрыты.

**Почему.** Workflow уже durable и хранит наблюдаемое состояние; дублировать
накопление в отдельной проекции — лишняя точка отказа и новая миграция. Подписчик
остаётся тонким (разбор + маршрутизация сигнала), а решение о завершении —
в графе исполнения, которому принадлежит переход.

**Дедупликация.** `message_id` — ключ дедупликации внутри workflow; на входе
подписка дедуплицируется по `event_id` (`platform/messaging/inbox`), как у
`engagement-observation`.

### Решение 4. Срок и исход недоставки

**Выбор.** Ожидание доставки делит срок человеческой паузы (`ApprovalTTL`,
по умолчанию 7 дней). По истечении срока без полного покрытия доставкой заявка
переходит в `cancelled` с явной причиной о недоставке.

**Почему.** Отдельный срок удлинил бы и без того длинную паузу и потребовал бы
новой конфигурации без пользы: оператор уже принял решение в `outreach`, а
недоставка в срок — честный терминальный исход, не «вечное processing». Причина
отличается от «утверждение: срок истёк», чтобы исходы не смешивались.

### Решение 5. Проброс `campaign_id` в `message-delivery`

**Выбор.** Кампания переносится аддитивно: `deliverycommand.Command.campaign_id`
(MINOR) → `domain.DeliveryCommand.CampaignID` → `MessageParams.CampaignID` →
агрегат `message` (поле + снимок) → `MessageDelivered`/`MessageDeliveryFailed` →
`deliveryevent.DeliveryEvent.campaign_id` (MINOR). Мост `approved-action` заполняет
`CampaignID` из `action.CampaignID`.

**Почему.** Значение уже приходит в мост; не хранить его — терять связь доставки
с кампанией. Расширение схемы снимка аддитивно (JSONB), миграции не требует.

## Risks / Trade-offs

- **[Детерминизм Temporal]** → ожидание доставки вводится под `GetVersion`; прежние
  бегущие исполнения воспроизводятся без ожидания. Уже залипшие заявки живого
  прогона требуют нового запуска (стандартное следствие версионирования).
- **[Срок = срок паузы]** → при отказе письма заявка ждёт полный срок паузы до
  `cancelled`; это честно, но не мгновенно. Отдельный «срок доставки» вынесен в
  открытый вопрос.
- **[Событие из чужого контура]** → событие доставки кампании, не созданной
  передачей заявок, игнорируется по кампании и тенанту; произвольная привязка
  исключена.
- **[Проводка подписки]** → подписка/очередь `request-fulfillment.delivery-event`
  собирается в `backend/cmd/lead-gen` (головной агент); без неё контур честно
  недоступен, а не завершает заявки выдуманно.

## Migration Plan

1. Контракты: `deliveryevent` и `deliverycommand` (MINOR `campaign_id`).
2. `message-delivery`: хранение `campaign_id` в агрегате `message` и проброс в
   `delivery-event`.
3. `request-fulfillment`: фиксация `campaign_id` заявки при передаче; сигнал
   завершения по доставке в workflow; подписчик `delivery-event`; чтение заявки по
   кампании.
4. Каталог/`docs/domain-model.md`/диаграммы; гейт; проводка в `cmd/lead-gen`.

**Откат.** Все изменения схем аддитивны и опциональны; поведение без подписки —
прежнее (пауза по сигналу/таймеру). Откат — снятие проводки подписки.
