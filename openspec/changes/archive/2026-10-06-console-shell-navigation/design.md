## Context

Мотив и объём — см. `proposal.md`; здесь — текущее состояние и ограничения, определяющие подход.

Общая навигация консоли уже собрана общим слоем `frontend/components`: канонический список разделов — `ConsoleSections` в `frontend/components/console.go` (Заявки, Исполнение, Лиды, Отчёты, Рассылки), сборка ссылок — `ConsoleNavWithContext`/`ConsoleNavMessagesWithContext`, разметка — `templates/nav.html`, которая рендерит `Nav.Items` и необязательные `Nav.Groups` внутри `templates/layout.html`. Ссылки разделов ведут на разные порты (разные сервисы-консоли), поэтому переход = полная загрузка новой страницы, и общий клиентский контекст между консолями не сохраняется.

Каждый сервис-консоль владеет своим представлением навигации:

- `lead-management` — `consoleSidebar` в `backend/contexts/lead-management/internal/adapters/http/views.go`: канонический состав (`ConsoleSectionLeads` активен) **плюс** вторичная группа «Экраны лидов» (Главная, Карточки, Лиды, Воронка, Отправка, Ассистент, Форумы);
- `outreach-orchestration` — `consoleNav` в `backend/contexts/outreach-orchestration/internal/adapters/http/console.go`: канонический состав (`ConsoleSectionOutreach` активен) **плюс** группа «Экраны рассылок» (очередь черновиков, зависшие);
- `request-fulfillment` (`internal/adapters/http/server.go`, `consoleNav`), `analytics` (`ConsoleNavWithContext` в `internal/adapters/http/*`), `platform-governance` (`internal/adapters/http/handlers_console.go`, `consoleNav`) — канонический состав без групп.

Ограничения: рендеринг серверный (`html/template`, POST/redirect/GET), канон проекта — экран остаётся работоспособным без JavaScript; контекст активного тенанта/актора переносится в ссылки через `ConsoleHrefWithContext`; переключатель темы — часть общей навигации (нормируется `console-appearance`). Требование `deployment-topology` о собственных портах клиентских экранов сохраняется — переходы между портами не устраняются этим change.

## Goals / Non-Goals

**Goals:**

- Один и тот же состав и порядок общей навигации на всех консолях; отсутствие вторичных групп отдельного сервиса в общем сайдбаре.
- Корректная подсветка ровно одного активного раздела, в том числе сразу после перехода на экран другого сервиса (полная загрузка).
- Отсутствие визуального скачка сайдбара при переходах между разделами.
- Чистка состава меню (убрать «Отправка», «Ассистент», «Форумы») **без** удаления экранов и маршрутов.
- Вторичная навигация раздела («Лиды», «Рассылки») — вне общего сайдбара, с подсветкой текущего экрана и сохранением `tenant_id`/`actor`.

**Non-Goals:**

- Не вводится единый origin/маршрутизатор: разделы по-прежнему отдают разные сервисы на разных портах (это отдельный срез развёртывания, см. `deployment-topology`).
- Не меняется визуальный стиль/тема (это `console-appearance` в части оформления), не проектируется дизайн-система.
- Не удаляются и не переписываются экраны «Отправка», «Ассистент», «Форумы»; их маршруты и обработчики сохраняются.
- Не вводятся новые доменные сущности, агрегаты, domain events или межконтекстные контракты.

## Decisions

### Решение 1. Канонический состав навигации — единственный владелец в общем слое

`ConsoleSections` (`frontend/components/console.go`) остаётся каноном разделов и порядка. Все консоли рендерят общую навигацию через `ConsoleNavWithContext`/`ConsoleNavMessagesWithContext` и **не добавляют** `Nav.Groups`. Вторичные группы (`lead-management`, `outreach-orchestration`) удаляются.

- Owning context — общий слой `frontend/components` (не bounded context: каркас представления). Новых сущностей/агрегатов/событий не вводится, межконтекстные контракты не меняются.
- Альтернативы: (а) добавить группы во все консоли — отклонено: не устраняет чужеродность и дублирование пункта «Лиды», сохраняет расхождение; (б) вынести состав в конфигурацию точки входа — отклонено: состав разделов есть свойство каркаса, а не параметр развёртывания.

### Решение 2. Вторичная навигация раздела — внутриэкранная панель, а не группа в сайдбаре

Переходы между экранами одного раздела (Лиды: Главная, Карточки, Лиды, Воронка; Рассылки: очередь черновиков, зависшие) переносятся в панель самих экранов раздела. Владелец панели — сервис-владелец раздела (`lead-management`, `outreach-orchestration`); конкретная форма (вкладки/сегментированная панель) — деталь реализации экрана, не контракт.

- Альтернативы: (а) постоянная группа в сайдбаре на **всех** консолях — отклонено: группа осмысленна только внутри своего раздела, на чужих консолях остаётся чужеродной и всё равно сохраняет расхождение; (б) отдельный экран-хаб раздела — отклонено: лишний переход, сайдбар не становится стабильнее; (в) дорисовка группы клиентским JavaScript — отклонено: ломает работу без JavaScript (канон проекта — работоспособность без JS).

### Решение 3. Подсветка активного раздела вычисляется сервером-получателем

Переход между сервисами — полная загрузка, поэтому состояние по клиенту не переносится. Каждая консоль серверно объявляет свой активный канонический раздел (leads → «Лиды»; request-fulfillment → «Заявки»/«Исполнение»; analytics → «Отчёты»; outreach → «Рассылки»), и именно он подсвечивается. Активный **подпункт** раздела подсвечивает внутриэкранная панель.

- Альтернативы: (а) перенос активного раздела через query/cookie — отклонено как избыточное: владелец экрана и так знает свою принадлежность к разделу; (б) клиентская подсветка — отклонено (см. Решение 2в). Этот подход уже действует; изменение лишь закрепляет инвариант «ровно один активный раздел» и отсутствие групп.

### Решение 4. Чистка меню не удаляет функциональность

Пункты «Отправка», «Ассистент», «Форумы» убираются только из общей навигации; маршруты `/send`, `/assistant`, `/forum-signals` и их обработчики не трогаются, экраны открываются по прямым адресам как прежде. Дельты не содержат `## REMOVED`; capability экранов (`lead-email`, `search-strategy`, `forum-lead-signals`) не меняются.

- Альтернатива: пометить экраны как удалённые — отклонено: это не удаление функциональности, а чистка навигации (см. `proposal.md`).
- Следствие: обнаружимость этих экранов снижается — они остаются доступны по прямым адресам (см. Open Questions).

### Решение 5. Контракт ссылок сохраняется

Ссылки и общей, и вторичной навигации строятся через `ConsoleHrefWithContext` и несут активные `tenant_id`/`actor`. Требование `client-portal` «Перенос контекста тенанта в навигации консолей» сохраняется, поэтому `client-portal` не меняется.

## Risks / Trade-offs

- **Снижение обнаружимости убранных экранов** («Отправка», «Ассистент», «Форумы») → маршруты сохранены и задокументированы; экраны достижимы по прямым адресам. Возврат точки входа — отдельным решением (Open Questions), спеку не меняет.
- **Расхождение консолей в будущем** (сервис снова добавит группу) → инвариант закрепляется тестом общего слоя/консоли на отсутствие групп и совпадение состава с `ConsoleSections`.
- **Существующие тесты ожидают группу** (`console_nav_test.go`, тесты каталога сообщений `messages_test.go`, тесты консоли рассылок) → обновляются под новый состав; живой прогон подтверждает отсутствие скачка.
- **Визуальный «скачок» из-за разной высоты содержимого сайдбара** → вне объёма: гарантируется стабильность состава/порядка и положения переключателя темы, а не пиксельная идентичность между портами.

## Migration Plan

- Изменение серверного рендеринга: миграций БД и переноса состояния нет.
- Деплой согласованно по затронутым сервисам-консолям (`lead-management`, `outreach-orchestration`); остальные консоли уже совместимы.
- Откат — revert изменения; побочных эффектов на данные нет.

## Open Questions

- Нужна ли обнаружимая точка входа к убранным экранам («Отправка», «Ассистент», «Форумы») с какого-либо экрана раздела «Лиды», или достаточно прямых адресов? Не меняет спеку (экраны обязаны оставаться доступными) и не меняет подход; решается отдельно.
