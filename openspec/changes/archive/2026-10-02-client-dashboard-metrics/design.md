## Context

`campaign-reporting` (`analytics`) описана как снимки (`report-snapshot`), дашборд клиента — real-time. Воронка — `lead-workflow` (`not warmed`/`email sent`/`warming`/`cold` + snooze). Сигналы — `engagement-observation` (без открытий, pixel-free). Мотивация — в `proposal.md`.

## Goals / Non-Goals

**Goals:**

- Определить дашборд как real-time read-модель (проекцию), не агрегат.
- Задать два слоя метрик и их визуализацию.
- Задать маскирование: только агрегаты/счётчики, порог минимальной группы, без открытий.

**Non-Goals:**

- Смена механизма `campaign-reporting` (снимки остаются).
- Передача клиенту содержимого ответов.
- Прогнозные модели и A/B-тесты (в non-goals `campaign-reporting`).

## Decisions

### Решение 1: дашборд — стриминговая read-модель, не агрегат

Дашборд — эксплуатационная проекция роли `api` (аналог `job-journal-console`), не владеет состоянием. Источник — CQRS read-модель, поддерживаемая доменными событиями (`lead-workflow`, `engagement-observed`, `message-sent`, `delivery-event`).

### Решение 2: два механизма аналитики

`campaign-reporting` остаётся снимками для исторической отчётности; дашборд клиента — live-проекция. Это два режима одного контекста `analytics`, не конфликт.

### Решение 3: real-time через SSE

Обновление — серверные события (SSE), уже заложенные в `web-frontend-architecture` для длинных операций. Read-путь — только агрегированные счётчики, сырые события не транслируются клиенту.

### Решение 4: два слоя визуализации

Ведущий слой — метрики прогресса (KPI-карточки, area-график роста, funnel воронки); второстепенный — операционные цифры (счётчики, списки ожидания, age-метрики). Это иерархия подачи реальных метрик, а не фабрикация данных.

### Решение 5: разнесение CRM

Клиент видит только счётчики; содержимое ответов и полная CRM — на админской части. Переход между ними — по роли (`access-decision`).

## Risks / Trade-offs

- **[Real-time vs снимки]** → Два явных механизма (Решение 2); дашборд не переписывает `campaign-reporting`.
- **[Раскрытие личности срезом]** → Порог минимальной группы + агрегация в контуре клиента.
- **[Нагрузка стрима]** → Агрегация на сервере, дельта-обновления счётчиков, а не поток сырых событий.
- **[«Красиво» = приукрашено]** → Ведущий слой — только реальные метрики прогресса; запрет на выдуманные числа зафиксирован в дизайне.

## Migration Plan

Поэтапно: поднять read-модель по событиям → SSE-эндпоинт → собрать ведущий слой → операционный слой. Откат: дашборд — проекция, при отключении падает только витрина, доменные потоки не затрагиваются.

## Open Questions
