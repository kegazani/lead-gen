## Context

Мотивация и объём — `proposal.md`. Состояние, определяющее подход:
`platform-governance` владеет тенантами (`RegisterClient`, `CreateTenant`,
`TenantUsers`) и уже имеет серверную проверку права на переключение тенанта
(`handleConsoleTenantSwitch` → `consoleGuard`/`SectionTenant`/`ActionSwitch`), но
экран переключения не предлагает список. Консоли других сервисов принимают
`tenant_id` в запросе частично: очередь утверждения заявок (`request-fulfillment`)
и экраны `platform-governance` — да; консоль лидов (`lead-management`) и отчёты
(`analytics`) определяют тенант из конфигурации процесса (`-tenant`). Общая
навигация (`frontend/components`, `components.ConsoleBases`) строит ссылки без
контекста тенанта.

## Goals / Non-Goals

**Goals:**
- Сделать возможным сквозной цикл «клиент → админ» на живом контуре: админ
  обнаруживает тенант клиента и работает в нём.
- Сохранить изоляцию тенантов и серверную проверку доступа.

**Non-Goals:**
- Не менять модель изоляции, правила доступа `platform-access` и аутентификацию.
- Не менять контракты и каталог.

## Decisions

### Решение 1. Список тенантов — read-модель владельца

**Выбор.** `platform-governance` отдаёт список тенантов (id, компания, статус)
через query-порт и экран консоли; персональные данные (пользователи, контакты) в
список не входят. Источник — хранилище тенантов сервиса.

**Почему.** Владелец тенантов — `platform-governance`; список нужен экрану
переключения того же сервиса. Свободный текст компании уже хранится у тенанта;
персональные данные не добавляются.

### Решение 2. Активный тенант — из запроса, с фолбэком на конфигурацию

**Выбор.** Консоли лидов и отчётов читают `tenant_id` из запроса; при пустом —
используют `-tenant` процесса (прежнее поведение). Доступ к данным тенанта
по-прежнему ограничен сервером.

**Почему.** Переключение в одном месте должно применяться ко всем разделам;
фолбэк сохраняет совместимость и dev-прогон без выбранного тенанта.

**Находка (2026-10-04, при apply).** Консоль лидов `lead-management` не может
менять выборку по `tenant_id`: её хранилище **не тенант-скоупно** — в таблицах
(`lead_profile`, `search_job`, …) нет колонки тенанта, RLS — только декларация в
`docs/architecture.md`. Фильтрация чтения была бы заглушкой. Поэтому задача 2.1
выполнена частично (команды чтения/записи с тенантом из запроса), а тенант-скоупное
хранилище лидов выделено в **отдельный change** `tenant-scoped-lead-storage`.
Для сквозного цикла «клиент → заявка → админ» это не блокер: заявка живёт в
`request-fulfillment`, чья очередь утверждения уже читает `tenant_id` из запроса.

### Решение 3. Перенос контекста в навигации

**Выбор.** Навигация `frontend/components` получает контекст (`tenant_id`,
`actor`) и подставляет его в ссылки разделов; потребители передают контекст из
текущего запроса.

**Почему.** Иначе выбранный тенант теряется при первом переходе между сервисами —
это и есть наблюдаемый дефект.

## Risks / Trade-offs

- **[Ссылки с контекстом в общем слое]** → `frontend/components` — один writer;
  изменения выполняются последовательно и обновляют golden-файлы всех консолей.
- **[Тенант из query без auth]** → доступ решает сервер по матрице; экран лишь
  передаёт выбранный тенант. Проверка права на переключение сохраняется.
- **[Утечка данных чужого тенанта]** → список содержит только платформенные
  атрибуты; консоли фильтруют данные по активному тенанту на сервере.

## Migration Plan

1. Read-модель списка тенантов + экран выбора (`platform-governance`).
2. Активный тенант из запроса в консолях лидов/отчётов (фолбэк на `-tenant`).
3. Контекст в навигации `frontend/components` + проводка в `cmd`.
4. Приёмка: клиент регистрируется → админ выбирает его тенант → видит заявку и
   одобряет; сквозной сценарий на раздельной топологии.

**Откат.** Фолбэк на `-tenant` оставляет прежнее поведение при пустом `tenant_id`.
