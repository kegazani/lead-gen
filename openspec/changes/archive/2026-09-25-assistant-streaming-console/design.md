## Context

См. `proposal.md` — Why. Текущее состояние, задающее подход:

- Экран ассистента живёт в HTTP-адаптере контекста `lead-management` (`backend/contexts/lead-management/internal/adapters/http/`): маршруты `GET /assistant` и `POST /assistant` (`server.go:137-138`), шаблон `templates/assistant.html`, модель представления `assistantView` (`views.go`), разбор диалога `decodeHistory`/`encodeHistory` (`dialogue.go`). Прикладной слой — `app.ConverseDialogue` (`internal/app/dialogue.go`).
- Диалог **stateless**: история транскрипта едет туда-обратно скрытым полем формы (`assistant.html:19`), план — полем `plan`. Требование спеки `search-strategy` «Состояние диалога вне сервера» это закрепляет: сервер SHALL NOT хранить историю между запросами.
- Технические параметры обхода сейчас задаются формой — `fieldset.plan-limits` с полями MaxPages/MaxDepth/Include/Exclude (`assistant.html:22-28`).
- Порт LLM — `contracts/integration-platform/llm/llm.go:23`: методы `Plan`, `Suggest`, `Converse`. `Converse` возвращает готовый `ConverseReply` (полный ответ), стриминга нет. Владелец контракта — bounded context `integration-platform`; связь с `lead-management` — `integrations-for-leads` (contract `provider-port`, sync/http-json).
- Клиент — серверный рендеринг + HTMX + небольшой JS-«остров» (`openspec/changes/web-frontend-architecture/design.md`, Решения 2 и 4). Существующий остров — `static/console.js`.
- CSP консоли (`server.go:34`) — `default-src 'none'`, директивы `connect-src` нет, поэтому `fetch`/`EventSource` к своему источнику заблокированы. Правку `connect-src 'self'` делает другой change — `console-thermal-relight`; здесь она только берётся как зависимость.
- Инструментарий — Go 1.25 (`go.work`), поэтому доступны итераторы `iter.Seq` (range-over-func). Реализации порта `llm` в контексте `integration-platform` подменяются в тестах фейками (`server_test.go`, `dialogue_test.go`).

## Goals / Non-Goals

**Goals:**

- Настоящая потоковая выдача реплики агента: текст появляется по мере генерации, а не единым готовым ответом.
- Расширить контракт `integration-platform/llm` операцией стриминга так, чтобы владелец контракта оставался единственным источником «рассуждения», а потребитель не знал деталей SDK.
- Разрешить форму транспорта диалога и зафиксировать выбор с обоснованием.
- Перенести сбор технических параметров из формы-панели в диалог (чипы), не сломав stateless-модель истории.

**Non-Goals:**

- Правка CSP `connect-src 'self'` — делает change `console-thermal-relight`.
- Введение новых доменных сущностей, агрегатов, domain events и policies.
- Смена канона серверного рендеринга/HTMX и отказ от PRG для остальных экранов.
- Стриминг других операций порта (`Plan`, `Suggest`) — только `Converse`.
- Переподключение потока с досылом пропущенных кадров (resume) — вне scope.

## Decisions

### Решение 1. Форма транспорта диалога: POST + `fetch` + `ReadableStream` (вариант «а»)

Выбран вариант: `POST /assistant/stream` возвращает `text/event-stream`, клиент читает поток из того же ответа через `fetch` + `ReadableStream`. Вариант «б» (классический `EventSource`: `POST /assistant` создаёт ход → `GET /assistant/stream/{id}`) отклонён.

**Почему так:**

- **Stateless-история сохраняется.** `EventSource` умеет только `GET` и не несёт тело: чтобы передать разговор, пришлось бы сначала создать серверный ход (`POST /assistant`), а затем стримить его по идентификатору. Это серверное состояние хода и буфер кадров — прямое противоречие требованию `search-strategy` «Состояние диалога вне сервера». Вариант «а» передаёт всю историю телом `POST` и не хранит её на сервере.
- **CSRF и заголовки.** `EventSource` не даёт задать произвольные заголовки; CSRF-токен и `Origin`-проверки на изменяющих/чувствительных запросах проще на `fetch`. Токен кладётся в тело запроса тем же способом, что и в текущей форме.
- **Идемпотентность.** Ход диалога не создаёт задание поиска (спека `search-strategy`: «Система SHALL NOT запускать краулинг в ходе диалога»). `POST /assistant/stream` — вычислительно-читающая операция без побочных эффектов: повтор при обрыве безопасен и не создаёт дублей. На время стрима клиент блокирует повторную отправку, чтобы не удвоить расход токенов.
- **Переподключение.** У `EventSource` есть автоматический reconnect с `Last-Event-ID`, но он требует серверного буфера событий (состояние). При варианте «а» авто-переподключения нет: при обрыве остров показывает ошибку и предлагает повторить ход; повтор переиспользует ту же клиентскую историю, диалог не начинается заново. Это осознанный обмен: простота и stateless важнее бесшовного resume.
- **История и «следующий ход».** Завершающий кадр потока несёт обновлённый черновик (цели и лимиты) и признак готовности — клиент сохраняет их для следующего хода, как сейчас сохраняет `plan`/`history` в скрытых полях.

**Следствие.** Транспорт остаётся односторонним (сервер → клиент), а «запрос» хода — обычный `POST` с телом. Кадры оформляются как SSE (`data:`), поэтому проводной формат стандартен, но читается через `fetch`; при появлении серверного состояния хода можно будет перейти на `EventSource` без смены формата кадров.

### Решение 2. Стриминг в контракте `integration-platform/llm`: итератор, а не канал

Порт получает операцию потоковой генерации, отдающую последовательность дельт и завершающий структурированный кадр:

```go
// ConverseDelta — один кадр потока: либо фрагмент текста, либо завершающий
// кадр с черновиком плана и расходом токенов.
type ConverseDelta struct {
    Text  string         // очередной фрагмент реплики; у завершающего кадра пуст
    Reply *ConverseReply // заполнен только в завершающем кадре
    Usage Usage          // учёт токенов (в завершающем кадре)
}

// Port:
ConverseStream(ctx context.Context, request ConverseRequest) iter.Seq2[ConverseDelta, error]
```

`ConverseReply` расширяется структурированными техническими лимитами (см. Решение 6), поэтому завершающий кадр несёт и цели, и лимиты, и `Ready`.

**Почему итератор, а не канал:**

- Нет горутины-производителя и риска её утечки при раннем выходе потребителя; отмена идёт через `ctx` итератора.
- Естественная обратная связь (backpressure): пока HTTP-адаптер пишет и сбрасывает кадр, следующий не запрашивается — нельзя «разогнать» буфер.
- Go 1.25 в `go.work` уже даёт range-over-func; API проверяется существующим контрактным suite легко (сбор `iter.Seq` в срез).

**Рассмотренная альтернатива.** Канал `<-chan ConverseDelta` + отдельный `err` — отклонён: требует горутины, внешнего протокола закрытия и ручной отмены, что дублирует то, что даёт итератор.

**Совместимость.** Операция добавляется к `llm.Port` рядом с `Converse`; добавление метода ломает реализации порта (**BREAKING** для адаптера `integration-platform/internal/adapters/openai` и тестовых фейков) — они обновляются в том же change. Существующий `Converse` может остаться как синхронная операция, но вызывающий ассистент переходит на `ConverseStream`; окончательное решение о сохранении `Converse` принимается при реализации (если он больше не нужен — удаление тоже правка контракта, отражается в каталоге).

### Решение 3. Прикладной метод стриминга в `lead-management`

`app.ConverseDialogue` получает метод потокового хода (`StreamReply`) поверх `llm.Port.ConverseStream`. Он:

- валидирует историю (`ConverseRequest.Validate`) и соблюдает предел ходов так же, как `Reply`: при достижении предела поток отдаёт одну реплику-сообщение о пределе без повторных уточнений;
- при отсутствии LLM отдаёт ошибку `errDialogueUnavailable` как единственный кадр-сбой;
- пишет в лог те же безопасные поля (без текста реплик), что и `Reply`.

Существующий синхронный `Reply` сохраняется до решения по `Converse` (см. Решение 2), чтобы не ломать текущий экран по частям.

### Решение 4. SSE-эндпоинт в HTTP-адаптере

Добавляется маршрут `POST /assistant/stream`. Обработчик:

- проверяет CSRF как изменяющий запрос (существующий `authMiddleware`), разбирает историю и план из тела тем же кодом, что и `handleAssistantReply`;
- ставит заголовки `Content-Type: text/event-stream`, `Cache-Control: no-store` (персональные данные и красная зона — канон `web-frontend-architecture`, Решение 15), `Connection: keep-alive`, `X-Accel-Buffering: no` (против буферизации обратного прокси);
- после каждого кадра явно сбрасывает буфер: `http.NewResponseController(w).Flush()`;
- не буферизует весь ответ: полный текст реплики не собирается в памяти до отдачи;
- формирует кадры SSE (`event:`/`data:`) с типами `delta` (фрагмент текста), `plan` (обновлённый черновик целей и лимитов) и `done`/`error`.

**Таймауты и отмена.** Долгий поток упирается в `WriteTimeout` сервера и в отмену запроса клиентом. Обработчик опирается на `r.Context()` для отмены генерации и на продление дедлайна записи через `ResponseController` (или конфигурацию сервера без жёсткого `WriteTimeout` для этого маршрута) — конкретная настройка фиксируется в задачах.

**Почему так:** это минимальное расширение существующего обработчика без нового слоя; правила остаются в `app`/порте, адаптер только транслирует поток в кадры.

### Решение 5. Клиент — JS-«остров», без доменных правил

Поток читается небольшим скриптом-островом (по образцу `static/console.js`), подключаемым отдельным файлом (CSP запрещает inline). Остров:

- перехватывает отправку формы ассистента и вместо полной перезагрузки открывает `fetch` к `/assistant/stream`;
- по кадрам `delta` дописывает текст в ленту диалога, по `plan` обновляет панель плана и чипы параметров, по `done`/`error` завершает ход;
- объявляет изменения через `aria-live` и оставляет базовый сценарий без JavaScript: форма по-прежнему отправляется обычным `POST /assistant` (прогрессивное улучшение, канон Решение 4).

**Граница.** Остров ничего не решает: он показывает значения, присланные сервером, и не содержит доменной логики. Валидация и решения остаются в `app`/порте; сервер уже присылает готовые, отрисованные значения.

### Решение 6. Параметры ассистента через чат: структурированное извлечение

`fieldset.plan-limits` из `assistant.html` убирается. Технические параметры (MaxPages, MaxDepth, Include, Exclude) собираются в диалоге:

- ассистент сам задаёт вопросы о недостающих параметрах; оператор отвечает репликой; ответ отображается чипом в панели плана;
- извлечение параметров — структурированный результат контракта: `ConverseReply` (и, соответственно, завершающий кадр `ConverseDelta`) получает поле лимитов, например `Limits PlanLimits` с `MaxPages`, `MaxDepth`, `Include`, `Exclude`;
- промпт порта формулирует задачу как структурированное извлечение: вернуть уточняющий вопрос, накопить цели (`Targets`) и лимиты (`Limits`), выставить `Ready`;
- модель представления `assistantView` теряет «форменные» поля лимитов, но сохраняет готовые для отображения строки целей и параметров; лимиты по-прежнему приезжают в теле `POST /assistant/stream` и проверяются как недоверенный ввод спеки `search-strategy` «Проверка плана, пришедшего от клиента».

**Почему так:** параметры — часть согласования стратегии, а не отдельная техническая форма; спека `search-strategy` после правки требует согласовывать лимиты в диалоге. Доменные ограничения (валидация лимитов, бюджет) не переезжают в клиент и не дублируются в JS.

### Решение 7. Зависимость от CSP: `console-thermal-relight`

`fetch` к своему источнику регулируется `connect-src`, которой сейчас нет, поэтому она падает до `default-src 'none'` и блокирует поток. Правку `connect-src 'self'` делает change `console-thermal-relight`; этот change на неё опирается и CSP как новую работу не описывает. Задача на подтверждение/согласование порядка изменений включается в `tasks.md`.

### Решение 8. Закрытие открытого вопроса №2 канона

`openspec/changes/web-frontend-architecture/design.md`, открытый вопрос №2 («Опрос или SSE для длительных операций») закрывается в пользу SSE: этот change — первый длительный сценарий, и он выбирает серверный поток событий. Обновление текста канона выполняется отдельной правкой (вне каталога этого change) и перечислено задачей.

### Решение 9. Доменная привязка

- Новых сущностей, агрегатов, domain events и policies не вводится: change транспортно-представительский.
- Меняется межконтекстный контракт: порт `llm` (contract `provider-port`, владелец `integration-platform`, связь `integrations-for-leads`) получает операцию `ConverseStream` и расширенный `ConverseReply`. Это правка формы контракта, а не перенос владения и не новая capability.
- `architecture/domain-catalog.yaml` объявляет контракты по имени (`provider-port`) и не перечисляет операции порта; поэтому каталог, `docs/domain-model.md` и диаграммы при формально неизменной идентичности контракта, вероятно, остаются без изменений. Эта гипотеза проверяется задачей: если документация перечисляет операции `provider-port` — она обновляется; в любом случае в том же change обязателен прогон `go -C tools/archlint run .`, и он должен остаться зелёным. Реализация начинается с owning context `integration-platform` (порт и адаптер), затем потребитель `lead-management`.

## Risks / Trade-offs

- **Долгие соединения на роли `api`.** SSE удерживает соединение на время генерации; много одновременных стримов давят на лимиты сервера. Компенсация: один стрим на сессию оператора, отмена по `r.Context()` при уходе со страницы, отсутствие буферизации ответа целиком.
- **Слабое переподключение.** Без `EventSource` нет авто-resume с `Last-Event-ID`; обрыв теряет незавершённую реплику. Компенсация: явная ошибка и повторный ход по той же клиентской истории; ход идемпотентен.
- **Протечка доменных правил в JS-остров.** Соблазн «досчитать» лимит или решить готовность плана в браузере. Компенсация: остров получает готовые значения, правило «шаблон/остров показывает, а не решает», проверка на отсутствие доменных импортов в адаптере (`tools/importlint`).
- **Двойной расход токенов при повторе.** Повтор хода после обрыва снова обращается к LLM. Компенсация: блокировка повторной отправки на время стрима; ход ограничен пределом числа ходов.
- **Порядок с CSP.** Без `connect-src 'self'` из `console-thermal-relight` поток заблокирован. Компенсация: зависимость зафиксирована, порядок проверяется задачей.
- **Расширение контракта ломает реализации порта.** Добавление метода к `llm.Port` — BREAKING для адаптера и фейков. Компенсация: обновление адаптера `openai` и всех фейков в том же change, контрактный suite.
- **Буферизация прокси.** Промежуточный прокси может копить SSE-кадры. Компенсация: `X-Accel-Buffering: no`, явный `Flush` после каждого кадра.

## Migration Plan

1. **Контракт.** В `contracts/integration-platform/llm` добавить `ConverseStream` и `ConverseDelta`, расширить `ConverseReply` лимитами; обновить контрактный suite.
2. **Адаптер владельца.** Обновить `integration-platform/internal/adapters/openai` под потоковую генерацию; обновить фейки.
3. **Прикладной слой.** Добавить `app.ConverseDialogue.StreamReply`, покрыть тестами (предел ходов, отсутствие LLM, безопасные логи).
4. **HTTP-адаптер.** Маршрут `POST /assistant/stream`, заголовки, `Flush`, кадры `delta`/`plan`/`done`/`error`; тесты через `httptest` с проверкой постепенной отдачи.
5. **Шаблон и остров.** Убрать `fieldset.plan-limits`, сделать панель отображением; добавить JS-остров `fetch`+`ReadableStream`, сохранить базовый сценарий без JS.
6. **Проверки и документы.** Прогон `tools/importlint`, `go -C tools/archlint run .`, golden-тесты шаблона, закрытие открытого вопроса №2 канона.

Порядок обеспечивает работоспособность на каждом шаге: пока остров не подключён, экран продолжает работать через обычный `POST /assistant`. Откат — снятие маршрута `/assistant/stream` и возврат формы лимитов; контракт откатывается вместе с адаптером.

## Open Questions

1. **Судьба синхронного `Converse`.** Оставить его ради других потребителей или удалить после перехода ассистента на `ConverseStream`. Не влияет на спеку и разбиение задач; решается при реализации.
2. **Точный режим таймаутов сервера для SSE.** Продление дедлайна через `ResponseController` или отдельная конфигурация `WriteTimeout` — решается при реализации, на поведение по спеке не влияет.
