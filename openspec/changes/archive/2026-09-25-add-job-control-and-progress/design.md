## Context

Задания поиска обслуживает примитив `backend/platform/jobs`: `Store` хранит состояние `queued → running → done/failed`, `Runner` в цикле опрашивает очередь и вызывает `Handler(ctx, job)` синхронно, в потоке воркера. Потребитель — `lead-management`: `RunSearch.Handle` декодирует непрозрачный `Payload`, при наличии `budget.Factory` создаёт бюджетную задачу Firecrawl, планирует цели и для каждой делает `Search`, а затем `Crawl` по каждому результату; карточки сохраняются сразу при обработке страницы (`saveCompany`). Хранилище задания — PostgreSQL (`search_job`) или memory-адаптер; журнал и формы консоли — серверный `html/template` + HTMX. Мотивация — см. `proposal.md`.

Ограничения: api- и worker-роли сегодня размещены в одном процессе (`in-process` механизм развёртывания), но по каталогу контекст вправе жить в разных процессах; примитив `jobs` обязан оставаться без доменных терминов; бюджет кредитов уже реализован (`firecrawl-credit-budget`) и допускает значение на задачу.

## Goals / Non-Goals

**Goals:**

- Отмена задания поиска из консоли — и для `queued`, и для `running` — с немедленным прерыванием текущего обхода и сохранением уже добытых карточек.
- Статус `cancelled`, отличимый от `failed`, и идемпотентная отмена.
- Наблюдаемый прогресс задания: фаза, текущий URL, обойдённые страницы, найденные компании, кредиты, — видимый в журнале в живом режиме.
- Бюджет кредитов Firecrawl как атрибут задания, задаваемый при создании запроса.

**Non-Goals:**

- Разделение api- и worker-процессов на разные инстансы и координация отмены между процессами через брокер сообщений.
- Ожидание/дозабор страниц незавершённого асинхронного crawl-задания Firecrawl сверх того, что движок уже вернул (см. риски).
- Отмена и прогресс для контекстов, кроме `lead-management` (рассылка и другие потребители примитива `jobs` — вне объёма).
- LLM-токены: бюджет задаётся в кредитах Firecrawl.
- Серверный верхний предел на бюджет запроса: значение уже ограничено остатком аккаунта и логикой бюджета задачи.

## Decisions

### Решение 1. Отмена — кооперативная через `context`, сигнал — in-process + персистентный запрос

`Runner` создаёт на каждое взятое задание дочерний `context.WithCancel` и регистрирует его `CancelFunc` в разделяемом реестре `jobs.CancelRegistry`. Запрос на отмену идёт двумя путями сразу: (а) через реестр — немедленно отменяет контекст выполняющегося задания; (б) через `Store.RequestCancel` — атомарно переводит `queued` в `cancelled`, а для `running` фиксирует флаг `cancel_requested` (нужен, чтобы отмена не потерялась и пережила перезапуск). Обработчик уважает отмену на границах шагов: между целями плана, между результатами поиска и между страницами обхода.

Реестр — расширение примитива `jobs` без доменных терминов (идентификатор задания → сигнал). Он даёт немедленное прерывание в текущем co-located развёртывании; при раздельных процессах отмена сработает на ближайшей границе шага по флагу в хранилище.

*Альтернативы:* только опрос хранилища (проще, но реакция с задержкой до десятков секунд из-за интервала обхода); отдельный брокер/событийная шина (избыточно для одного контекста и текущего развёртывания).

### Решение 2. Отменённое задание не является ошибкой: sentinel и маппинг статуса

Обработчик возвращает sentinel `jobs.ErrCancelled`, когда остановился из-за отмены. `Runner` маппит исход: `nil → StatusDone`, `ErrCancelled → StatusCancelled`, иная ошибка → `StatusFailed` с текстом. Процессный `context` при остановке сервиса отменяется иначе, чем отмена задания, поэтому `Runner` различает их по признаку запроса отмены конкретного задания, а не по одному `ctx.Err()`. Для `cancelled` текст ошибки не записывается (как и для `done`).

Добавляется `jobs.StatusCancelled`; `Status.Valid()` расширяется. `Store.UpdateStatus` сохраняет прежнюю семантику сброса ошибки для не-`failed` — менять не требуется.

*Альтернатива* (вводить отдельный тип ошибки в каждом контексте) отклонена: маппинг исходов принадлежит примитиву жизненного цикла, а не домену.

### Решение 3. Сохранение результата при отмене — на двух уровнях

Гарантия «отмена с сохранением результата» опирается на то, что карточки сохраняются сразу при обработке страницы (`saveCompany`), плюс на две правки:

1. Приложение ставит проверку отмены на границы шагов и, обнаружив отмену, прекращает запускать новую работу и возвращает `jobs.ErrCancelled`, не откатывая уже сохранённые карточки.
2. Адаптер Firecrawl при отменённом контексте перестаёт выбрасывать результат: если ответ уже получен, он возвращает разобранные страницы вместе с признаком отмены; если асинхронное задание ещё идёт — делает одну финальную попытку получить текущий снимок с коротким дедлайном. Приложение обрабатывает возвращённые страницы и затем возвращает `ErrCancelled`.

Явный предел гарантии: страницы, которые Firecrawl ещё не отдал в снимке незавершённого crawl, не выкачиваются принудительно. Гарантированный результат — карточки, сохранённые до отмены.

*Альтернатива* (переписывать crawl на потоковую выдачу страниц из Firecrawl) отклонена: не поддерживается текущим асинхронным API и не нужна для «сохранить уже добытое».

### Решение 4. Прогресс — операционная запись задания с коалесцированием записей

Прогресс описывается значением `ports.SearchJobProgress{ Phase, CurrentURL, PagesCrawled, CompaniesFound, CreditsSpent, CreditsAvailable, UpdatedAt }` и хранится в задании (`progress jsonb` в `search_job`, поле в памяти). Фазы — константы прикладного слоя: `planning`, `searching`, `crawling`, `finalizing`. `SearchJobStore` получает `RecordProgress(ctx, id, progress)`, `SearchJob` — поле `Progress`.

`RunSearch` пишет прогресс на смене фазы и по каждому облавливаемому URL, а постраничные счётчики — не чаще заданного интервала (коалесцирование), чтобы не бить по БД на каждой странице. Кредиты берутся из снимка бюджетной задачи. Журнал показывает прогресс и обновляется HTMX-опросом фрагмента `/jobs` (короткий интервал), пока есть выполняющееся задание.

*Альтернатива* (SSE/WebSocket) отклонена: консоль серверно-рендерная на HTMX, push усложняет адаптер без выигрыша.

### Решение 5. Бюджет — атрибут задания, а не глобальная настройка

`ports.SearchJob` получает `MaxCredits int` (0 — «использовать значение по умолчанию»), значение пишется в колонку `max_credits` и в `Payload` задания. `CreateSearchJob(ctx, query, maxCredits)` и `RunSearch.Enqueue(ctx, query, maxCredits)`; `RunSearch.handle` выбирает бюджет задания, а при нуле — сконфигурированный по умолчанию `RunSearch.MaxCredits`. HTTP-форма поиска принимает поле бюджета и отклоняет неположительное/некорректное значение с понятным сообщением до постановки в очередь; ассистент ставит seed-запросы с заданным бюджетом либо по умолчанию. Действующая логика бюджета задачи (`firecrawl-credit-budget`) не меняется — меняется источник `max_credits`.

*Альтернатива* (оставлять бюджет только глобальным и плодить отдельные сервисы-профили) отклонена: усложняет эксплуатацию и не даёт «цену» конкретного запроса.

### Решение 6. Расширение контракта `jobs`, а не новый примитив

Отмена и прогресс — части жизненного цикла задания, поэтому живут в примитиве и его потребителях, а не в новом модуле: `jobs.StatusCancelled`, `jobs.CancelRegistry`, `Store.RequestCancel`, sentinel `jobs.ErrCancelled`; доменно-специфичное (фазы, счётчики, бюджет) — в `ports`/`app` контекста `lead-management`.

### Решение 7. Домен не меняется; обновляется только каталог capability

Задание поиска остаётся операционной записью, а не доменным агрегатом: новых сущностей, aggregate roots, domain events и policies не появляется. Change добавляет две capability (`search-job-control`, `search-job-progress`), поэтому в том же change обновляются `architecture/domain-catalog.yaml` (привязка capability к primary context `lead-management`) и `docs/domain-model.md`. Capability `firecrawl-credit-budget` остаётся за `integration-platform`.

## Risks / Trade-offs

- **[Отмена между процессами]** Реестр сигналов действует только внутри процесса → смягчение: текущее развёртывание co-located; намерение отмены персистентно; при разделении процессов отмена сработает на границе шага, а полноценная межпроцессная координация — вне объёма.
- **[Частичный незавершённый crawl]** Гарантия сохранения ограничена уже сохранёнными карточками и снимком, который отдал движок → смягчение: явный предел гарантии в Решении 3; best-effort финальный снимок.
- **[Нагрузка прогресса на БД]** Частые записи прогресса → смягчение: коалесцирование по интервалу и запись на смене фазы, а не на каждой странице.
- **[Некорректный бюджет запроса]** Оператор может задать слишком большой бюджет → смягчение: значение всё равно ограничено остатком аккаунта и логикой бюджета задачи; бюджет виден в журнале.
- **[Гонка отмены и завершения]** Отмена приходит, когда задание уже терминальное → смягчение: `RequestCancel` атомарен и идемпотентен, для терминальных — no-op.
- **[Неизвестный статус при откате]** Старый код не знает `cancelled` → смягчение: статус трактуется как терминальный; при откате кода строки со статусом `cancelled` не считаются `queued` и не берутся в обработку.

## Migration Plan

1. Миграция зелёной зоны `0005_search_job_control.sql`: добавить `max_credits integer`, `cancel_requested boolean NOT NULL DEFAULT false`, `progress jsonb` в таблицу `search_job`.
2. Совместимость: существующие задания имеют `max_credits = NULL` (берётся дефолт) и пустой `progress`; новые поля не обязательны для старых записей.
3. Порядок выката: сначала миграция, затем код (приложение читает и пишет новые поля; отсутствие значения трактуется как «по умолчанию»).
4. Откат: вернуть прежний код и откатить колонки; статусы `cancelled` при откате остаются терминальными и не влияют на очередь.
5. Обновить `architecture/domain-catalog.yaml` и `docs/domain-model.md`; прогнать `go -C tools/archlint run .`.
