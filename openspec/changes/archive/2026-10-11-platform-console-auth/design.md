## Context

`backend/platform/consoleauth` — общий приём аутентификации операторских консолей:
серверные сессии в cookie `session`, общий `Store` (PostgreSQL) делает вход,
выданный одним процессом, действительным в другом. Консоли заявок, лидов и
рассылок его используют. `platform-governance` — нет: `consoleActor` читает
`?actor=`/`X-Actor`, а `/console` без актора/тенанта отвечает `400`.

Клиентский портал `platform-governance` уже владеет путём `/login`; поэтому вход
консоли выносится на `/console/login`.

## Goals / Non-Goals

- **Цель:** администратор входит в консоль платформы обычным логином и получает
  доступ к разделам, включая «Регистрации».
- **Цель:** защита `/console/**` и `/platform/**` серверной сессией; субъект — из
  сессии.
- **Не цель:** менять домен, права, контракты, клиентский портал.
- **Не цель:** выносить консоль на отдельный домен (это deployment-вопрос).

## Decisions

### Решение 1. Общий `consoleauth`, вход на `/console/login`

Сервис собирает `consoleauth.Manager` из `Config.ConsoleAuth` (логин/пароль из
точки входа, общий `Store`). Маршруты консоли оборачиваются `Middleware` с
публичной страницей входа и статикой; остальные пути (портал, JSON API доступа)
не оборачиваются. Путь входа `/console/login` не конфликтует с клиентским
`/login`.

### Решение 2. Аутентификация включается при заданных учётных данных

Если `ConsoleAuth.Username` пуст, middleware не включается, и консоль сохраняет
прежнее поведение `?actor=` (dev/тесты). В контуре учётные данные заданы
(`CONSOLE_USER`), поэтому защита действует.

`platform-governance.Build` обязан проверять пару `ConsoleAuth.Username`/
`ConsoleAuth.Password` непосредственно внутри builder: задан ровно один компонент
— ошибка сборки. Проверка внешней конфигурации не заменяет эту проверку, поскольку
builder вызывается и напрямую. Отдельные тесты покрывают username-only и
password-only через этот путь; вход с пустым паролем не создаёт сессию.

Пароль передаётся только путём внешнего password file (`CONSOLE_PASSWORD_FILE`),
не через raw `CONSOLE_PASSWORD` ENV и не через argv. Файл открывается с
`O_NOFOLLOW`; тип, owner UID и mode проверяются через `fstat` открытого descriptor,
чтение идёт из того же descriptor. Требуется owner-only `0400` и UID владельца,
совпадающий с runtime `nonroot:nonroot` UID из Dockerfile. Symlink, не-regular
file, mode с правом чтения группы/прочих и root-owned файл, не читаемый runtime UID,
отвергаются. Тесты используют только временные файлы с фиктивным значением;
документация и отчёты фиксируют пути, владельцев и режимы, но не секретные значения.

### Решение 3. Субъект из сессии, фолбэк — из запроса

`consoleActor` сначала читает сессию (`consoleauth.Current`), затем форму, query
и заголовок. Порядок сохраняет совместимость тестов и dev, но в рабочем контуре
субъект приходит из проверенной сессии.

### Решение 4. Лендинг `/console` — «Регистрации»

Раздел регистраций доступен платформенному оператору без выбранного тенанта,
поэтому корень ведёт туда (с переносом tenant/actor), а не на `/console/users`,
требующий тенанта.

## Risks / Trade-offs

- **[Тесты консоли без сессии]** → Аутентификация включается только при
  заданном `ConsoleAuth`; тесты с `?actor=` остаются зелёными.
- **[Пустой пароль при заданном пользователе]** → Конфигурация fail closed;
  тест проверяет отказ username без непустого password и невозможность
  получить сессию с пустым паролем.
- **[CSRF на маршрутах консоли]** → Middleware проверяет токен сессии на POST;
  формы консоли уже несут CSRF-поле (общий слой), при необходимости токен
  выводится через сессию.
- **[Смена лендинга]** → `/console` теперь открывает «Регистрации»; это
  эксплуатационное решение, домен и права не меняются.

### Решение 5. Доказуемый и повторяемый cleanup live acceptance

Fixture генерирует уникальное имя child database и ставит cleanup сразу после
успешного `CREATE DATABASE`. Флаг создания выставляется только после успешного
выполнения именно этого `CREATE`; сразу после него fixture сохраняет OID базы и
OID владельца из `pg_database`. Удаление допускается только для точного
сгенерированного имени, при подтверждённых OID/owner и отсутствии активных
соединений. Совпадающий marker — дополнительная проверка, но его отсутствие
после ошибки `COMMENT` может быть компенсировано только доказательством создания
этим fixture и совпадением всех сохранённых идентификаторов. Чужой marker,
изменение owner/OID или невозможность проверить состояние запрещают `DROP`.

При ошибке установки marker fixture повторно читает marker и повторяет запись,
если база по-прежнему подтверждённо принадлежит fixture; иначе завершает
инициализацию с явной диагностикой и инструкцией ручной проверки/очистки.
Cleanup сериализован mutex-ом и идемпотентен после успешного `DROP`. При любой
ошибке до успешного удаления parent connection остаётся открытым, чтобы cleanup
можно было вызвать повторно; диагностика сообщает уникальное имя базы и marker,
не секреты. Fixture не удаляет базу без точного доказательства своего создания.

Unit-тесты покрывают сбой `COMMENT` после `CREATE`, чужой marker и несовпадение
identity, повторную попытку после transient `DROP` и повторный успешный cleanup.
Это не меняет поведение production-сервисов.

## Migration Plan

Миграций данных нет (схема `consoleauth` уже существует и применяется точкой
входа). Порядок: конфигурация и `consoleauth.Manager` → маршруты входа и
middleware → шаблон входа → тесты → пересборка `platform`, живая проверка
входа и доступа к «Регистрациям».
