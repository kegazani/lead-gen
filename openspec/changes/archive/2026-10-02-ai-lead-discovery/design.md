## Context

Мотивация — в `proposal.md`. Здесь только ограничения, формирующие подход.

- `llm.Port` (`contracts/integration-platform/llm`) несёт единственную операцию `Plan`: разложение готового запроса в поисковые цели. Адаптер — `openai` (провайдер DeepSeek).
- Поиск ведётся через `search.Port` (Firecrawl `/search`); обход — `crawl.Port`. Оба за `provider-port` в `integration-platform`.
- Канон `web-frontend-architecture`: серверный рендеринг, экраны в `adapters/http` контекста-владельца.
- Канонические границы — `architecture/domain-catalog.yaml`; capability и агрегаты добавляются только через change с обновлением каталога.

## Goals / Non-Goals

**Goals:**

- Дать оператору не выбирать цель поиска вручную: ИИ предлагает сектора, ниши и seed-запросы по описанию задачи.
- Дать первый обезличенный источник сигналов — форумы — для выбора ниш.

**Non-Goals:**

- Не извлекаем контакты участников форумов (первый шаг — только обезличенные сигналы).
- Не строим автономного агента и фоновый подбор: всё — по явному запросу оператора.

## Decisions

### Решение 1. ИИ-стратег — новая операция `Suggest` на `llm.Port`

К `llm.Port` добавляется операция `Suggest(ctx, SuggestRequest) ([]Suggestion, error)`, где `Suggestion` — сектор, ниша и готовые seed-запросы. `Plan` остаётся для разложения уже выбранного запроса; `Suggest` отвечает за «что искать», `Plan` — «куда идти».

**Почему так:** порт уже типизирован и протестирован контрактным suite; расширение операцией сохраняет границу «пайплайн ↔ LLM». Один generic-порт или отдельный `chat`-порт — избыточно для структурированного ответа.

### Решение 2. Экран ассистента — use case `SuggestNiches` в `lead-management`

Оператор описывает задачу → `SuggestNiches` возвращает предложения → оператор выбирает → выбранные seed-запросы ставятся в очередь через существующий `RunSearch.Enqueue`. Никакого нового владения состоянием: предложения — временный результат app-слоя, не агрегат.

**Почему так:** предложения не переживают сессию и не имеют инвариантов — это не доменная сущность. Переиспользуется существующая очередь заданий.

### Решение 3. Форумы — новый порт `forum` с анонимизацией в app-слое

Вводится порт `forum.Port` (`contracts/integration-platform/forum`) с операцией `SearchSignals(ctx, Query) ([]Signal, error)`, где `Signal` — тема, выжимка, URL источника и дата, без прямых идентификаторов участников. Анонимизация — шаг app-слоя `lead-management` (удаление/исключение материалов с прямыми идентификаторами) поверх результата провайдера.

**Почему так:** форумный источник — это отдельный внешний движок с собственной семантикой «сигналы, а не контакты»; типизированный порт сохраняет заменяемость провайдера. Анонимизация на нашей стороне — то же правило «интерфейс/пайплайн не доверяет внешнему движку», что и в `osint-enrichment`.

### Решение 4. Владение форумного источника — `lead-management`

`forum-lead-signals` принадлежит `lead-management` — это источник выбора ниш для лидогенерации.

**Почему так:** цель форумного поиска — лидогенерация, а не дайджест сообщества.

### Решение 5. Доменная привязка

- Capability `search-strategy` и `forum-lead-signals` добавляются к контексту `lead-management` в каталоге.
- Новых агрегатов и domain events не вводится: предложения и сигналы — временные результаты app-слоя, не владение состоянием.
- Новые порты `llm.Suggest` и `forum.SearchSignals` — расширение `contracts/integration-platform`; это порты внешних движков, а не межконтекстные доменные контракты.

**Следствие:** обновляется только `architecture/domain-catalog.yaml` (список capability `lead-management`); `docs/domain-model.md` и диаграммы не меняются, так как агрегаты не добавляются. `go -C tools/archlint run .` остаётся зелёным.

## Risks / Trade-offs

- **[Качество предложений LLM]** Подбор ниш может быть поверхностным или ошибочным. → Оператор выбирает и подтверждает вручную; ИИ не запускает поиск сам, только предлагает.
- **[Стоимость LLM]** Каждый `Suggest` — вызов провайдера. → Операция только по явному запросу; без ключа LLM экран ассистента недоступен, как и `Plan`.
- **[ToS и доступность форумов]** Источник может требовать авторизации или запрещать чтение. → Только публично доступные и разрешённые источники; спецификация фиксирует «без обхода защиты».
- **[Персональные данные в сигналах]** Сырой материал может содержать идентификаторы. → Анонимизация/исключение на нашей стороне; контакты участников — вне среза.

## Migration Plan

Данных нет; миграция — новые порты, адаптеры и экран.

1. Расширить `contracts/integration-platform/llm` операцией `Suggest` и добавить `contracts/integration-platform/forum`.
2. Реализовать адаптеры: `openai.Suggest` и адаптер форумного провайдера (выбор провайдера — открытый вопрос) в `integration-platform`.
3. Use case `SuggestNiches` и `SearchForumSignals` в app-слое `lead-management`, анонимизация сигналов.
4. Экран ассистента в `adapters/http`: описание → предложения → выбор → постановка в очередь поиска.
5. Обновить каталог (capability `lead-management`); прогнать `make check` и `go -C tools/archlint run .`.

**Откат.** Новые операции портов и адаптеры без внешних потребителей; откат — удаление адаптера и экрана.

## Open Questions

1. **Форумный провайдер.** Reddit API, специализированный провайдер или `search.Port`, ограниченный доменами форумов. Решается до реализации адаптера; порт не зависит от выбора.
2. **Контакты участников форумов (второй шаг).** Возможен ли вообще — зависит от юридического гейта `full-enterprise-core-scope`; в этом срезе не решается.
