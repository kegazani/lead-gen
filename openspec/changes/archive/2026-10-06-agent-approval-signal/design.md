## Context

Мотивация — `proposal.md` (Why). Требования — дельты `company-agent-orchestration`, `outreach-approval`, `delivery-bridge`.

Текущее состояние, задающее рамку:

- Агент (`agent-orchestration`) уже исполняет блоки `await-approval` (подаёт черновик владельцу `outreach-orchestration` по контракту `campaign-command` и останавливает запуск в `awaiting-approval`) и `send` (публикует утверждённое действие в `message-delivery` по контракту `approved-action`, решение перечитывает по read-контракту `draftdecision`). Оба контракта подключены в точке сборки (`backend/cmd/lead-gen/agent_approval_contracts.go`).
- Сценарий `command.RecordApproval` уже реализован: фиксирует решение в агрегате и подаёт сигнал бегущему исполнению (`Workflows.SignalApproval`). Он **собран** (`service.go`, `Slice.RecordApproval`) и **передан** HTTP-серверу роли `api` (`httpapi.Dependencies.RecordApproval`), но ни один маршрут его не вызывает — это и есть незакрытый шов.
- Контракт `agent-command` (`start`/`stop`/`retry`) — управляющие команды агенту; HTTP-поверхность роли `api` (`POST /agent-commands`) уже разбирает команду, проверяет доступ и переводит доменные ошибки в коды.
- Живой прогон выявил две cross-context правки, уже внесённые в код: (1) событие `action-approved` и публикуемый `approved-action` несли получателя черновика (`ActionApproved.Recipient` → `FromActionApproved.RecipientRef`); (2) `delivery-target` (`lead-management`) разрешает непрозрачную ссылку-компанию в контакт компании с адресом.

## Goals / Non-Goals

**Goals:**

- Закрыть шов: решение оператора по запуску в `awaiting-approval` подаётся через внешнюю поверхность владельца и возобновляет исполнение, чтобы шаг `send` агента исполнялся после решения.
- Сделать поведение, найденное живым прогоном, явным в спецификациях, не раздувая дубликаты и не меняя границы.

**Non-Goals:**

- Не вводится второй механизм утверждения: решение оператора остаётся у `outreach-orchestration`, шаг `send` перечитывает его.
- Не меняется доменная модель и каталог границ: новых контекстов, агрегатов, capability и связей нет.
- Не меняется реализация cross-context правок живого прогона — они уже в коде; change закрепляет их требованиями.
- Не проектируется консольный экран подачи решения: поверхность — контракт владельца; экран, если потребуется, отдельный change.

## Decisions

### Решение 1. Поверхность решения — действия `approve`/`reject` контракта `agent-command`, а не новый контракт

`RecordApproval` — это команда владельцу (агент фиксирует решение и возобновляет запуск), семантически родственная `stop`/`retry`. Расширяем `agent-command` двумя аддитивными действиями и полями `draft_ref`/`draft_version` (MINOR `1.1.0`): существующие действия и потребители не ломаются, нового контракта и второго маршрута не появляется, каталог границ не меняется.

**Альтернатива.** Новый контракт `agent-approval` — отвергнута: решение оператора по запуску — та же природа, что и иные команды агенту (адресация запуска, актор, причина, доменные отказы), а `RecordApproval` уже передан HTTP-серверу. Отдельный контракт добавил бы сущность без новой границы.

**Форма.** Действия `approve`/`reject` адресуются `run_id` и точной версии ожидающего черновика (`draft_ref`, `draft_version`); `reject` требует `reason`; `actor` — инициатор. `Validate` контракта проверяет обязательные поля, домен (`GrantApproval`/`RejectApproval`) — что запуск действительно в ожидании и что версия черновика совпадает (`ErrNoApprovalPending`, `ErrDraftChanged`).

### Решение 2. Разграничение поверхностей: решение агента возобновляет запуск, но не санкционирует отправку

Поверхность агента **не** заменяет решение оператора в `outreach-orchestration`. Шаг `send` независимо читает решение владельца по `draftdecision` и без положительного решения не публикует действие (`ErrApprovedActionPending`/`Rejected`). Поэтому двойная фиксация не создаёт дыры: даже при расхождении отправка невозможна без реального решения в очереди утверждения. Отрицательное решение переводит запуск в `needs-attention` (терминальное требующее вмешательства), не выполняя отправку.

### Решение 3. Хранение решения и возобновление

Отрицательное решение завершает ожидание (запуск требует вмешательства). Положительное — фиксируется в агрегате (`GrantApproval`) и сигналит бегущему исполнению (`SignalApproval`); workflow выходит из паузы и вызывает activity шага. Если исполнение в рантайме не найдено (пауза истекла, процесс завершён), состояние запуска уже сохранено, а `SignalApproval` честно сообщает недоступность — решение не теряется, повтор команды идемпотентен по состоянию агрегата.

### Решение 4. Cross-context правки живого прогона: что закрепляем спеками, что остаётся в дизайне

- **Получатель в `approved-action`** — наблюдаемое поведение контура утверждения (доставка получает разрешимого получателя). В `outreach-approval` добавляется требование; в `delivery-bridge` уже описано разрешение `RecipientRef`, поэтому дубликат не создаётся.
- **Резолв компании в контакт** — наблюдаемое поведение владельца `delivery-target` (`lead-management`). Отдельного требования `delivery-target` в спеках нет; оно уточняется в требовании `delivery-bridge` «Разрешение получателя и материала» (MODIFIED): владелец трактует ссылку как контакт, а при отсутствии — как компанию с контактом. Дубликата не создаётся, существующее требование уточняется.

Каталог `architecture/domain-catalog.yaml` и диаграммы **не меняются**: границы, capability и связи те же (`agent-command` уже объявлен контрактом `agent-orchestration`, `approved-action`/`delivery-target` — контракты своих владельцев).

## Risks / Trade-offs

- [Двойная фиксация решения может разойтись] → Решение 2: отправка санкционируется только решением владельца очереди утверждения; шаг `send` перечитывает его.
- [Расширение контракта ломает потребителей] → Решение 1: расширение аддитивное (MINOR), существующие действия и поля не меняются.
- [Решение не найдёт бегущего исполнения] → Решение 3: состояние агрегата сохраняется в хранилище, недоступность рантайма честно сообщается, повтор идемпотентен.
- [Спека раздувается дубликатами] → Решение 4: уточняются существующие требования (`delivery-bridge`, `outreach-approval`), а не создаются параллельные.

## Migration Plan

1. Расширить контракт `agent-command` (действия и поля) и его тесты; ввести тип команды решения без ломки существующих.
2. Добавить ветку решения в HTTP-адаптер роли `api` и провести её в `RecordApproval`; покрыть HTTP-тестами (успех, отказ, версия черновика, отсутствие ожидания, доступ).
3. Прогнать живой прогон: агент до `awaiting-approval`, решение через поверхность, шаг `send`, подтверждение доставки в mailpit.
4. Гейт: `make check`, `make test-postgres PG_TEST_PORT=5544`, `go -C tools/archlint run .`, importlint, `openspec validate --all --strict`.

Откат не требуется: изменение аддитивное; без него поведение прежнее (запуск остаётся в ожидании).
