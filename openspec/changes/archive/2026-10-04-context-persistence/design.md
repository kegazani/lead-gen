## Context

Мотивация — `proposal.md`; фактура — `docs/implementation-matrix.md` §0 пункт B. Образец сервисной персистентности уже существует: `lead-management`, `outreach-orchestration`, `request-fulfillment` (`internal/adapters/persistence/postgres` + `migrations/` + `backend/platform/migrate`).

## Goals / Non-Goals

**Goals:**

- Заменить in-memory хранение на PostgreSQL в семи контекстах, сохранив домен, app и контракты без изменений.
- Соблюсти `schema-per-service`: схема на сервис, роль СУБД на сервис, миграции под `backend/contexts/<context>/migrations/`.
- Сохранить in-memory адаптеры как тестовые/dev, не на продуктовом пути.

**Non-Goals:**

- Изменение доменной модели, агрегатов, событий и межконтекстных контрактов.
- Персистентность `message-delivery` — она в изменении `message-delivery`.
- Сетевой транспорт и разделение сервисов — предмет `service-per-context`.

## Decisions

### 1. Один адаптер на порт, снимок агрегата целиком

Для каждого порта хранения контекста создаётся PostgreSQL-реализация в `internal/adapters/persistence/postgres`. Агрегат сохраняется снимком (upsert по идентификатору), подчинённые сущности — в подчинённых таблицах с колонкой порядка, как в образце `outreach-orchestration`.

- **Альтернатива — ORM.** Отклонено: в проекте принят ручной `pgx`/`database/sql` без ORM.

### 2. `schema-per-service` и миграции на сервис

Схема называется по идентификатору сервиса; миграции лежат в `backend/contexts/<context>/migrations/` и применяются загрузчиком `backend/platform/migrate` (директива принадлежности схемы в шапке файла). Пул — общий по DSN зелёной зоны.

- **Альтернатива — единая схема.** Отклонено: нарушает изоляцию владения и `schema-per-service`.

### 3. Transactional outbox в БД

Если контекст публикует доменные события через outbox, outbox хранится в той же схеме и пишется в транзакции с изменением агрегата.

### 4. In-memory адаптеры — только тесты и dev

Продуктовая сборка получает PG-адаптеры; in-memory остаётся значением по умолчанию для тестов и явного dev-режима без DSN. `unavailable`-заглушки на путь продуктовой функции не ставятся.

## Risks / Trade-offs

- **[Расхождение схемы и снимка]** → Схема и код снимка меняются вместе; contract-тесты адаптера проверяют round-trip и уникальные ключи.
- **[Миграции против общей базы]** → Каждый сервис владеет своей схемой; применяются только свои миграции.
- **[Пропуск PostgreSQL-тестов без Docker]** → `make check` их пропускает; контрактный suite включается целью `make test-postgres` (нужен Docker).

## Migration Plan

1. Добавить адаптер и миграции в контекст, не удаляя in-memory.
2. Подключить PG-адаптер в сборке при заданном DSN; без DSN — in-memory + предупреждение.
3. Расширить `make test-postgres` новым контекстом (централизованно).
4. Откат: снятие DSN возвращает in-memory сборку.
