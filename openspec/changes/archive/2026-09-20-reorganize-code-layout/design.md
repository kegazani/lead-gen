## Context

Раскладку и мотивацию см. в `proposal.md`. Состояние, из которого исходит дизайн:

- Корневого `go.mod` нет; модули связаны `go.work`. Модули: `backend/cmd/lead-gen`, `contexts/outreach-orchestration`, `contracts/{content-production,engagement-observation,outreach-orchestration}`, `platform`, `frontend/public`, `tools/{archlint,importlint}`.
- Реализован один контекст — `outreach-orchestration`; каркас слоёв `internal/{domain,app,ports,adapters}` уже чистый и переносится как есть.
- Границы импортов проверяет `tools/importlint`; его `parseRole` выводит роль пакета из пути **после** префикса `lead-gen/` и первым сегментом ждёт `contexts`/`contracts`/`platform`/`cmd`/`frontend`. Обход (`analyze`) идёт от корня репозитория, а путь пакета строит как `lead-gen/<путь-от-корня>` (`importPathOf`). Это инвариант: **каталог пакета относительно корня = путь модуля относительно префикса**.
- `deploy/services.yaml` читают две стороны: `backend/cmd/lead-gen` (через строгий парсер) и `tools/archlint` (правило «деплой не спорит с моделью»). Загрузка `deploy/infrastructure.yaml` и графа сервисов живёт в `backend/platform/deployment`.
- `docs/domain-model.md` §«Реализация на Go», `deploy/README.md` и незакрытые change'ы описывали **прежнее** дерево под `internal/…`; README и код уже живут в модульной раскладке `backend/…`. Это дрейф, закрытый в этом же change.

## Goals / Non-Goals

**Goals:**

- Сделать так, чтобы четвёрка контуров — бэкенд, фронтенд, деплой, архитектура — читалась прямо из корня, без разбора содержимого каталогов.
- Сохранить инвариант инструментов «каталог = путь модуля», чтобы `tools/importlint` продолжал выводить границы из путей без ручных карт соответствия.
- Свести знание о деплое в один дом и разложить `platform` по назначению.
- Дать фронтенду компонентный слой, пригодный для двух потребителей (`public` и будущая консоль), не меняя стек.
- Перенести код без изменения поведения: состав пакетов и тестов сохраняется.

**Non-Goals:**

- Не вводить `internal/`-раскладку и общие `internal/{domain,app,ports}` — это прямо запрещено (`openspec/config.yaml`).
- Не переименовывать bounded contexts, контракты, сервисы и роли.
- Не менять транспорт, контракты и наблюдаемое поведение edge.
- Не строить консоль оператора и не разносить тринадцать сервисов на отдельные процессы.

## Decisions

### Решение 1. Целевая раскладка: `backend/` группирует служебный код

```text
backend/                      # служебный Go-код (модули workspace)
  cmd/lead-gen/               # единая точка входа единого образа
  contexts/<context-id>/      # модуль на bounded context: internal/{domain,app,ports,adapters}
  platform/                   # общие технические примитивы служебного контура
contracts/<owner>/            # published language (общий для backend и frontend)
frontend/
  public/                     # публичный edge (отдельный образ)
  components/                 # общий слой серверных UI-компонентов
deploy/                       # services.yaml, infrastructure.yaml, tofu/
architecture/                 # domain-catalog.yaml, схема, диаграммы
docs/                         # проза
openspec/                     # спеки и изменения
tools/                        # archlint, importlint
```

**Почему так.** `backend/` отделяет служебный код от контуров развёртывания и документации ровно так, как `frontend/` уже отделяет edge. `contracts/` и `frontend/` остаются в корне, потому что это разделяемые поверхности, а не внутренность бэкенда.

**Рассмотренные альтернативы:**

- **Обернуть под `backend/` всё, включая `contracts/` и `frontend/`.** Отклонено: контракты импортирует публичный edge (`frontend/public/Dockerfile` копирует `contracts/*`, README edge это закрепляет). Вложить разделяемый модуль внутрь одного потребителя — объявить ложное владение.
- **Оставить модули в корне и только разложить `platform/` по подгруппам.** Отклонено: не убирает исходную жалобу — бэкенд остаётся неотличим от `docs/`, `architecture/`, `deploy/` на верхнем уровне, а бэкенд и фронтенд остаются асимметричны.
- **Ввести `services/` или `src/` вместо `backend/`.** Отклонено: `src/` не в духе Go, `services/` конфликтует с уже занятым смыслом «сервис = единица развёртывания» (модуль контекста), и `backend` точнее называет контур.

### Решение 2. Пути модулей следуют каталогам

Модуль переименовывается вместе с переездом: `lead-gen/cmd/lead-gen` → `lead-gen/backend/cmd/lead-gen`, `lead-gen/contexts/<ctx>` → `lead-gen/backend/contexts/<ctx>`, `lead-gen/platform` → `lead-gen/backend/platform`; `lead-gen/contracts/<owner>` и `lead-gen/frontend/public` сохраняют имена. Все импорты `lead-gen/...` (≈285 строк) переписываются механически.

**Почему так.** Это сохраняет инвариант `tools/importlint` из Context: каталог относительно корня совпадает с путём модуля, и роль пакета снова выводится из пути без карт соответствия. Вариант «каталог переехал, путь модуля остался» отклонён: расхождение каталога и пути ломает `importPathOf` и вводит в заблуждение читателя. Вариант «не менять пути, заставить линт обходить модули по `go.work`» отклонён как более дорогой: он переписывает обход линта, чтобы сохранить пути, которые всё равно стоит привести в порядок.

### Решение 3. `backend/platform` раскладывается по назначению

```text
backend/platform/
  composition/     # сборка сервиса (composition root)
  contracts/       # envelope, routing, version
  messaging/       # outbox, inbox, idempotency
  observability/   # observ, prometheus
  reliability/     # resilience (breaker, bulkhead, retry)
  transport/       # http, amqp
  deployment/      # разбор services.yaml и загрузка topology
  migrate/         # миграции
```

**Почему так.** Плоский `platform/` из тринадцати пакетов не сообщает, что к чему относится; после перегруппировки `transport`, `messaging` и `observability` находятся там, где их ищут. Пакеты `internal/*` внутри `platform` не вводятся — уровни и так видны по подпакетам.

**Альтернативы.** Оставить плоско и добавить только `deployment` — отклонено: половина жалобы была именно про склад. Дробить `platform` на отдельные модули — отклонено: это уже сервисные модули, а `platform` сознательно один разделяемый модуль (`deployment-topology`).

### Решение 4. Знание о деплое сводится в `backend/platform/deployment`

Парсер `deploy/services.yaml` переносится из `backend/cmd/lead-gen` в `backend/platform/deployment`, туда же переезжает загрузчик `backend/platform/deployment` (`infrastructure.yaml`, схема топологии). `backend/cmd/lead-gen` продолжает вызывать разбор, но как потребитель, а не владелец правил. `deploy/` остаётся декларативным: только `services.yaml`, `infrastructure.yaml`, `tofu/` и README.

**Почему так.** Сейчас «что такое деплой» знает и точка входа, и платформенный пакет. Один дом снимает дублирование и делает валидацию конфигурации переиспользуемой. Отдельный Go-модуль `deploy/` отклонён: он превратил бы декларативный каталог в модуль и завёл бы ребро «бэкенд зависит от деплоя-как-кода», размывая границу.

### Решение 5. Компонентный фронтенд: новый модуль `frontend/components`

Вводится модуль `lead-gen/frontend/components` — общий слой серверных UI-компонентов на `html/template`: layout, переиспользуемые фрагменты, формы, разбор ошибок в представление, заголовки безопасности. `frontend/public` переводится на него: страницы собираются из компонентов, монолитные шаблоны `internal/web/templates/*` распадаются на компоненты. Маршруты и наблюдаемое поведение edge не меняются.

**Почему так.** Компонентность здесь серверная — по канону стека (`docs/architecture.md` §11; `web-frontend-architecture`, Решение 2, где SPA и отдельный фронтенд-процесс отклонены явно). Слой выделяется отдельным модулем, потому что у него два потребителя: edge `public` и будущая консоль оператора. Держать компоненты внутри `frontend/public/internal` отклонено: тогда консоль либо дублирует разметку, либо тянет `internal` edge. Хранить компоненты в бэкендном `backend/platform/web` отклонено: фронтенд-модуль не должен зависеть от служебного бэкенда ради разметки.

**Следствие для канона.** Решение 3 `web-frontend-architecture` размещало примитивы рендеринга в бэкендном `internal/…`. Это решение его замещает: общий слой живёт в `frontend/components` и общий для `public` и консоли. Правка ссылок — задача синхронизации документации, продуктовые требования консоли не пересматриваются.

### Решение 6. Стек и границы не меняются

HTMX и `html/template` остаются; JS-фреймворк не вводится. `tools/importlint` сохраняет проверяемые рёбра (слои контекста, межконтекстность только через `contracts/<owner>`, запрет edge импортировать контексты и хранилища) и получает лишь новую грамматику путей: `backend/contexts/<ctx>/internal/<layer>`, `backend/platform`, `backend/cmd`, `frontend/<...>`, `contracts/<owner>`. Правило edge распространяется на `frontend/public` и `frontend/components`.

**Почему так.** Меняется раскладка, а не правила. Сохранение состава проверок делает перенос доказуемо нейтральным: те же рёбра, те же запреты.

## Risks / Trade-offs

- **Механический переезд путей задевает ≈285 импортов и три инструмента сборки** (`go.work`, `Makefile`, два `Dockerfile`) → компенсация: перенос без изменения состава пакетов, критерий — `make check` (сборка, тесты, `vet`, `importlint`, `archlint`, `openspec`) зелёный до и после; работа ведётся одним change'ем с коммитами по слоям.
- **Расхождение сборки с layout** (обход `MODULES` в `Makefile`, `COPY` в образах, минимальный `go.work` в образе edge) → компенсация: `Dockerfile`-копирования и список модулей входят в задачи переноса, проверка — сборка обоих образов.
- **`importlint` может ослабить проверку, если грамматику расширить неаккуратно** (например, оставить `contexts` без `backend/` и не заметить) → компенсация: фикстуры `testdata` обновляются под новый layout, а негативные случаи (импорт чужого `internal`, чужого хранилища, edge→context) остаются и проверяются тестами линта.
- **Дрейф документации в незакрытых change'ах** (`web-frontend-architecture`, `service-per-context`, `migrate-platform-to-go`, `service-topology-console`) → компенсация: задача синхронизации путей; если формулировка дизайна противоречит новому слою компонентов, правится ссылка, а не продуктовая часть.
- **Преждевременный общий слой с одним потребителем** (`frontend/components` сегодня нужен только `public`) → компенсация: слой ограничен разметкой и не несёт доменных терминов; это ровно тот контракт, что нужен консоли, и его отсутствие вернёт дублирование разметки, которое канон `web-frontend-architecture` (Решение 4) прямо запрещает.
- **Большой единовременный diff** → компенсация: change — чистый рефакторинг без смены поведения и без внешних потребителей путей, поэтому откат — один revert.

## Migration Plan

1. **Перенос каталогов и путей.** Переместить `cmd/`, `contexts/`, `platform/` под `backend/`; переименовать модули в `lead-gen/backend/...`; переписать импорты; обновить `go.work`.
2. **Разложение `platform`** на подпакеты по назначению (Решение 3) с обновлением импортов потребителей.
3. **Сведение деплоя** в `backend/platform/deployment` (Решение 4); `deploy/` оставить декларативным.
4. **Инструменты и сборка:** грамматика `tools/importlint` + фикстуры; `Makefile` (`MODULES`, цели); корневой `Dockerfile` и `frontend/public/Dockerfile`.
5. **Фронтенд:** создать `frontend/components`, перевести `frontend/public` на компонентный слой без смены маршрутов и поведения.
6. **Документация:** `README.md`, `docs/domain-model.md` §«Реализация на Go», `deploy/README.md`, `docs/architecture.md` §2, ссылки на пути в незакрытых change'ах.
7. **Проверка:** `make check` и сборка обоих образов зелёные; поведение edge подтверждается существующими тестами.

**Откат:** рефакторинг без внешних потребителей путей и без изменения поведения, поэтому откат — revert change'а на уровне репозитория; миграции данных не требуется.
