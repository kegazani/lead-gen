## Context

Мотивация и объём — в `proposal.md`. Здесь состояние и ограничения, определяющие подход.

**Что уже зафиксировано и не пересматривается.**

- Границы среза задаёт каталог `architecture/domain-catalog.yaml`: capability `osint-enrichment` принадлежит контексту `lead-management` (сервис `lead-management`, роли `api`, `worker`); контракт `provider-port` и capability `provider-agnostic-integrations` — контексту `integration-platform`. Карточка компании строится по агрегату `lead-profile` (AR `company`), контакты — по агрегату `contact` (AR `contact`, entity `attribute-provenance`). Каталог, `docs/domain-model.md` и диаграммы не меняются: MVP реализует уже объявленную модель, а не вводит её.
- Полный домен `integration-platform` (агрегаты `adapter-registration`, `integration-invocation`, нормализация ошибок, manifest) — за change'ем ЭТАПА 0 (`openspec/changes/integration-platform`), этим срезом не реализуется. Срез берёт только его сборочную часть: порты и адаптеры.
- Требования среза — дельта `specs/osint-enrichment/spec.md`: обогащение по явному запросу, открытые источники без обхода авторизации, соблюдение robots.txt со сдерживанием лимитами страниц и глубиной обхода, минимизация, карточка с происхождением полей, эскалация на LLM без перетирания сильных сигналов, хранение по зонам, журнал заданий со статусами, витрина с удалением/скрытием.
- Стек интерфейса — серверный рендеринг `html/template` + HTMX; экраны — эксплуатационная часть роли `api` в `adapters/http` контекста-владельца, общие примитивы — `frontend/components` (канон `web-frontend-architecture`).
- Хранилище — PostgreSQL через `pgx/v5`; зелёная зона — schema-per-service, красная — отдельная база (`docs/architecture.md` §11). Миграции — примитив `backend/platform/migrate` (SQL-файлы с директивой `-- schema:`).
- `deploy/services.yaml` уже объявляет `lead-management` с ролями `[api, worker]` в группе `demand` — конфигурация развёртывания не меняется; меняется только сборка в `backend/cmd/lead-gen` (заглушка `stubService` заменяется реальной сборкой).
- Границы импортов проверяет `tools/importlint`: контекст импортирует другой контекст только через `contracts/<owner>`; composition root `backend/cmd/lead-gen` границами не ограничен.

**Ключевое напряжение.** Краулер — ядро среза, но адаптеры портов принадлежат чужому контексту (`integration-platform`), а вся логика обогащения — `lead-management`. Дизайн обязан развести «кто исполняет» и «кто владеет правилом»: пайплайн обогащения живёт в `lead-management` и работает только с интерфейсами портов из `contracts/integration-platform`; реализации портов (клиент Firecrawl, клиент LLM) живут в модуле `integration-platform` и впрыскиваются composition root'ом. При этом модуль `integration-platform` в срезе не собирает собственный сервис каталога — это библиотека адаптеров, которую соберёт ЭТАП 0.

## Goals / Non-Goals

**Goals:**

- Провести вертикальный срез capability `osint-enrichment`: задание поиска → поиск → обход → экстракция → карточка в базе → витрина, на реальных портах с тестовыми адаптерами и с реальными адаптерами (Firecrawl, DeepSeek).
- Закрепить границу «пайплайн обогащения ↔ внешние движки» так, чтобы движок краулинга менялся правкой адаптера, а не ядра: порты типизированы, адаптеры за интерфейсами `contracts/integration-platform`.
- Сдерживать нагрузку на сайты лимитами страниц и глубиной обхода при соблюдении robots.txt (поведение движка Firecrawl).
- Дать оператору видимый журнал заданий (queued/running/done/failed) и витрину карточек с происхождением каждого поля, с возможностью удалить/скрыть запись.
- Заложить готовность к следующему срезу без переделки: единый job-механизм (переиспользует рассылка), компоненты витрины отдельно от страниц (заготовка трёх вкладок), схема расширяется миграциями, адаптер краулера не различает режимы discovery/targeted.

**Non-Goals:**

- Не реализуем домен `integration-platform`: регистрацию адаптеров, manifest, invocation-агрегат, нормализацию ошибок в доменные категории — за ЭТАПОМ 0.
- Не реализуем аутентификацию и RBAC: консоль работает в режиме dev-актора (по образцу флагов `-actor`/`-tenant` среза `outreach-approval-slice`).
- Не отправляем письма, не строим кампании, CRM-слой и статусы лидов — следующий срез.
- Не делаем автономную кликательную навигацию: Firecrawl `/interact`/`/agent` (клики, формы, логин) — самый дорогой режим, вне MVP.
- Не поддерживаем собственный прокси-пул/ротацию: ротация IP — на стороне Firecrawl.
- Не держим собственный LLM для экстракции: LLM-экстракция — через Firecrawl `extract`; свой LLM — только для планирования поиска (`Plan`).
- Не добавляем сетевые адаптеры контрактов: связи in-process (совмещённый деплой).

## Decisions

### Решение 1. Порты — в `contracts/integration-platform`, адаптеры — в модуле `integration-platform`

Порты Search/Crawl/LLM объявляются интерфейсами в опубликованном модуле `contracts/integration-platform` (пакеты `search`, `crawl`, `llm`), адаптеры — в `backend/contexts/integration-platform/internal/adapters` (`firecrawl`, `openai`). Корневой пакет модуля публикует конструкторы адаптеров. `lead-management` импортирует только `contracts/integration-platform` — легальный межконтекстный импорт по `importlint`; composition root `backend/cmd/lead-gen` собирает адаптеры и впрыскивает их в сборку `lead-management`.

Порты типизированы, а не выражены одним generic `Invoke`:

- `search.Port.Search(ctx, Query) ([]Result, error)` — запрос и найденные URL с заголовком и сниппетом (markdown);
- `crawl.Port` — две операции: `Crawl(ctx, Request) (CrawlOutcome, error)` (стартовый URL, бюджет `max_pages`/`max_depth`, фильтры путей `include_paths`/`exclude_paths`, режим `map`-затем-scrape; исход — набор страниц с Markdown и метаданными) и `Extract(ctx, ExtractRequest) ([]ContactCandidate, error)` (структурированная экстракция по схеме name/email/phone/role через `extract`-режим Firecrawl);
- `llm.Port.Plan(ctx, PlanRequest) ([]Target, error)` — разложение запроса оператора в поисковые запросы и стартовые URL (единственная операция порта).

**Почему так:** typed-порты тестируются контрактными suite против фейков и не протекают деталями движка в прикладной слой; интерфейс — единственный способ связать контексты в этом проекте. DTO `crawl` фиксирует понятия бюджета/глубины/фильтров путей, а не конфигурацию конкретного движка — это и есть граница, за которой меняется только адаптер (Crawl4AI → Firecrawl, и обратно при необходимости).

**Рассмотренные альтернативы.** Порт как generic `Invoke(ctx, Request) (Result, error)` (форма из design ЭТАПА 0) — отклонено: теряется типобезопасность операций, а выигрыш от generic-формы нужен только регистрации адаптеров, которой в срезе нет. Адаптеры в `lead-management/internal/adapters` — отклонено: порты принадлежат `integration-platform` по каталогу, и предложение закрепляет их в контексте-владельце.

### Решение 2. Пайплайн обогащения — app-слой `lead-management`

Use case `RunSearch` (app-слой) исполняет задание поиска: планирование (LLM-порт, опционально) → поиск (Search-порт) → обход каждого URL (Crawl-порт) → слои экстракции → оценка качества → эскалация на Firecrawl `extract` → слияние по приоритету → дедупликация → сохранение. Все пороговые правила (что считать «плохим результатом», приоритет слоёв при слиянии, происхождение поля) — решения прикладного слоя контекста-владельца, а не адаптеров.

Домен реализует минимальный срез агрегатов каталога: `lead-profile` (AR `company`: название, описание, соцсети; на каждое поле — источник и дата) и `contact` (AR `contact`: email/телефон/роль; entity `attribute-provenance` — источник, дата, способ извлечения). Восстановление агрегатов — по образцу срезов ЭТАПА 0: Snapshot/Rehydrate в домене, адаптер репозитория работает только со снимками. События `lead-profile-enriched` объявляются в домене, но наружу контекста в срезе не публикуются: потребителей нет.

**Задание поиска — операционная запись app-слоя, не доменный агрегат** (по proposal): оно хранит запрос, статус, ссылку на результаты и причину отказа. Если в следующем срезе у задания появятся доменные инварианты — отдельное изменение каталога (открытый вопрос).

**Почему так:** capability принадлежит `lead-management`; правила качества и слияния — его язык, а адаптер не вправе решать, что «достаточно хорошо». Домен остаётся минимальным, чтобы не придумывать инварианты сверх каталога.

### Решение 3. Слои экстракции: Firecrawl отдаёт чистый Markdown, логика эскалации — в Go

Firecrawl используется как рендерер и навигатор: `/search` (поиск с markdown), `/crawl` с `includePaths` (`contact`, `team`, `about`, `staff`, `impressum`) и `excludePaths` (блог/новости/каталог), быстрый путь `/map` + точечный `/scrape`, лимиты `limit`/`maxDepth`. JS-рендеринг и ротация IP — на стороне Firecrawl. Наш адаптер передаёт параметры обхода через API.

Нормализация — в Go-адаптере/прикладном слое: regex email/телефона поверх Markdown, деобфускация Cloudflare (`__cf_email__`), слияние полей из метаданных и текста; оценка качества (заполнены ли название, описание, контакты). При плохом качестве — эскалация на LLM.

**LLM-экстракция — через Firecrawl `extract`** (structured-режим по JSON-схеме name/email/phone/role), а не отдельным LLM-портом: при низком качестве пайплайн вызывает `crawl.Port.Extract`, и Firecrawl отдаёт структурированные контакты по схеме. Результат не перетирает поля, извлечённые слоями 1–2: слияние по приоритету, у каждого поля фиксируется происхождение (URL, дата, способ).

**Почему так:** экстракция — часть того же «web → данные», что и рендер; она живёт в Firecrawl, а наша сторона держит только оценку качества, порог эскалации и слияние по приоритету — одно место принимает решение, и его покрывают тесты без вызова внешних сервисов. Отдельный LLM-порт остаётся только для планирования поиска (`Plan`).

**Рассмотренные альтернативы.** Собственный LLM-порт для экстракции (`llm.Port.Extract`) — отклонено: дублировал бы structured-режим Firecrawl и требовал бы отдельной LLM-конфигурации и ключа. Полный отказ от LLM в срезе — отклонено: эскалация зафиксирована спекой.

### Решение 4. Соблюдение robots.txt — поведение движка, не флаг адаптера

Firecrawl соблюдает robots.txt при обходе; наш адаптер не пытается это обойти и не принимает флага «игнорировать robots». Сдерживание нагрузки — лимиты конфигурации: бюджет страниц (`limit`/`max_pages`), максимальная глубина (`max_depth`), минимальная пауза между вызовами на нашей стороне.

**Почему так:** отступление от robots.txt, которое ранняя редакция среза закладывала как осознанное (`respect_robots_txt: false`), с переходом на hosted-движок недоступно и нежелательно: Firecrawl соблюдает robots по умолчанию, а требование «без обхода защит» из каталога возвращается в силу. Нагрузку сдерживают лимиты и бюджет, а не попытки обойти запреты краулинга.

**Следствие принято:** страницы, закрытые robots.txt, не обходятся — полнота карточки на части сайтов ниже, чем при обходе запретов; это принимается как плата за соблюдение правил доступа.

### Решение 5. Хранилище: два DSN, дедупликация по нормализованным ключам

Зелёная зона — схема `lead-management` в общем кластере: таблицы снимков агрегата `lead-profile` и операционных записей задания поиска. Красная зона — отдельная база данных (в локальном контуре — отдельная БД на том же инстансе): контакты и `attribute-provenance`. Оба адреса приходят конфигурацией; миграции — SQL-файлы через `backend/platform/migrate`, отдельные каталоги для зелёной и красной базы.

Дедупликация в app-слое перед сохранением: компания — по нормализованному домену сайта, контакт — по нормализованному адресу в пределах компании. Повторный обход того же сайта не создаёт второй карточки, а дополняет существующую новыми полями с происхождением.

**Почему так:** схема-на-сервис и физическое разделение зон — канон (`docs/architecture.md` §11, `backend/platform/migrate`). Дедup по ключу домена/адреса — минимум BRD 3.4, достаточный для среза.

### Решение 6. Единый job-механизм — примитив `backend/platform/jobs`

Статусы заданий (queued/running/done/failed), хранилище и цикл выполнения выносятся в примитив `backend/platform/jobs` без доменных терминов: интерфейс `Store` (создать задание, взять queued, обновить статус), тип `Status`, раннер с интервалом опроса. App-слой `lead-management` регистрирует обработчик задания поиска и pgx-реализацию `Store` в своей схеме. Роль `worker` сервиса `lead-management` запускает раннер; роль `api` ставит задания и читает журнал.

**Почему так:** это требование готовности к следующему срезу — механизм переиспользует рассылка, поэтому он обязан жить в `backend/platform` без доменных терминов, а не внутри `lead-management`.

**Рассмотренные альтернативы.** Задание как агрегат каталога — отклонено (proposal: операционная запись; отдельное изменение каталога при появлении инвариантов). Локальная очередь внутри `lead-management` — отклонено: механизм был бы недоступен рассылке и требовал бы переноса при следующем срезе.

### Решение 7. Консоль: экраны в `adapters/http` контекста, компоненты — отдельно от страниц

Роль `api` сервиса `lead-management` поднимает HTTP-сервер: экран запуска поиска (запрос или стартовые URL), журнал заданий со статусами, таблица найденных карточек, карточка с полями и источниками, действия удалить/скрыть. Экраны и шаблоны — в `backend/contexts/lead-management/internal/adapters/http`; HTMX раздаётся статикой. POST/redirect/GET, фрагментное обновление журнала опросом.

Новые общие примитивы — в `frontend/components` без доменных терминов: навигация вкладок (заготовка трёх вкладок: разведка сегментов / кампании / CRM), бейдж статуса задания, отображение происхождения поля. Компоненты не знают о сущностях `lead-management`: данные приходят моделями представления.

**Почему так:** канон `web-frontend-architecture` (Решения 1–4): интерфейс — эксплуатационная часть роли `api`, не владеет моделью; компоненты отдельно от страниц — требование готовности к трём вкладкам следующего среза.

### Решение 8. Сборка: реальная сборка `lead-management` вместо заглушки

`backend/cmd/lead-gen` получает ветку `case leadmanagement.ServiceID` в `buildService`: сборка читает конфигурацию (DSN зелёной/красной базы, ключ Firecrawl, параметры LLM, лимиты), собирает адаптеры портов из модуля `integration-platform`, впрыскивает их в сервис `lead-management`. `deploy/services.yaml` не меняется: роли `api` и `worker` группы `demand` уже объявлены. Сервис `integration-platform` остаётся заглушкой: его адаптеры — библиотека, сервис соберёт ЭТАП 0.

Модули `backend/contexts/lead-management`, `backend/contexts/integration-platform`, `contracts/integration-platform` регистрируются в `go.work` и в `MODULES` Makefile.

**Почему так:** конфигурация развёртывания уже совпадает с целевой; изменение — только замена заглушки сборкой. Единая точка входа — канон (`architecture.md` §8).

## Risks / Trade-offs

- **[Качество парсинга на неоднородных сайтах — главный риск]** → Навигация по релевантным путям (`includePaths`), слои дешёвый→дорогой, LLM-эскалация, лог по URL, метрика «доля страниц с извлечёнными полями».
- **[Блокировки]** → Ротация IP на стороне Firecrawl, лимиты и backoff через `resilience`; robots.txt соблюдается — часть страниц недоступна, принято как следствие.
- **[Стоимость и лимиты Firecrawl]** → Кредиты/rate limit; смягчение бюджетом страниц, лимитами глубины и ограничением параллелизма; мониторинг расхода кредитов на задание; `extract`-режим дороже markdown, подключается только на эскалации.
- **[Зависимость от облака и ключа]** → Firecrawl — hosted API, секрет вне репозитория; при недоступности сервиса задания падают с причиной (журнал).
- **[LLM-провайдер (планирование) недоступен или дорог]** → Планирование опционально: без LLM запрос идёт как есть; эскалация экстракции — через Firecrawl `extract`, её стоимость входит в кредиты Firecrawl.
- **[Firecrawl не подойдёт]** → Запасной путь: self-hosted адаптер (Crawl4AI или colly+chromedp) за тем же `crawl.Port`/`search.Port`, без правки ядра.
- **[Локальный запуск требует PostgreSQL и ключ Firecrawl]** → Контур поднимается `deploy/tofu` (env `local`); Docker для краулера не нужен; инструкция — в README среза.
- **[Расхождение с неархивированной спекой рамки]** → `full-enterprise-core-scope/specs/osint-enrichment` утверждает запрет хранения и «без обхода защит»; этот срез создаёт первую версию capability в своей редакции (robots.txt соблюдается, но хранение остаётся). При архивации рамки её ADDED-дельта потребует конвертации в MODIFIED — открытый вопрос архивации, не блокирующий реализацию.

## Migration Plan

Данных нет; миграция — только новые модули и схемы.

**Порядок.**

1. Модули и скелет: `contracts/integration-platform` → `backend/contexts/integration-platform` (адаптеры за фейками) → `backend/contexts/lead-management` (домен → app → порты → адаптеры) → сборка в `cmd/lead-gen`, регистрация в `go.work` и Makefile.
2. Миграции зелёной и красной баз; pgx-адаптеры репозиториев и job-`Store`.
3. Реальные адаптеры портов: Firecrawl (search/crawl), DeepSeek (планирование `Plan`); контрактные suite против тестовых адаптеров.
4. Консоль: экраны, шаблоны, компоненты; e2e-сценарий «запрос → поиск → обход → карточки в БД → таблица в консоли».
5. Обновить `docs/system-map.md` (строка capability `osint-enrichment`: спека теперь первая версия среза, зона/хранение — по факту), `docs/progress-log.md`; заменить `docs/crawl4ai-playbook.md` на Firecrawl-плейбук (или пометить устаревшим).

## Open Questions

1. **Архивация `full-enterprise-core-scope`.** После архивации этого среза capability `osint-enrichment` получает первую версию в `openspec/specs/`; дельта рамки с запретом хранения станет MODIFIED-дельтой при архивации рамки. Решается порядком архивации, не сейчас.
2. **Доменные инварианты задания поиска.** Пока задание — операционная запись app-слоя; если в следующем срезе появятся инварианты (например, квоты на параллельные задания) — отдельное изменение каталога.
3. **Метрика качества парсинга.** Название и порог «доли страниц с извлечёнными полями» уточняются на реальных данных первого запуска; в срезе — лог и счётчик, без алертов.
4. **Бюджет кредитов Firecrawl на задание.** Предел расхода кредитов на одно задание и политика при исчерпании (пауза/отказ) уточняются после первого прогона на реальном тарифе.
