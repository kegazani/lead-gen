# Design: lead-target-on-approval

## Context

Workflow `Fulfillment` (`internal/adapters/workflow/fulfillment.go`) вычисляет
недобор `shortfall = target - found` только при `explicitTarget := target > 0`.
При `target <= 0` цель подменяется значением по умолчанию (`defaultLeadTarget = 1`),
но `explicitTarget` остаётся `false`, поэтому `state.Shortfall` не заполняется, а
гейт `shortfall-gate` (`draftsAllowed`) не пропускает шаг генерации черновиков.
Следствие: без явной числовой цели письма не генерируются.

Штатный UI-путь одобрения — `handleValidationApprove` → `startFulfillment`
(`internal/adapters/http/validation_screen.go`) — стартует исполнение с
`LeadTarget: 0`. У администратора нет способа задать цель из UI. API-путь
`POST /requests/{id}/start-workflow` (`handlers.go`) поле `lead_target` уже
принимает, но проверок не делает.

## Goals / Non-Goals

**Goals.**

- Дать администратору задать необязательную числовую цель на экране одобрения и
  пробросить её в `ports.StartFulfillment.LeadTarget`.
- Сохранить обратную совместимость: пусто/`0` = цель не задана (прежнее поведение).
- Некорректная цель (отрицательная/нецелая) — понятный `400`, без частичного
  применения одобрения.
- Согласовать проверку цели между UI- и API-путями.

**Non-Goals.**

- Не хранить числовую цель в агрегате `request` (она остаётся параметром запуска).
- Не согласовывать свободный текст `request-target` с числом (открытый вопрос из
  `shortfall-to-letters/design.md`).
- Не менять граф workflow, контракт `email-generation`, векторный recall.

## Decisions

### Решение 1. Поле «Цель по числу лидов» в форме одобрения

Поле рисуется в существующей форме `POST .../validation/approve`, показываемой при
`CanDecide` (статус `validating`). Виджет — `<input type="number" min="0" step="1">`
с именем `lead_target`. Общий фрагмент `field` (`frontend/components`) не умеет
тип `number`, а его правка вне границ контекста, поэтому числовой контрол
рендерится в шаблоне экрана валидации; конфигурация поля (ID, имя, подпись)
собирается в модели `screenView`, как и остальные поля экрана.

Пустое поле и отсутствие параметра равнозначны «цель не задана» (`0`).

### Решение 2. Разбор и проверка значения — в HTTP-адаптере, до применения одобрения

`parseLeadTarget(raw string) (int, error)`: пусто → `0`; не целое → ошибка;
отрицательное → ошибка. Сентинел `errInvalidLeadTarget` даёт статус `400` через
`statusForError` (не `500`). Разбор выполняется **первым** в замыкании approve: при
некорректной цели `ValidateRequest` не вызывается, заявка остаётся в `validating`,
исполнение не стартует — одобрение не применяется частично.

Альтернатива — валидировать после перехода — отклонена: она оставляла бы заявку в
`validated` без запуска исполнения, то есть в неотличимом от штатного «цель не
задана» состоянии при видимой ошибке. Разбор до перехода даёт чистое «ничего не
произошло, покажи причину».

### Решение 3. Единая проверка для UI и API

`validateLeadTarget(int) error` отвергает отрицательное значение и вызывается в
обоих путях: на экране — через `parseLeadTarget`, в `handleStartWorkflow` — над
`body.LeadTarget`. Так отрицательная цель не просачивается в workflow ни через UI,
ни через API. `writeDomainError` отображает `errInvalidLeadTarget` в `400`.

### Решение 4. Цель не персистится в агрегате

`ports.StartFulfillment` уже несёт `LeadTarget`; workflow принимает его как
`Params.LeadTarget`. Спека `request-shortfall` описывает расчёт недобора «при
явной цели заявки», не определяя способ её задания. Данный change задаёт способ
(одобрение) и проброс, не меняя доменную модель: новых полей агрегата, событий и
связей нет.

## Risks / Trade-offs

- **Значение поля не сохраняется при ошибке.** При повторной отрисовке экрана
  после ошибки числовое поле пустое (модель не знает отправленное значение).
  Компенсация — понятное сообщение об ошибке; сохранение введённого значения —
  возможное улучшение UX, вне объёма.
- **Цель не видна после запуска.** Числовая цель не отображается на экране после
  одобрения и не хранится в заявке. Наблюдение недобора идёт через состояние
  исполнения (фаза/`Found`/`Shortfall`); при необходимости цель можно сохранить
  отдельным change.
- **`min="0"` — только клиентская подсказка.** Серверная проверка обязательна и
  реализована; браузерная валидация не заменяет её.

## Migration

Изменение обратно совместимо: старые формы без `lead_target` дают `0` и прежнее
поведение. Миграций данных и контрактов нет.
