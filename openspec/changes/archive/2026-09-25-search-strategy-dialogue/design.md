## Context

См. `proposal.md` — Why. Что важно из текущего состояния:

- Экран ассистента (`handleAssistant` / `handleAssistantSuggest` / `handleAssistantEnqueue`, шаблон `assistant.html`) — один выстрел: `SuggestNiches.Suggest` → `llm.Port.Suggest` → список секторов/ниш/seed-запросов → `RunSearch.EnqueueMany`.
- `llm.Port` несёт две операции без состояния: `Plan(query) []Target` и `Suggest(description) []Suggestion`. Истории диалога в контракте нет.
- Задание поиска несёт только `{query, maxCredits}` (`ports.SearchJobPayload`); цели обхода вычисляются **внутри** раннера через `Plan`, а лимиты (`RunSearch.Limits`: `MaxPages`, `MaxDepth`, `IncludePaths`, `ExcludePaths`) — глобальные из конфига.
- Сессии оператора серверные, в памяти; долговечный результат работы — задание поиска.
- Бюджет кредитов (`firecrawl-credit-budget`) клампит обход сверху независимо от запрошенного лимита — это существующая защита, на неё опираемся.
- `docs/domain-model.md` уже объявляет capability `search-strategy` («Подбор секторов, ниш и seed-запросов с помощью LLM по описанию задачи оператора»), отдельного `spec.md` у неё нет.

## Goals / Non-Goals

**Goals:**

- Диалог с агентом, который уточняющими вопросами доводит оператора до согласованного плана обхода.
- План = цели (seed-запросы, стартовые URL) + технические лимиты; оператор видит и правит его, запуск подтверждает вручную.
- План доезжает до задания и используется раннером; при пустом плане сохраняется прежнее поведение.
- Безопасность: недоверенный план от клиента валидируется и клампится бюджетом; диалог не тратит кредиты Firecrawl.

**Non-Goals:**

- Персистентность транскрипта диалога (история у клиента, эфемерна).
- Streaming ответа модели по токенам (реплика приходит целиком).
- Операционный CRM-слой и сохранение диалогов между сессиями.
- Изменение логики бюджета кредитов и порта обхода — переиспользуем как есть.

## Decisions

### 1. Финиш — готовый план, запуск подтверждает человек

Диалог ведёт к готовому плану, но задание создаёт явное действие оператора. Альтернатива (агент сам запускает по своей готовности) отклонена: она тратит кредиты без согласия человека и противоречит принятому в проекте ручному подтверждению.

### 2. Хозяин плана — диалог; пустой план откатывается на `Plan`

Цели рождаются в диалоге и едут в задании. Раннер использует пришедший план, а при пустых целях зовёт существующий `Plan` — старое поведение остаётся рабочим фолбэком, ломать его не нужно.

### 3. Состояние диалога — у клиента, сервер stateless

История едет в каждом запросе; сервер её не хранит. Альтернативы: серверная сессия в памяти (теряется с рестартом, но проще) и транскрипт в БД (новая сущность, миграции — избыточно для эфемерного разговора). Выбрано клиентское состояние: долговечная ценность здесь только план в задании, а под транскрипт заводить владение состоянием дорого.

Следствие: план приходит от клиента — это недоверенный ввод, см. решение 7.

### 4. Интерфейс — гибрид: лента диалога + панель плана

Лента отвечает на исходную боль («не знаю, как сформулировать»), панель показывает, что согласовано, и даёт править лимиты. Чистые слоты-wizard отклонены (не отвечают на «не знаю»), голый чат отклонён (подтверждать план вслепую плохо). Панель рендерится на клиенте, что естественно при клиентском состоянии.

### 5. Контракт хода — `Converse` (черновик) + финальный `Plan` (истина)

`llm.Port` дополняется операцией диалогового хода:

```
Converse(ctx, ConverseRequest{ History []Message }) (ConverseReply, error)
  Message{Role, Content}
  ConverseReply{ Text string, Targets []Target, Ready bool }
```

Черновик (`Targets`) наполняет панель по ходу. Перед запуском финальный `Plan` собирает **авторитетный** план из критериев диалога. Черновик — предпросмотр, финал — истина; это не два независимых источника, а «показали» → «зафиксировали».

Критерии для финального `Plan` app-слой склеивает из ходов диалога в текст и передаёт существующим `PlanRequest{Query}`. Расширение `PlanRequest` структурными полями (сфера/ниша/гео по отдельности) не входит в этот change: текущий контракт справляется, а структурность добавим, если понадобится точность.

Лимиты агент не выдумывает: начальные значения — серверные умолчания (`RunSearch.Limits`), оператор их правит в панели.

### 6. Владелец — расширение `search-strategy`; контракт `llm` — через `integration-platform`

- Owning context диалога — `lead-management`, capability `search-strategy`.
- Межконтекстный контракт — расширенный порт `llm` (`integration-platform` → `lead-management`), существующее relationship `integrations-for-leads`. Адаптер `openai` реализует `Converse`.
- Новых агрегатов и domain events не появляется (см. «Non-Goals»); plan-структура — временная проекция app-слоя.

### 7. Недоверенный план: валидация + бюджетный кламп

План от клиента валидируется на сервере (непустой стартовый URL/запрос, компилируемость include/exclude regex, неотрицательные лимиты) — теми же правилами, что уже есть в `crawl.Request.Validate`. Верхнюю границу обхода независимо клампит бюджет кредитов задания.

### 8. План в задании — расширение `SearchJobPayload`, обратно совместимое

`SearchJobPayload` получает опциональные поля целей и лимитов:

```
{"query": "...", "maxCredits": N,
 "plan": {"targets": [{"query"|"url"}], "limits": {"maxPages", "maxDepth",
          "includePaths", "excludePaths"}}}
```

Поле `plan` — `omitempty`: задания без плана декодируются и обрабатываются как раньше (фолбэк на `Plan`). Оба хранилища (`memory`, `postgres`) кодируют/декодируют расширенный payload. В `postgres` задание нормализовано в колонки, поэтому плану нужна собственная колонка `plan jsonb` (миграция `0007_search_job_plan.sql`, nullable); в `memory` план — поле записи.

### 9. Ограничение длины диалога

Число ходов ограничено пределом (конфигурируемое значение); при достижении система прекращает спрашивать и сообщает оператору. Бюджета на токены LLM в проекте нет, поэтому предохранитель — обязателен.

## Risks / Trade-offs

- **Двойная работа LLM** (черновик по ходу + финальный `Plan`) → выше задержка и расход токенов. Смягчение: финальный `Plan` только по подтверждению запуска; черновик лёгкий (только цели); предел числа ходов.
- **Подделка плана на клиенте** (оператор меняет лимиты) → серверная валидация + кламп бюджетом кредитов; обход сверх бюджета невозможен.
- **Потеря диалога при перезагрузке** (состояние клиента) → принятая плата; оператор начинает заново, план задания при этом уже сохранён.
- **Рост запроса историей** → предел числа ходов и разумная обрезка истории в запросе.
- **Prompt injection через ввод оператора** → оператор доверенный, но структурные выходы модели всё равно валидируются (решение 7).
- **Черновик vs финал расходятся** → черновик явно помечен как предпросмотр, авторитетен только финальный план задания.

## Migration Plan

1. Расширить `llm`-контракт и адаптер (аддитивно, старые операции не меняются).
2. Расширить `SearchJobPayload` с `omitempty` и научить оба хранилища; добавить колонку `plan` в `search_job` (миграция `0007`); проверить декодирование старых заданий (обратная совместимость).
3. Раннер: план из payload при непустых целях, иначе существующий фолбэк.
4. Экран ассистента: диалог + панель плана; старый поток одного выстрела заменяется.
5. Откат: revert кода; задания, созданные с планом, всё равно декодируются (поле опционально) — данные не рвутся.

## Open Questions

- Точный набор бизнес-критериев (обязательными намечены сфера, ниша, география; остальное — по желанию) — можно уточнять без смены подхода и контрактов.
- Нужен ли стриминг реплики ассистента вместо ответа целиком — влияет на восприятие, но не на структуру.
