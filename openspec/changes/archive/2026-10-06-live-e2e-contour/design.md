## Context

Мотивация и объём — `proposal.md`. Состояние, определяющее подход:
`deploy/services.yaml` объявляет совмещённый первый деплой (группы сервисов) и
целевые отдельные контейнеры; `workflow`-исполнение заявки (Temporal) реально;
портал/дашборд и пять консолей реализованы; мост `approved-action → delivery-command`
собран в `cmd/lead-gen` как **один экземпляр на процесс** (`buildOnce`) и разделяется
lead-management/content-production/outreach/message-delivery. Все сервисы берут один
`-addr`, поэтому несколько `api`-ролей в одном процессе не запускаются. Сетевые
адаптеры синхронных контрактов объявлены (`sync/http-json`), но не реализованы.

## Goals / Non-Goals

**Goals:**
- Сделать локальный контур **исполняемым** и прогнать полный цикл клиент + админ.
- Сохранить co-location (in-process) как рабочий режим и добавить сетевой транспорт.
- Остаться в рамках существующих требований `deployment-topology`/`delivery-bridge`.

**Non-Goals:**
- Не менять доменную модель, каталог, состав и семантику контрактов.
- Не тянуть реальные внешние ключи/SMTP в репозиторий (параметры запуска).
- Не делать production-оркестрацию (OpenTofu) — только локальный контур.

## Decisions

### Решение 1. Per-service адреса API для совмещённого процесса

**Выбор.** Флаг `-api-port-base`: при `>0` каждому выбранному сервису с ролью `api`
назначается собственный адрес `:<base+индекс>` (детерминированно по порядку
выбора). `buildOptions` получает резолвер адреса по идентификатору сервиса; при
`base=0` поведение прежнее (`-addr`), то есть один сервис на процесс.

**Почему.** Совмещённый деплой из `deploy/services.yaml` не запускается из-за
конфликта `-addr`; резолвер минимально меняет `cmd` и не трогает контексты.
Браузерные адреса консолей уже задаются отдельно (`CONSOLE_*`), их связывает
`compose`.

### Решение 2. Сетевой транспорт трёх синхронных контрактов (Фаза 2)

**Выбор.** Для `approved-action`, `content-version`, `delivery-target` реализуются
HTTP-адаптеры по образцу существующих `httpport` (`leadsearch`, `emailgeneration`,
`requestintent`): владелец публикует обработчик, потребитель получает клиент за
интерфейсом контракта. Топология выбирает адаптер (in-process при co-location,
сетевой при разделении) — код потребителя не меняется.

**Почему.** Это уже объявленный механизм каталога (`sync http-json`) и паттерн,
принятый в проекте. In-process адаптеры сохраняются.

**Решение (зафиксировано в apply).** Выбран вариант (а): у `message-delivery`
появляется принимающая HTTP-поверхность `POST /approved-action`, которую
обслуживает роль `worker` (отдельный слушатель `Config.IntakeAddr`, не новая роль
каталога). Клиент — `contracts/outreach-orchestration/approvedaction/httpport`
(только стандартная библиотека), реализует `approvedaction.Publisher`; точка
сборки заворачивает его в `outreachorchestration.SinkFunc`. Вариант (б) (брокер)
отклонён: он меняет объявленный механизм `sync → async` и требует правки
каталога, тогда как HTTP сохраняет контракт и повторяет принятый в проекте
паттерн `httpport` (`leadsearch`, `emailgeneration`, `requestintent`).
In-process адаптер (`NewApprovedActionBridge`) остаётся для co-location —
поведение совмещённого процесса не меняется.

### Решение 3. Приёмка ведётся на живом контуре

Сквозной сценарий гоняется на `docker compose` (PG + RabbitMQ + Temporal + SMTP),
с реальным `lead-search` (без заглушки шага поиска). Шаги, требующие внешних
ключей, честно помечаются как недоступные, а не выдаются за пройденные.

## Risks / Trade-offs

- **[Много контейнеров/процессов в dev]** → совмещённый процесс (Решение 1) даёт
  быстрый запуск; разделение (Решение 2) — целевая проверка топологии.
- **[Сетевой транспорт без ретраев/идемпотентности]** → контракты идемпотентны по
  ключу; таймауты/повторы — за вызывающим слоем (как в существующих httpport).
- **[SMTP/LLM/Firecrawl ключи]** → параметры `.env`; без них шаги честно недоступны.

## Migration Plan

1. Per-service адреса + `Dockerfile` + `compose.yaml` (совмещённый контур).
2. Приёмка Фазы 1 на живом контуре.
3. Сетевые адаптеры трёх контрактов + разнесение контейнеров по ролям `api`.
4. Приёмка Фазы 2 (топология без co-location).

**Откат.** Возврат `compose`/`Dockerfile` к прежним; резолвер адресов при `base=0`
не меняет поведения.
