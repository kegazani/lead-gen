## 3. Приёмка

- [x] 3.1 Сквозной сценарий Фазы 1: клиент регистрирует компанию → заявка → админ правит/одобряет → поиск (реальный `lead-search`, без заглушки шага поиска) → недобор → письма → оператор утверждает → отправка (SMTP-захват) → дашборд клиента. Проверка: сценарий проходит на живом контуре; письмо получено захватчиком; дашборд отражает метрики. **Цепочка «AI-письма заявки → утверждение → отправка → замыкание заявки» ПРОЙДЕНА живьём (раздельная топология, `docker compose`, контейнеры не пересоздавались). Обрыв — на последней проверке: дашборд метрик не отражает прогон.** Прогон: (1) регистрация компании порталом `POST :8087/register` → `303`, создан отдельный тенант `tenant-2be4642dd9d817841fcd5799bfc11402`; (2) заявка клиента через портал `POST :8087/portal/request` от клиента с пулом — тенант `tenant-0b828ff5bd692e6dc9a6e09fd391a2d9` (резолвер получателя `lead-management` привязан к тенанту процесса, поэтому сквозная отправка возможна только в клиентском тенанте с пулом; свежерегистрированный тенант пула не имеет и цепочкой не проходит — оговорка (2) ниже) → `req-8fa0531dcbf94f1cfd3aeafe6fb69603` (`submitted`); (3) админ правит оффер (`POST :8085/requests/{id}/offer` → `validating`, ревизия оффера) и одобряет (`POST .../validation/complete` → `validated`; `POST .../processing/start` → `processing`); (4) durable-workflow (`POST .../workflow`, `lead_target=20`) с реальным `lead-search` (заглушка шага выключена `-workflow-search-stub-leads 0`): `found 3 / target 20 / shortfall 17`, `DraftEmails drafted:3 failed:0`; (5) звено `HandoffDrafts` создало кампанию `handoff-req-8fa0531dcbf94f1cfd3aeafe6fb69603` с 2 черновиками в очереди утверждения outreach (`info@1forma.ru`, `info@rechka.ai`; `dm-marketing.pro` пропущен — нет получателя), заявка встала в `awaiting-approval`; (6) оператор утвердил оба (`POST :8080/campaigns/{c}/drafts/{d}/approve`, `recorded:true`) → outbox (`action-approved`) → relay (`core`) → сетевой `POST /approved-action` (`delivery:8090`, `204`) → `delivery` разрешил получателя (`demand:8082 /delivery-target`) и материал (`demand:8084 /content-version`) → SMTP в **mailpit** (total 10 → 12: `info@1forma.ru` «Автоматизация длинного цикла продаж…», `info@rechka.ai` «Партнёрство по внедрению CRM…»), оба `message.status=delivered`; (7) `delivery-event` → заявка `phase=fulfilled, execution=Completed`, статус `fulfilled` (лог `все письма заявки доставлены — завершение по доставке … expected 2`), клиентский портал `:8087/portal` показывает заявку в статусе `fulfilled`. **Не закрыто (обрыв):** дашборд метрик клиента (`:8081/dashboard`, `records=0`, срез скрыт порогом минимальной группы) не отражает прогон, т.к. контур заявки/поиска/отправки не публикует события `analytics-event` (единственный издатель — `lead-management` при ручной смене стадии или отправке из карточки; `request-fulfillment`/`outreach-orchestration`/`message-delivery` их не публикуют; очередь `analytics.analytics-event` за прогон пуста). Этот пробел закрыт change `analytics-delivery-feed`: `analytics` подписан на очередь `analytics.delivery-event` и проецирует исходы доставки (delivered → прокоммуницировано, failed → отбой). Повторный живой прогон (заявка `req-f3fa5221fad697244ccb84b5f067262b`: реальный `lead-search` found 5 / target 20 / shortfall 15; 4 черновика утверждены; mailpit 12 → 16; заявка `fulfilled`) дал **непустой дашборд**: `:8081/dashboard/stream?tenant_id=tenant-0b828ff5…` → `visible=true, found=4, communicated=4, in_progress=4`. Критерий «дашборд отражает метрики» выполнен (§3: событие не подменено — это реальные `delivery-event` цикла).
