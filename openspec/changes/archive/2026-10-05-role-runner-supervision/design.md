## Context

Мотивация — `proposal.md`. Точка отказа — `startRoles` в
`backend/cmd/lead-gen/main.go`: для каждой роли сервиса запускается горутина,
которая при ошибке `runner.Run(ctx)` логирует `роль остановлена с ошибкой`,
вызывает `cancel()` и тем самым отменяет **весь** процесс. Комментарий рядом
фиксирует намерение «единица отказа и единица запуска совпадают»; на практике это
означает, что транзиентный сбой внешней зависимости у роли уносит процесс и
соседние роли, стартовавшие в том же процессе.

Сборка сервисов идёт **до** запуска ролей (`buildService`, `assembleApprovedActionBridge`,
`assembleAccessDecision`) и обрабатывает ошибку через `os.Exit(1)`. Супервизор не
должен менять это: ошибка сборки — неисправимая конфигурация, а не транзиентный
сбой.

## Decisions

### Решение 1. Супервизор — обёртка вокруг исполнения роли, не вокруг сборки

**Выбор.** Новый тип `roleSupervisor` (файл `supervisor.go`) владеет циклом
«запустить → дождаться → при ошибке подождать backoff → повторить». Сборка
сервисов остаётся в `main` и завершается `os.Exit(1)`. Роли берутся из
`composition.Service` и не меняются: супервизор зависит только от
`composition.RoleRunner`.

**Почему.** Смешение сборки и исполнения — причина текущего дефекта. Граница
«сборка фатальна, исполнение перезапускаемо» должна быть видна структурно: цикл
по выбранным сервисам вынесен в `startSelectedServices`, который **возвращает**
ошибку сборки (её и не глотает), а супервизор вызывается только после успешной
сборки.

### Решение 2. Перезапускается любая ошибка исполнения при живом контексте

**Выбор.** Если `runner.Run(ctx)` вернул ошибку и `ctx.Err() == nil` — попытка
считается неуспешной, выполняется backoff и роль запускается снова. Ошибки не
классифицируются (нет анализа SQLSTATE или типа сетевой ошибки).

**Почему.** Различать «транзиентную» и «фатальную» ошибку БД на уровне процесса
нельзя достоверно: `57P01`/`no such host` выглядят так же, как постоянный отказ
без дополнительного анализа, а собственная классификация разошлась бы с политикой
контекста. Перезапуск с ограниченным backoff безопасен и для постоянного отказа:
роль просто ретраится редко (потолок 30s) и не завершает процесс. Кратный
перезапуск хуже падения группы, а `ctx` всё равно завершает процесс по сигналу.

### Решение 3. Backoff: экспонента с потолком и jitter

**Выбор.** Задержка `attempt`: `0.5s * 2^(attempt-1)`, с потолком `30s`; к
потолку применяется jitter (равномерно `[d/2, d]`). Значения по умолчанию —
константы `roleRestartInitialBackoff`/`roleRestartMaxBackoff`; поля структуры
позволяют подменить их в тестах.

**Почему.** Экспонента снижает нагрузку на восстанавливающуюся зависимость,
потолок не даёт попытке ждать бесконечно, jitter разводит одновременные
перезапуски нескольких ролей одного процесса (шторм реконнектов). Jitter только
укорачивает задержку, не удлиняя её выше потолка.

### Решение 4. Плановая остановка не перезапускается

**Выбор.** После возврата роли проверяется `ctx.Err()`: если контекст отменён,
супервизор завершается независимо от того, вернула роль `nil` или ошибку.
Возврат `nil` при **живом** контексте тоже завершает цикл супервизора (с
предупреждением), без перезапуска.

**Почему.** `RoleRunner` документирован: «Run блокируется до отмены контекста; nil
означает штатное завершение (контекст отменён)». Ошибка/`nil` после отмены — это
следствие остановки. Возврат `nil` при живом контексте — не сбой БД; повторный
запуск здесь мог бы зациклиться, а прежнее поведение не роняло процесс — оно
сохраняется.

### Решение 5. Shutdown через существующий `WaitGroup`

**Выбор.** Горутина на роль остаётся в `sync.WaitGroup`; `wg.Done()` вызывается,
когда супервизор вернулся. Из `startRoles` убирается параметр `cancel`: отмену
теперь задаёт только сигнал/`shutdown` в `main`, а не ошибка роли. Ожидание
`wg.Wait()` в пределах `-shutdown-timeout` не меняется.

**Почему.** Единственный источник отмены `ctx` в норме — сигнал ОС. Роль,
ошибшаяся транзиентно, больше не должна отменять соседей; при остановке же
процесса роли завершаются по `ctx`, как и раньше.

## Risks / Trade-offs

- **[Постоянный отказ зависимости]** → роль ретраится вечно (редко, до 30s), но
  процесс и соседние роли живы; при постоянной недоступности это деградация, а не
  молчаливая подмена успехом.
- **[Роль-однодневка вернула `nil` при живом контексте]** → супервизор не
  перезапускает и предупреждает; прежнее поведение (процесс продолжает работать)
  сохранено.
- **[Тесты времени]** → параметры backoff подменяются малыми значениями; тест не
  ждёт десятков секунд.
- **[Логи при шторме]** → каждая неуспешная попытка логируется с причиной,
  номером и задержкой; это осознанно, чтобы отказ был наблюдаем.

## Migration Plan

1. Добавить `supervisor.go`: `roleSupervisor`, `backoff`, `sleepContext`,
   `startRoles` (через супервизор) и `startSelectedServices` (сборка + запуск).
2. В `main.go` заменить цикл по `selected` на вызов `startSelectedServices` с
   `os.Exit(1)` на ошибку сборки; из старого `startRoles` убрать `cancel`.
3. Тесты `supervisor_test.go`: перезапуск после ошибки; останов по отмене `ctx`;
   возврат ошибки сборки из `startSelectedServices`; рост/потолок backoff.

**Откат.** Реверт правок: `main.go` возвращается к прямому запуску ролей и
`cancel()` по ошибке; новый файл удаляется.
