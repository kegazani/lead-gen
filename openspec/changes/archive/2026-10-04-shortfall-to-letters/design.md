## Context

Мотивация и объём — в `proposal.md`. Здесь состояние и ограничения, определяющие
подход.

**Что уже есть.** Workflow `request-fulfillment` (`internal/adapters/workflow/`)
исполняет граф: `validated → processing → поиск (уникальные лиды, добор до
LeadTarget) → черновики писем → пауза утверждения → fulfilled`. Числовая цель —
`Params.LeadTarget` (по умолчанию 1). Наблюдаемое состояние — `Status` (фаза,
`Found`, `Drafted`, `NoLeads`). Черновики генерируются activity `DraftEmails` под
найденных лидов при `len(leadIDs) > 0` (версия графа `email-drafts`).

**Что не выражено.** «Недобор» (цель минус число уникальных найденных лидов) нигде
не вычисляется и не наблюдается. Шаг черновиков не различает «цель достигнута» и
«цель недостижима»: письма генерируются в обоих случаях. Явной capability
«недобор → письма» нет.

**Ограничение детерминизма.** Workflow версионируется
(`workflow.GetVersion`): бегущие исполнения не должны ломаться при изменении
графа. Любая новая ветка обязана быть версионирована.

## Goals / Non-Goals

**Goals:**

- Вычислять и наблюдать недобор `target − Found`.
- Автоматически запускать генерацию писем при недоборе, без ручного действия.
- Сохранить детерминизм: новые ветки версионированы, прежние исполнения
  воспроизводятся.

**Non-Goals:**

- Не менять статусную модель заявки и не автоматизировать отправку.
- Не менять контракт `email-generation` и шаг черновиков как таковой.
- Не выдумывать лидов и не подменять недобор нулём.

## Decisions

### Решение 1. Недобор — производное значение наблюдаемого состояния

**Выбор.** `Status` получает поле `Shortfall`. Недобор вычисляется как
`max(0, target − |уникальные найденные|)` после цикла поиска. При `target <= 0`
(цель не задана) недобор не показывается как выдуманный ноль — поле отражает
только случай явной цели.

**Почему.** Недобор — производное от уже известных `target` и `Found`; отдельного
хранения в агрегате не требует. Наблюдаемость (query `status`) — достаточная
форма, чтобы UI/отчётность показали остаток.

**Рассмотренные альтернативы.** Хранить недобор в агрегате `request` — отклонено:
это производное значение, дублирование состояния. Ввести target в агрегат — уже
есть (`request-target`, хотя и свободным текстом; числовая цель графа остаётся
источником для расчёта).

### Решение 2. Черновики гейтятся недобором (версионированно)

**Выбор.** Шаг `DraftEmails` выполняется, когда найден хотя бы один лид **и есть
недобор**. При достижении цели шаг пропускается. Гейт версионируется отдельным
маркером (`shortfall-gate`), чтобы прежние бегущие исполнения воспроизводились в
прежней структуре (без гейта).

**Почему.** Письма нужны, чтобы добрать недостающее: при недоборе есть смысл
выходить на связи. При достигнутой цели outreach не нужен. Это и есть содержание
шага 5 целевого потока.

**Рассмотренные альтернативы.** Генерировать письма всегда (как сейчас) —
отклонено: избыточный outreach при выполненной цели. Никогда не генерировать
автоматически — отклонено: не закрывает контур.

**Следствие.** Шаг черновиков перестаёт быть безусловным. Это уточнение фиксируется
MODIFIED-дельтой `request-fulfillment-execution`, чтобы спеки не противоречили
друг другу.

### Решение 3. Авто-триггер — свойство графа, а не ручное действие

**Выбор.** Триггер генерации не выносится в отдельную команду оператора: он
происходит в том же workflow сразу после поиска, до человеческой паузы.

**Почему.** Иначе недобор остался бы незакрытым до действия человека, а смысл
capability — автоматически закрывать контур «поиск → письма».

### Решение 4. Честность недобора

**Выбор.** При недостижимой цели workflow завершается с видимым остатком
(`Shortfall > 0`), а не с подставным результатом. Ошибка чтения заявки или
сохранения черновиков остаётся честной ошибкой шага.

**Почему.** `AGENTS.md` §3: выдуманный «полный» результат недопустим.

### Решение 5. Доменная привязка

Capability `request-shortfall` принадлежит контексту `request-fulfillment`. Недобор
не образует нового агрегата: это производное значение агрегата `request`
(root `request`), при необходимости оформляемое value object `request-shortfall`.
Доменных событий и policies не добавляется. Связи не меняются. Обновляются
`architecture/domain-catalog.yaml` (список capability) и `docs/domain-model.md`.

## Risks / Trade-offs

- **[Гейт меняет поведение существующих исполнений]** → Смягчение: ветка версионирована (`shortfall-gate`); прежние исполнения воспроизводятся без гейта.
- **[Цель заявки — свободный текст]** → Числовая цель графа берётся из `Params.LeadTarget`; согласование свободного `request-target` с числом — открытый вопрос.
- **[Недобор при недостижимой цели виден «вечно»]** → Это честное состояние: система не выдумывает лидов. Оператор решает, продолжить дозабор или отклонить.

## Migration Plan

1. Вычисление `Shortfall` в workflow после цикла поиска.
2. Версионированный гейт черновиков (`shortfall-gate`).
3. MODIFIED-дельта `request-fulfillment-execution` (согласование требования шага).
4. Обновление каталога и `docs/domain-model.md`.
5. Сквозная проверка: недобор → письма сгенерированы; цель достигнута → письма не генерируются; ноль лидов → писем нет.

**Откат.** Снятие гейта возвращает безусловную генерацию; `Shortfall` можно
оставить как наблюдаемое поле без последствий.

## Open Questions

1. **Источник числовой цели заявки.** `request-target` — свободный текст; нужен ли структурный числовой target в оффере (отдельное решение).
2. **Поведение при недостижимой цели.** Продолжать ли попытки добора при исчерпанном пуле или завершать с остатком — порог/стратегия за оператором.
