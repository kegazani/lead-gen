## Context

Мотивация — в `proposal.md`. Ниже только текущее состояние и ограничения, которые определяют подход.

- Примитив `jobs` (`backend/platform/jobs`) задаёт пять состояний и уже различает владельцев: хранилище переводит `queued` и пишет признак отмены, а `Runner.RunOnce` решает терминальный исход и зовёт `UpdateStatus`.
- Текущий `UpdateStatus(ctx, id, status, reason, code)` выполняет `SET status = $2 WHERE id = $1` — без проверки исходного состояния. Любой статус перезаписывается любым.
- `cancel_requested` пишется в хранилище (`Store.RequestCancel`) и читается в `Job`, но приложение его нигде не использует: остановку `running`-задания обеспечивает только in-process сигнал `CancelRegistry`.
- Развёртывание co-located: роли `api` и `worker` сервиса `lead-management` живут в одном процессе (`deploy/services.yaml`), реестр сигналов общий. Но каталог допускает раздельные процессы, и дизайн `add-job-control-and-progress` (Решение 1) обещает работу на границе шага по флагу в хранилище — это обещание не выполнено.
- Контракт-тест `internal/ports/contracttest/search_job_store.go` фиксирует текущую нестрогую семантику: он создаёт задание и переводит его `queued → done` напрямую, без взятия. Строгие переходы требуют правки контракта.
- Задание поиска — операционная запись, не доменный агрегат: owning bounded context — `lead-management`; новых сущностей, агрегатов и domain events не появляется, межконтекстных контрактов не меняется.

## Goals / Non-Goals

**Goals:**

- Состояние задания — единственный источник правды о его жизненном цикле; каждый переход легален, атомарен и наблюдаем.
- Терминальное состояние неизменяемо: позднее завершение или повторная отмена не переворачивают уже принятый исход.
- Отмена активного задания гарантирована как факт в хранилище, а не как сигнал, который может не дойти.
- Нет задания, «вечно» висящего в `running` без живого обработчика.
- Отмена отличима от падения в журнале, логах и метриках.

**Non-Goals:**

- Межпроцессная координация через брокер, lease/heartbeat и аренда владельца задания — вне объёма; согласование сирот опирается на текущий co-located однопроцессный деплой.
- Дозабор страниц незавершённого асинхронного обхода Firecrawl сверх уже отданного движком — вне объёма (как и в `add-job-control-and-progress`).
- Ограничение числа попыток повторной обработки — см. «Open Questions».

## Decisions

### Решение 1. Охраняемый переход как часть контракта хранилища

`jobs.Store.UpdateStatus` получает исходное состояние и становится проверкой перехода:

```
UpdateStatus(ctx, id string, from, to Status, reason, code string) error
```

Реализация выполняет `SET status = $to WHERE id = $id AND status = $from`; ноль затронутых строк означает отклонённый переход и возвращает sentinel `jobs.ErrTransitionRejected` (не ошибку хранилища). Так терминальная неизменяемость (`done`/`failed`/`cancelled` нельзя переписать, потому что `from` для них уже не совпадёт) и легальность переходов обеспечиваются данными, а не дисциплиной вызывающего.

Почему так, а не отдельным методом `Finish`: один вход для смены состояния означает, что любой новый вызывающий обязан объявить исходное состояние, — иначе переход не компилируется. `Runner` вызывает `UpdateStatus(ctx, id, StatusRunning, status, ...)`; отклонение трактует как «задание уже терминально» (info-лог), а не как сбой.

Альтернативы: (а) оставить сигнатуру и добавить проверку только в SQL для воркера — не защищает будущих потребителей; (б) ввести `Finish` рядом с `UpdateStatus` — оставляет неохраняемый `UpdateStatus` в API как ловушку. Обе отклонены.

**BREAKING** для `jobs.Store` и `ports.SearchJobStore`. Сейчас единственный потребитель — `lead-management`; контракт-тесты обновляются в рамках change.

### Решение 2. Решительная отмена: `RequestCancel` сам переводит `running` в `cancelled`

`RequestCancel` перестаёт быть только «заявкой» для активного задания:

```
queued   -> cancelled                       (без изменений)
running  -> cancelled + cancel_requested = TRUE
terminal -> no-op
```

Терминальное решение принимает хранилище в момент отмены, а не воркер потом. Журнал и UI показывают `cancelled` немедленно, независимо от того, дошёл ли сигнал и жив ли обработчик. `cancel_requested` сохраняется как durable-признак для живого обработчика (Решения 3 и 4). Позднее завершение воркера отклоняется охраной из Решения 1.

Сохранение результата не страдает: `RecordResult`, `RecordBudget` и `RecordProgress` статус не меняют и остаются допустимыми для `cancelled`; обработчик при обнаружении отмены по-прежнему досылает ссылки на найденные компании через отсоединённый контекст.

Альтернатива — кооперативная схема (флаг + перевод воркером) с lease/reaper. Отклонена: отмена остаётся невидимой до реакции воркера, а осиротевшее задание требует отдельного механизма аренды, которого в объёме нет.

### Решение 3. Обработчик распознаёт отмену по данным

Добавляется чтение задания из хранилища: `jobs.Store.FindByID(ctx, id) (*Job, error)` (отсутствие — `jobs.ErrNotFound`). `Runner.RunOnce` после взятия запускает лёгкий наблюдатель: пока обработчик работает, он периодически (интервал опроса раннера) читает задание и, увидев `Status == cancelled` или `CancelRequested == true`, отменяет контекст задания.

Это закрывает сразу три разрыва: гонку «взято → сигнал зарегистрирован», недоставленный сигнал в том же процессе и раздельные процессы api/worker. Приложение не меняет границы шагов — оно уже уважает `ctx.Err()` между целями, URL и страницами; наблюдатель делает эти границы точками распознавания отмены из хранилища. Реестр `CancelRegistry` остаётся как мгновенный путь (срабатывает раньше опроса), но перестаёт быть единственным.

Альтернатива — вызывать `FindByID` из прикладного слоя на каждой границе шага. Отклонена: размазывает гарантию жизненного цикла по контексту и требует правок в `app`, тогда как гарантия принадлежит примитиву.

### Решение 4. Согласование осиротевших заданий при старте воркера

Добавляется `jobs.Store.ReconcileRunning(ctx) (int, error)`: перед входом в цикл `Runner.Run` переводит все `running`-задания в терминальное или обратно в очередь:

```
running + cancel_requested = TRUE  -> cancelled
running + cancel_requested = FALSE -> queued   (повторная обработка, attempts сохраняются)
```

Вызывается один раз при запуске роли `worker`, до первого `TakeQueued`, поэтому «живого» обработчика в этом процессе ещё нет и согласование не может отобрать задание у работающего воркера. Повторная обработка безопасна: карточки ищутся и сохраняются идемпотентно по домену (`saveCompany`), а ссылки результата перезаписываются.

Ограничение (осознанное): при нескольких репликах воркера стартовое согласование одного процесса затронуло бы задания другого. Это Non-Goal; при масштабировании заменяется на lease/heartbeat, не меняя спек.

### Решение 5. Отмена — не падение в наблюдаемости

`RunSearch.Handle` различает sentinel `jobs.ErrCancelled`: пишет info-лог «задание отменено» и метрику исхода `cancelled` вместо `failed`, не записывает событие ошибки. `Runner` при `ErrTransitionRejected` после отмены не повышает уровень лога до ошибки — это ожидаемое следствие Решения 2, а не сбой.

### Решение 6. Схема хранилища

Новая миграция `green/0008_job_state_transitions.sql`:

- `CHECK (status IN ('queued','running','done','failed','cancelled'))` на `search_job.status` — недопустимое значение состояния отклоняется на уровне данных;
- частичный индекс `(created_at, id) WHERE status = 'queued'` — под выбор из очереди `selectQueuedSearchJobID`.

Дефолты колонок не меняются; существующие строки валидны, поэтому миграция аддитивна.

## Risks / Trade-offs

- **[Решительная отмена уменьшает окно результата]** Отмена переводит задание в `cancelled` до того, как воркер дошлёт уже добытые страницы → сохранение опирается на то, что `RecordResult`/`RecordProgress` разрешены для `cancelled`, а дренаж уже полученных страниц остаётся. Митигация: явный предел числа дренируемых страниц (задача в tasks) и тест «отмена во время обхода сохраняет карточки».
- **[Повторная обработка дублирует расход кредитов]** Согласование возвращает осиротевшее задание в очередь → возможен повторный обход и расход. Митигация: только осиротевшие `running` (а не успешные), идемпотентное сохранение карточек; предел попыток — Open Question.
- **[Охрана может замаскировать настоящий сбой записи]** `ErrTransitionRejected` и ошибка хранилища различаются явно: первое — info, второе — ошибка, останавливающая цикл раннера.
- **[Правка контракта `jobs.Store` — BREAKING]** Единственный потребитель сегодня — `lead-management`; изменение и тесты идут одним change, других вызывающих нет.
- **[Гонка двух воркеров при согласовании]** Вне объёма (Non-Goal); при нескольких репликах требуется lease.

## Migration Plan

1. Миграция `0008` (аддитивна: `CHECK` + индекс) применяется вместе с кодом; откат не требуется.
2. Правка контракта `jobs.Store` и реализаций (`memory`, `postgres`) идёт одним коммитом с обновлением контракт-тестов, иначе сборка развалится на несовпадении сигнатуры.
3. Порядок включения: сначала охраняемые переходы и решительная отмена, затем наблюдатель отмены, затем согласование сирот — каждый шаг покрыт тестами.
4. Откат кода: прежняя версия трактует `cancelled` как терминальное и не берёт такие строки в очередь, поэтому откат безопасен (как и в `add-job-control-and-progress`).
