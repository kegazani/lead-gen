# Дизайн уточнения извлечения телефонов

## Context

Мотивация — в `proposal.md`. Здесь только то, что важно для решения.

Извлечение телефонов сосредоточено в
`backend/contexts/lead-management/internal/app/`:

- `extract.go`: `phoneRe` находит кандидатов, `ExtractPhones` нормализует
  (только цифры) и отсеивает кандидатов короче семи цифр.
- `extract_layers.go`: слой 2 применяет `ExtractPhones` к Markdown; LLM-слой
  (`contactCandidatesFromExtract`) нормализует телефон из `crawl.ContactCandidate`
  той же функцией `NormalizePhone`.

Текущий `phoneRe` — `\+?[0-9(][0-9 ()\-.]{5,}[0-9]`. Он пропускает даты
(`2024.01.01` → `20240101`), цены, годы и прочие числовые последовательности,
потому что не требует ни телефонного разделителя, ни ведущего `+`, а длина
«не короче семи цифр» такие строки не отсеивает.

Существующий тест `TestExtractPhones` ждёт извлечения `+1 (234) 567-8901`,
`555-1234` и `(415) 555-2671` — то есть кандидатов с ведущим `+`, дефисом или
скобками.

## Goals / Non-Goals

**Goals:**

- Перестать принимать даты и прочие не-телефонные числовые последовательности за
  телефоны.
- Сохранить извлечение настоящих телефонов, включая уже покрытые тестом формы.
- Единая проверка кандидата для regex-слоя и LLM-слоя.

**Non-Goals:**

- Не меняем формат хранения телефона (по-прежнему только цифры).
- Не чистим уже извлечённые ранее мусорные телефоны в существующих карточках.
- Не вводим внешний сервис валидации номеров и не определяем страну/формат
  оператора связи.

## Decisions

### Решение 1. Проверка кандидата как отдельная функция

Вводится проверка телефонного кандидата (например, `isPhoneCandidate(raw string)
bool`), которая применяется в `ExtractPhones` до нормализации. Отдельная функция,
а не усложнение одного regex, потому что часть условий (отсев дат, счёт цифр)
проверяются по уже найденной строке и не выражаются единственным RE2-шаблоном
читаемо.

**Почему так:** единая точка правила; легко покрыть табличными тестами
«мусор/телефон».

### Решение 2. Условия отсева

Проверка кандидата отсеивает последовательности, не являющиеся телефоном:

- число цифр вне диапазона 7–15 (нижняя граница уже есть, добавляется верхняя —
  предел E.164);
- дата в узнаваемой форме: `ГГГГ.ММ.ДД`, `ДД.ММ.ГГГГ`, `ДД.ММ.ГГГГ` с дефисом или
  точкой, `ГГГГ-ММ-ДД`;
- кандидат без телефонного разделителя (пробел, дефис, скобки) и без ведущего
  `+`: одиночная слитная последовательность цифр телефоном не считается.

**Почему так:** именно эти три класса дают наблюдаемый мусор. Ведущий `+`,
скобки, дефисы и пробелы остаются признаками телефона и сохраняют уже
существующий тест зелёным.

**Рассмотренная альтернатива.** Разрешить точку как телефонный разделитель
(формат `123.456.7890`) — отклонено: точка конфликтует с датами в формате
`ДД.ММ.ГГГГ` и даёт основной наблюдаемый мусор. Точность важнее полноты для этого
источника (замечание оператора — о лишних цифрах, а не о пропущенных номерах).

**Trade-off.** Номер, записанный слитно без `+` и разделителей (например,
`88005553535`), не будет извлечён. Это осознанный выбор в пользу точности; при
необходимости правило ослабляется точечно.

### Решение 3. Применение к LLM-кандидатам

Телефон из LLM-экстракции (`contactCandidatesFromExtract`) проходит ту же
проверку: не-телефонный кандидат отбрасывается, как и в regex-слое.

**Почему так:** иначе мусор придёт другим слоем, и правило окажется дырявым.

### Решение 4. Тесты

Табличные тесты на проверку кандидата и на `ExtractPhones`:

- мусор не извлекается: `2024.01.01`, `2024-01-01`, `01.02.2023`, `12,5`,
  `2024`, длинная слитная последовательность из 20 цифр;
- телефоны извлекаются: `+1 (234) 567-8901` → `12345678901`, `555-1234` →
  `5551234`, `(415) 555-2671` → `4155552671`, `+7 495 123-45-67` →
  `74951234567`.

**Почему так:** сценарии — это и есть проверяемое поведение; таблица делает
границы правила явными.

## Risks / Trade-offs

- **Потеря настоящих номеров.** Слитно записанные номера без `+` и разделителей
  перестанут извлекаться. Компенсация: осознанный выбор в пользу точности,
  правило легко ослабить; тест фиксирует текущее поведение.
- **Даты не по шаблону.** Нестандартная запись даты всё же пройдёт проверку.
  Компенсация: правило ловит узнаваемые формы; расширение — по мере наблюдений.
- **Старые данные.** Уже извлечённые мусорные телефоны останутся в карточках.
  Компенсация: явно вынесено в Non-Goals; очистка — отдельная задача.
- **Два слоя извлечения.** Забыть применить проверку к LLM-слою. Компенсация:
  единая функция и тесты на оба слоя.

## Migration Plan

1. Ввести проверку кандидата и применить её в `ExtractPhones`.
2. Применить её в `contactCandidatesFromExtract` для телефона.
3. Добавить табличные тесты; убедиться, что `TestExtractPhones` зелёный.
4. Прогнать тесты контекста `lead-management`.

Откат — возврат прежнего `ExtractPhones`; данные не меняются.
