## Context

Мотивация — в `proposal.md`. Ниже — текущее состояние и ограничения, определяющие подход.

- Durable-исполнение заявки введено change `temporal-execution-platform`: workflow `request-fulfillment` живёт в `backend/contexts/request-fulfillment/internal/adapters/workflow`, activities — тонкие адаптеры к application services; рантайм — platform-primitive `backend/platform/workflow` (Temporal SDK).
- Граф (`fulfillment.go`) сейчас: `validated → processing → поиск → (добор) → черновики писем → пауза утверждения → fulfilled`. Все activities используют одни `ActivityOptions{StartToCloseTimeout: 30s, MaximumAttempts: 3}`. Пауза утверждения — `workflow.GetSignalChannel(...).Receive` без таймера. Добор складывает `state.Found += result.Found` по раундам. Граф версионируется (`changeTopUpLoop`, `changeEmailDrafts`, `changeApprovalGate`).
- Переходы двигает aggregate root `request` (`internal/domain/request.go`): `applyTransition` отвергает терминальные статусы (`ErrTerminalState`), недопустимые переходы (`ErrInvalidTransition`) и переход без причины (`ErrReasonRequired`). Повторное применение, когда заявка уже в целевом статусе, сейчас даёт `ErrInvalidTransition` — activity возвращает ошибку и роняет workflow после потери ack.
- `SearchLeads` различает только `leadsearch.ErrRejected` как non-retryable; `ports.ErrRequestNotFound` и «контракт не подключён» идут обычной retryable-ошибкой.
- `starter.go` при любой ошибке `Start` возвращает `ports.ErrWorkflowUnavailable`, а HTTP-слой переводит его в 503 — в том числе при `WorkflowExecutionAlreadyStarted`.
- Репозиторий заявок реализован только in-memory (`internal/adapters/persistence/inmemory`); PostgreSQL-адаптер отсутствует, миграций у контекста нет. Образец для подражания — `lead-management` (`internal/adapters/persistence/postgres` + `migrations/green` + `internal/ports/contracttest`, suite под `LEADGEN_POSTGRES_TEST_DSN`, цель `make test-postgres`).
- `platform/workflow.NewWorker` создаёт воркер с пустыми `worker.Options{}`; graceful drain опирается на закрытие `interrupt`-канала без `WorkerStopTimeout`.
- `main.go` вызывает `platformworkflow.Dial` один раз; при транзиентном сбое рантайм помечается выключенным на процесс целиком. Единой пробы готовности нет: у сервисов есть только `/healthz` (liveness).
- HTTP-клиенты `integration-platform`: `firecrawl.New` и `openai.New` при `nil` подставляют `http.DefaultClient` (нулевой таймаут).
- Домен: owning context — `request-fulfillment`, aggregate root — `request`. Новых сущностей, агрегатов, domain events, policies и межконтекстных контрактов change не вводит; добавляются только capability `request-fulfillment-execution` (owner `request-fulfillment`) и `integration-call-resilience` (owner `integration-platform`).

## Goals / Non-Goals

**Goals:**

- Повторная доставка activity и повторный старт исполнения безопасны: workflow не падает и не отвечает 503 из-за уже достигнутого состояния.
- Постоянные отказы не тратят попытки, транзиентные — ретраятся.
- Длинные activities не висят дольше заданного и не расходуют внешние ресурсы дважды без нужды.
- Человеческая пауза завершается в обозримый срок и различает «ждём решение» и «срок истёк».
- Нуль лидов наблюдаем и не маскируется успехом без решения оператора.
- Состояние заявки и её событий переживает рестарт; рантайм исполнения стартует устойчиво и честно сообщает готовность.

**Non-Goals:**

- Перенос самописного движка `search-job-lifecycle` на Temporal — вне объёма (как и в `temporal-execution-platform`).
- Миграция уже бегущих исполнений на новую структуру графа «на лету» — вместо этого версионирование сохраняет воспроизводимость старых исполнений (см. Risks).
- Полная персистентность производных артефактов (черновики писем, вложения) — вне объёма; фиксируется как риск.
- Мультитенантное секционирование Temporal и self-hosted кластер — вне объёма.
- Изменение доменной модели заявки: никаких новых сущностей, событий и контрактов.

## Decisions

### Решение 1. Идемпотентность — свойство агрегата, activity остаётся тонкой

Правило «повторное применение перехода, когда заявка уже в целевом статусе, — успех/no-op» живёт в aggregate root `request` (`applyTransition`), а не в activity. Это сохраняет принцип «activity без доменной логики» и делает поведение одинаковым для workflow, ручного API и любых будущих вызывающих. При совпадении целевого и текущего статуса переход возвращает успех без `version++` и без эмиссии события; доменное решение (validation decision) повторно не создаётся. Терминальное состояние и переходы в *другой* статус по-прежнему отвергаются.

Альтернатива — проверять статус в activity и глотать ошибку — отклонена: это переносит доменное правило в адаптер и расходится между вызовами.

**Спека:** требование добавлено в `client-request` (статусная модель заявки).

### Решение 2. Классификация отказов на границе activity

Каждый переход-activity переводит доменные sentinels (`domain.ErrInvalidTransition`, `domain.ErrTerminalState`, `domain.ErrReasonRequired`) и `ports.ErrRequestNotFound` в `temporal.NewNonRetryableApplicationError`; `SearchLeads` расширяет текущую логику: `leadsearch.ErrRejected` (уже есть), `ports.ErrRequestNotFound` и постоянный «контракт не подключён» — non-retryable, а транзиентная недоступность владельца (`leadsearch.ErrUnavailable` в смысле «сбой транспорта») — retryable. Чтобы различить «контракт не подключён» и «владелец недоступен», «контракт не подключён» получает отдельный sentinel-отказ (конфигурационная ошибка), а не переиспользует `ErrUnavailable`.

Альтернатива — полагаться на `MaximumAttempts = 3` для всех ошибок — отклонена: доменный отказ повторяется впустую и задерживает исход.

### Решение 3. Идемпотентный старт: `Start` возвращает признак «уже запущено»

`platformworkflow.Client.Start` распознаёт `WorkflowExecutionAlreadyStarted` и возвращает `Run` существующего исполнения вместе с признаком `AlreadyStarted` (или отдельным sentinel’ом), а не ошибку. Адаптер `starter.go` переводит это в исход порта «уже запущено» с `WorkflowRun` существующего исполнения; HTTP-слой отвечает 200/409 с явным исходом, но **не** 503. `ports.ErrWorkflowUnavailable` остаётся только для настоящей недоступности рантайма.

### Решение 4. Уникальные лиды при доборе

Workflow ведёт `seen map[string]struct{}` по `leadsearch.LeadRef.ID`; `state.Found` становится числом уникальных лидов. `searchResult` по-прежнему может нести сырые счётчики раунда, но наблюдаемое состояние и условие остановки цикла считают уникальные. Это снимает двойной расход и ложное достижение цели при пересекающихся раундах.

### Решение 5. Раздельные опции длинных и коротких activities

Вводятся два набора `ActivityOptions`: короткие переходы (`StartProcessing`, `FulfillRequest`, `CancelRequest`) — малый `StartToCloseTimeout` и без heartbeat; длинные (`SearchLeads`, `DraftEmails`) — `StartToCloseTimeout` в минутах и `HeartbeatTimeout` с периодическим `activity.RecordHeartbeat` внутри адаптера. Значения — конфигурируемы, с осмысленными умолчаниями; пропущенный heartbeat даёт повтор activity, а не вечное ожидание.

### Решение 6. Ограниченная пауза утверждения и согласованный предел исполнения

Пауза утверждения реализуется `workflow.NewSelector`: сигнал `approval-decision` и `workflow.NewTimer(ctx, approvalTTL)`. Сработал таймер — заявка переходит в `cancelled` с причиной «утверждение: срок истёк» (через `CancelRequest`). `approvalTTL` конфигурируем (по умолчанию 7 дней). При старте исполнения задаётся `WorkflowExecutionTimeout`, не меньший `approvalTTL`, чтобы таймер успевал сработать раньше предельного времени исполнения. Новая ветка гейта версионируется (`GetVersion`), чтобы старые исполнения воспроизводились детерминированно.

### Решение 7. Нуль лидов — отдельная наблюдаемая фаза и запрет молчаливого успеха

Добавляется фаза `no-leads` и поле в `Status` (и в `ports.WorkflowStatus`), выставляемые, когда уникальных лидов ноль. Шаг генерации черновиков при нуле лидов не запускается (уже так). Заявка при нуле лидов **не** переходит в `fulfilled` автоматически: путь к `fulfilled` проходит через гейт утверждения, и оператор должен явно одобрить пустой результат; без сигнала — по Решению 6 исход `cancelled` по сроку. Так «0 лидов» виден в API/консоли и не превращается в молчаливый успех.

### Решение 8. Персистентный репозиторий заявок по образцу `lead-management`

В контексте `request-fulfillment` добавляется `internal/adapters/persistence/postgres` (реализация `ports.RequestRepository` и unit-of-work), `migrations/green` с таблицами заявки и outbox (и при необходимости — черновиков) и контрактный suite `internal/ports/contracttest`, общий для in-memory и PostgreSQL. Оптимистичная блокировка (`Save(ctx, request, expectedVersion)`) переносится в SQL-`UPDATE ... WHERE version = $expected`; ноль строк — `ports.ErrVersionConflict`. Транзакция записи агрегата и outbox — через `UnitOfWork.WithinTransaction`. Паттерн копируется с `lead-management`: фабрика suite, `LEADGEN_POSTGRES_TEST_DSN`, `TestMain` с пулом, применение миграций загрузчиком `backend/platform/migrate` с `OwnSchema`. In-memory остаётся dev-реализацией.

### Решение 9. Устойчивость воркера и graceful drain

`platformworkflow.WorkerOptions` расширяется: `WorkerStopTimeout`, лимиты конкурентности (workflow и activity), обработчик фатальных ошибок. `NewWorker` прокидывает их в `worker.Options`. `Run` по отмене контекста инициирует `Worker.Stop()` и даёт завершиться взятым задачам в пределах `WorkerStopTimeout`.

### Решение 10. Проба готовности и её источник

Сервис `request-fulfillment` (и, где нужно, другие) отдаёт `/readyz`; готовность вычисляется по состоянию рантайма исполнения: если Temporal доступен — 200, иначе — 503. `/healthz` остаётся liveness и не зависит от Temporal. Состояние рантайма (доступен/недоступен) — единый атомарный признак, обновляемый при подключении и при ошибках рантайма.

### Решение 11. Ретрай подключения к Temporal при старте

Подключение `platformworkflow.Dial` оборачивается в ретрай с backoff в пределах настроенного бюджета (число попыток/задержка). Транзиентный сбой не помечает рантайм выключенным навсегда; после исчерпания попыток сервис работает в режиме деградации, явно логирует это, а `/readyz` сообщает о неготовности. Признак доступности рантайма (Решения 3 и 10) отражает фактическое состояние.

### Решение 12. Явный таймаут HTTP-клиентов провайдеров

`firecrawl.New` и `openai.New` при отсутствии переданного клиента создают `*http.Client` с ограниченным `Timeout`, а не `http.DefaultClient`. Запросы выполняются через `NewRequestWithContext`, поэтому дедлайн и отмена контекста прекращают вызов. Таймаут клиента согласуется с `StartToCloseTimeout`/heartbeat длинных activities, чтобы клиент не переживал activity.

## Risks / Trade-offs

- **[Миграция уже бегущих исполнений при деплое]** Изменение графа (новая ветка гейта, таймер паузы, новые activities) ломает детерминированный replay, если применить его к исполнениям, начатым до деплоя. Компенсация — версионирование: все новые ветки закрыты `workflow.GetVersion` с `DefaultVersion`, означающим прежнее поведение; старое исполнение воспроизводится без таймера и без новых опций. Отдельный риск, который требуется зафиксировать явно: при использовании `DefaultVersion` для *новых* исполнений гейт утверждения может оказаться снят — поэтому версии для новых исполнений задаются явными значениями (`GetVersion` → 1), а `DefaultVersion` остаётся только веткой воспроизведения старых. Тест `TestFulfillmentReproducesOldGraph` расширяется на новые ветки.
- **[Стоимость повторного краулинга]** Retryable-повтор `SearchLeads` (после подключения heartbeat и таймаутов) и идемпотентный повтор перехода могут привести к повторному обходу и повторному расходу кредитов Firecrawl. Компенсация: дедуп лидов по id (Решение 4) убирает двойной учёт; повтор поиска ограничен политикой повтора; бюджет Firecrawl (`firecrawl-credit-budget`) остаётся жёстким предохранителем.
- **[Персистентность карточек черновиков]** Письма-черновики живут в `EmailDraftStore`, который в change не персифицируется: после рестарта воркера черновики, сгенерированные до рестарта, могут исчезнуть, хотя заявка и её события сохранятся. Осознанно вынесено за объём: черновик — производный материал, его можно пересоздать; при необходимости — отдельный change. Риск фиксируется, чтобы не считать durable-исполнение полностью восстановимым.
- **[Неверная классификация отказов]** Если транзиентный отказ ошибочно пометить non-retryable, заявка упадёт раньше времени. Компенсация — узкие sentinels (только доменные отказы и постоянные отказы поиска), тесты на retryable/non-retryable для каждого класса.
- **[Таймаут HTTP рвёт долгий обход]** Слишком малый таймаут клиента может обрывать законный долгий `crawl`. Компенсация — таймаут клиента согласован с `StartToCloseTimeout` и heartbeat; значения конфигурируемы.
- **[Персистентный адаптер и мультипроцессность]** Оптимистичная блокировка должна одинаково работать при co-location и разделении процессов. Компенсация — единый контрактный suite для in-memory и PostgreSQL, проверяющий конфликт версий и атомарность outbox.
- **[Ложная неготовность при старте]** `/readyz` вернёт неготовность, пока идёт ретрай подключения. Это ожидаемое поведение (трафик не направляется до готовности); важно, чтобы `/healthz` при этом оставался 200.

## Migration Plan

1. **Миграции аддитивны** (`migrations/green`, по образцу `lead-management`): применяются вместе с кодом, откат не требуется. Существующие данные в памяти не мигрируются — durable-состояние начинается с чистого персистентного хранилища.
2. **Порядок включения (без breaking для ручных потоков):** сначала идемпотентность агрегата и классификация отказов → затем идемпотентный старт → затем раздельные опции activities и heartbeat → затем ограниченная пауза и фаза «0 лидов» → затем персистентный адаптер и прогон контрактного suite → затем устойчивость воркера, `/readyz` и ретрай подключения.
3. **Версионирование workflow:** новые ветки закрываются `workflow.GetVersion`; для новых исполнений — явная версия 1, для старых — `DefaultVersion`. Деплой не перезапускает бегущие исполнения; они доигрывают по старой ветке.
4. **Откат кода:** прежняя версия не знает новых activities/полей; так как граф ветвится по `GetVersion`, откат безопасен, а персистентные данные читаются прежним адаптером не будут — откат подразумевает возврат к in-memory и не теряет корректность домена.
5. **Проверки:** `go -C backend/platform test ./...`, `go -C backend/contexts/request-fulfillment test ./...`, `make test-postgres` (контрактный suite под `LEADGEN_POSTGRES_TEST_DSN`), `go -C tools/archlint run .`, `openspec validate --all --strict`.

## Open Questions

- Точные значения `approvalTTL` и `WorkflowExecutionTimeout` для продакшена (7 дней как умолчание согласовано; уточняется конфигурацией деплоя, не меняет спеки).
- Бюджет ретрая подключения к Temporal (число попыток и потолок задержки) — уточняется при настройке деплоя.
- Нужен ли отдельный сигнал для «одобрить пустой результат» сверх обычного `approval-decision` или достаточно фазы `no-leads` плюс существующего сигнала — решается при реализации, не меняя требований.
- Персистентность черновиков писем (`EmailDraftStore`) — отдельный change при подтверждённой потребности.
