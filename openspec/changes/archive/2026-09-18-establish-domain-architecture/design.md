## Context

Мотивация описана в `proposal.md`. Сейчас `docs/system-map.md` назначает владельцами сущностей процессы (`api`, `worker`, `sender`), хотя те же процессы размещают несколько независимых моделей. `docs/architecture.md` группирует функциональность по BRD-движкам, а `migrate-platform-to-go` предлагает общие каталоги `internal/domain`, `internal/app` и `internal/ports`; такая структура быстро превращается в общий монолит без проверяемых границ.

Ограничения:

- production-кода и main specs ещё нет; источники поведения — дельта-спеки активных changes;
- процессы `api`, `ingest`, `sender`, `worker`, `chains`, `schedule` остаются единицами развёртывания;
- красная и зелёная зоны, обязательное утверждение и запрет прямых вызовов движков не пересматриваются;
- один разработчик должен понимать и проверять архитектуру локально без отдельного сервиса или сетевого registry.

## Goals / Non-Goals

**Goals:**

- Сделать bounded context основной единицей владения моделью и правилами.
- Дать человеку и инструменту один каталог контекстов, aggregates, aggregate roots, entities/value objects, domain events, policies, capability и связей.
- Отделить доменную декомпозицию от процессов, BRD-движков и поставщиков.
- Подготовить context-first структуру Go-кода до создания корневого `go.mod` и пакетов приложения; `archlint` при этом получает изолированный `tools/archlint/go.mod`.
- Реализовать весь добавляемый исполняемый архитектурный tooling на Go без Python-кода и Python runtime.
- Обнаруживать архитектурный дрейф одной локальной командой.

**Non-Goals:**

- Не менять поведение существующих продуктовых capability.
- Не проектировать таблицы, API-поля и внутреннее устройство агрегатов до уровня Go-типов; при этом границы aggregates, их roots, входящие entities/value objects, публикуемые domain events и применяемые policies фиксируются явно.
- Не превращать каждый context в отдельный сервис: модульный монолит остаётся базовой формой.
- Не вводить event sourcing, универсальную шину событий или code generation.
- Не архивировать change в рамках реализации: архивация требует отдельного подтверждения.

## Decisions

### 1. Bounded context — граница модели, процесс — граница эксплуатации

Каталог вводит контексты `identity-access`, `data-governance`, `lead-management`, `audience`, `content-production`, `outreach-orchestration`, `message-delivery`, `engagement-observation`, `sales-workflow`, `community-intelligence`, `publishing`, `analytics`, `billing` и `integration-platform`.

Контекст владеет терминами, сущностями и инвариантами. Процесс только размещает application service контекста. Поэтому один контекст может исполняться в `api` и `worker`, а `worker` может размещать несколько контекстов, не превращаясь в владельца общей модели.

Альтернатива — считать каждый процесс bounded context. Отклонена: `worker` объединяет импорт, генерацию документов, Telegram, отчётность и CRM без общего языка и жизненного цикла. Альтернатива — контекст на каждую capability. Отклонена: это создаёт десятки искусственно мелких границ и не отражает совместное владение моделью.

### 2. Каталог — канонический источник структуры, документы и диаграммы — представления

`architecture/domain-catalog.yaml` хранит:

- `contexts`: идентификатор, русское имя, классификацию `core|supporting|generic`, назначение, primary capability, deployment targets и contracts;
- `aggregates`: стабильный идентификатор, owning context, единственный aggregate root, входящие entities и value objects, а также кратко сформулированные invariants;
- `entities` и `value_objects`: стабильный идентификатор, owning context и aggregate; для entity также зона и тип хранилища, а для value object — семантика равенства;
- `domain_events`: стабильный идентификатор, declaring context, producing aggregate и contracts потребителей;
- `policies`: стабильный идентификатор, owning context, входные события/команды и инициируемое доменное действие;
- `relationships`: upstream/downstream, паттерн отношений, интеграционный способ и контракт;
- `required_diagrams`: четыре обязательных представления.

Файл записывается в JSON-синтаксисе, который является допустимым YAML 1.2. Это позволяет Go-версии `archlint` читать его через `encoding/json` без стороннего YAML-парсера, сохраняя требуемое имя `.yaml` и возможность позднее перейти к обычному YAML без изменения схемы.

Альтернатива — сделать Markdown-таблицы источником истины. Отклонена: однозначно проверить уникальность и ссылки сложно. Альтернатива — генерировать все документы. Отклонена: содержательная проза не сводится к шаблону, а generated-файлы усложнят небольшому проекту ревью.

### 3. Схема отвечает за форму, Go-версия `archlint` — за семантику

JSON Schema запрещает неизвестные поля, фиксирует шаблоны идентификаторов и перечисления. `tools/archlint/` реализуется на Go и проверяет межобъектные инварианты, которые неудобно или невозможно выразить схемой:

- уникальность идентификаторов и единственного владельца;
- ровно один aggregate root в каждом aggregate, принадлежность entities/value objects одному aggregate и совпадение owning context;
- покрытие каждого context хотя бы одним aggregate;
- корректность producing aggregate у domain events и ссылок policies на события, команды и доменные действия;
- существование всех ссылок;
- ровно один primary context для каждой capability из активных дельта-спек и main specs;
- отсутствие self-loop и повторяющихся relationships;
- наличие четырёх диаграмм и маркеров всех контекстов, упомянутых каждой диаграммой.

Инструмент собирает все ошибки и возвращает их одним запуском. `tools/archlint/go.mod` изолирует инструмент от будущего корневого модуля приложения; команды запуска и тестов используют стандартный Go toolchain (`go -C tools/archlint run .`, `go -C tools/archlint test ./...`). Python-код и Python runtime запрещены. Инструмент не требует сети и production-зависимостей.

Альтернатива — shell-набор из `rg` и `jq`. Отклонена: сообщения об ошибках и проверка вложенной модели становятся хрупкими. Полный JSON Schema validator не добавляется как обязательная зависимость; валидатор реализует используемое подмножество схемы и сверяет саму схему с `$schema`/`$id`.

### 4. Межконтекстные связи направлены по владельцу модели

`upstream` владеет контрактом и семантикой, `downstream` потребляет. Используются паттерны `customer-supplier`, `conformist`, `published-language` и `anticorruption-layer`; интеграции ограничены `command`, `event`, `query` и `policy`.

Чужие entity-типы через границу не передаются. Контракт использует собственный DTO или опубликованное событие. Поставщики находятся за `integration-platform` и anti-corruption layer, но этот контекст не владеет бизнес-решениями о повторах, согласии или утверждении.

Альтернатива — разрешить общую `internal/domain` модель. Отклонена: она делает владельца неразличимым и создаёт циклические импорты.

### 5. Go-код получает context-first дерево

Целевая форма:

```text
internal/
  contexts/<context-id>/
    domain/
    app/
    ports/
    adapters/
  platform/
  composition/
cmd/<process>/
```

`domain` не импортирует `app`, `ports`, `adapters`, `platform` или другой context. Межконтекстный вызов идёт через контракт, объявленный владельцем, и wiring в `composition`. Процессные команды выбирают нужные application services, но бизнес-код не импортирует `cmd`.

Внутри `domain` aggregate root является единственной точкой изменения aggregate; entities не покидают aggregate как изменяемые ссылки, value objects сравниваются по значению, domain events фиксируют уже произошедшие доменные факты, а policies реагируют на команды или события и инициируют следующий доменный шаг. Эти понятия обязательны в модели и каталоге, но не предписывают event sourcing.

Альтернатива — общие `internal/domain`, `internal/app`, `internal/ports`. Отклонена: технический слой становится первой осью навигации, а контекстные границы невозможно проверить простым правилом импортов.

### 6. Четыре диаграммы отвечают на разные вопросы

1. `bounded-context-map.puml` — все контексты и их группы.
2. `context-relationships.puml` — направленные зависимости и контракты.
3. `outreach-flow.puml` — сквозной поток от пула и кампании до утверждённой отправки и обратного события.
4. `data-ownership.puml` — владение сущностями и пересечение красной, зелёной и аналитической зон.

Диаграммы хранят стабильные context-маркеры `CTX:<context-id>`, чтобы `archlint` мог проверять ссылки без парсинга полного языка PlantUML.

### 7. Foundational change архивируется до зависимых реализационных changes

После выполнения и проверки `establish-domain-architecture` архивируется отдельным подтверждённым шагом. Это создаёт main spec `domain-architecture`. Затем реализационные changes, прежде всего `migrate-platform-to-go`, могут ссылаться на неё как на действующую capability.

Это уточняет, но не отменяет правило `archive-order-and-rule-deltas`: создатель capability архивируется до changes с `MODIFIED`. `full-enterprise-core-scope` сохраняет приоритет перед `telegram-community-digest`; два независимых foundational change не обязаны искусственно упорядочиваться между собой, если не меняют одну capability.

## Risks / Trade-offs

- **[Четырнадцать контекстов кажутся избыточными до появления кода]** → контексты не становятся сервисами; объединение допустимо отдельным change после появления доказанной общей модели.
- **[Каталог и проза разойдутся]** → каталог объявлен каноническим, а `archlint` проверяет ссылки и обязательные диаграммы; ревью смысловой прозы остаётся человеческим.
- **[JSON-синтаксис в `.yaml` менее удобен для ручного редактирования]** → цена принята ради нулевых зависимостей валидатора; формат остаётся стандартным YAML 1.2 и может быть механически преобразован позднее.
- **[Проверка capability читает незавершённые changes]** → `archlint` учитывает только каталоги с `specs/**/spec.md` и main specs, дедуплицируя идентификаторы; документные changes без спек не создают ложных записей.
- **[Контекстная граница может оказаться неверной при реализации]** → перенос владения оформляется отдельным OpenSpec change с обновлением каталога, диаграмм и migration plan, а не скрытым перемещением пакетов.

## Migration Plan

1. Создать каталог, схему и Go-версию `archlint`; добиться успешной проверки текущих capability, aggregates, владельцев, domain events и policies.
2. Создать модель домена с bounded contexts, aggregates, aggregate roots, entities/value objects, domain events и policies, а также четыре диаграммы как представления каталога.
3. Привести BRD, архитектуру и карту системы к трём разным осям: context, process, engine.
4. Добавить context-first правила в `openspec/config.yaml` и согласовать артефакты `migrate-platform-to-go`.
5. Уточнить процедурный change порядка архивации.
6. Выполнить `archlint`, строгую OpenSpec-валидацию и проверку ссылок.
7. После отдельного подтверждения архивировать `establish-domain-architecture`; миграцию production-кода платформы на Go начинать только после появления main spec. Самостоятельный Go-модуль `archlint` создаётся и проверяется внутри этого foundational change.

Откат до появления кода состоит в удалении добавленных архитектурных артефактов и возврате точечных правок документов. После создания Go-пакетов откат выполняется отдельным change с миграцией импортов; молчаливый возврат к общему `internal/domain` запрещён.
