## Context

Мотивация и объём — `proposal.md`. Состояние, определяющее подход:

- Роль `worker` сервиса `analytics` уже читает очередь брокера
  (`analytics.analytics-event`) транспортным адаптером
  `internal/adapters/transport` и наполняет проекцию (`readmodel.ReadModel`) через
  `command.ApplyEvent` (`backend/contexts/analytics/service.go`, `runWorker`).
- Read-модель уже различает виды событий `lead-workflow`, `message-sent`,
  `delivery-event`, `engagement-observed`, `email-verification`, `outreach-outcome`,
  `lead-outcome`: `delivery-event` поддерживается (`Apply`) и покрыт тестами, но из
  брокера в проекцию он не попадал.
- Единственный реальный издатель записей о цикле «письмо отправлено/доставлено» —
  `message-delivery`: контракт `delivery-event` (routing key `delivery-event.1`)
  публикуется в общий topic exchange платформы и уже потребляется
  `request-fulfillment` и `agent-orchestration`. Каталог объявляет связь
  `delivery-to-analytics` с тем же контрактом, но потребителя у `analytics` нет.
- Нормализованный `analytics-event` в цикле не публикуется: единственный издатель —
  `lead-management` — шлёт его только при ручной смене стадии и отправке из карточки.
- `delivery-event` не содержит `company_id` и поля `kind`: его тело — `tenant_id`,
  `campaign_id`, `recipient_ref`, `message_id`, `approved_action_id`, `outcome`,
  `attempt_number`.

## Goals / Non-Goals

**Goals:**
- Наполнить витрину клиента реальными исходами доставки цикла, не меняя чужие
  контексты и не вводя заглушек.
- Соблюсти конвенцию каталога: очередь потребителя `<downstream>.<contract>` →
  `analytics.delivery-event`.
- Сохранить существующий поток `analytics.analytics-event` без изменений.

**Non-Goals:**
- Публикация нормализованного `analytics-event` из `request-fulfillment`,
  `outreach-orchestration`, `message-delivery` (владельцы вне scope).
- Приём `engagement-event`/`agent-event` (в этом цикле нет событий на проводе).
- Изменение контракта `delivery-event` (добавление `company_id`/`kind` — это правка
  владельца `message-delivery`).
- Изменение доменной модели, агрегатов и связей каталога: связь уже объявлена.

## Decisions

### Решение 1. `analytics` принимает реальные события цикла (`delivery-event`), а не ждёт `analytics-event`

**Выбор.** Второй транспортный подписчик `analytics` читает очередь
`analytics.delivery-event` и нормализует исходы доставки в проекцию дашборда.

**Почему.** Цикл уже публикует `delivery-event`; это единственный реальный сигнал
«прокоммуницировано» на проводе. Альтернатива — «цикл публикует `analytics-event`» —
требует правки `outreach-orchestration`/`message-delivery`/`lead-management`, которые
вне scope этого изменения (и принадлежат другим изменениям/агентам). Вариант с
нормализованным `analytics-event` остаётся открытым и совместимым: подписка на
`analytics.analytics-event` сохраняется.

### Решение 2. Ключ записи витрины — получатель (`recipient_ref`), а не `company_id`

**Выбор.** Нормализованное событие из `delivery-event` несёт идентификатор записи,
равный `recipient_ref` (непрозрачная ссылка на получателя; в почтовом контуре — один
получатель на компанию). При пустом `recipient_ref` используется `message_id`.

**Почему.** Контракт `delivery-event` персональных данных не несёт и `company_id` не
содержит; выдумывать принадлежность проекция не вправе (инвариант read-модели:
событие без принадлежности игнорируется). Непрозрачная ссылка получателя — честная и
устойчивая идентичность «до кого дошли» для воронки клиента: повторные кампании к
тому же получателю не создают дублирующих записей. Альтернатива — `campaign_id` —
отвергнута: одна кампания на заявку даёт одну запись, а порог минимальной группы
скрывает такой срез.

### Решение 3. Маппинг исходов в проекцию

**Выбор.**
- `outcome=delivered` → нормализованное событие вида `message-sent` (статус `sent`):
  получатель учитывается как прокоммуницированный, стадия — `email_sent`.
- `outcome=failed` → событие вида `delivery-event` с исходом `failed`: отбой,
  переход в `cold` (коммуникация не засчитывается).

**Почему.** Доставленное сообщение и есть состоявшаяся коммуникация; отказ доставки
— противоположный исход. Виды и правила уже реализованы в read-модели и покрыты
тестами, поэтому семантика не расширяется.

### Решение 4. Обобщение транспортного подписчика без дублирования логики

**Выбор.** `transport.Subscriber` получает декодер контракта как параметр:
`NewSubscriber` (по умолчанию `analytics-event`, сохранён) и
`NewDeliveryEventSubscriber` (`delivery-event`, очередь
`analytics.delivery-event`). Дедупликация по `event_id`, порядок «эффект → запись»
и обработка ошибок не меняются.

**Почему.** Одна точка жизненного цикла очереди и дедупликации; второй подписчик не
копирует идемпотентность и повторную доставку.

### Решение 5. Подписка собирается только при заданном потребителе брокера

**Выбор.** `analytics.Config` получает поле очереди доставки; подписчик на
`delivery-event` собирается, как и текущий, только при непустом `Consumer`. Без
брокера витрина честно наполняется только dev-приёмом, а роль `worker` сообщает об
отсутствии источника.

**Почему.** Не притворяться работающим контуром; сохранить текущую модель
`Config.Consumer` (общий потребитель брокера процесса).

## Risks / Trade-offs

- **[Витрина считает «найдено» по доставкам, а не по результату поиска]** → Событие
  поиска (`found 3`) цикл на провод не публикует (владелец — `lead-management`, вне
  scope). Проекция честно отражает достигнутых и прокоммуницированных; пробел
  питания «найдено» закрывается change'ом владельца поиска. В `docs/domain-model.md`
  фиксируется явно, подмена нулём не делается.
- **[Несколько получателей одной компании дают несколько записей]** → Для почтового
  контура один получатель на компанию; при появлении множественных контактов
  идентичность записи уточняется владельцем контракта (`company_id` в `delivery-event`).
- **[Разные версии схемы `delivery-event`]** → Декодер читает обязательные поля формы
  `1.1.0` терпимо к неизвестным: MINOR-совместимость соблюдается.
- **[Порог минимальной группы на малом прогоне]** → Порог не меняется (требование
  `client-dashboard`); для живой проверки подбирается датасет, дающий ≥ 2 записи.

## Migration Plan

1. Обобщить транспортный подписчик и добавить декодер `delivery-event` с тестами.
2. Собрать вторую подписку роли `worker` в `analytics` (по `Config`).
3. Обновить `docs/domain-model.md` (питание витрины исходами доставки).
4. Гейт: `make check`, `go -C tools/archlint run .`, `openspec validate --strict`.
5. Живой прогон: пересобрать образ, прогнать цикл, подтвердить непустой дашборд.

**Откат.** Убрать вторую подписку (очередь доставки не задавать) — поведение
возвращается к питанию только `analytics-event`; данные и контракты не мигрируют.
