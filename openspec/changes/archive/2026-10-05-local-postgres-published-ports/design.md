## Context

`compose.yaml` уже поднимает три PostgreSQL (`postgres-green`, `postgres-red`,
`postgres-temporal`) и использует их внутри контура по именам сети
(`postgres://…@postgres-green:5432/…`, см. `x-app-command`). Сервисы данных
объявлены без `ports:`, поэтому хостовых портов нет. Остальные инфраструктурные
сервисы уже публикуют порты (`rabbitmq`, `mailpit`, `temporal-ui` и app-группы) —
пробел именно у баз. `make test-postgres` публикует `5433` для одноразовой
тестовой базы (`postgres:16-alpine`, БД `leadgen`), поэтому этот порт на хосте
может быть занят во время прогона `make test-postgres`; его нужно избегать.

## Goals / Non-Goals

**Goals:**

- Дать подключение к базам локального контура с хоста (DBeaver, `psql`) без
  `docker exec`.
- Не менять внутреннюю топологию и DSN приложения.
- Не выставлять базы в сеть за пределы хоста по умолчанию.

**Non-Goals:**

- Не менять код, миграции, схемы, доменную модель и `deploy/tofu` (prod).
- Не открывать доступ по сети (это включается осознанно сменой bind-адреса).
- Не вводить пароли/учётки в репозиторий — только параметры портов.

## Decisions

### Решение 1. Привязка к `127.0.0.1`, а не `0.0.0.0`

**Выбор.** `ports:` с явным bind-адресом хоста: `127.0.0.1:<host_port>:5432`.

**Почему.** Нужен доступ с того же хоста (DBeaver рядом с docker). Привязка к
loopback не публикует базы в локальную сеть и не открывает их наружу.
`0.0.0.0` (а также более широкий `POSTGRES_HOST_AUTH_METHOD`) отклонены: это
расширяло бы поверхность доступа к красной зоне и БД рантайма без запроса.

### Решение 2. Разные host-порты, переопределяемые через `.env`

**Выбор.** Внутренний порт у всех трёх сервисов — `5432`, поэтому host-порты
разводятся: `5433` (green), `5434` (red), `5435` (temporal). Значения берутся
из переменных `.env` (`POSTGRES_GREEN_PORT`, `POSTGRES_RED_PORT`,
`POSTGRES_TEMPORAL_PORT`) с указанными дефолтами.

**Почему.** Один и тот же внутренний порт нельзя замапить на один host-порт
трижды. Дефолты не конфликтуют с `make test-postgres` (`5433`): во время
`make test-postgres` одноразовый контейнер занимает `5433` на хосте, поэтому
`postgres-green` может не стартовать — это редкое пересечение, снимается сменой
переменной порта. Дефолты, а не хардкод, оставляют свободу при занятых портах.

### Решение 3. Публиковать все три базы, включая red и temporal

**Выбор.** Публикуются `postgres-green`, `postgres-red`, `postgres-temporal`.

**Почему.** Пользователю нужен доступ ко всем базам контура для инспекции.
Риск ограничен привязкой к loopback (Решение 1) и тем, что контур локальный и
dev. Пароль `lead_gen` общий для green/red, `temporal`/`temporal` — dev-хардкод;
это уже существующие свойства контура, изменение их не вводит.

### Решение 4. Внутренние DSN не трогаются

**Выбор.** Строки подключения приложения (`x-app-command`) остаются
`postgres-green:5432`/`postgres-red:5432`; меняется только блок `ports:`.

**Почему.** `ports:` лишь публикует порт контейнера на хост и не влияет на
связи контейнеров по сети. Проверка регрессии — приложение поднимается и
работает как прежде.

## Risks / Trade-offs

- **[Открыт доступ к красной зоне и БД рантайма с хоста]** → bind на
  `127.0.0.1`; в сеть базы не выходят, откат — удаление блока `ports:`.
- **[Конфликт host-портов при занятых 5433/5434/5435]** → порты вынесены в
  `.env`; документация объясняет переназначение.
- **[Пересечение с `make test-postgres` по порту `5433`]** → зафиксировано в
  `deploy/README.md`; при необходимости `POSTGRES_GREEN_PORT` переназначается.

## Migration Plan

1. Добавить `ports:` в три сервиса и переменные портов в `.env.example`.
2. Обновить `deploy/README.md` (порты + готовые DSN).
3. Перезапустить контур: `docker compose up -d` (для сервисов данных —
  пересоздание контейнеров).
4. Подключиться из DBeaver / `psql` по `localhost:<порт>`.

**Откат.** Удаление блоков `ports:` и переменных — внутренняя топология не
затрагивалась, поэтому данных и связей откат не ломает.
