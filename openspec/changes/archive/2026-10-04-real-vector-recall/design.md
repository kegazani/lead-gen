## Context

Мотивация и объём — в `proposal.md`. Здесь состояние и ограничения, определяющие
подход.

**Что уже есть.** Контракт `contracts/integration-platform/vector` (`Port`:
`Embed`/`Upsert`/`Search`, типы `Vector`/`Document`/`Match`, ошибки
`ErrUnavailable`/`ErrRejected`). In-memory реализация
`integration-platform/internal/adapters/vector/memory.go` (детерминированный
`HashEmbedder` + карта документов). Потребители порта: `lead-management` (app
`semantic.go`), `request-fulfillment` (app `command/embed_offer.go`). Связи
каталога `vector-for-leads` и `vector-for-requests` уже объявлены.

**Что не работает.** `HashEmbedder` — лексический хеш слов: совпадающие слова дают
близкие векторы, синонимия и смысл не учитываются. Состояние — в памяти процесса.
Порт `vector` не собирается в `backend/cmd/lead-gen`, поэтому `cfg.Vector` у
`request-fulfillment` остаётся `nil`, а семантический recall в `lead-management`
не получает хранилище.

**Среда.** Обязательный PostgreSQL доступен. Расширение pgvector в тестовом образе
(`postgres:16-alpine`) отсутствует; вводить его — отдельное инфраструктурное
решение. Для объёма пула одного клиента достаточно точного поиска по косинусной
близости средствами SQL/приложения без ANN-индекса.

## Goals / Non-Goals

**Goals:**

- Дать реальный эмбеддинг и реальный персистентный индекс за неизменным портом `vector`.
- Сохранить наблюдаемое поведение контракта и совместимость потребителей.
- Подключить порт к потребителям централизованно в `cmd/lead-gen`.

**Non-Goals:**

- Не менять вердикт релевантности (остаётся за `lead-management`).
- Не вводить ANN-индекс (HNSW/IVF) и не требовать pgvector.
- Не проектировать tenant-изоляцию индекса (контракт `vector` не несёт тенанта).

## Decisions

### Решение 1. Провайдер эмбеддингов — отдельный порт владельца, а не детерминизм

**Выбор.** Эмбеддинг идёт через интерфейс `Embedder` (внутренний порт адаптера),
реализуемый реальным HTTP-провайдером (`/v1/embeddings`, OpenAI-совместимый), уже
используемым в `integration-platform` (`openai`-адаптер). `HashEmbedder` остаётся
только для тестов/dev.

**Почему.** `AGENTS.md` §3: детерминизм допустим лишь там, где он и есть
требование. Здесь требование — семантика, значит лексический хеш — заглушка.
Провайдер эмбеддингов — та же категория внешней зависимости, что LLM и краулер.

**Рассмотренные альтернативы.** Локальная модель эмбеддингов в процессе —
отклонено: тянет за собой рантайм и лицензии; не нужно на этом этапе. Хеш-эмбеддинг
как «достаточно хороший» — отклонено как заглушка на продуктовом пути.

### Решение 2. Персистентность — PostgreSQL зелёной зоны, точный поиск

**Выбор.** Таблица `vector_document(tenant_scoped? нет, id TEXT PRIMARY KEY,
embedding real[] NOT NULL, updated_at timestamptz)`. Upsert по `id`; поиск — выборка
всех строк с вычислением косинусной близости (векторы нормализованы, поэтому
близость = скалярное произведение). Миграция — в существующем каталоге миграций
`integration-platform`.

**Почему.** Реально персистентно, разделяемо ролями, без нового расширения СУБД.
Точный поиск честен и детерминирован; для целевого объёма приемлем по стоимости.

**Рассмотренные альтернативы.** pgvector + ANN — отклонено на этом этапе:
инфраструктурное решение и смена тестового образа. Внешний векторный сервис (stor)
— отклонено: ещё одна внешняя система без необходимости.

**Следствие.** При росте индекса стоимость поиска растёт линейно. Точка расширения
обозначена: замена на pgvector/ANN за тем же портом.

### Решение 3. Нормализация ошибок и честная недоступность

**Выбор.** Ошибки провайдера эмбеддингов и СУБД нормализуются до
`vector.ErrUnavailable`; пустой текст/id — до `vector.ErrRejected`. Конструктор
провайдера без ключа оставляет порт в честном недоступном состоянии, а `cmd/lead-gen`
логирует это, а не подставляет хеш-эмбеддер молча.

**Почему.** Потребитель различает отказ транспорта и доменный отказ; заглушка не
маскируется под успех.

### Решение 4. Подключение в `cmd/lead-gen`

**Выбор.** Точка сборки строит персистентный векторный порт (DSN + провайдер
эмбеддингов) и передаёт его в `lead-management` и `request-fulfillment`; без DSN
или без ключа — тестовый/dev-двойник либо честный недоступный порт с
предупреждением.

**Почему.** Сейчас порт не собирается вовсе — это и есть главный разрыв. Впрыск
делается централизованно, как для остальных внешних портов.

### Решение 5. Доменная привязка

Capability `vector-recall` принадлежит контексту `integration-platform`. Новых
агрегатов и сущностей не появляется: индекс — инфраструктурный адаптер, не домен.
Контракт `vector` и связи `vector-for-leads`/`vector-for-requests` остаются как
есть. Обновляется только список capability контекста в
`architecture/domain-catalog.yaml` и описание в `docs/domain-model.md`.

## Risks / Trade-offs

- **[Линейный поиск при росте индекса]** → Приемлемо для целевого объёма; точка расширения — pgvector/ANN за тем же портом.
- **[Зависимость от внешнего провайдера эмбеддингов]** → Недоступность честно возвращается потребителю; recall не выдумывает кандидатов. Деградация видна, а не скрыта.
- **[Расхождение размерности векторов]** → Размерность фиксируется провайдером; при смене провайдера требуется переиндексация — фиксируется как открытый вопрос.
- **[Дублирование конфигурации провайдера]** → Эмбеддинги и LLM могут использовать один OpenAI-совместимый endpoint; конфигурация сводится в одну секцию.

## Migration Plan

1. Добавить миграцию таблицы индекса (каталог миграций `integration-platform`).
2. Реализовать адаптер `vector/postgres` и эмбеддер-адаптер.
3. Прогнать контрактные проверки `vector.Port` против in-memory и postgres.
4. Подключить порт в `cmd/lead-gen`; передать в потребителей.
5. Проверить, что без ключа/DSN порт честно недоступен, а не подменён хешем.

**Откат.** Возврат на in-memory двойник в `cmd/lead-gen` (dev); продовая семантика
при этом снова деградирует — это явное, а не молчаливое состояние.

## Open Questions

1. **Провайдер эмбеддингов и его размерность.** По умолчанию — тот же OpenAI-совместимый endpoint; модель и размерность задаются конфигурацией.
2. **Переиндексация при смене модели.** Требуется ли фоновая задача или ручной прогон — отдельное решение.
3. **Порог близости.** Контракт возвращает ранжирование; порог отсечения — за потребителем (`lead-relevance`), не за хранилищем.
