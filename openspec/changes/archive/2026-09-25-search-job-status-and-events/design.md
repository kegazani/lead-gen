## Context

Задания поиска обслуживает примитив `backend/platform/jobs` (состояние `queued → running → done/failed/cancelled`, `Runner` опрашивает очередь и синхронно вызывает `Handler`). Потребитель — `lead-management`: `RunSearch.handle` декодирует `Payload`, при наличии `budget.Factory` создаёт бюджетную задачу Firecrawl, планирует цели и для каждой делает `Search`, затем `Crawl` по каждому результату; карточки сохраняются сразу при обработке страницы. Хранилище — PostgreSQL (`search_job`) или memory-адаптер; журнал и формы консоли — серверный `html/template` + HTMX (опрос `/jobs` каждые 2с). Адаптер Firecrawl (`integration-platform`) делает асинхронный `POST /v1/crawl` и опрашивает `GET /v1/crawl/{id}` в `pollCrawl`; при отмене контекста сейчас лишь снимает best-effort снимок, не останавливая удалённое задание. Мотивация — см. `proposal.md`.

Ограничения: api- и worker-роли размещены в одном процессе; примитив `jobs` обязан оставаться без доменных терминов; бюджет кредитов уже реализован (`firecrawl-credit-budget`); правила наблюдаемости (`observability`) запрещают секреты и персональные данные в логах.

## Goals / Non-Goals

**Goals:**

- Наблюдаемая статусная модель: очередь (позиция/причина ожидания), под-фазы выполнения, счётчики `planned`/`found`/`parse_errors`/`tokens_spent`/кредиты.
- Стабильные коды ошибок с бизнес-формулировкой; техническая деталь — только в лог.
- Персистентный append-only журнал событий задания.
- Активная остановка удалённого обхода Firecrawl при отмене.
- Запись `ResultRef` при отмене; прокручиваемый журнал с единым лимитом; hover-детализация.

**Non-Goals:**

- Push-транспорт (SSE/WebSocket): остаёмся на HTMX-опросе.
- Полная пагинация журнала (только прокрутка + единый лимит).
- Межпроцессная координация отмены через брокер (текущее развёртывание co-located).
- Домен админки-агрегатора: этот change лишь пишет события, админка — отдельный change.
- Retry задания целиком: повторяется только разбор страницы через эскалацию, а не задание.

## Decisions

### Решение 1. Прогресс — расширение `ports.SearchJobProgress`, очередь — производная

`SearchJobProgress` дополняется полями: `PlannedTargets int`, `PlannedURLs int`, `ParseErrors int`, `TokensSpent int`; фаза добавляет значение `extracting` (разбор страниц). Поля живут в уже существующем `progress jsonb` — схема таблицы не меняется.

Позиция в очереди и причина ожидания — производные, не персистентные: `position` вычисляется при чтении журнала ранжированием среди `queued`; причина — «ждёт воркера» (текущий развёртывание — один воркер) либо «недостаточно кредитов» при пустом остатке аккаунта Firecrawl. Это честно отражает MVP и не вводит денормализованное состояние.

*Альтернатива* (хранить позицию/причину в задании) отклонена: позиция меняется при каждой постановке/взятии, хранение — источник рассинхрона.

### Решение 2. Коды ошибок — типизированная ошибка + расширение примитива `jobs`

Вводится типизированная ошибка прикладного слоя `SearchJobError{ Code, Message, Detail }`: `Code()` — стабильный машинный код (`search.failed`, `crawl.failed`, `parse.failed`, `budget.exhausted`, `payload.invalid`, …), `Message()` — бизнес-формулировка для оператора, `Error()` — техническая деталь (для лога).

Примитив `jobs` получает доменно-нейтральный интерфейс:

```go
type CodedError interface {
    error
    Code() string    // стабильный код исхода (значение задаёт домен)
    Message() string // сообщение для оператора
}
```

`Runner` при неуспехе обработчика, если ошибка реализует `CodedError`, извлекает `Code()` и `Message()`; иначе — пустой код и `Error()`. `Store.UpdateStatus` расширяется параметром `code`; `search_job` получает колонку `error_code`, а в `error` пишется бизнес-сообщение. `RunSearch.Handle` продолжает логировать `err` (техническую деталь) в наблюдаемость.

Значения кодов определяет `lead-management` (прикладной слой); примитив лишь переносит непрозрачную строку, поэтому остаётся без доменных терминов.

*Альтернатива* (хранить код отдельным `RecordError` прикладного слоя и не трогать `jobs`) отклонена: раннер всё равно перезаписывает `error` при завершении, поэтому код должен идти через контракт завершения задания, а не параллельным путём.

### Решение 3. Журнал событий — операционная append-only таблица и порт

Новая таблица `search_job_event` в зелёной зоне `lead-management`: `job_id`, `seq`, `type` (`enqueued`/`taken`/`phase`/`error`/`cancel_requested`/`cancelled`/`done`/`failed`), `code` (для `error`), `payload jsonb` (снимок счётчиков), `created_at`. Только вставка, без обновлений и удалений.

События пишет `RunSearch` через новый метод хранилища (`SearchJobStore.RecordEvent`). Это операционная запись, а не доменная сущность: owning context — `lead-management`, aggregate root и domain events не появляются, межконтекстных контрактов нет. Админка будет читать таблицу отдельным change.

*Альтернатива* (события в общий журнал наблюдаемости) отклонена: наблюдаемость пишет в stderr и не персистирует для агрегации.

### Решение 4. Активная отмена — остановка удалённого обхода в адаптере

`firecrawl.Client.pollCrawl` при `ctx.Done()` отправляет движку запрос остановки (`DELETE /v1/crawl/{id}`, отсоединённым контекстом с коротким дедлайном), затем делает best-effort `finalSnapshot`. Порядок: сначала сигнал остановки (немедленно освободить ресурсы Firecrawl), затем снимок уже добытого. Контракт `crawl.Port` не меняется — отмена по-прежнему управляется через `context`, адаптер лишь активно останавливает удалённую работу. Бюджетная обёртка `Task.Crawl` прозрачна: отмена контекста доходит до `client.Crawl`.

Гарантия отмены — локальная и безусловная: задание немедленно помечается `cancelled` и прекращает опрос, даже если вызов остановки к Firecrawl не удался (запрос — best-effort, повторная отмена идемпотентна).

*Альтернатива* (только локальная отмена без запроса к движку) отклонена: оставляет удалённое задание жечь кредиты и ресурсы.

### Решение 5. Токены LLM — расширение контракта `llm`

`llm.Port.Plan` и `Suggest` начинают возвращать `llm.Usage{ PromptTokens, CompletionTokens, TotalTokens }` (через структуру результата либо дополнительное возвращаемое значение). Адаптер `openai` парсит поле `usage` ответа chat completion. `RunSearch.planTargets` накапливает `TokensSpent` в прогрессе задания. Это меняет межконтекстный контракт `contracts/integration-platform/llm`.

*Альтернатива* (учитывать Firecrawl `token-usage`) отклонена: это остаток по аккаунту, а не расход конкретного задания; для «потрачено на выполнение» нужны токены LLM.

### Решение 6. `ResultRef` при отмене

`finishCancelled` в `RunSearch.handle`, помимо сброса прогресса, вызывает `RecordResult` с накопленными `companyIDs` через отсоединённый контекст, чтобы журнал показывал ссылки на найденные компании отменённого задания. Исправляет расхождение «компаний N, найдено —».

### Решение 7. Консоль — hover, бизнес-ошибка, прокрутка

- Hover-детализация статуса — атрибут `title` бейджа со строкой «фаза · счётчики · причина» (CSP-безопасно, без inline-скриптов); более богатая разбивка остаётся в строке прогресса.
- Ошибка в журнале показывается бизнес-формулировкой (`Message`), а не сырым текстом; при пустом коде (старые задания) — нейтральное «ошибка» без технической строки.
- Прокрутка журнала — CSS `max-height` + `overflow-y: auto` на контейнере таблицы; единый предел (например, 100) и для `handleDashboard`, и для `handleJobs` — устраняет расхождение 10/50.

## Risks / Trade-offs

- **[Остановка Firecrawl может не успеть]** Удалённое задание могло завершиться между запросом отмены и `DELETE` → смягчение: `DELETE` по завершённому заданию — no-op/404, отмена идемпотентна, локальный исход уже `cancelled`.
- **[Снимок после остановки пуст]** Firecrawl может не отдать частичные данные после отмены → смягчение: снимок — best-effort; гарантия сохранения — карточки, уже обработанные до отмены.
- **[Старые записи без `error_code`]** Консоль обязана корректно показывать failed-задания, созданные до миграции → смягчение: пустой код отображается нейтрально.
- **[Нагрузка событий на БД]** Событие на каждой смене фазы → смягчение: коалесцирование на границах шагов, как у прогресса; событий немного относительно страниц.
- **[Рост таблицы событий]** Append-only растёт → смягчение: отдельная таблица, ретенция/архивация — забота будущей админки.

## Migration Plan

1. Миграция зелёной зоны `0006_search_job_status_events.sql`: `ALTER TABLE search_job ADD COLUMN IF NOT EXISTS error_code text;` и `CREATE TABLE search_job_event (...)`. Поля прогресса — в существующем `progress jsonb`, изменений схемы не требуют.
2. Совместимость: существующие задания имеют `error_code = NULL` и пустой `progress` без новых счётчиков; консоль трактует отсутствующие значения как «по умолчанию».
3. Порядок выката: миграция → код (приложение пишет новые поля; отсутствие значения — «по умолчанию»).
4. Откат: откатить колонку/таблицу и код; `cancelled` остаётся терминальным и не влияет на очередь.
5. Обновить `architecture/domain-catalog.yaml` (capability `search-job-error-codes`, `search-job-events` в `lead-management`) и `docs/domain-model.md`; прогнать `go -C tools/archlint run .`.
