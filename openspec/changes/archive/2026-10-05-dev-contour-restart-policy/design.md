## Context

`compose.yaml` описывает локальный (dev) контур полного цикла. Шесть групп
процессов (`core`, `delivery`, `demand`, `intake`, `public`, `platform`) собраны
через YAML-якорь `x-app` (`<<: *app`), а инфраструктура задана отдельными
сервисами (`postgres-green`, `postgres-red`, `rabbitmq`, `mailpit`,
`postgres-temporal`, `temporal`, `temporal-ui`). Ни у одной группы нет ключа
`restart:`, поэтому действует политика по умолчанию — `no`: упавший контейнер не
поднимается сам. Симптом: после краткого пропадания `postgres-green` сервисы
`core` и `demand` завершились и остались лежать, пока контур не подняли вручную.

## Goals / Non-Goals

**Goals:**

- Автоматический подъём сервисов контура после падения, рестарта демона docker
  или хоста.
- Вручную остановленный сервис не должен подниматься вопреки решению оператора
  (нужен явный запуск).
- Минимальная и обратимая правка — только `compose.yaml`.

**Non-Goals:**

- Не менять команды, переменные, порты, тома, healthcheck'и и связи `depends_on`.
- Не трогать код, `Dockerfile`, `Makefile`, `deploy/**` и prod-контур.
- Не вводить политику `always`: она поднимает и вручную остановленный сервис,
  что мешает `docker compose stop` при отладке.

## Decisions

### Решение 1. `restart: unless-stopped` для всех долгоживущих сервисов

**Выбор.** Всем перечисленным сервисам задаётся `restart: unless-stopped`.

**Почему.** Политика поднимает контейнер после падения, рестарта демона и
перезагрузки хоста, но уважает ручную остановку: остановленный через
`docker compose stop` контейнер не запускается до явной команды. Это ровно нужное
поведение для dev-контура и не мешает отладке.

**Альтернативы.** `always` — поднимает и вручную остановленные контейнеры,
неудобно при отладке. `on-failure` — не поднимает контейнер после рестарта
демона/хоста и не покрывает намеренную остановку зависимостью. Отклонены.

### Решение 2. Шесть групп процессов получают политику через общий якорь `x-app`

**Выбор.** `restart: unless-stopped` добавляется один раз в YAML-якорь `x-app`
(рядом с `build`, `depends_on`, `volumes`, `command`, `environment`), от которого
наследуются все шесть групп (`core`, `delivery`, `demand`, `intake`, `public`,
`platform`).

**Почему.** Якорь `x-app` используется только этими шестью долгоживущими
сервисами, поэтому одно объявление даёт требуемый результат без шести повторов и
без риска расхождения между группами. Инфраструктурные сервисы не используют
этот якорь и получают ключ каждый у себя.

### Решение 3. Инфраструктура получает политику каждый сервис

**Выбор.** `postgres-green`, `postgres-red`, `rabbitmq`, `mailpit`,
`postgres-temporal`, `temporal`, `temporal-ui` получают
`restart: unless-stopped` в своих блоках.

**Почему.** Это тоже долгоживущие сервисы контура; именно их временное
пропадание (например, `postgres-green`) роняло зависимые группы. Общего якоря у
них нет, поэтому ключ ставится явно.

### Решение 4. Ничего другого по смыслу не меняется

**Выбор.** Правка ограничена добавлением ключа `restart:`; `command`,
`environment`, `ports`, `volumes`, `healthcheck`, `depends_on` остаются как есть.

**Почему.** Задача — только политика перезапуска. Проверка эквивалентности
конфигурации — `docker compose config`, в выводе которого появляется
`restart: unless-stopped` у перечисленных сервисов и не меняется ничего иное.

## Risks / Trade-offs

- **[Перезапуск маскирует реальную поломку конфигурации]** → в dev-контуре
  автоматический подъём предпочтительнее простоя; логи сервиса доступны через
  `docker compose logs`, причина падения не теряется.
- **[Зацикливание перезапусков при постоянной ошибке старта]** → docker
  применяет экспоненциальную задержку между попытками; при необходимости сервис
  останавливается вручную (`docker compose stop` не поднимается политикой
  `unless-stopped`).

## Migration Plan

1. Добавить `restart: unless-stopped` в якорь `x-app` и в семь
   инфраструктурных сервисов `compose.yaml`.
2. Проверить валидность: `docker compose config -q`.
3. Применить: `docker compose up -d` (пересоздаст сервисы с новой политикой);
   проверки на живом контуре — за пользователем.

**Откат.** Удаление ключа `restart:` возвращает политику по умолчанию `no`;
другие свойства сервисов не затрагивались.
