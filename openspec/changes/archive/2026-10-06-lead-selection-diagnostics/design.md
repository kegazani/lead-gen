## Context

Мотивация — в `proposal.md` (Why). Технические данные для сводки отбора уже
хранятся и наблюдаемы; ничего нового в домене не вводится. Что есть сейчас:

- `ports.SearchJobProgress` (`backend/contexts/lead-management/internal/ports/search_job_store.go`):
  `Phase`, `PagesCrawled`, `CompaniesFound`, `TargetCompanies`, `TargetReached`,
  `StopReason`, `ParseErrors`, `AssessmentErrors`, `TokensSpent`,
  `CreditsSpent`, `CreditsAvailable` и распределение вердиктов
  `VerdictFits`/`VerdictHypothesis`/`VerdictUnsuitable`.
- Оценки: агрегат `lead-assessment` со свидетельствами
  `llm.Assessment.Evidence` — `Criterion`, `Fact`, `SourceURL`, `Reasoning`,
  `SignalKind`, `Missing` («чего не хватает»), `Mismatch` («что не сошлось»).
- Контакты компаний и признак отсутствия/недоступности email (пакетное чтение
  контактов для витрины — существующее `lead-cards-console`).
- Заявка: `state.Shortfall` (`request-fulfillment`,
  `internal/adapters/workflow/fulfillment.go`) — производное `цель − найдено`.
- Исходящие сообщения: `outbound-message` со статусами
  (`queued`/`sent`/`failed`/`bounced`/`unsubscribed`/`rejected`).

Экран задания и экран карточек — `html/template` + HTMX в
`backend/contexts/lead-management/internal/adapters/http` (`server.go`,
`views.go`, `templates/job.html`, `templates/cards.html`, `templates/card.html`).
Экран заявки/утверждения —
`backend/contexts/request-fulfillment/internal/adapters/http` (`approval_screen.go`,
`templates/approval_screen.html`). Границы контекстов — `architecture/domain-catalog.yaml`.

## Goals / Non-Goals

**Goals:**

- Единая проекция «Сводка отбора» на экране задания и на экране заявки,
  собираемая из уже читаемых данных владельца экрана.
- Диагноз недостигнутой цели/недобора с различением наблюдаемых причин.
- Наблюдаемая группировка причин отсева с числом и переходом к списку.
- Четыре группы карточек со счётчиками и фильтр по причине отсева.

**Non-Goals:**

- Новые агрегаты, value objects, domain events, policies, контракты и связи —
  домен и каталог не меняются.
- Изменение правил и инвариантов оценки (`lead-relevance` — только проекция).
- Сбор новых данных (например, отдельная телеметрия причин): используются
  только сохранённые свидетельства и счётчики.
- Изменение воронки клиентского дашборда (`client-dashboard`).

## Decisions

### Решение 1. Проекция собирается в адаптере HTTP владельца экрана

Сводка, диагноз и группы — не новый домен, а проекция. Для экрана задания и
экрана карточек её собирает `lead-management`, для экрана заявки —
`request-fulfillment`; каждый читает только свои данные и уже подключённые к
экрану проекции. Новых агрегатов и контрактов не вводится (это и есть
«`job-journal-console` и `lead-cards-console` не добавляют модель» из
`docs/domain-model.md`, распространённое на диагностику отбора).

Альтернатива — новая capability `lead-selection-diagnostics` и сквозной
контракт. Отклонено: потребовало бы правки каталога, `docs/domain-model.md` и
связей ради чисто консольной проекции; наблюдаемое поведение полностью
покрывается существующими ability-путями.

### Решение 2. Воронка отбора — по данным владельца задания, недоступное честно

Стадии воронки: найдено (`ResultRef`/`CompaniesFound`) → проверено email
(контакты компании) → оценено (оценки задания) → подходит/гипотеза/не подходит
(распределение вердиктов) → писем (черновики/исходящие) → отправлено (статус
`outbound-message`) → ответили. Данные стадий «найдено…отправлено» принадлежат
`lead-management` и читаются из уже существующих хранилищ. Стадия «ответили» —
данные `analytics`/`engagement-observation` и на уровне отдельного задания в
текущих поверхностях недоступна: она SHALL показываться как недоступная, а не
нулём (см. Open Questions). Так соблюдается запрет заглушки (`AGENTS.md` §3):
отсутствие данных — явное состояние, не подмена.

### Решение 3. Группировка причин отсева — по свидетельствам, без домысла

Группы строятся из сохранённых свидетельств задания:
`«Не подходит»` → ключ по `Mismatch`; `«Гипотеза»` → ключ по `Missing`;
`«нет email / email недоступен»` → по контактам компании;
`«ошибки оценки»` → по счётчику `AssessmentErrors`/ошибкам оценки компании.
Ключ группы — нормализованный текст причины; пустая причина не создаёт
выдуманного ключа. Переход к списку — это адрес списка карточек с параметром
причины (см. Решение 4), данные берутся из того же задания, поэтому причина не
смешивается с оценкой другого задания. Альтернатива — хранить отдельный
справочник причин; отклонено как новая модель без нужды.

### Решение 4. Экран карточек: четыре группы и фильтр по причине

Состав результатов расширяется с двух групп до четырёх
(«Подходит»/«Гипотеза»/«Не подходит»/«Не оценено») со счётчиками. Группа
выбирается на клиенте (как сейчас переключатель состава), но счётчики
рендерятся сервером, чтобы работать без JavaScript. Фильтр по причине —
параметр запроса, сужающий выборку до карточек с выбранным свидетельством;
снятие фильтра возвращает полную группу. Фильтр и представление
независимы и сохраняются при переключении. Расшифровка карточки (вердикт + по
каждому критерию: критерий, факт, источник, обоснование, тип сигнала,
`Missing`/`Mismatch`) уже есть в `templates/card.html` (define `evidence-list`)
и переиспользуется без изменений — карточка для групп «Гипотеза»/«Не
подходит»/«Не оценено» получает явную подпись вердикта.

### Решение 5. Диагноз «почему мало» — упорядоченные наблюдаемые причины

Диагноз собирается из наблюдаемых полей и не додумывает: сначала причина
остановки (`StopReason` — цели исчерпаны/бюджет), затем счётчики ошибок
(`ParseErrors`/`AssessmentErrors`), затем распределение вердиктов (всё
отсеялось оценкой). Если ни один признак не даёт однозначной причины, экран
показывает наблюдаемый остаток (`TargetCompanies − CompaniesFound`) и
счётчики без формулировки причины. На экране заявки тот же диагноз строится
из состояния исполнения (`Shortfall`) и данных связанного задания; при
недоступности данных поиска — недобор без объяснения.

## Risks / Trade-offs

- [Стадия «ответили» на уровне задания недоступна] → этап показывается честной
  недоступностью; выдуманный ноль запрещён (Решения 2, 5).
- [Свободный текст `Mismatch`/`Missing` даёт шумные группы] → группировка по
  нормализованному тексту, рядом с группой показывается исходная формулировка;
  число групп ограничивается показом, причина компании не подменяется.
- [Дорогое чтение] → данные читаются пакетно теми же запросами, что уже
  обслуживают экран (контакты — пакетно), без запроса на каждую карточку.
- [Утечка чужого тенанта в фильтре/группах] → выборка идёт тем же
  тенант-скоупом, что и существующие экраны; чужие данные не попадают.
- [Расширение групп меняет привычный экран] → изменение только на экране
  карточек; данные не теряются, прежняя группа доступа к «неподходящим»
  сохраняется через новые группы.

## Migration Plan

- Изменение аддитивное (проекции и разметка), миграций данных нет.
- Порядок: сначала серверные проекции и счётчики, затем разметка и фильтр,
  затем экран заявки; откат — возврат прежнего шаблона/разметки.
- Обновление `architecture/domain-catalog.yaml`, `docs/domain-model.md` и
  диаграмм не требуется (домен не меняется); это подтверждается прогоном
  `go -C tools/archlint run .` (код 0).
