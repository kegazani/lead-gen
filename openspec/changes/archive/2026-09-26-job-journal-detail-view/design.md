# Дизайн журнала заданий и экрана подробностей

## Context

Мотивация — в `proposal.md`. Здесь только то, что важно для решения.

Сейчас главная страница (`backend/contexts/lead-management/internal/adapters/http/`)
рендерит журнал заданий таблицей `dashboard.html`, где строка содержит полный
запрос, длинную склейку хода (`progressText` в `views.go`) и текст ошибки. Строка
перегружена, а подробный ход выполнения не показан нигде, хотя append-only
журнал событий задания уже ведётся: `ports.SearchJobStore.ListEvents` реализован
в memory- и postgres-хранилищах, но в UI не подключён.

Ограничения, заданные существующей архитектурой (change
`web-frontend-architecture`, Решения 2–15):

- Серверный рендеринг `html/template`, маленькие острова JS; SPA отклонён.
- Строгая CSP без inline-скриптов; скрипты только из `console.js`.
- Журнал — живой HTMX-фрагмент: `hx-get="/jobs"`, `hx-trigger="every 2s"`,
  `hx-swap="outerHTML"`. Фрагмент заменяется целиком.
- Шаблон только показывает; доменные правила в него не проникают.
- `console.js` уже удерживает выбор чекбоксов между подстановками фрагмента
  (`sync()` на `htmx:afterSwap` / `htmx:afterSettle`).

## Goals / Non-Goals

**Goals:**

- Ужать строку журнала до состояния, даты и короткого запроса.
- Дать быстрый взгляд на задание без ухода с главной — раскрытие строки на месте.
- Дать полный ход выполнения задания на отдельном экране.
- Сохранить раскрытие строк при живом авто-обновлении.
- Остаться без JavaScript-обязательности для базового чтения: прямое открытие
  экрана подробностей и работа журнала без HTMX сохраняются.

**Non-Goals:**

- Не менять правила записи событий и публикации прогресса (это
  `search-job-events` и `search-job-progress`, они не трогаются).
- Не переделывать остальные экраны консоли (карточки, воронка, отправку) —
  это отдельные изменения.
- Не вводить фильтры, пагинацию и поиск по журналу.
- Не менять формат и поведение уже показанных данных: содержимое «хода
  выполнения» и кодов ошибок берётся как есть.

## Decisions

### Решение 1. Три уровня детализации: строка, раскрытие, экран

- **Строка журнала** — состояние, дата, короткий запрос.
- **Раскрытие строки** — сводка: полный запрос, текущее состояние хода, текст
  ошибки, ссылка «Открыть полностью».
- **Экран `/jobs/{id}`** — полный ход выполнения по времени.

**Почему так:** это отвечает на две разные потребности («что с заданием?» и
«что именно произошло?») без компромисса между плотностью и полнотой. Раскрытие
рассчитано на быстрый взгляд, экран — на разбор.

**Альтернативы:** только раскрытие (тесно под длинный лог и ломается от
авто-обновления) или только экран (лишает быстрого взгляда) отклонены.

### Решение 2. Раскрытие — через `details`/`summary`, состояние удерживает `console.js`

Строку дополняем нативным `details` с `summary` (состояние/дата/короткий
запрос), сводка — в теле. Так раскрытие работает без JavaScript, доступно с
клавиатуры и не требует новых примитивов.

Проблема: HTMX заменяет фрагмент журнала целиком каждые 2 секунды, и
раскрытые строки схлопнутся. Решение — расширить существующий остров
`console.js`: держать множество раскрытых идентификаторов заданий в памяти
страницы, помечать раскрытые `details` атрибутом `data-expanded` и после
`htmx:afterSwap` / `htmx:afterSettle` восстанавливать раскрытие и синхронно
обновлять множество при ручном сворачивании. Это тот же приём, что уже
применяется для `input[data-select-job]`.

**Почему так:** механизм удержания состояния между HTMX-подстановками в проекте
уже есть; расширяем его, а не вводим второй.

**Альтернатива:** опрашивать фрагмент только по действию — отклонено, живой
прогресс нужен оператору.

### Решение 3. Экран задания — отдельный маршрут `GET /jobs/{id}`

Новый обработчик читает задание и его события и рендерит новую страницу
`templates/job.html`. Слой `app.Showcase` получает метод, возвращающий задание и
его события через уже существующий `ports.SearchJobStore.ListEvents`; чтение
отдельного задания выполняется запросом списка и выборкой по идентификатору,
либо (если хранилище позволит позже) методом поиска по идентификатору —
интерфейс `SearchJobStore` расширяется только при необходимости.

**Почему так:** это повторяет уже принятый в проекте паттерн «список → карточка»
(`/cards` → `/cards/{id}`), где подробности живут на своём адресе; так работает
закладка «назад», и экран не зависит от авто-обновления.

### Решение 4. Короткий запрос — на сервере, полный — на экране

Короткое представление запроса формирует слой представления (`views.go`), а не
CSS или шаблонная логика: обрезка по длине с добавлением многоточия. Полный
запрос показывается в раскрытии и на экране задания.

**Почему так:** «шаблон показывает, а не решает» (Решение 16 дизайна
`web-frontend-architecture`); длина представления — деталь отображения, её место
в модели представления.

### Решение 5. Ход выполнения — по журналу событий, снимок Progress — как запас

Экран показывает события задания (`enqueued`, `taken`, `phase`, `error`,
`cancel_requested`, `cancelled`, `done`, `failed`) по времени. Если у задания
нет событий, экран показывает текущее состояние и снимок `Progress`, если он
есть, и пометку об отсутствии хода выполнения.

**Почему так:** журнал событий — источник временного ряда; снимок прогресса —
только последнее состояние.

### Решение 6. Отсутствие задания — понятное сообщение

Неизвестный идентификатор задания даёт существующий `renderNotice` с кодом 404
и нейтральным текстом, без внутренних деталей.

**Почему так:** экран не должен отличать «нет задания» от «нет доступа» лишними
подробностями (Решения 7 и 9 дизайна `web-frontend-architecture`).

### Решение 7. Новая capability `job-journal-console` и обновление каталога

Поведение консоли описывается capability `job-journal-console`, назначаемой
существующему контексту `lead-management` — по образцу `service-topology-console`
(коммит консольной capability контексту-владельцу как уточнение покрытия).

Следствие, обязательное в том же change: `architecture/domain-catalog.yaml`
получает `job-journal-console` в списке capability контекста `lead-management`, а
`docs/domain-model.md` — строку матрицы capability и пояснение «не добавляет
модель». Это требуется и правилом проекта, и проверкой `archlint`
(`validateCatalog`: каждая OpenSpec-capability должна иметь ровно один primary
context в каталоге).

**Почему так:** без записи в каталоге `go -C tools/archlint run .` увидит новую
OpenSpec-capability без владельца и упадёт.

**Альтернатива:** `skip_specs: true` без capability — отклонено, потому что
экран вводит наблюдаемое поведение, а не является чистым рефакторингом.

## Risks / Trade-offs

- **Раскрытие против авто-обновления.** Рассинхрон удержания раскрытых строк
  приведёт к миганию или схлопыванию строк. Компенсация: тот же механизм, что
  для чекбоксов, плюс тесты «раскрытие переживает подстановку фрагмента».
- **Дублирование чтения.** Экран задания читает событие тем же хранилищем, что и
  журнал; при большом числе заданий лишнее чтение допустимо, так как экран
  открывается по одному заданию.
- **Серверный рендеринг против интерактивности.** Раскрытие и удержание — это
  источник JS-ошибок при подменах. Компенсация: `console.js` без inline-скриптов
  (CSP), декларативные атрибуты и минимум логики на клиенте; сервер остаётся
  источником истины.
- **Совместимость тестов.** Разметка журнала меняется, поэтому обновляются
  шаблонные, golden- и view-тесты; это ожидаемая цена, а не регресс.
- **Расширение `SearchJobStore`.** Если для поиска по идентификатору потребуется
  новый метод интерфейса, его придётся реализовать в обоих хранилищах (memory и
  postgres) и контрактных тестах. Компенсация: сначала ограничиться выборкой из
  списка, расширять интерфейс только при явной необходимости.

## Migration Plan

Изменение чисто презентационное и обратно совместимое по данным:

1. Слой `app`: чтение задания и его событий; модель представления.
2. HTTP-адаптер: маршрут `GET /jobs/{id}`, модель `jobView`, шаблон `job.html`.
3. Журнал: компактная строка, `details`-раскрытие, ссылка на экран.
4. `console.js`: удержание раскрытых строк между HTMX-подстановками.
5. `console.css`: стили разворота и экрана.
6. Каталог и модель: `architecture/domain-catalog.yaml`, `docs/domain-model.md`.
7. Тесты: views, шаблоны/golden, `httptest` для нового маршрута; прогон
   `go -C tools/archlint run .`.

Откат — возврат шаблона и `console.js` к прежней разметке; хранилище и данные не
меняются.

1. **Поиск задания по идентификатору в хранилище.** Достаточно ли выборки из
   `ListSearchJobs` для отдельного задания в текущем масштабе (предел журнала —
   100), или сразу добавлять метод поиска по идентификатору в
   `ports.SearchJobStore` и оба адаптера. Не влияет на спеку и разбиение задач:
   реализуем выборкой, расширим при необходимости.
2. **Состав найденных компаний на экране.** Показывать ли список идентификаторов
   найденных компаний ссылками на их карточки (`/cards/{id}`) или только
   количество. Не влияет на спеку, решается при реализации.
