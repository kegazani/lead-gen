## Context

Владелец доступа — `platform-governance`: решение о доступе считается по ролям
актора **из состава конкретного тенанта** (`DecideAccessHandler.Roles` в
`internal/app/query/decide_access.go`); роли тенанта хранятся в агрегате `tenant`
(`platform-governance.tenant_user`). Оператора консолей (`-console-user`,
сейчас `admin`) нет ни в одном тенанте, поэтому экран выбора тенанта и
переключение отказывают, а консоли, определяющие активный тенант из
`?tenant_id`, при пустом параметре падают на конфигурацию процесса
(`lead-management`: `activeTenant` → `-tenant demo`; `request-fulfillment`:
пустой фолбэк). Данные клиентов при этом в базе есть, но не видны оператору.

См. `proposal.md` — мотивацию; спеки `platform-access` и `client-portal` —
требуемое поведение.

## Goals / Non-Goals

**Goals:**

- Один платформенный оператор, заданный конфигурацией, получает доступ ко всем
  активным тенантам без ослабления изоляции для остальных акторов.
- Активный тенант, выбранный оператором, сохраняется между запросами и не
  требует ручного `tenant_id` в адресе.

**Non-Goals:**

- Управление составом операторов через консоль (пока один оператор из
  конфигурации).
- Сводный экран «все тенанты сразу»: консоли работают в контексте выбранного
  тенанта. Сводная диагностика — предмет отдельного change
  (`lead-selection-diagnostics`).
- Изменение модели изоляции для клиентов: клиент по-прежнему видит только свой
  тенант.

## Decisions

### Решение 1. Платформенный оператор как конфигурируемый субъект

`platform-governance` признаёт оператором субъекта из числа заданных
конфигурацией (точка входа передаёт логин оператора консолей). При запросе доступа
`Roles`/`DecideAccess` возвращает платформенному оператору набор прав
администратора платформы для любого **активного** тенанта; для отключённого
тенанта — пусто; для остальных акторов поведение не меняется.

*Альтернатива (отклонена):* заводить оператора администратором в каждый тенант
(в т.ч. задним числом миграцией). Это загрязняет состав пользователей тенанта,
требует миграции существующих тенантов и делает оператора частью данных клиента —
противоречит изоляции и владению `tenant-access`.

### Решение 2. Активный тенант оператора хранится в cookie консоли

Оператор выбирает тенант на экране выбора (владелец `platform-governance`),
выбор записывается в cookie `active_tenant` с `Path=/`. Cookie не различает порт,
поэтому выбор переносится между консолями одного хоста (разные сервисы — разные
порты) — в том числе в консоль управления, у которой нет серверной сессии. Консоль
определяет активный тенант в порядке: `?tenant_id` запроса → cookie выбранного
тенанта → конфигурация процесса. Общий помощник — пакет
`backend/platform/consolescope` (`SetActiveTenant`/`ActiveTenant`).

*Альтернатива (отклонена):* хранить выбор в серверной сессии `consoleauth`.
Консоль управления `platform-governance` сессии не использует (актор берётся из
запроса), поэтому выбранный там тенант не попал бы в общий стор сессий, которые
читают консоли лидов/заявок. Cookie — единственный механизм, общий для всех
консолей на хосте.

*Альтернатива (отклонена):* продолжать прокидывать тенант только по ссылкам
навигации. При открытии консоли по прямому адресу (закладка, переход на другой
порт) контекст теряется — ровно наблюдаемая проблема.

## Risks / Trade-offs

- **Признание оператора по запросу, а не по сессии** → оператор должен
  определяться по субъекту из серверной сессии консоли, а не по `?actor=`.
  Митигируется тем, что консольные guard'ы `platform-governance` берут актора из
  сессии; консоли, читающие актора из запроса (`analytics`), для решения доступа
  оператором не пользуются.
- **Устаревший выбор тенанта после отключения тенанта** → решение о доступе
  перепроверяется на каждом запросе; отключённый тенант даёт отказ, и консоль
  показывает явное состояние, а не данные.
- **Существующие сессии/страницы без выбранного тенанта** → пустой cookie не
  мешает: срабатывает фолбэк на конфигурацию, поведение совместимо.
- **Cookie управляется клиентом** → выбор тенанта — это удобство навигации, а не
  право доступа: переключение проверяется владельцем на сервере, а изоляция
  клиентских данных обеспечивается существующими требованиями изоляции.
- **Параметр `?tenant_id=` в консолях остаётся** → он нужен для совместимости и
  переноса контекста между разделами; разграничение доступа к выбранному
  тенанту проверяется существующими требованиями изоляции и здесь не
  расширяется (отдельный предмет при необходимости).
