## Why

Read-контракт решения оператора по черновику `draftdecision` (владелец —
`outreach-orchestration`, реализация — `query.ApprovedAction.Handle`) возвращает
решение **текущей** версии черновика, **игнорируя запрошенную `DraftVersion`**.
Дефект найден на живой приёмке (`agent-approval-signal`, наблюдение вне scope).

Последствие. Если черновик доработан и по новой версии уже принято решение, запрос
по **устаревшей** версии получает решение **новой** версии: чужое/старое решение
выдаётся за действующее для запрошенной версии. Инвариант спеки «изменённый черновик
требует нового решения» обеспечивается только на стороне потребителя
(`agent-orchestration` сверяет версию до/после), то есть защита стоит на границе
потребителя, а не в контракте владельца. Ошибку в самом контракте нельзя
обнаружить по результату: он выглядит как валидное положительное решение, но
относится не к той версии.

Нарушены два инварианта. (1) Владелец обязан выдавать решение **только** для
запрошенной версии — этого нет. (2) Комментарий самого контракта
(`contracts/outreach-orchestration/draftdecision`) уже декларирует: «запрос версии,
не совпадающей с текущей, не выдаёт старое решение за действующее» — реализация
расходится с собственным контрактом.

## What Changes

- **`query.ApprovedAction.Handle` привязывает решение к запрошенной версии черновика.**
  Решение выдаётся, только если `q.DraftVersion` совпадает с текущей версией
  черновика **и** по этой версии есть решение. Запрос версии, не совпадающей с
  текущей (устаревшей после доработки либо неизвестной), SHALL NOT выдавать решение
  иной версии: возвращается явный исход «решение не найдено» (`ErrDraftDecisionNotFound`).
- **Явные исходы не смешиваются.** Ожидание по текущей версии —
  `ErrDraftDecisionPending`; отклонение — `ErrDraftDecisionRejected`; отсутствие
  черновика/решения или несовпадение версии — `ErrDraftDecisionNotFound`;
  недоступность источника — честная недоступность (не «решение не принято»).
- **Тесты владельца.** Добавляются сценарии: запрос точной версии; запрос устаревшей
  версии после доработки (в том числе когда по текущей версии уже есть решение) —
  решение не выдаётся; ожидание; отсутствие; отклонение; недоступность (через
  контракт/порт).

Публикуемая форма и семантика ошибок контракта `draftdecision` **не меняются**: все
необходимые исходы (`ErrNotFound`/`ErrPending`/`ErrRejected`/`ErrUnavailable`) уже
объявлены и уже документируют привязку к точной версии. Изменение — исправление
реализации владельца под объявленную семантику, а не новое расширение контракта.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `outreach-approval` (владелец `outreach-orchestration`): добавляется требование
  «Решение читается только по запрошенной версии черновика» — чтение решения
  привязано к точной версии, несовпадение версии даёт явный исход, а не решение
  другой версии.

**Обоснование состава Modified.** Дефект — в поведении владельца очереди
утверждения при чтении решения, то есть в capability `outreach-approval`. Новых
capability, агрегатов, владения и межконтекстных связей не появляется; публикуемая
форма контракта не меняется (только его соблюдение), поэтому другие capability и
каталог границ не затрагиваются.

## Impact

**Затрагиваемые bounded contexts.**

- `outreach-orchestration` — владелец read-контракта `draftdecision`: исправляется
  use case `query.ApprovedAction.Handle` и его тесты. Контракт, HTTP-поверхность и
  перевод исходов (`agent_approval_port.go`, `handlers_approved_action.go`) уже
  несут нужные исходы — правок не требуют.
- `agent-orchestration` — потребитель `draftdecision` (шаг `send`): **изменений не
  требуется**. Потребитель отображает `ErrNotFound` и `ErrPending` в один исход
  «отправка не санкционирована» (`ErrApprovedActionPending`), поэтому исправление
  не меняет наблюдаемого поведения потребителя, а лишь закрывает дыру «чужое
  решение по чужой версии».

**Код.** `backend/contexts/outreach-orchestration/internal/app/query/approved_action.go`
(и его тест) — привязка к запрошенной версии и явные исходы. Контракт
`contracts/outreach-orchestration/draftdecision` правится только при необходимости
(семантика ошибок уже достаточна) — аддитивно. Миграций и схем нет.

**Доменная модель и документация.** Каталог `architecture/domain-catalog.yaml`,
`docs/domain-model.md` и диаграммы **не меняются**: capability, агрегаты, владение
и связи те же (исправление поведения существующего контракта). Спека
`outreach-approval` обновляется дельтой (ADDED-требование).

**Риски.** (1) Потребитель может полагаться на выдачу решения «по текущей версии»
при запросе устаревшей — это и есть дефект, и такое поведение не санкционировано
ни спекой, ни контрактом; потребитель обрабатывает `ErrNotFound` безопасно.
(2) Новый вид ошибки контракта сломал бы невыправляемый в этой зоне потребитель
(`backend/cmd/lead-gen/**` маппит неизвестную ошибку в недоступность) — поэтому
новые исходы не вводятся, используются существующие.
