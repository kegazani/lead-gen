# tasks.md — request-failure-terminal-state

Задачи открыты: прежние отметки «выполнено» относились к синхронному rerun и бесконечной компенсации, которые не соответствуют выбранному решению B2:1. Закрывать задачу можно только после её наблюдаемого критерия; общий гейт и реальные инфраструктурные проверки обязательны.

Реализованный batch не закрывает 2.1–2.3: durable admission имеет только частичный контур, dispatcher/reconciler и verified terminal source отсутствуют. v2 rerun остаётся явно заблокированным; менять этот gate без trusted verifier запрещено.

## 1. Хранилище intent и поколений попыток

- [x] 1.1 Спроектировать доменные типы `ExecutionIntent`, `CommandID`, generation и явное состояние `LeadTarget` (`explicit`/`unspecified`/`unknownLegacy`); повтор `CommandID` с отличающимися параметрами отклонять. **Верификация:** доменные тесты доказывают идемпотентный повтор и конфликт параметров без изменения сохранённого состояния.
- [ ] 1.2 Добавить additive PostgreSQL migration и адаптеры для intent/attempt, reconcile state и append-only resolutions. Хранить unverified runtime observations отдельно от verified runtime resolution; только trusted reconciler/history verifier с отдельной узкой capability вправе создавать verified resolution после проверки identity и полной Temporal history. Наблюдение, target resolution, совпадение ID/runID, actor-строка или fingerprint не устанавливают terminal и не открывают admission. Версии resolutions append-only с монотонной expected revision, CAS и детерминированным current pointer/цепочкой supersedes; устаревшая/конкурентная запись конфликтует, выбор не зависит от timestamp (одинаковые timestamps допустимы). Evidence fingerprint — каноническая lowercase SHA-256 по определённому безопасному evidence либо явным content-hash metadata; он не является proof/auth. Memory и PostgreSQL соблюдают одинаковые format, CAS, чтение current resolution и конфликтные semantics. DB запрещает UPDATE/DELETE и `BEFORE TRUNCATE`; зафиксировать, что trigger не защищает от владельца таблицы/superuser. В рамках migration follow-up 0008/0009 (0005–0008 неизменны) обеспечить составной FK `(request_id, tenant_id)` к `request(id, tenant_id)` с `ON DELETE RESTRICT` и оба `BEFORE STATEMENT TRUNCATE` triggers, проверяя в каталоге PostgreSQL событие, функцию-обработчик и enabled state, а не только имя. До добавления FK проверить все существующие rows; при mismatch/orphan не удалять и не изменять audit-данные. Роли приложения и их grants относятся к отдельному OpenSpec change `service-per-context`, не к этой задаче. Неполная audit-запись запрещена. Legacy request без доказуемого target/attempt остаётся unknown: migration не выводит target из snapshot и не создаёт синтетическую попытку; admission остаётся blocked до verifier-а. **Верификация этого migration follow-up:** isolated upgrade с данными через все миграции до 0009; UPDATE/DELETE/TRUNCATE отклоняются на legacy и revision таблицах; удаление родительской заявки с revision отклоняется; обе сохранённые audit-строки остаются. Очистка contract suite пересоздаёт только изолированную схему и не применяет `TRUNCATE CASCADE`. Задача 1.2 целиком остаётся открытой до всех остальных критериев: legacy target/attempt unknown, не `0`; memory/PG contract tests по CAS, fingerprint и gate; отсутствие неполной audit-записи. Она не утверждает, что live Temporal authenticity verifier реализован. Live user compose не используется.
- [ ] 1.3 Расширить общий contract suite memory/PostgreSQL сценариями atomic claim, replay команды, generation fencing, unknown target, resolution audit, receipts и admission. Replay того же `CommandID` с идентичными параметрами возвращает существующий intent идемпотентно; новый `CommandID` при ACTIVE/UNKNOWN отклоняется до repository record, без queued бизнес-generation. Сохранить queued/claimed только для уже принятой единственной generation. **Верификация:** один общий suite проходит против memory и PostgreSQL; отдельно проверяются (а) rejection NEW command до записи при ACTIVE/UNKNOWN и (б) replay того же CommandID в том же состоянии с ответом существующего intent и без новой строки/attempt; PostgreSQL suite использует реальную изолированную БД.
- [x] 1.4 Уточнить и реализовать transaction/claim contract. PostgreSQL claim/renew использует часы БД; memory использует единый injected clock. State transitions parity обязательна. Один общий эксклюзивный context-aware gate/channel semaphore защищает полный memory UoW lifecycle clone → callback → prepare → commit и все прямые доступы repository/journal, включая все UoW; никакой прямой доступ не ждёт скрытый `sync.RWMutex` после gate и ни один writer не обходит gate. До захвата, во время ожидания, после захвата и непосредственно перед callback учитывается отмена context: если он отменён до callback, `WithinTransaction` возвращает cancellation без callback и commit. Gate освобождается при возврате, ошибке и panic. Commit делает финальную проверку cancellation до публикации, затем публикует состояние атомарно и безошибочно. Callback получает derived transaction-scoped context и обязан передавать его во вложенные вызовы того же repository; такой `WithinTransaction` использует `txCtx`/производный контекст и promptly возвращает typed `ports.ErrNestedTransaction` (без reentrant lock). Если callback отбросил контекст и вызвал тот же repository с `context.Background()` или исходным context, это нарушение API-контракта: generic goroutine nesting надёжно обнаружить нельзя. Callback ограничен транзакционными доменными вычислениями и tx ports; внешние I/O запрещены. Это проверяется spies/review call graph, но механически изолировать callback нельзя. Cancellation во время уже исполняющегося callback не гарантирует остановку некооперативного callback. **Верификация:** тестовый hook `Contended`/`Acquired` устанавливается до тестов и подтверждает реальную конкуренцию/захват; timeout — только watchdog, не доказательство scheduling. Проверить полную сериализацию lifecycle, all-before/all-after visibility, отсутствие частичной публикации и rollback при callback error/panic. Отмена до acquire, во время ожидания и после acquire/до callback подтверждает cancellation без callback/commit; ошибка и panic подтверждают освобождение gate. Commit cancellation проверяется до публикации. Вложенный вызов с производным tx context promptly возвращает `ports.ErrNestedTransaction`. Hook не должен создавать нежелательный production seam: допустимы internal/injected fake gate на адаптерах. Отдельный PostgreSQL suite подтверждает собственные transaction/claim/state invariants; memory gate не является доказательством PostgreSQL. Задача остаётся открытой до прохождения этих критериев.

## 2. Домен, команда и HTTP intent

- [ ] 2.1 Объединить approve, rerun и прямой workflow HTTP endpoint в одни owner admission commands и единую транзакцию: проверить прежнее состояние, принять/отклонить, записать immutable intent + `attempt_id`/generation/`CommandID` + distinct stable `workflow_id` и outbox entry. Replay сравнивает полный canonical semantic payload (kind, reason, target state/value, request version, offer ID/revision/snapshot reference и прочие lifecycle-поля); identical replay возвращает прежнюю receipt раньше lifecycle gate, отличие конфликтует. Новый `CommandID` при ACTIVE/UNKNOWN отклоняется до любой записи. Rerun допускается только после доказанного terminal; без verifier остаётся blocked, это не критерий завершения dispatcher path. `request_id` остаётся идентификатором заявки, `workflow_id` — стабильный Temporal WorkflowID, они различны. Temporal server выдаёт RunID только после старта. **Зависит от:** 1.2, 1.4. **Верификация:** command tests для всех трёх входов доказывают один transaction/outbox contract; конкурентные NEW команды дают одну admission; same-CommandID replay не создаёт новую запись/attempt; ACTIVE/UNKNOWN отклонён без записи; terminal допускает новый distinct CommandID.
- [ ] 2.2 Согласовать HTTP ответы/ошибки и защиту API: durable commit предшествует принятому ответу (`202` с `request_id`, `workflow_id`, `attempt_id`, generation и текущим состоянием); конфликт CommandID и admission rejection имеют явные неперепутанные ответы; tenant scope и CSRF проверяются для соответствующих cookie-authenticated mutation endpoints. Query текущего состояния использует owner storage и остаётся доступным при outage Temporal runtime. HTTP handlers не вызывают Temporal starter синхронно. **Зависит от:** 2.1. **Верификация:** HTTP integration scenarios проверяют 202 только после commit; ACTIVE/UNKNOWN rejection и отсутствие intent/outbox; same CommandID replay возвращает существующий результат; конфликт параметров; cross-tenant отказ; mutation без CSRF отказана; query возвращает durable state при недоступном Temporal; spy подтверждает отсутствие прямого starter call.
- [ ] 2.3 Обеспечить durable intent admission и запрет нового бизнес-намерения при предшественнике ACTIVE/UNKNOWN до сохранения любого intent/outbox бизнес-generation. Единственный автоматический технический dispatcher/reconciler повторяет только уже принятую команду; автоматического бизнес-rerun нет. Запись resolution не обходит runtime gate без независимого подтверждения terminal и безопасного доменного перехода. **Зависит от:** 1.2, 2.1. **Верификация:** сценарии для ACTIVE, UNKNOWN и неизвестного legacy target проверяют отказ без новой intent/outbox/generation; target resolution без runtime evidence оставляет отказ; terminal + безопасный переход допускает отдельную новую команду.
- [ ] 2.4 Добавить durable embedding preparation после принятия intent, привязанную к неизменяемому versioned/fingerprinted input snapshot. Ошибка — явно наблюдаемое retryable состояние подготовки той же принятой команды, не повторный admission/business run. **Зависит от:** 2.1, 2.2. **Верификация:** изменение live input не меняет принятую version/fingerprint; retry использует те же version/fingerprint и attempt; preparation failure виден, не создаёт новый attempt и не запускает бизнес-rerun.

## 3. Протокол старта и dispatcher

- [ ] 3.1 Реализовать единственный dispatcher, атомарно захватывающий accepted attempt и передающий `request_id`, `attempt_id`, generation, `command_id` и immutable snapshot; оставить стабильный `workflow_id`. `run_id` назначает Temporal server, не dispatcher. **Зависит от:** 1.2, 1.4, 2.1. **Верификация:** параллельные dispatcher проходы для одного attempt не создают более одного принятого RunID; технические retries используют тот же attempt.
- [ ] 3.2 Связывать server `run_id` с attempt только после проверки request/attempt/generation/command/params в candidate payload. `AlreadyStarted` — подтверждение только при полном совпадении candidate identity; несовпадение даёт UNKNOWN/blocked. **Зависит от:** 3.1. **Верификация:** same candidate идемпотентно подтверждается; foreign candidate отклоняется; один attempt никогда не принимается с другим RunID.
- [ ] 3.3 Запретить admission нового бизнес-запроса при ACTIVE/UNKNOWN, не создавать очередь; технические повторы dispatcher относятся только к тому же уже принятому intent. **Зависит от:** 2.1, 3.2. **Верификация:** tests на active run, ambiguous Describe и UNKNOWN подтверждают явный admission rejection и отсутствие следующего generation/intent; после terminal проверяется успешный admission нового generation с новым CommandID.
- [ ] 3.4 Подключить ровно один dispatcher/reconciler в реальную worker wiring/composition с настроенным реальным Temporal endpoint, namespace и task queue; конфигурация не содержит credentials и не вводит in-memory production fallback/no-op. **Верификация:** изолированный интеграционный тест запускает worker с настоящим Temporal test server/environment и owner PostgreSQL; недоступность/ошибочная конфигурация явно видны, а после восстановления Temporal сохранённая intent запускается тем же attempt. Проверить запуск только одной активной dispatcher/reconciler роли.
