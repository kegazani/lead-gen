## Context

См. `proposal.md` — Why. Что важно для дизайна из текущего состояния:

- Граница уже есть: `crawl.Port` (`Crawl`/`Extract`) и `search.Port` объявлены в `contracts/integration-platform`, адаптер Firecrawl их реализует, ядро `RunSearch` (`backend/contexts/lead-management/internal/app/run_search.go`) работает только через порт. Замена движка — новый адаптер, не правка ядра.
- `crawl.Request` фиксирует бюджет/глубину/фильтры путей абстрактно, без терминов Firecrawl. Прокси и режим robots в контракт сейчас не входят.
- Эскалация на LLM живёт в app-слое (`RunSearch.processPage`): слои 1–2 (markdown + regex) → при низком качестве вызов `crawl.Port.Extract`. То есть логика «когда эскалировать» — не в адаптере.
- Лимиты/бюджет: `firecrawl-credit-budget` — кредитная обёртка `Guard`/`Task` вокруг Firecrawl; `manual-crawl-params-and-company-target` снял обязательные лимиты обхода. Кредиты — понятие Firecrawl.
- Конфигурация и впрыск — `backend/cmd/lead-gen` (флаги/env, `NewFirecrawl`, `NewFirecrawlGuard`); развёртка — `compose.yaml`, `deploy/services.yaml`.
- `docs/crawl4ai-playbook.md` зафиксировал приёмы Crawl4AI (навигация по релевантности, слои экстракции, OCR, граница автономности) — источник для дизайна.

## Goals / Non-Goals

**Goals:**

- Self-hosted движок краулинга за существующим портом, с возможностью вернуться к Firecrawl конфигурацией.
- Управляемый прокси-пул с уровнями стоимости, расширяемый до провайдера без смены политики.
- Режим robots.txt, управляемый конфигурацией (по умолчанию выключен), с фиксацией в журнале задания.

**Non-Goals:**

- Удаление адаптера Firecrawl (остаётся альтернативой).
- Автономная кликательная навигация (`/interact`/`/agent`-класс) — non-goal и по `osint-enrichment`.
- Выбор коммерческого прокси-провайдера — интерфейс закладываем, провайдер позже.
- Изменение доменных агрегатов `lead-profile`/`contact` и их инвариантов.

## Decisions

### Решение 1. Движок — Crawl4AI контейнером; адаптер — HTTP-клиент на stdlib

Crawl4AI (Apache-2.0) запускается отдельным контейнером с HTTP-сервером; наш адаптер `backend/contexts/integration-platform/internal/adapters/crawl4ai` — HTTP-клиент (stdlib) за `crawl.Port`/`search.Port`, по образцу `firecrawl`. Move over: JS-рендер и навигация по релевантности — внутри Crawl4AI (`BestFirstCrawlingStrategy` + `KeywordRelevanceScorer`, `AsyncUrlSeeder`, `FilterChain`/`URLPatternFilter`), наш код — маппинг запроса, нормализация ответа, дедупликация.

**Почему не colly+chromedp (чистый Go):** совпадает со стеком и не тянет Python, но требует самим собрать навигацию по релевантности, SPA-ожидание и антибот — месяцы работы ради паритета с готовыми стратегиями Crawl4AI. Оставляем как запасной путь за тем же портом, если контейнер окажется неудобен.

**Почему не остаёмся только на Firecrawl:** зависимость от чужого облака, ключа и кредитов; ротация IP и robots — не наши. Выбор движка — конфигурация (`crawl_engine=firecrawl|crawl4ai`), Firecrawl не удаляем.

### Решение 2. Прокси-политика — в адаптере, источник — интерфейс

Прокси нужны движку, а не ядру, поэтому политика живёт в адаптере (`adapters/crawl4ai/proxy`), в `crawl.Request` не протекает. Две оси:

```text
  Source (откуда прокси)        Policy (как выбирать)
  +---------------------+       +---------------------------------+
  | StaticList (env)    | ----> | tier: cheap -> premium          |
  | Provider (позже)    |       | sticky per registrable domain   |
  +---------------------+       | health: ok / bad / quarantine   |
         складываются           | escalate on block/error         |
                                +---------------------------------+
```

- `Source` — интерфейс (`Proxies(ctx) ([]Proxy, error)`), сейчас одна реализация — статический список из конфигурации; провайдер добавится второй реализацией, обе складываются в один пул.
- `Proxy` несёт `URL`, `Tier` (`cheap`/`premium`), источник — для учёта.
- Выбор: дешёвый уровень первым; при блокировке/ошибке — повтор на `premium`; привязка к домену (sticky) на время успешного обхода; неработающие — в карантин с возвратом по таймауту.
- Признак блокировки — по коду ответа/странице-заглушке; точный набор сверяется в задаче (эвристика движка).
- Конфигурация уровней: строка вида `scheme://user:pass@host:port#tier`, секреты — env, вне репозитория; логи без учётных данных.
- Формат `ProxyConfig`/ротации в Crawl4AI сверяется по документации версии контейнера (см. Open Questions) — интерфейс `Source` от него не зависит.

### Решение 3. Режим robots.txt — собственная ответственность адаптера

С self-hosted движком robots перестаёт быть поведением провайдера: адаптер сам решает, запрашивать ли `robots.txt` и фильтровать ли пути. Вводится конфигурация `crawl_respect_robots` (**по умолчанию `false`** — обход без проверки robots.txt, как решил владелец продукта). Авторизацию, платные зоны и ограничения доступа адаптер не обходит ни при каком значении.

Альтернатива — оставить robots безусловным (вариант C прошлого обсуждения) — отклонена владельцем.

**Следствие для журнала задания.** Требование фиксирует режим в журнале поиска: `SearchJobPayload` (порт `lead-management`) получает признак эффективного режима robots, а снапшот задания — отображение режима. Это правка wire-формата задания обратно совместимая (старые задания читаются как дефолт).

### Решение 4. LLM-экстракция — эскалацию решает Go, вызов выполняет адаптер

Логика «когда эскалировать» остаётся в `RunSearch` (слои 1–2 → `Extract` при низком качестве) — не дублируется в движке. Внутри `crawl.Port.Extract` адаптер Crawl4AI выполняет `LLMExtractionStrategy` по схеме `name/email/phone/role`, используя наш DeepSeek (`base_url`+`model`+key), уже присутствующий в конфигурации.

Альтернатива — отдельный `Extract` в `llm.Port` на Go-стороне: даёт более простой фейк в тестах, но разносит один шаг на два вызова и требует расширять `llm.Port`. Отклонена для первого этапа; пересмотреть, если качество LLM-экстракции Crawl4AI окажется нестабильным.

### Решение 5. Лимиты вместо кредитов; кредитный бюджет остаётся у Firecrawl

Self-hosted не тратит кредиты Firecrawl. Вместо кредитной обёртки — собственные лимиты адаптера: параллелизм, частота запросов, глубина/страницы (по конфигурации, не обязательные — см. `manual-crawl-params-and-company-target`). `firecrawl-credit-budget` не меняется: он остаётся у Firecrawl-адаптера и отключается вместе с движком.

### Решение 6. Развёртка: контейнер в compose и services.yaml

Crawl4AI добавляется сервисом в `compose.yaml` (для локального запуска) и описывается в `deploy/services.yaml`; `integration-platform`/`lead-management` получают адрес движка, прокси-конфигурацию и `crawl_respect_robots` через env. Секреты (прокси, LLM-ключ) — вне репозитория.

### Решение 7. Capability `crawler-proxy-pool` и обновление каталога

Поведение пула специфицируется новой capability `crawler-proxy-pool` (владелец `integration-platform`). Каталог `architecture/domain-catalog.yaml`, `docs/domain-model.md` и диаграммы обновляются в этом же change (иначе `archlint` падает). Доменных агрегатов и domain events не появляется — это операционная инфраструктура адаптера, как `firecrawl-credit-budget`.

## Risks / Trade-offs

- **[Игнор robots.txt по умолчанию]** Юридический и репутационный риск: в отдельных юрисдикциях обход запретов robots оспаривается. → Осознанное отклонение, фиксируется в спеке; юридический гейт `full-enterprise-core-scope` 1.1 обязан это подтвердить; авторизация/платные зоны не обходятся ни при каком режиме.
- **[Качество и стабильность прокси]** Дешёвые списки часто мёртвые. → Уровни, карантин, эскалация на премиум; учёт по источнику; провайдер добавляется позже как второй `Source`.
- **[Ресурсоёмкость Playwright]** Контейнер Crawl4AI тяжёл по CPU/RAM, параллелизм ограничен. → Собственный лимитер, ограничение параллельных браузерных сессий, вынос в отдельный сервис.
- **[Расхождение качества парсинга с Firecrawl]** Другой движок — другой Markdown/навигация. → Слои экстракции и LLM-эскалация сохраняются; метрика «доля страниц с извлечёнными полями»; Firecrawl остаётся для сравнения и отката.
- **[Зависимость спеки от архива `mvp-lead-search`]** MODIFIED `osint-enrichment` требует, чтобы основная спека уже существовала. → Архивация `mvp-lead-search` (и других завершённых change'ей) выполняется до архивации этого change'а; `validate` уже сообщает об этом.
- **[Расширение wire-формата задания]** Признак режима robots в задании. → Обратная совместимость: отсутствие поля = дефолт.

## Migration Plan

1. Добавить адаптер `crawl4ai`, прокси-политику и конфигурацию, не меняя поведение по умолчанию (движок — Firecrawl).
2. Добавить признак режима robots в задание и журнал (дефолт — выключено).
3. Включить `crawl_engine=crawl4ai` в тестовом контуре, прогнать e2e и приёмку на реальных сайтах.
4. Переключить конфигурацию по умолчанию на Crawl4AI после подтверждения паритета.
5. **Откат:** сменить `crawl_engine` обратно на `firecrawl` (код Firecrawl остаётся); прокси-конфигурация и robots-флаг не влияют на Firecrawl-путь.

## Open Questions

- Точный формат прокси-конфигурации и признак блокировки в актуальной версии Crawl4AI (`ProxyConfig`, ротация, `robots.txt` support) — сверяется по документации контейнера в задаче 1.x; интерфейс `Source`/политика от этого не зависят.
- Границы «соблюдения robots.txt» в Crawl4AI (собственный `RobotsParser` или внешняя проверка в адаптере) — если движок не умеет, проверка делается в адаптере до рендера.
- Нужен ли OCR (email в картинках) в первой версии или отдельным шагом — зависит от приёмки на реальных сайтах.
