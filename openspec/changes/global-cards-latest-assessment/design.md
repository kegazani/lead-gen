## Context

См. `proposal.md` — Why. Существенное для подхода:

- `LeadAssessment` — aggregate root контекста `lead-management`, ключ пары
  (job, company), хранение в `LeadAssessmentStore` (memory и postgres). Запросов
  «последняя оценка по компании» в порту нет: есть только `GetByJobAndCompany`,
  `ListByJob`, `VerdictDistribution`.
- Оценки пишутся **по ходу** прогона (`run_search.go`: `Assess` на каждую
  извлечённую компанию, `state.verdicts` → `rep.verdicts`), поэтому к моменту
  появления карточки в результатах вердикт уже доступен для чтения.
- Ссылки на результаты задания (`SearchJob.ResultRef`) фиксируются только в
  `finishCancelled` и в финале `RunSearch`: во время прогона список пуст, из-за
  чего пусты и экран задания («Найденные компании»), и `/cards?job=`.
- Прогресс уже публикуется на границах шагов — `progressReporter.flush`
  вызывается на каждой фазе и странице; там же пишутся `RecordProgress` и
  `RecordEvent`.
- Витрина карточек уже умеет рисовать группу и подсветку `is-no-email`
  (`cards.html`, `console.css`); `job.html` рисует найденные компании простым
  списком без email и подсветки. Авто-обновление по htmx есть только у журнала
  (`dashboard.html`).

## Goals / Non-Goals

**Goals:**

- Общая витрина `/cards` делится по последней по времени оценке компании по
  всем заданиям; неоценённые — «Не оценено» во второй группе.
- Экран выполняющегося задания показывает уже извлечённые компании и
  обновляется без ручной перезагрузки.
- Компании без email подсвечены красным и на экране задания.

**Non-Goals:**

- Изменение модели/инвариантов `lead-assessment` и перенос оценки между
  заданиями. Проекция «последняя оценка» — только представление витрины.
- Новые domain events, агрегаты, миграции схемы (запрос читающий, колонки уже
  есть).
- Изменение логики `RunSearch` (порядок фаз, добор целей, бюджеты) — трогаем
  только фиксацию результата и экран.
- Единая «глобальная оценка» как записываемое свойство компании.

## Decisions

### Решение 1. Порт «последняя оценка по компаниям»

Добавляем в `LeadAssessmentStore` читающий метод:

```go
// LatestByCompany возвращает последнюю по времени оценку каждой из переданных
// компаний по всем заданиям. Компания без оценок в результат не попадает.
LatestByCompany(ctx context.Context, companyIDs []string) (map[string]*domain.LeadAssessment, error)
```

- «Последняя» — по `updatedAt` (upsert по паре перезаписывает оценку), при
  равенстве — по `createdAt`, затем по `jobID` для детерминированности.
- Аргумент — список компаний видимой страницы (`ListCards` ограничен лимитом),
  чтобы не тянуть весь корпус оценок.
- Реализации: memory — обход карты с выбором максимума по каждой компании;
  postgres — `SELECT DISTINCT ON (company_id) ... ORDER BY company_id, updated_at DESC, created_at DESC, job_id`.

**Альтернативы.** Прогонять `ListByJob` по всем заданиям — N запросов и чтение
лишнего; хранить «последнюю оценку» отдельным полем компании — превращает
проекцию в записываемое свойство и нарушает инвариант переноса. Отклонены.

### Решение 2. Группировка общей витрины

`handleCards` без `?job=` строит строки новой функцией
`cardRowsWithLatestAssessments(cards, latest)`: «Подходит» → `cardGroupFits`,
«Гипотеза»/«Не подходит» → `cardGroupOther` с подписью; отсутствие оценки →
`cardGroupOther`, подпись «Не оценено», класс `unknown`. Логика подписи и класса
переиспользуется (`verdictLabel`/`verdictClass`), как в job-контексте.

**Почему не отдельная вкладка «Без оценки»:** выбран вариант «Не оценено» во
второй группе; третья вкладка усложняет переключатель без запроса.

### Решение 3. Инкрементальная фиксация `ResultRef`

`RunSearch` пишет `ResultRef` не только в финале, а на границах `flush`
(фаза/страница), синхронно с публикацией прогресса. Для одного места записи
`progressReporter` получает поставщика результата:

```go
// result — снимок найденных компаний на момент flush; nil — не фиксировать.
rep.result(func() []string { return sortedCompanyIDs(companyIDs) })
```

В `flush` появляется запись `store.RecordResult(ctx, id, result())` **только при
изменении** набора (грязный флаг), ошибка логируется и не прерывает задание —
как у `RecordProgress`/`RecordEvent`.

**Альтернативы.** Писать `RecordResult` на каждой найденной компании — лишние
записи на каждую компанию; не менять ничего и достраивать список во время чтения
из событий/прогресса — прогресс не несёт идентификаторов компаний, а состав
карточек требует их. Отклонены.

### Решение 4. Живое обновление экрана задания

`job.html` получает htmx-опрос по образцу журнала: пока задание не терминальное
(`AutoRefresh`), контейнер с экраном несёт
`hx-get="/jobs/{id}" hx-trigger="every 2s" hx-swap="outerHTML"`. Терминальные
задания опроса не получают.

**Почему 2s:** тот же интервал, что у журнала (`dashboard.html`), — единообразие
поведения и нагрузки.

### Решение 5. Email и подсветка на экране задания

`jobCompanyRow` расширяется полями `Email` и `NoEmail`; `jobFrom` для списка
компаний задания получает контакты **пакетно** тем же способом, что `ListCards`
(один запрос на список, без запроса на каждую компанию). `job.html` рисует
строку найденной компании с email и классом `is-no-email` — визуально и
семантически как в `cards.html` (текстовая пометка «нет email» + `aria-label`),
переиспользуя существующие стили `console.css`.

**Почему не переиспользовать `cards.html` целиком:** модель экрана задания несёт
вердикт, основания и источники, которых в витринной карточке нет; расширение
строки компании дешевле и не тянет переключатели витрины на экран задания.

### Доменная архитектура

Owning context — `lead-management`. Aggregate root — `lead-assessment`; новых
агрегатов и domain events нет, межконтекстных контрактов нет. Проекция
«последняя оценка» — производное представление чтения и не объявляется
свойством компании, поэтому `architecture/domain-catalog.yaml`, `docs/domain-model.md`
и диаграммы владения не меняются (обосновано инвариантом каталога «оценка
привязана к паре (job, company) и не переносится между заданиями»).

## Risks / Trade-offs

- [Дополнительные записи `RecordResult` на границах flush] → писать только при
  изменении набора; частота совпадает с уже существующими записями прогресса и
  событий; ошибка записи не влияет на исход задания.
- [Стоимость `LatestByCompany` на 200 карточек] → читающий запрос по
  ограниченному списку id с индексом по `(company_id, updated_at)`; memory-реализация
  линейна по числу оценок.
- [«Последняя оценка» может вводить в заблуждение, если она получена в другом,
  незнакомом оператору задании] → подпись вердикта на глобальной витрине остаётся
  ориентиром; контекст оценки доступен в карточке; доменный инвариант не нарушен.
- [Опрос экрана задания раз в 2s нагрузка] → включается только для незавершённых
  заданий, как в журнале.
- [Расхождение «Не оценено» между job-контекстом и общей витриной] → одна и та же
  функция подписи/класса для обоих путей.

## Migration Plan

Изменение аддитивно: добавляется читающий метод порта (миграция схемы не нужна),
запись `ResultRef` использует существующий столбец, поведение экранов меняется
без миграции данных. Откат — возврат шаблонов/вызовов; записанный `ResultRef`
остаётся корректным.
