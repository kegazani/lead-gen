## Последовательный демонстрационный путь

- [ ] 1. Проверить существующий стенд, при его блокировке поднять изолированный dev-контур из текущих исходников и выполнить первый ручной crawl через UI. Проверка: записать препятствия старого Compose (`login`, отсутствие password/release mounts, `SECRET_GENERATION`) и исход свежего запуска в изоляции; основная БД и пользовательский Compose не меняются.
- [ ] 2. Сверить и при необходимости минимально исправить существующую регистрацию/profile approval, форму заявки (offer/services отдельно от desired leads) и operator approval. Проверка: компания проходит существующие UI шаги, request сохраняет оба разных текста и одобряется.
- [ ] 3. Устранить только блокеры, мешающие approval → существующий реальный тематический Firecrawl crawl → реальные LLM emails для найденных лидов независимо от target shortfall. Использовать sender facts из доступного состояния компании; добавлять snapshot только если без этого путь не работает. Проверка: относящиеся к сценарию тесты и код успешно собирается; сценарий показывает реальный crawl и письма, без fabricated output.
- [ ] 4. Обеспечить в существующем intake/operator разделе «Исполнение» доступ к заявке после запуска и показать состояние workflow (в работе/завершено/ошибка), найденные лиды и сформированные письма; завершённая заявка не должна пропадать из доступного оператору списка. Проверка: оператор может открыть request из очереди/истории после завершения, видит фактическое состояние и сохранённые письма; отдельная capability, editorial approval flow и новый самостоятельный экран не добавляются.
- [ ] 5. Выполнить один сквозной acceptance на одном свежем tenant через UI: регистрация/profile approval → заявка → approve заявки → реальный crawl → LLM emails видны оператору. Проверка: сохранён воспроизводимый результат одного прогона; запуск доставки/SMTP и отдельного approve/reject писем не требуется и не выполняется.
