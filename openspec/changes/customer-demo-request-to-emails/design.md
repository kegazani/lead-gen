## Context

Демонстрация опирается на существующий регистрационный поток, request approval, Firecrawl search/crawl, LLM generation и операторский экран intake. Цель — увидеть сформированные письма после реального поиска, а не построить полный editorial/delivery lifecycle.

## Goals / Non-Goals

**Goals:** один новый tenant через UI; offer отдельно от описания желаемых лидов; approve заявки запускает существующий Firecrawl путь; реальный LLM формирует тематические письма найденным лидам; оператор может найти исполнение в существующем разделе «Исполнение» и открыть результат после завершения workflow.

**Non-Goals:** доставка/SMTP; отдельное approve/reject писем; новый capability или экран; exact-version editorial CAS; frozen sender snapshot, если актуальные данные пользователя доступны и работают; PG upgrade/CAS/legacy replay hardening; no-recipient acceptance; полный no-action-approved sweep; recovery/hardening; новый forced-crawl mode.

## Decisions

1. **Повторно использовать существующие UI и доменные потоки.** Регистрация и profile approval остаются как есть. Клиент создаёт request с отдельными полями offer/services и желаемых лидов; оператор одобряет request обычным экраном.
2. **Не добавлять режим обхода.** Одобрение использует существующий crawl/search путь Firecrawl. Первый реальный прогон делается на новом tenant с пустым lead pool, чтобы проверить, вызывает ли текущий путь реальный тематический crawl.
3. **Генерировать после поиска независимо от shortfall.** Для найденных лидов запрашивается письмо и при достижении, и при недостижении target. Ноль результатов означает ноль писем, не успешный синтетический результат. Используется реальная LLM.
4. **Данные отправителя — минимально необходимые.** Генерация использует текущие факты компании, доступные через уже работающий контур. Замороженный snapshot добавляется только если без него сценарий фактически не работает.
5. **Исполнение и письма остаются доступны в существующем operator UI.** Раздел «Исполнение» показывает заявки после запуска, в том числе завершённые, и ведёт на существующий approval/result экран с состоянием, найденными лидами и черновиками. Не вводятся отдельная editorial capability, отдельное решение, outreach campaign/handoff или новый самостоятельный экран.
6. **Отправка вне сценария.** Не запускать SMTP/sender. Не расширять работу ради гарантий отсутствия любого delivery-side effect за рамками подтверждения, что выбранный UI-сценарий не отправляет письма.

## Risks / Trade-offs

- Реальный crawl может выявить инфраструктурный или конфигурационный блокер. Сначала выполнить его через интерфейс; фиксировать фактический блокер и исправлять только если он препятствует сквозному сценарию.
- Firecrawl/LLM и действующие credentials обязательны для единственной live acceptance; без них готовность не заявлять.
- Текущие данные профиля могут оказаться недостаточны для тематичного письма; только тогда рассматривать минимальный доступный контекст, не вводя обязательный frozen snapshot заранее.
- Сформированные письма могут пока не отображаться в имеющемся экране; допускается минимально показать результат генерации в существующем intake/request view, без нового capability и без требования exact-version CAS.

## Migration Plan

Не планировать миграции заранее. Сначала пройти реальный сценарий на интерфейсе и выявить блокер. PostgreSQL upgrade/CAS, legacy Temporal replay и обратная совместимость не являются acceptance-критериями этого demo change.
