## Context

Демонстрация опирается на существующий регистрационный поток, request approval, Firecrawl search/crawl, LLM generation и операторский экран intake. Цель — увидеть сформированные письма после реального поиска, а не построить полный editorial/delivery lifecycle.

## Goals / Non-Goals

**Goals:** один новый tenant через UI; offer отдельно от описания желаемых лидов; approve заявки запускает существующий Firecrawl путь; реальный LLM формирует тематические письма найденным лидам; оператор может найти исполнение в существующем разделе «Исполнение» и открыть результат после завершения workflow.

**Non-Goals:** доставка/SMTP; отдельное approve/reject писем; новый capability или экран; exact-version editorial CAS; frozen sender snapshot, если актуальные данные пользователя доступны и работают; PG upgrade/CAS/legacy replay hardening; no-recipient acceptance; полный no-action-approved sweep; recovery/hardening; новый forced-crawl mode.

## Decisions

1. **Повторно использовать существующие UI и доменные потоки.** Регистрация и profile approval остаются как есть. Клиент создаёт request с отдельными полями offer/services и желаемых лидов; оператор одобряет request обычным экраном.
2. **Не добавлять режим обхода.** Одобрение использует существующий crawl/search путь Firecrawl. Первый реальный прогон делается на новом tenant с пустым lead pool, чтобы проверить, вызывает ли текущий путь реальный тематический crawl.
3. **Генерировать после поиска независимо от shortfall.** Для найденных лидов запрашивается письмо и при достижении, и при недостижении target. Ноль результатов означает ноль писем, не успешный синтетический результат. Используется реальная LLM.
4. **Данные отправителя — минимально необходимые.** Генерация использует текущие факты компании, доступные через уже работающий контур. Замороженный snapshot добавляется только если без него сценарий фактически не работает.
5. **Исполнение и письма остаются доступны в существующем operator UI.** Раздел «Исполнение» показывает заявки после запуска, в том числе завершённые, и ведёт на существующий approval/result экран с состоянием, найденными лидами и черновиками. Не вводятся отдельная editorial capability, отдельное решение, outreach campaign/handoff или новый самостоятельный экран.
6. **Отправка вне сценария.** Не запускать SMTP/sender. Не расширять работу ради гарантий отсутствия любого delivery-side effect за рамками подтверждения, что выбранный UI-сценарий не отправляет письма.
7. **Добор до явной цели использует поле аудитории.** Для Firecrawl при наличии `desired leads` брать именно описание аудитории, оставляя offer для генерации письма. Поиск запрашивает до удвоенного числа кандидатов, но не меньше десяти при малом остатке, в пределах настроенного максимума: не каждый результат доступен или является уникальным доменом. Следующие два существующих раунда используют тематические уточнения и отдельные budget scopes; каждый сайт получает отдельный scope, чтобы таймаут одного обхода не закрывал поиск остальных. Общий cap раунда соблюдается консервативным резервом: верхняя стоимость поиска плюс `MaxPages` на каждый запускаемый сайт. Лимиты времени, кредита и частоты crawl задаются конфигурацией стенда, сохраняя консервативные значения по умолчанию. Недобор остаётся наблюдаемым, если реальные источники не дали 25 компаний.
8. **Завершение демо после черновиков фиксируется в заявке.** Новые editorial executions после сохранения черновиков вызывают существующий переход `processing → fulfilled`, затем завершают workflow. Версионный маркер сохраняет replay прежних историй, завершавшихся в фазе `drafts-generated`. `fulfilled` здесь означает завершение ограниченного демо, а цель и недобор отображаются отдельно.
9. **Compose получает проверенные пределы демо.** Общая команда Compose передаёт demand те же настраиваемые через `.env` параметры, с которыми прошёл live-прогон на 25 лидов. Docker build context сохраняет каталог сервисов, который копирует Dockerfile; образ загружает только зависимости служебного бинарника. Это подготовка конфигурации, не подтверждение запуска на удалённом сервере: штатные intake release gates и серверные secret volumes проверяются отдельно.
10. **Прогресс показывается прямо в «Заявках».** Список читает все заявки выбранного tenant, а не только `submitted`, и добавляет наблюдаемую фазу workflow и счётчики лидов/писем. Одобренные заявки ведут на существующий экран исполнения. Внешний встроенный скрипт обновляет строки каждые 5 секунд; сбой обновления сохраняет последний результат и показывает сообщение. Не вводится отдельный экран или новый источник прогресса: счётчики отражают завершённые шаги workflow, а не процент обхода сайтов.
11. **Локальное тестирование имеет отдельный Compose.** `compose.demo.yaml` воспроизводит проверенный dev-путь: четыре контекста, собственные PostgreSQL/RabbitMQ/Temporal, постоянные тома и один nginx origin на порту 18000. Одноразовый helper переводит пароль оператора из локального `.env` в файл для runtime UID 65532. Production intake release gates не меняются; demo app явно выбирает существующий `legacy` DB policy и не использует внешние пользовательские DB/release volumes. Адреса и команды закреплены в `deploy/demo/README.md`.

## Risks / Trade-offs

Общий образ demo Compose собирает только `app`; `demand` с `pull_policy: never`
использует этот же локальный тег. Два параллельных export одного тега исключаются:
Docker Desktop с containerd image store отклонял такой запуск как `image already exists`.

- Реальный crawl может выявить инфраструктурный или конфигурационный блокер. Сначала выполнить его через интерфейс; фиксировать фактический блокер и исправлять только если он препятствует сквозному сценарию.
- Firecrawl/LLM и действующие credentials обязательны для единственной live acceptance; без них готовность не заявлять.
- Текущие данные профиля могут оказаться недостаточны для тематичного письма; только тогда рассматривать минимальный доступный контекст, не вводя обязательный frozen snapshot заранее.
- Сформированные письма могут пока не отображаться в имеющемся экране; допускается минимально показать результат генерации в существующем intake/request view, без нового capability и без требования exact-version CAS.

## Migration Plan

Не планировать миграции заранее. Сначала пройти реальный сценарий на интерфейсе и выявить блокер. PostgreSQL upgrade/CAS, legacy Temporal replay и обратная совместимость не являются acceptance-критериями этого demo change.

## Исправление наблюдаемых блокеров навигации демо

Сессии lead-management используют support DB при её настройке, сохраняя lead DB как совместимый fallback. Для отчётов запускается существующий analytics API с общим сессионным входом и постоянной проекцией; nginx направляет /reporting на его API. Отчёты отражают только накопленную проекцию, crawl не подменяется данными доставки. Очереди без выбранной компании ведут на платформенный выбор. Платформенный оператор может открыть список компаний независимо от невалидного активного выбора, но переключение разрешается только в активную компанию. Неактивные компании показывают своё фактическое состояние без кнопки выбора.
