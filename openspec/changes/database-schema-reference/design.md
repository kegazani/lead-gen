## Context

Мотивация — `proposal.md`. Состояние на момент изменения:

- Миграции — единственный первичный источник факта: 37 SQL-файлов в `backend/contexts/<ctx>/migrations[/green|red]` и `backend/platform/consoleauth/migrations/green`. Загрузчик `backend/platform/migrate/apply.go` создаёт схему сервиса, ведёт `<schema>.schema_migrations` и сериализует применение advisory-локом по имени схемы.
- Обзорные документы уже есть, но не заменяют справочник: `docs/architecture.md` §5 — таблица сущностей (модель, не физическая схема); `docs/implementation-matrix.md` §4 — сводка персистентности (числа миграций); `docs/domain-model.md` — владение и capability.
- `AGENTS.md` §7 фиксирует источники истины: `architecture/domain-catalog.yaml` (границы, владельцы) и `docs/domain-model.md` (модель) главнее любого описания хранилища.

## Goals / Non-Goals

**Goals:**

- Один документ, по которому видно: какая схема какому контексту принадлежит, какие таблицы там лежат, зачем каждая (роль в агрегате/операционной записи), и как всё связано.
- Явно и с атрибуцией зафиксировать расхождения между декларацией и кодом, не выдавая незакрытое за готовое.

**Non-Goals:**

- Не менять код, миграции, схемы БД, контракты, `deploy`.
- Не закрывать расхождения (роли СУБД, RLS, PII красной зоны) — это чужие change'и или открытые вопросы.
- Не назначать владельцев данных: это делает только `architecture/domain-catalog.yaml`.
- Не заменять `docs/architecture.md` §5 и `docs/domain-model.md`; справочник им подчинён.

## Decisions

### Решение 1. Формат — описательный документ (as-is), а не capability-спека

Справочник оформляется как документ `docs/database-schema-reference.md`, а не как capability с `SHALL`-требованиями.

*Альтернатива (отклонена):* capability `data-persistence` с требованиями к хранению. Отклонено, потому что спека описывает поведение: открытые расхождения (нет прав роли на схему, RLS не включён, PII красной зоны не материализованы) стали бы нарушениями требований, а сам change пришлось бы блокировать до их внедрения. Кроме того, границу данных уже описывает активный change `service-per-context` (design, Решение 4) — новая capability конкурировала бы с ним. Документ позволяет зафиксировать факт и расхождения без подмены незакрытого готовым (`AGENTS.md` §3).

### Решение 2. Место и подчинённость

Новый файл `docs/database-schema-reference.md`. Документ **подчинён** `architecture/domain-catalog.yaml` и `docs/domain-model.md`: описывает хранилище, но не владение. На обзорные документы добавляются обратные ссылки, чтобы детали не дублировались:

- `docs/architecture.md` §5 «Модель данных» → ссылка «физическая схема — в справочнике»;
- `docs/implementation-matrix.md` §4 «Персистентность» → ссылка на справочник за деталями.

### Решение 3. Структура документа

1. Принципы: зоны (зелёная/красная), schema-per-service, JSONB-снимок агрегата + денормализованные колонки, transactional outbox, ось `tenant_id`.
2. Карта схем по зонам (контекст → схема → зона → таблицы).
3. Разбор по контекстам: для каждой таблицы — назначение, ключи, денормализованные колонки и индексы, зачем они.
4. Связи: FK внутри одной схемы (жёсткая целостность) и логические связи между контекстами (по идентификаторам и событиям, без FK).
5. Сквозные механизмы: идемпотентность, оптимистичная блокировка, append-only журналы, частичные индексы, CHECK-инварианты.
6. «Известные расхождения» (см. Решение 4).

### Решение 4. Расхождения фиксируются с атрибуцией, не закрываются

| Расхождение | Факт по коду | Владелец / статус |
|---|---|---|
| Роли schema-per-service | Схемы и `schema_migrations` создаются загрузчиком, но отдельной роли СУБД на схему и отзыва межсхемных прав нет | change `service-per-context` (44/54 задач; design, Решение 4) |
| RLS по тенанту | Политик `CREATE POLICY`/`ENABLE ROW LEVEL SECURITY` в миграциях нет; изоляция — колонкой `tenant_id` в запросах | открытый факт; уже признан в архивах `tenant-context-visibility`, `tenant-scoped-lead-storage` |
| PII красной зоны | В красной зоне материализован только `contact`; сущности provenance/verification из `docs/architecture.md` §5 не заведены | открытый вопрос без владельца |

Разделение ролей в этом change **не делается** — по решению пользователя. Роль справочника — не закрыть расхождения, а назвать их и указать владельца/статус.

### Решение 5. Синхронность с миграциями

Документ ведётся вручную (автогенератора нет). Первичный источник — файлы миграций; таблица задач включает сверку с ними при создании и правило обновления справочника в том же change, что меняет миграции.

## Risks / Trade-offs

- **[Документ устареет относительно миграций]** → в справочнике указан первичный источник (файлы миграций), в `tasks.md` есть задача сверки, а `AGENTS.md` §8 требует править документы в том же change, что меняет их содержание.
- **[Справочник воспримут как to-be и как назначение владельцев]** → явный раздел «Известные расхождения» с пометкой, что это факт; явная подчинённость `architecture/domain-catalog.yaml` и `docs/domain-model.md`.
- **[Дублирование с `docs/architecture.md` §5]** → §5 остаётся обзором модели, физические детали живут только в справочнике, между ними кросс-ссылка.

## Migration Plan

1. Создать `docs/database-schema-reference.md` из фактических миграций.
2. Добавить обратные ссылки в `docs/architecture.md` §5 и `docs/implementation-matrix.md` §4.
3. Зафиксировать изменение в `docs/progress-log.md`.
4. Откат: удалить новый документ и обратные ссылки; миграции и код не затронуты, откат безопасен.

## Open Questions

- Кто владеет материализацией PII красной зоны помимо `contact` — отдельный change, здесь только зафиксировано как открытый вопрос.
