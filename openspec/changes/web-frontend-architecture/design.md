# Дизайн веб-интерфейса платформы

## Context

Мотивация и объём — в `proposal.md`. Здесь только состояние проекта и ограничения, формирующие подход.

**Что уже зафиксировано и не пересматривается.**

- Стек интерфейса — **HTMX + серверные шаблоны на `html/template`**, серверный рендеринг (`docs/architecture.md` §11). Стек вынесен за пределы архитектурных разделов 1–10: замена строки стека не пересматривает архитектуру.
- Интерфейс — эксплуатационная часть роли **`api`** (внутренний контур), поднимаемой сервисами, а не отдельный процесс и не bounded context (`docs/system-map.md` §2.1). Роль `api` не делает долгих операций и не отправляет письма.
- **Обязательное утверждение человеком** — центральный инвариант продукта (`full-enterprise-core-scope`, Решение 3): очередь черновиков `предложено → ожидает утверждения → утверждено/отклонено → исполнено/ошибка`. Автоутверждение по сроку запрещено. Прямой вызов API без решения оператора не исполняет действие.
- **Границы данных физические** (Решение 1): персональные данные физлиц живут в контуре клиента; вынос в логи, события и аналитику запрещён без отдельного правила.
- **Прочтение определяется только переходами**, пикселей нет (Решение 8); состояние `read` / `unknown`, состояния «непрочтение подтверждено» нет.
- **Требование к терминологии** (BRD §3.18): формулировка «адрес существует» запрещена; допустимы «доставляемый», «рискованный», «неизвестно», «недействительный».

**Ограничения, определяющие дизайн.**

- Кода интерфейса нет; канон стека есть. Дизайн обязан совпасть с context-first структурой Go-модуля (`migrate-platform-to-go` §2, `service-per-context`): `domain` не импортирует другие слои и контексты, `app` использует только свой `domain`/`ports` и опубликованные контракты, SDK — только в `adapters`; межконтекстная сборка в одном пакете запрещена — контексты соединяются транспортом (HTTP по контракту владельца, AMQP).
- Первый вертикальный срез (`outreach-approval-slice`) уже реализует очередь утверждений в `outreach-orchestration`. Веб-интерфейс — потребитель его прикладных сервисов.
- Один экран часто показывает данные нескольких контекстов (очередь показывает и черновик из `outreach-orchestration`, и карточку лида из `lead-management`). Чужие данные приходят только через объявленные контракты владельцев: экран принадлежит контексту-владельцу основного агрегата и добирает остальное по объявленным синхронным `query`-контрактам (`sync`/`http-json`).
- Наблюдаемое поведение очереди уже задано спекой `outreach-approval`: состав пакета, число исключённых черновиков с причинами, запрет решения без просмотра состава, отдельная запись решения по каждому черновику.

**Ключевое напряжение.** Интерфейс — единственное место, где человек принимает необратимые решения, и одновременно — самый дешёвый способ обойти инвариант утверждения (кнопка вместо серверной проверки, «оптимистичный» JavaScript, кэш страницы). Дизайн обязан сделать обход невозможным по построению, а не по соглашению. Это напряжение формирует большинство решений ниже.

## Goals / Non-Goals

**Goals:**

- Сделать очередь утверждений центральным, быстрым и безопасным рабочим местом оператора: индивидуальные решения и пакетные, с предъявлением состава и причин отказа.
- Свести данные из нескольких контекстов в связные экраны, не создав ни общей доменной модели, ни второго владельца состояния.
- Исключить обход инварианта утверждения через интерфейс: любое необратимое действие проходит серверную проверку и привязано к точной версии решения.
- Дать предсказуемую работу с длительными операциями: команда отделена от результата, прогресс виден, потеря задания невозможна.
- Показать честную неопределённость: статусы верификации, свежесть данных, отсутствие сигнала — без ложных обещаний.

**Non-Goals (на уровне дизайна):**

- Не проектируем публичные страницы `ingest` (трекинг, вебхуки, выбор слота, просмотр презентации) — другой контур, без сессии оператора.
- Не проектируем визуальный стиль, дизайн-систему и брендбук: задаём структуру, состояния и ограничения.
- Не строим SPA, мобильное приложение и офлайн-режим.
- Не вводим собственные механизмы утверждения, доступа и идемпотентности — используем ядро.

## Decisions

### Решение 1. Веб-интерфейс — эксплуатационная часть роли `api` внутри сервисов, а не bounded context

Веб-интерфейс не получает собственного bounded context, агрегатов и состояния. Это способ представить уже существующую модель человеку. Ни один экран не владеет сущностью и не хранит собственное авторитетное состояние: он читает проекции и отправляет команды прикладным сервисам owning context.

**Почему так:** `docs/system-map.md` §2.0–§2.1 различает контекст (модель и владение) и роль (режим запуска внутри сервиса). Интерфейс — эксплуатационная часть роли `api`: её поднимает каждый сервис, чьи экраны нужны человеку (`deploy/services.yaml`). Роль не владеет моделью и не становится вторым владельцем: экран, показывающий данные нескольких контекстов, принадлежит контексту-владельцу основного агрегата и добирает чужие данные по объявленным контрактам.

**Следствие.** Правила видимости, права и решения живут в owning context; сервис-владелец экрана применяет локальный контрактный снимок правила `access-decision` и политики owning context, а не условие в шаблоне.

### Решение 2. Стек: серверный рендеринг на `html/template` + HTMX; SPA отклонён

Экран собирается на сервере: HTML отдаётся целиком при переходе и фрагментом при частичном обновлении. JavaScript ограничен библиотекой HTMX (BSD-2-Clause) и небольшими вспомогательными скриптами; клиент не содержит бизнес-логики.

**Почему так:**

- Интерфейс — внутренний инструмент оператора, а не публичный продукт с богатым клиентским состоянием. Очередь утверждений и карточки — это списки и формы, где выигрыш от клиентского состояния мал, а цена (второй набор правил доступа и валидации) высока.
- Инвариант «ноль исходящих действий без утверждения» дешёвле всего проверяется на сервере в одном месте. Чем меньше логики в браузере, тем меньше способов её обойти.
- `html/template` экранирует вывод по умолчанию и делает XSS-класс ошибок маловероятным.
- Стек уже канонизирован (`architecture.md` §11); смена стека — отдельное решение, а не деталь этого дизайна.

**Рассмотренные альтернативы:**

- **SPA (React/Vue) с JSON API.** Отклонено. (а) Требует второго набора проверок доступа и валидации на клиенте или доверия к клиенту, что противоречит Решению 1 и инварианту утверждения. (б) Персональные данные лида попадали бы в JSON-ответы и клиентское состояние шире, чем нужно для отображения, что увеличивает риск выноса красных данных. (в) Усложняет доступность и тестирование без выигрыша для списков и форм. (г) Вводит сборку и второй стек в проекте, сознательно выбравшем стандартную библиотеку.
- **Гибрид: серверные страницы + остров клиентского состояния для очереди.** Отклонено как промежуточное: усложняет модель, не снимая рисков; при необходимости отзывчивости достаточно HTMX-фрагментов и опроса прогресса.
- **Отдельный фронтенд-процесс/сервис.** Отклонено: нарушает «один образ, назначение задаётся конфигурацией» (`architecture.md` §8) и создаёт второй контур доступа к данным.
- **Готовая админ-панель или UI Twenty CRM как интерфейс.** Отклонено: не выражает семантику очереди утверждений и пакетного решения с индивидуальной фиксацией, а также потребовала бы доступа к красной зоне из чужого UI.

### Решение 3. Слои и место в context-first структуре

```text
cmd/lead-gen/                         # единая точка входа: сервис и роли из deploy/services.yaml
backend/contexts/<context-id>/    # сервисная сборка: composition root сервиса, собирает
                                      # только свой контекст и публикует его роли
frontend/components/                # примитивы без доменных терминов: layout, рендеринг
                                      # шаблонов, CSRF, idempotency-key, flash, пагинация,
                                      # i18n, разбор ошибок в представление
backend/platform/transport/http/     # синхронный транспорт границы сервиса (пакет transport)
backend/contexts/<context-id>/
  adapters/http/                      # обработчики и шаблоны экранов этого контекста
    templates/
  app/                                # вызываемые use cases
  ports/                              # контракты, нужные контексту
```

**Правило зависимостей.** `adapters/http` вызывает только `app` своего контекста (и его `ports`); `domain` не видит представления; `frontend/components` не содержит доменных терминов. Экран, которому нужны данные другого контекста, запрашивает их через объявленный синхронный `query`-контракт владельца (транспорт `sync`/`http-json`, `backend/platform/transport/http`), а не импортом чужого контекста. Межконтекстная сборка в одном пакете запрещена (`service-per-context`): `backend/contexts/<context-id>` собирает ровно один контекст.

**Почему так:** сохраняется один владелец модели, а представление остаётся заменяемым. Обработчики и шаблоны экрана живут в `adapters/http` контекста-владельца этого экрана, сервисная сборка — в `backend/contexts/<context-id>`. Данные чужих контекстов приходят по опубликованным контрактам владельцев.

**Следствие.** Проверка границ импортов расширяется правилом: пакет HTTP-адаптера не импортирует `domain` и `app` чужого контекста. Это проверяемо `go run ./tools/importlint`. Если экрану нужен контракт, которого каталог не объявляет, — это предмет отдельного изменения каталога, а не этого дизайна.

### Решение 4. Модель рендеринга: полная страница + гипермедиа-фрагменты, POST/redirect/GET

- Переход по навигации отдаёт полную страницу (layout + содержимое).
- Действие в интерфейсе отдаёт **фрагмент** (`hx-*`), который заменяет часть страницы. Тот же обработчик по прямому запросу без заголовка HTMX отдаёт полную страницу — так работает прогрессивное улучшение и обновление адреса.
- Изменяющие действия идут только через POST с последующим redirect (PRG), чтобы обновление страницы не повторяло необратимое действие.
- Обновление списков — по явному действию или мягкому опросу; длительные задачи — через опрос статуса (Решение 11).

**Почему так:** PRG убирает самый частый способ случайного дублирования решения — перезагрузку страницы. Возврат полной страницы по прямому запросу делает каждый экран работоспособным без JavaScript и упрощает тестирование.

**Следствие.** Шаблон фрагмента и шаблон полной страницы используют общую разметку блока; дублирования разметки не допускается — фрагмент включается в страницу как часть.

### Решение 5. Навигация и карта экранов

Навигация строится вокруг работы оператора, а не вокруг контекстов: контексты — внутренняя граница, пользователь видит задачи.

| Раздел | Экран | Основные данные (owning context) |
|---|---|---|
| **Очередь** | Входящие черновики, пакеты, зависшие | `outreach-orchestration`; карточка лида — `lead-management` |
| **Карточки** | Компания, контакт/лид, история касаний | `lead-management`, `engagement-observation`, `sales-workflow` |
| **Кампании** | Список, карточка кампании, аудитория и снимок | `outreach-orchestration`, `audience` |
| **Цепочки** | Сценарии, выполнения, шаги, звонки, form-задания | `outreach-orchestration` |
| **Контент** | Версии, предпросмотр, документы, бренд-комплекты | `content-production` |
| **Импорт** | Загрузка файла, маппинг колонок, прогресс разбора, результат по строкам | `lead-management` |
| **Отправка** | Статусы отправки, ход прогрева, отказы и жалобы, репутация доменов | `message-delivery` |
| **Публикации** | Выжимки сообществ, материалы на утверждение | `community-intelligence`, `publishing` |
| **Отчёты** | Дашборды, воронка, менеджеры, качество базы, экспорт | `analytics` |
| **Настройки** | Пользователи и роли, тенант, интеграции, домены, лимиты, аудит | `platform-governance`, `integration-platform`, `billing`, `data-governance` |
| **Топология** | Топология сервисов (только администратор платформы) | `platform-governance`; поведение и данные — change `service-topology-console` |

**Правила навигации.** Разделы и действия, недоступные роли, не показываются, но отсутствие в навигации — не защита: сервис-владелец экрана применяет локальный снимок `access-decision` и проверяет право на каждое действие (Решение 9). Видимые разделы строятся по тому же снимку, а не по конфигурации шаблона. Появление новых черновиков уведомляет ответственного счётчиком в навигации и явным уведомлением (BRD §1.1).

**Топология сервисов.** Вкладка «Топология сервисов» — административная: она видна только администратору платформы. Её поведение и данные (состав узлов и рёбер, состояние, интенсивность, раскладка, всплывающие карточки и панель метрик из Prometheus через серверный прокси) определены change'ем `service-topology-console` и здесь не дублируются. Вкладка стоит на общем слое интерфейса — серверный рендеринг и небольшой JS-«остров» (Решения 2–4) — и применяет тот же локальный контрактный снимок `access-decision` (Решение 9), без синхронного запроса решения; владелец экрана — `platform-governance`.

### Решение 6. Очередь утверждений — центральный экран

Очередь — главный сценарий и единственная точка необратимого действия. Её поведение уже нормировано спекой `outreach-approval`; дизайн задаёт, как оно выражается.

**Список (inbox).** Фильтры по кампании, каналу, сегменту, признаку риска, сроку. Каждая строка показывает: получателя, кампанию, канал, время в очереди, результат автоматических проверок (согласие, стоп-лист, лимиты, готовность домена, верификация адреса). Строки с признаком риска визуально отделены от однородной массы.

**Индивидуальное решение.** Экран разбора предъявляет: данные лида, сгенерированный контент, вложение, историю предыдущих касаний, результат проверок. Решения: подтвердить, отредактировать и подтвердить, отклонить (при необходимости с причиной), отложить. Отредактированный вариант фиксируется отдельно от сгенерированного.

**Пакетное решение.** Пакет формируется ядром только из однородных черновиков; рисковые исключаются и требуют индивидуального решения. Перед решением интерфейс обязан предъявить число черновиков, основание однородности, образец содержимого, перечень отличий и число исключённых с причинами. Решение без предъявления состава не принимается (требование `outreach-approval`). Пакетное решение фиксируется как отдельное решение по каждому черновику с признаком пакетного.

**Зависшие черновики.** Отдельный срез очереди: черновики с истёкшим сроком; автоутверждение запрещено, эскалация уведомляет оператора, действие остаётся неисполненным.

**Масштаб и пагинация.** Очередь рассчитана на пакет не менее 50 черновиков и кампанию до 50 000 черновиков (`outreach-approval`, «Пропускная способность»): список постраничный, с фильтрами и сортировкой по сроку и риску; счётчики показывают объём до и после фильтра, а пакетное решение охватывает пакет целиком и не требует открывать все страницы вручную. Размер пакета и предел берутся из owning context, а не вычисляются в шаблоне.

**Уведомление о новых черновиках.** Появление новых черновиков в очереди уведомляет ответственного (BRD §1.1): счётчик в навигации и явное уведомление; уведомление не заменяет решение и не исполняет действие.

**Почему так:** это единственное место, где интерфейс способен превратить инвариант в формальность — «подтвердить всё, не читая». Предъявление состава и исключение рисковых черновиков делают формальное подтверждение бессмысленным, а не запрещённым соглашением.

### Решение 7. Состояния, формы и свежесть данных

Каждый экран обязан иметь явные состояния, а не только «повезло»:

- **Загрузка:** индикатор на фрагменте (`hx-indicator`), кнопка действия блокируется на время запроса.
- **Пусто:** осмысленное пустое состояние с подсказкой следующего шага, а не пустая таблица.
- **Ошибка:** серверная ошибка показывается как понятное сообщение с возможностью повтора; технические детали без идентификатора корреляции наружу не отдаются.
- **Отказ в доступе:** экран объясняет, что действие недоступно, а не показывает 404 скрытно; факт отказа фиксируется в аудите при значимом действии.
- **Свежесть:** там, где проекция отстаёт (eventual consistency), показывается watermark или время расчёта. Отчёт, построенный по устаревшему снимку, помечается временем; недоступность контура не скрывается под «нулём».
- **Формы:** серверная валидация — источник истины; ошибки возвращаются к форме с сохранением введённого; обязательные поля помечены; ввод не сбрасывается при ошибке.

**Почему так:** «показать ноль вместо недоступного» — прямое нарушение требования BRD §3.17 (недоступная метрика не подменяется нулём). Дизайн интерфейса обязан выражать неопределённость честно.

### Решение 8. Идемпотентность и утверждения в интерфейсе

- **Ключ идемпотентности на форму.** При отрисовке формы сервер вкладывает ключ идемпотентности команды (тенант + ключ). Повторная отправка с тем же ключом не создаёт второе действие (`architecture.md` §6.1). Подтверждение решения — типовой пример: ключ связан с парой «черновик + оператор + намерение».
- **Защита от двойной отправки.** Кнопка блокируется на время запроса; повторный POST не приводит к второму решению — сервер дедуплицирует по ключу.
- **Решение привязано к точной версии черновика.** Экран решения содержит версию черновика. Если черновик изменён между отрисовкой и отправкой, решение не применяется: интерфейс перечитывает состояние и просит принять решение заново. Это соответствует инварианту «изменённый черновик требует нового решения».
- **CSRF.** Каждый изменяющий запрос несёт токен; проверка на сервере; cookie сессии `HttpOnly`, `Secure`, `SameSite`.
- **Интерфейс не обходит утверждение.** Никакой клиентский путь (кнопка, фрагмент, скрытое поле) не исполняет действие: исполнение возможно только после записи решения в owning context, а отправку выполняет `sender` по `approved-action`.

**Почему так:** интерфейс — самый вероятный источник дублей и «случайных» необратимых действий. Ключ идемпотентности вместе с привязкой решения к версии делает обе проблемы структурными, а не дисциплинарными.

### Решение 9. Доступ и RBAC

- Аутентификация и права — в `platform-governance`; интерфейс не воспроизводит правила ролей локально.
- **`access-decision` — подписка, а не синхронный запрос.** Связь объявлена как `policy`/`async` (`async`/`amqp`): сервис-владелец экрана хранит локальный контрактный снимок правила и применяет его к своим экранам и действиям. Синхронного запроса решения на каждое действие нет — он сделал бы `platform-governance` общей точкой отказа интерфейса.
- Роли из BRD §3.16: владелец, менеджер, маркетолог, дизайнер контента, администратор, аналитик. Матрица «роль → раздел → действие» — отображение снимка решений доступа, а не условие в шаблоне.
- **Проверка на сервере для каждого действия.** Навигация скрывает недоступное, но ни одно действие не полагается на скрытие; решение принимает owning context по своему снимку правила и политикам.
- **Ограничение видимости по роли.** Видимость красных данных (контакты, содержимое переписки) — минимально необходимая; интерфейсы поддержки маскируют персональные данные (`architecture.md` §10).
- **Аудит.** Административные действия и решения оператора фиксируются неизменяемо (субъект, действие, объект, время, результат) и доступны для экспорта. Интерфейс показывает журнал, но не редактирует записи.

**Почему так:** RBAC на клиенте не является RBAC. Любое правило, продублированное в шаблоне, рано или поздно разойдётся с серверным и превратится в уязвимость. Подписка на снимок сохраняет правило и не делает общий контекст обязательным для каждого запроса; расширение числа потребителей policy — предмет каталога, а не этого дизайна.

### Решение 10. Мультитенантность

- Тенант определяется **на сервере** из сессии и пользователя; он не читается из параметров запроса, пути или скрытых полей формы.
- Изоляция обеспечивается политикой хранилища (row-level security), а не фильтром в представлении; интерфейс полагается на то, что запросы контекста уже ограничены тенантом.
- Переключение тенанта доступно только пользователю, которому разрешён более чем один тенант; факт переключения фиксируется.
- Тяжёлые задания одного тенанта не должны исчерпывать общие ресурсы интерфейса; прогресс и лимиты показываются в разрезе тенанта.

**Почему так:** тенант, пришедший из клиента, — классическая уязвимость изоляции; `architecture.md` §6.4 требует изоляции политикой доступа хранилища, а **не только** фильтром в запросах.

### Решение 11. Длительные операции через очередь

Интерфейс никогда не выполняет долгую работу в рамках запроса. Модель единая:

1. Действие публикует команду и получает **идентификатор задания**.
2. Экран показывает прогресс: процент, текущий шаг, время начала; источник — статус задания из очереди/воркфлоу.
3. Прогресс обновляется мягким опросом или серверным потоком событий; по завершении фрагмент заменяется результатом.
4. Неуспешное задание показывает нормализованную причину и путь к повтору; исчерпавшие попытки задания видны администратору (DLQ).

Такая модель применяется к импорту файлов, генерации контента, рендерингу PDF, пакетной верификации адресов, построению отчётов на больших периодах и сбору данных. Экран импорта файла — эталонный случай: пользователь выбирает файл, сопоставляет колонки и видит прогресс разбора (до 1 млн строк) и результат по строкам; запрос возвращает идентификатор задания, а не ждёт завершения.

**Почему так:** `architecture.md` §3 разделяет синхронные и асинхронные операции, а §6.2 требует, чтобы потеря задания была невозможна. Интерфейс, ожидающий результат внутри запроса, нарушил бы и то, и другое.

### Решение 12. i18n и терминология

- Интерфейс мультиязычный: тексты выносятся в каталоги сообщений, а не остаются строковыми литералами в шаблонах; локализуются форматы дат, чисел, валют, часовых поясов и множественные формы.
- **Терминология верификации.** Словарь интерфейса следует BRD §3.18: используются «доставляемый», «рискованный», «неизвестно», «недействительный», «одноразовый», «ролевой». Формулировка «адрес существует» запрещена в интерфейсе, документации и коммерческих материалах. Дата и источник проверки показываются рядом со статусом; срок актуальности учитывается.
- **Открытия не показываются.** В интерфейсе нет метрик открытий; состояние прочтения — `read` / `unknown`, без «непрочтение подтверждено» (Решения 4 и 8 рамки).
- **Формулировки инварианта.** Там, где речь о решении оператора, интерфейс говорит «утвердить/отклонить/отложить», а не «отправить»: отправка — следствие утверждения, а не действие оператора.

**Почему так:** терминология — часть продукта. Обещание «проверка существования ящика» не соответствует технологии и создаёт ложное ожидание; словарь должен это удерживать на уровне интерфейса.

### Решение 13. Доступность

- Целевой уровень — WCAG 2.1 AA: семантическая разметка, корректные заголовки и landmarks, текстовые метки у полей.
- Полная клавиатурная доступность: очередь и формы проходятся без мыши; фокус видим.
- При подмене фрагментов HTMX фокус управляется явно, чтобы пользователь клавиатуры и скринридера не терял контекст; изменения объявляются через `aria-live`.
- Цвет не является единственным носителем смысла (признак риска, статусы — с текстом и иконкой).
- Ошибочные формы дают сводку ошибок и связывают её с полями.

**Почему так:** очередь утверждений — рабочий инструмент на часы в день; недоступность бьёт по продуктивности и создаёт риск ошибок при массовых решениях.

### Решение 14. Тестирование интерфейса

- **Рендеринг-тесты шаблонов:** golden-файлы для фрагментов и ключевых страниц; проверка обязательных элементов (результаты проверок, состав пакета, число исключённых).
- **Интеграционные тесты обработчиков:** `net/http/httptest`, прикладные сервисы подменяются тестовыми реализациями контрактов.
- **Тесты контракта фрагментов:** один и тот же обработчик возвращает корректный фрагмент с заголовком HTMX и полную страницу без него.
- **Тесты инвариантов интерфейса:** решение привязывается к версии (устаревшая версия не применяется); повторный POST с тем же ключом не создаёт второго решения; рисковый черновик не попадает в пакет.
- **Проверки доступности:** автоматизированные (разметка, контраст, метки) в CI, плюс ручные сценарии клавиатуры для очереди.
- **Проверка границ:** HTTP-адаптер не импортирует `domain` и `app` чужого контекста (`go run ./tools/importlint`); отсутствие новых сущностей, контрактов и capability проверяет `go -C tools/archlint run .`; шаблоны не содержат доменных правил; доменные проверки не дублируются в клиентском JavaScript.

**Почему так:** интерфейс — самая изменчивая часть; без golden-файлов и тестов инвариантов он быстро перестаёт соответствовать спеке `outreach-approval`.

### Решение 15. Ресурсы, безопасность фронтенда, развёртывание

- HTMX и вспомогательные скрипты поставляются как статические ресурсы; обязательной сборки фронтенда нет — допускается только примитивная минификация. Это сохраняет «стандартный toolchain» и отсутствие второго стека.
- Строгая Content-Security-Policy без inline-скриптов; разметка без `unsafe-inline`.
- `html/template` экранирует вывод по умолчанию; ссылки из пользовательских данных обезвреживаются; произвольный HTML из контента не вставляется без очистки.
- Секреты интеграций и токены в HTML не попадают; учётные данные почтовых ящиков платформа не хранит (BRD §7).
- Кэширование страниц с персональными данными запрещено; ответы с красными данными — `Cache-Control: no-store`.
- Ограничение частоты попыток входа и чувствительных действий (`architecture.md` §10).

**Почему так:** запрет кэширования и отсутствие inline-скриптов — прямые следствия физической границы данных и отказа от лишнего клиентского состояния.

### Решение 16. Доменная привязка

Изменение не вводит сущностей, агрегатов, domain events, policies и межконтекстных контрактов. Веб-интерфейс — эксплуатационная часть роли `api` внутри сервисов; владельцами данных остаются контексты, перечисленные в `proposal.md` (Impact). Первичный источник очереди — aggregate `campaign` (aggregate root `campaign`) в `outreach-orchestration`: entities `action-draft`, `operator-decision`; events `action-approved`, `campaign-state-changed`; policy `operator-approval-required`. Права и аудит — aggregate `tenant-access` в `platform-governance` (события `tenant-access-changed`, `audit-recorded`; контракт `access-decision`). Отчёты — aggregate `campaign-report` в `analytics`. Интерфейс читает эти данные и отправляет команды через существующие контракты.

**Следствие:** `architecture/domain-catalog.yaml`, `docs/domain-model.md` и обязательные диаграммы **не меняются**. Проверка `go -C tools/archlint run .` должна остаться зелёной: ни одной новой capability не добавляется (изменение помечено `skip_specs: true`), поэтому покрытие capability не меняется.

**Рассмотренная MODIFIED-дельта `domain-architecture`.** Чтобы нормативно закрепить «интерфейс — эксплуатационный слой без доменных правил», можно было бы расширить требование «Различение доменных и эксплуатационных границ». Отказались: требование уже покрывает случай «роль не владеет моделью», а `architecture.md` §2 относит веб-интерфейс к эксплуатационной проекции. Требование ради валидации не вводится; если команда решит закрепить это явно — отдельным изменением (см. «Открытые вопросы»).

## Risks / Trade-offs

- **Протечка доменных правил в представление.** Самый вероятный способ со временем нарушить context-first: удобно «дописать условие в шаблоне». Компенсация: правило зависимостей, проверка импортов, тесты и явное «шаблон не решает, шаблон показывает».
- **Проникновение чужого контекста в экран.** Соблазн собрать страницу из данных нескольких контекстов в одном пакете или через чужой `domain`/`app`. Компенсация: экран принадлежит контексту-владельцу, чужие данные — только по объявленным контрактам; межконтекстный импорт запрещён и проверяется `go run ./tools/importlint`.
- **HTMX-фрагменты без JavaScript.** Прямой запрос без заголовка обязан отдавать полную страницу; расхождение фрагмента и страницы даёт разный результат. Компенсация: общая разметка блока и тесты «фрагмент = часть страницы».
- **Слабая мгновенность отклика.** Опрос и обновления фрагментов уступают SPA по «живости». Принято осознанно ради инварианта утверждения и простоты; при необходимости отзывчивость повышается точками, без смены модели.
- **Мультиязычность удорожает шаблоны.** Вынос текстов и форматов добавляет работу. Принято как требование к продукту, а не оптимизация.
- **Дублирование разметки состояний.** У каждого экрана набор состояний (загрузка/пусто/ошибка/доступ), и без общих блоков они размножатся. Компенсация: общие блоки в `frontend/components`.

## Migration Plan

Изменение задаёт структуру интерфейса и создаёт первые пакеты и экраны; порядок работ:

1. **Каркас.** Опирается на `migrate-platform-to-go` §2 и `service-per-context`: точка входа `backend/cmd/lead-gen` с ролями из `deploy/services.yaml`, `frontend/components`, синхронный транспорт `backend/platform/transport/http`, монтирование маршрутов, middleware сессии и CSRF.
2. **Первый экран — очередь утверждений.** Реализуется поверх `outreach-approval-slice`: список, индивидуальное решение, пакет с предъявлением состава, зависшие. Это проверочный сценарий всего дизайна.
3. **Общий слой.** Выносятся layout, блоки состояний, пагинация, i18n, идемпотентность формы, представление ошибок.
4. **Остальные разделы** по одному, каждый — потребитель уже опубликованных контрактов; новые контракты вводятся только если их требует owning context, а не экран.
5. **Проверки.** Тесты шаблонов, обработчиков, инвариантов и доступности входят в общий набор `make check`; проверка границ импортов дополняется правилом для HTTP-адаптеров.

## Open Questions

1. **Нормативное закрепление статуса интерфейса.** Нужно ли отдельным изменением внести в `domain-architecture` требование «веб-интерфейс — эксплуатационная часть роли `api`, не владеющая доменными правилами», или достаточно документации и проверки импортов?
2. **Транспорт прогресса.** Опрос или серверные события (SSE) для длительных операций: SSE требует удержания соединений на роли `api`, опрос проще, но шумнее. Решение можно принять при первом длительном сценарии.
3. **Управление ресурсами и CSP.** Нужен ли минимальный шаг сборки для объединения и хэширования статических ресурсов, или достаточно раздачи файлов с хэшем в имени. Влияет на строгость CSP.
4. **Локали первой версии.** Состав языков не зафиксирован целевым рынком (BRD §8, вопрос 6; `architecture.md` §13). Дизайн предполагает мультиязычность, но конкретный набор локалей определяется рынком.
5. **Единый словарь терминов.** Нужен ли общий глоссарий интерфейса как артефакт (терминология верификации уже обязательна; остальные термины пока не формализованы).
