## Context

Мотивация и объём — в `proposal.md`. Здесь только состояние и ограничения, определяющие подход.

Рамка продукта (`full-enterprise-core-scope`, Решения 1-8) построена на двух опорах, и обе этот источник запрещают: **Решение 1** — «только открытые источники, отказ при требовании авторизации», **Решение 2** — «никакого фонового сбора, обогащение только по явному запросу человека». Задача 1.2 вынесла «источники с авторизацией» в машинно-читаемый перечень недопустимого, то есть запрет был сделан проверяемым.

Ограничение по технике, а не по политике: Bot API не имеет методов истории сообщений и не отдаёт состав участников ни одним вызовом (`getChatMemberCount` — только число, `getChatAdministrators` — только администраторы). Публичный предпросмотр `t.me/s` даёт окно последних постов публичного канала и не даёт ни глубины, ни состава, ни приватных групп. Требование «полное чтение сообществ» этими путями не выполняется в принципе.

Второе ограничение: **читаемое содержание неотделимо от авторов.** В отличие от агрегатов раздела 3.17, выжимка строится из высказываний конкретных людей, и короткая цитата может быть атрибутируемой. Это определяет, что попадает в какую зону.

Третье: **автоматизация пользовательского аккаунта приводит к его ограничению.** Это не риск аварии, а ожидаемое поведение платформы, которое надо проектировать как штатный режим.

## Goals / Non-Goals

**Goals:**

- Выполнить требование полного чтения: история, публичные и приватные сообщества, состав участников.
- Сохранить разделение зон как физическое разделение хранилищ — единственную защиту, оставшуюся от рамки после отмены Решения 1.
- Сделать потерю аккаунта чтения штатным событием, не останавливающим продукт.
- Ограничить пересмотр рамки Telegram-источником, не отменяя Решения 1 целиком.

**Non-Goals:**

- Не пересматриваем остальные запреты рамки: утверждение человеком (Решение 3), отказ от отслеживания открытий (Решение 8), прогрев доменов, верификация адресов, пул лидов в контуре клиента.
- Не отменяем перечень недопустимых источников задачи 1.2 целиком: из него выводится только Telegram.
- Не проектируем публикацию или перепродажу прочитанного содержания.
- Не проектируем обход ограничений платформы: система соблюдает требование приостановить работу, а не уклоняется от него.

## Decisions

### Решение 1. MTProto под пользовательским аккаунтом, а не Bot API и не t.me/s

**Выбор.** Источник чтения — MTProto-клиент (Telethon, Pyrogram или GramJS) под пользовательским аккаунтом.

**Почему.** Это единственный способ получить историю, приватные группы и состав участников. Bot API не имеет методов истории и не отдаёт состав; `t.me/s` ограничен окном последних постов публичного канала. Требование спеки «полное чтение» достижимо только этим путём.

**Рассмотренные альтернативы.** Bot API — отклонён как недостаточный по технике, а не по политике. `t.me/s` — оставлен как вспомогательный путь для публичных каналов без авторизации, но не как основной. Гибрид «t.me/s + Bot API» — отклонён: не даёт ни истории, ни состава, то есть не выполняет требование.

**Следствие.** Появляется хранилище авторизованных сессий — компонент, которого рамка избегала. Он изолируется: данные авторизации доступны только компоненту чтения и не попадают в зелёную зону.

### Решение 2. Пересмотр рамки точечный, а не полный

**Выбор.** Решение 1 отменяется **в части Telegram**: для остальных источников запрет на авторизацию сохраняется. Перечень задачи 1.2 сохраняется и теряет только одну строку.

**Почему.** Полная отмена Решения 1 сняла бы запрет на авторизованные источники вообще, включая те, ради отказа от которых рамка создавалась. Точечный пересмотр сохраняет позицию продукта для всего, кроме Telegram, и оставляет перечень проверяемым.

**Рассмотренные альтернативы.** Полная отмена Решения 1 — отклонена: уничтожает больше, чем требуется для выполнения требования. Отдельный продукт вне рамки — отклонён: чтение сообществ обслуживает тот же конвейер и должно жить в общей модели данных.

**Что это стоит.** Перечень недопустимых источников перестаёт быть последовательным: продукт сам использует то, что ещё недавно относил к недопустимому. Это не техническое следствие, а позиционное, и оно вынесено в риски.

### Решение 3. Зоны сохраняются: выжимка — зелёная, авторы — красная

**Выбор.** Выжимка содержания относится к зелёной зоне. Авторы сообщений и состав участников — к красной. Выгрузка красной зоны за пределы контура отклоняется.

**Почему.** Разделение зон — единственная часть рамки, которую этот источник не обязан ломать. Выжимка не нуждается в идентичности авторов: темы, частота и повторяющиеся запросы считаются по содержанию. Сохранив зону, мы сохраняем и статус обработчика по поручению, и возможность выгружать результат клиенту.

**Рассмотренные альтернативы.** Единое хранилище — отклонено: снимает последнюю структурную защиту и делает выжимку неотделимой от персональных данных. Полный отказ от хранения авторов — недостаточен: состав участников по требованию спеки всё равно возвращается, значит хранить его надо контролируемо.

**Что это даёт.** Выжимка остаётся товаром, авторы — нет. Это различие удерживает продуктовую позицию: выгружается агрегат, а не люди.

### Решение 4. Непрерывное чтение вместо обогащения по запросу

**Выбор.** Чтение выполняется по расписанию в фоне. Модель «stateless-обогащение по явному запросу» (Решение 2 рамки) к этому источнику не применяется.

**Почему.** Сообщества обновляются непрерывно. Обогащение по запросу человека создавало бы искусственную задержку и бессмысленный шаг: между запросами содержание меняется, и выжимка устаревает.

**Рассмотренные альтернативы.** Чтение по запросу человека — отклонено: не выполняет требование непрерывности и не даёт динамику по периодам. Периодические полные перечитки — отклонены: перегружают аккаунт и повышают вероятность ограничения.

**Что это стоит.** Платформа начинает хранить прочитанное постоянно, что Решение 2 запрещало в отношении данных о лицах. Смягчение — Решение 6.

### Решение 5. Пул аккаунтов чтения с ротацией

**Выбор.** Система работает с более чем одним аккаунтом чтения, распределяет нагрузку между ними и переводит чтение на резервный при потере доступа.

**Почему.** Ограничение аккаунта — ожидаемое событие. При одном аккаунте потеря доступа останавливает продукт целиком.

**Рассмотренные альтернативы.** Один аккаунт — отклонён: единственная точка отказа. Официальные пути (Bot API) — невозможны по технике.

### Решение 6. Сообщения хранятся в окне обработки, в выжимку идут агрегат и обезличенные цитаты

**Выбор.** Прочитанные сообщения живут в окне обработки, после которого сохраняются: выжимка, короткие цитаты без авторов и ссылки на источник (сообщество, идентификатор сообщения). Авторство отделяется сразу при обработке и уходит в красную зону.

**Почему.** Это минимизирует объём удерживаемого содержания, сохраняя прослеживаемость и возможность показать формулировки. Требование спеки «примеры формулировок без имён» выполняется без хранения авторства рядом с цитатой.

**Рассмотренные альтернативы.** Хранить все сообщения целиком — отклонено: превращает платформу в архив чужих высказываний. Не хранить цитаты — отклонено: выжимка без примеров не проверяема.

## Risks / Trade-offs

- **[Блокировка аккаунта чтения]** → Пул аккаунтов и автоматический перевод чтения (Решение 5); обнаружение ограничения как штатное событие, а не авария.
- **[Позиционная несогласованность]** → Продукт использует источник, который сам относил к недопустимому. Смягчение: точечный пересмотр (Решение 2) и вынесение на решение владельца продукта в `proposal.md`, раздел Impact. Полностью не снимается.
- **[Цитата может быть атрибутируемой]** → Даже без имени короткая фраза из маленького сообщества позволяет узнать автора. Смягчение: порог сообщества по размеру и запрет на цитаты из малых групп; проверка перед выгрузкой.
- **[Отмена Решения 1 затрагивает требования всех 12 capability]** → Смягчение: пересмотр ограничен Telegram, остальные capability не меняются. При отказе от изменения правки откатываются комплексно (Migration Plan).
- **[Состав участников недоступен для крупных сообществ]** → Требование спеки допускает частичный результат с явной пометкой; подмена оценкой запрещена.
- **[Непрерывное чтение хранит чужое содержание постоянно]** → Смягчение: окно обработки и обезличивание при обработке (Решение 6).
- **[Смешение данных разных сообществ в выжимке]** → Смягчение: каждый пункт выжимки связан с сообществом-источником и не агрегируется между сообществами без явного указания.

## Migration Plan

**Порядок применения.** Изменение не может быть реализовано до правки рамки: пока Решение 1 запрещает авторизованные источники, реализация противоречит действующей рамке.

1. Правка `full-enterprise-core-scope`: Решение 1 (исключение для Telegram), Решение 2 (пересмотр запрета фонового сбора для этого источника), таблица Решения 9 (строка 3.12), следствия Решения 9 (вопрос 8 открывается заново), задача 1.2 (вывод Telegram из перечня).
2. Переоценка задачи 1.1: предмет юридической рамки изменился, заключение по прежней формулировке теряет силу.
3. Правка `docs/business-requirements.md` §3.12 и §7, `docs/architecture.md` §4: движок выводится из «исключён» в объём.
4. Реализация capability `telegram-community-digest`.
5. Сквозная проверка: выжимка не содержит авторов, выгрузка авторов отклоняется, потеря аккаунта не останавливает чтение.

**Откат.** Изменение затрагивает основание продукта, поэтому откат комплексный: снятие capability, возврат Решения 1 и задачи 1.2 в исходную редакцию, повторное исключение движка 3.12. Частичный откат — например, оставить чтение, но вернуть запрет — не предусмотрен: без отмены Решения 1 чтение нереализуемо.

## Open Questions

Эти вопросы можно решить позже, не меняя спеки, подход и разбивку задач:

1. **Выбор MTProto-библиотеки.** Telethon, Pyrogram или GramJS. Различия в устойчивости к ограничениям и в поддержке, но требования спеки от выбора не зависят.
2. **Размер пула аккаунтов чтения.** Определяется опытным путём после первых ограничений.
3. **Срок хранения данных красной зоны.** Параметр настройки; требования спеки задают разделение, а не конкретный срок.
4. **Период по умолчанию для выжимки.** Операционное значение, задаётся при настройке сообщества.
5. **Физическое размещение хранилища сессий.** Отдельный узел, отдельная БД или шифрование ключом — все варианты удовлетворяют требованию изоляции сессии от зелёной зоны.
