## Context

Мотивация и объём — в `proposal.md`. Здесь только состояние проекта и ограничения, формирующие подход.

`openspec/specs/` пуст: рамка `full-enterprise-core-scope` не заархивирована. Движок создаётся как новая capability, опираясь на требования рамки, но не меняя их — менять пока нечего, архивированных спек нет.

Ограничения рамки, определяющие дизайн:

- **Решение 1** — граница данных физическая: персональные данные физлиц живут в контуре клиента, а не на стороне платформы.
- **Решение 3** — очередь утверждений как ядро: единственный вход в отправку — утверждённый черновик; автоутверждение по таймауту запрещено.
- **Решение 8** — прочтение фиксируется только по переходам, пиксели не используются, автоматические переходы распознаются.
- **Решение 9** — `docs/business-requirements.md` — функциональный бэклог, приоритет у рамки.
- В системе один публичный эндпоинт — трекинговый домен. Страница выбора слота станет вторым.

**Ключевое напряжение.** Движок по природе событийный: он обязан исполнять напоминания по таймеру. Рамка требует человека перед каждым исходящим действием. Разрешение этого напряжения — центральное решение дизайна, и от него зависит всё остальное.

## Goals / Non-Goals

**Goals:**

- Свести приём из четырёх источников к одной сущности без дублей и без «последний записавший прав».
- Сохранить обязательность утверждения, не сделав напоминания неисполнимыми.
- Не расширить красную зону: ни одного нового хранилища персональных данных на стороне платформы.
- Обойтись без доступа к календарям третьих лиц и без хранения их токенов.

**Non-Goals (на уровне дизайна):**

- Не проектируем согласование времени: переписка о слотах остаётся обычными черновиками писем `outreach-channel-email`.
- Не проектируем собственные механизмы утверждения, отправки и трекинга — используем существующие.
- Не проектируем двустороннюю синхронизацию календарей и чтение занятости участников.
- Не проектируем голосовой канал и запись разговора.

## Decisions

### Решение 1. Ключ идемпотентности — «источник + внешний идентификатор»

Каждый источник обязан предъявить идентификатор, уникальный внутри источника. Пара образует ключ: форма выбора слота выдаёт идентификатор при создании звонка, вебхук CRM передаёт идентификатор записи, разбор ответа использует пару «идентификатор письма + идентификатор звонка из ссылки».

**Почему так:** один и тот же звонок приходит из нескольких источников, и свести их можно только по общему ключу. Хеш содержимого для этого не годится — у разных источников разный состав полей, а при переносе меняется время. Пара «участник + время» ломается по той же причине.

**Следствие:** источник без идентификатора не принимается. Это отсекает «любой источник» на уровне данных, а не соглашения.

### Решение 2. Подтверждение и утверждение — два разных механизма

**Подтверждение** (контрагент или менеджер) — сигнал о том, что встреча согласована. **Утверждение** (оператор) — единственный гейт, защищающий рамку.

**Почему разделяем:** если считать гейтом подтверждение, движок либо блокируется на встречах, согласованных вне платформы, либо требует обходных путей и тем самым обесценивает правило. Если убрать утверждение — исчезает заявленный результат продукта.

**Рассмотренные альтернативы:** (а) единственный гейт «подтверждено контрагентом» — отклонено: встреча, согласованная в мессенджере, необслуживаема; (б) автоматический инвайт при подтверждении контрагентом — отклонено: исходящее действие без утверждения, прямое противоречие Решению 3.

**Следствие:** состояния `слот подтверждён` и `подтверждён вне платформы` различимы в данных и в аудите и учитываются в отчётности отдельно. Оба ведут к формированию черновика плана, и ни одно не отменяет утверждение.

### Решение 3. Утверждение плана коммуникации — решение на каждое сообщение

Утверждается план целиком и по предъявлению: состав, тексты и расписание. Решение при этом фиксируется **отдельно по каждому сообщению плана** — по инвайту и по каждому напоминанию; одно решение на план вместо решений по сообщениям не сохраняется. Исполнение по расписанию нового решения не требует: напоминание исполняет уже принятое по нему решение, каждое отправление даёт отдельную запись аудита со ссылкой на это решение. Автоутверждение по таймауту запрещено. Любое изменение времени, текста или состава напоминаний сбрасывает решение по изменённому сообщению и требует нового.

**Почему это не отдельное правило, а применение существующего.** Рамка требует предварительного явного утверждения каждого исходящего действия и запрещает автоутверждение по таймауту. Для группового случая она уже установила, как согласовать одно с другим: пакет утверждается одним действием, но решение фиксируется по каждому черновику отдельно, и запрос журнала по черновику возвращает его собственное решение (`outreach-approval`, требование об индивидуальном решении внутри пакета). Здесь применяется тот же способ: предъявление одно, решений — по числу сообщений.

**Ссылка на BRD §1.1 убрана как неверная.** Она указывала на пакетное подтверждение, но BRD допускает его «пакетно по 50-100 **однотипных**», а инвайт и напоминания однотипными не являются: у них разные тексты и разные моменты отправки. Опора не держала, и прежняя редакция вводила правило заново, а не выводила его из рамки.

**Остаточная граница.** Требование рамки об индивидуальном решении сформулировано для пакета, а здесь применяется вне пакета — к плану одного звонка. Способ взят существующий, буква требования покрывает пакет. Если применение должно стать общим правилом, требование рамки расширяется отдельно.

**Что принимаем осознанно:** между утверждением и отправкой человека нет, поэтому ошибка в тексте напоминания тиражируется на все шаги расписания. Компенсация: план предъявляется целиком до принятия решений; отмена доступна в любой момент; по каждому отправлению сохраняется ссылка на принятое по нему решение.

**Границы:** напоминание — единственное исходящее действие, исполняемое без человека в момент отправки. Инвайт, перенос и уведомление об отмене человека требуют.

### Решение 4. Сущность звонка и внутренний календарь — в контуре клиента

Сущность звонка рассматривается как единый объект и целиком хранится в красной зоне: время, ссылка, состояние и источник не отделяются от участников в другую зону. Событие календаря также содержит имя и контакт участника. Хранилище платформы с такими данными противоречит Решению 1 напрямую, поэтому «внутренний календарь» означает календарь в красной зоне — в контуре клиента. В зелёную зону уходят только обезличенные агрегаты: число звонков, доля состоявшихся, конверсия.

**Рассмотренная альтернатива:** календарь платформы с маскированием участников — отклонено. Маскирование обязано быть обратимым для отображения, а обратимое маскирование означает хранение исходных данных на стороне платформы.

### Решение 5. ICS вместо доступа к календарю контрагента

Приглашение передаётся вложением ICS в утверждённом письме. Токены и доступы третьих лиц не требуются, объём собираемых данных не растёт, граница Решения 1 не расширяется.

**Что принимаем осознанно:** движок не знает, принял ли контрагент приглашение, и не видит занятость его участников. Движок не подбирает время автоматически — слоты задаёт человек, а выбор делает контрагент.

**Рассмотренная альтернатива:** интеграция с Google Calendar и Microsoft 365 — отклонено: токен доступа к аккаунту сотрудника и передача персональных данных участников во внешний сервис.

### Решение 6. Исход звонка фиксирует человек

Состояния «состоялся» и «не состоялся» устанавливаются решением человека. Переход по ссылке на конференцию SHALL NOT трактоваться как подтверждение проведения разговора.

**Почему:** связь с фактом разговора у платформы не наблюдаема — телефония вне объёма, записи разговора нет. Логика здесь та же, что в Решении 8 рамки: сигнал, который не доказывает событие, не должен переводить состояние. Отсутствие фиксации не трактуется ни как «состоялся», ни как «не состоялся» — состояние остаётся неопределённым.

### Решение 7. Страница выбора слота — отдельный публичный эндпоинт с уникальной ссылкой

Это второй публичный эндпоинт системы и единственное место, где персональные данные вводит внешний человек. Требования к нему: уникальная ссылка, привязанная к звонку; невозможность перечисления чужих звонков; ограничение частоты; минимум запрашиваемых полей; размещённая политика обработки персональных данных; вынесение на отдельный домен по аналогии с трекингом.

**Почему не обошлись разбором ответа на письмо:** подтверждение слота из свободного текста неоднозначно и даёт ложные срабатывания там, где цена ошибки — неверное время встречи. Страница даёт структурированное подтверждение с точным временем.

### Решение 8. Ссылка генерируется при исполнении, провайдер не получает участников

Ссылка создаётся в момент исполнения утверждённого плана, а не при формировании черновика: это сокращает окно жизни ссылки до неизбежного. Провайдер обязан позволять создать встречу без передачи данных участников.

**Принимаемое следствие:** часть популярных сервисов отпадёт, если они требуют участников при создании встречи. Совместимы сервисы с минимальным контрактом и self-hosted варианты.

**Почему не генерируем заранее:** ссылка — это фактически предъявительский доступ к переговорам с клиентом. Ссылка, созданная на этапе черновика, живёт до утверждения неограниченно долго, при том что черновик может быть отклонён.

### Решение 9. Доменная привязка

Изменение целиком лежит в context `outreach-orchestration`; новые элементы принадлежат aggregate `call` (root `call`, entities `call`, value objects `call-window`); утверждение плана коммуникации опирается на поддерживающий aggregate `campaign` (root `campaign`, entities `campaign`, `action-draft`, `operator-decision`, события `action-approved`, policies `operator-approval-required`); доменные факты — события `call-scheduled`; правила — policies нет; взаимодействия — через контракты `approved-action`, `campaign-command`, `outreach-outcome`; прямой импорт доменной модели чужого контекста запрещён; каталог остаётся без изменений.

## Risks / Trade-offs

- **[Ошибка в утверждённом плане тиражируется на все напоминания]** → План утверждается целиком и виден до утверждения; изменение плана сбрасывает утверждение; отмена снимает неотправленные шаги; аудит фиксирует каждое отправление.
- **[Два разных подтверждённых состояния усложняют отчётность]** → Состояния различимы в данных и аудите, отчётность считает их отдельно; смешивать их в одной метрике запрещено.
- **[Публичная страница — новая поверхность ввода персональных данных]** → Уникальная ссылка на звонок, ограничение частоты, минимум полей, политика обработки; юридическая проверка вынесена отдельной задачей.
- **[Исход звонка фиксируется вручную и может быть забыт]** → Владелец получает задачу после окончания слота; отсутствие фиксации не трактуется как «не состоялся» и не искажает отчётность.
- **[Зависимость от провайдера ссылок]** → Провайдер не выбран; контракт ограничен созданием встречи без данных участников, поэтому замена не затрагивает остальные решения.
- **[Напоминания требуют надёжного таймера]** → Исполнение идемпотентно по ключу «звонок + шаг расписания»; пропущенное окно не приводит к дублю и не отправляет пропущенное напоминание задним числом.
- **[Разбор ответа на письмо может ложно распознать согласие]** → Разбор используется как источник сведений, но состояние подтверждения требует либо действия на странице, либо ручного ввода с основанием; текст ответа сам по себе подтверждением не является.

## Migration Plan

Применение не требуется: проект пустой, кода нет, существующих данных нет.

Порядок ввода: сначала приём сведений и модель состояний; затем утверждение плана и внутренний календарь; затем генерация ссылки и ICS; затем напоминания; страница выбора слота — последней, так как на неё можно временно опираться ручным вводом.

Откат: отключение движка не затрагивает ядро, очередь утверждений и канал email; уже созданные события календаря остаются у клиента.

## Open Questions

1. **Провайдер генерации ссылки на конференцию.** Ограничение задано — без передачи данных участников. Влияет только на интеграционный слой.
2. **Длительность звонка по умолчанию и шаг сетки слотов.** Влияет на интерфейс страницы выбора слота, не на требования.
3. **Срок жизни ссылки на страницу выбора слота.** Параметр конфигурации, модель не затрагивает.
4. **Размещение страницы выбора слота.** Тот же вопрос размещения, что открытый вопрос 1 рамки: SaaS с раздельными контурами, шифрование ключом клиента или on-prem.
