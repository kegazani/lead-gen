## Context

Мотивация и объём — в `proposal.md`. Здесь состояние и ограничения, определяющие подход.

Модуль получает вход из `telegram-community-digest` и отдаёт результат на внешние площадки. Оба края накладывают ограничения, которых у внутренних модулей платформы не было.

**Первый край — источник.** Выжимка устроена так, что авторы и состав участников вынесены в красную зону, а наружу отдаётся только производная: темы, частоты, обобщённые запросы. Это единственный вход, совместимый с публикацией. Сырые сообщения содержат авторство, и работать с ними модуль публикации не должен — иначе граница зон обходится через него.

**Второй край — площадки.** У каждой свой санкционированный способ публикации, и он единственный. Правила площадок прямо запрещают автоматизацию браузера и пользовательской сессии даже на собственном аккаунте: владение аккаунтом не даёт исключения. Официальный API — не самый удобный путь, а единственный допустимый.

Отсюда третий ограничения-источник: **рамка исключила движок LinkedIn (3.13) с формулировкой «парсинг под авторизацией»**. Чтение данных LinkedIn и публикация в LinkedIn — разные действия, но формулировка в BRD §7 («автоматизированный доступ нарушает условия использования») их не различает, и при буквальном чтении запрещает оба. Различие требуется зафиксировать в документе, иначе репозиторий начнёт противоречить себе.

Четвёртое: **публикация необратима.** Материал, ушедший на внешнюю площадку, отозвать нельзя, и его увидит не адресат письма, а любой. Это делает утверждение человеком не формальностью, а условием существования модуля.

## Goals / Non-Goals

**Goals:**

- Реализовать публикацию через официальные API трёх площадок и только через них.
- Не допустить, чтобы модуль стал обходным путём к контуру персональных данных.
- Сделать невозможной публикацию без утверждения человеком.
- Развести материалы по площадкам так, чтобы одна и та же публикация не уходила в три места.

**Non-Goals:**

- Не проектируем публикацию от имени клиентов и хранение их токенов.
- Не проектируем закупку рекламы, продвижение публикаций, ответы на комментарии.
- Не проектируем полную аналитику площадок: фиксируем результат публикации, не собираем охваты.
- Не проектируем автоматизацию браузера и работу через сессии — это исключённый класс.
- Не проектируем работу с сырыми сообщениями сообществ: вход только выжимка.

## Decisions

### Решение 1. Публикация через официальные API как граница, отделяющая её от исключённого движка

**Выбор.** Все три канала реализуются только через официальные программные интерфейсы: официальный API Дзена по OAuth, официальный API публикаций LinkedIn по OAuth, Bot API Telegram. Конфигурация, отличная от официального API, отклоняется системой.

**Почему.** Рамка исключила движок 3.13 за чтение данных LinkedIn под сессией. Публикация ничего не читает и защиты не обходит. Но различие проходит ровно по способу доступа: официальный API санкционирован самой площадкой, автоматизация сессии — нет. Поэтому граница не «LinkedIn разрешён», а «разрешён только официальный интерфейс».

**Рассмотренные альтернативы.** Автоматизация браузера — отклонена: площадки прямо запрещают её даже на своём аккаунте, и это ровно исключённый класс. Неофициальные библиотеки — отклонены: используют внутренние токены, ломаются при изменениях площадки и нарушают её правила. Отказ от LinkedIn целиком — отклонён как избыточный: официальный путь существует и достаточен.

**Следствие.** Система обязана уметь отклонять конфигурацию, а не только «не использовать» запрещённый способ. Это требование спеки, а не пожелание.

### Решение 2. Публикация от имени платформы, не от имени клиентов

**Выбор.** Один набор учётных данных на канал: аккаунты Дзена, LinkedIn и Telegram принадлежат платформе.

**Почему.** Публикация от имени клиента требует хранения его токенов, отдельной заявки на доступ к API Дзена для каждого аккаунта и подтверждённого согласия — LinkedIn прямо запрещает публикацию от чужого имени без OAuth-согласия. Один набор учётных данных убирает целый класс задач: нет мультитенантного хранения токенов, нет вопросов согласия, нет разделения доступа.

**Рассмотренные альтернативы.** Мультитенантная публикация — отклонена на этом этапе: объём растёт кратно, а ценность для первого запуска не доказана. Смешанный режим — отклонён: две модели согласия в одной capability.

### Решение 3. Вход — только выжимка, без доступа к сырым сообщениям

**Выбор.** Модуль работает исключительно с готовой выжимкой. Доступа к сообщениям и к данным авторов у него нет.

**Почему.** Это техническая гарантия, а не договорённость. Если модуль публикации получит доступ к сырым сообщениям, он сможет перенести в публикацию авторство — и граница зон, выстроенная в `telegram-community-digest`, обходится через него. Ограничив вход выжимкой, мы делаем такой перенос невозможным по структуре, а не по дисциплине.

**Рассмотренные альтернативы.** Разрешить модулю читать сообщения для «более живого» текста — отклонено: цена ошибки при публикации выше, чем выигрыш в выразительности. Переносить цитаты с разрешения — отклонено: согласие участников сообщества получить нельзя.

### Решение 4. Отдельный материал под каждую площадку

**Выбор.** Дзен получает статью, LinkedIn — пост, сообщество Telegram — сообщение. Один материал на три площадки не формируется.

**Почему.** Две причины. Формат: у площадок разная длина, структура и ожидания читателя. Правила: массовая однотипная автоматическая публикация отнесена площадками к нарушениям, а идентичный материал в разных местах — признак автоматизации, а не редакции.

**Рассмотренные альтернативы.** Один материал с автоподгонкой длины — отклонён: даёт одинаковый текст с разной обрезкой, то есть ровно то, что запрещено.

### Решение 5. Расписание формирует материал, но не публикует

**Выбор.** Планировщик может подготовить материал к заданному времени. Публикация выполняется только после утверждения человеком, независимо от расписания.

**Почему.** Решение 3 рамки запрещает исполнение необратимого действия без утверждения. Исключение «по расписанию» уничтожило бы это правило целиком: расписание есть у любой регулярной публикации.

**Рассмотренные альтернативы.** Автопубликация утверждённого заранее шаблона по расписанию — отклонена: утверждается материал, а не правило его публикации.

### Решение 6. Порог по сообществу для публикаций строже, чем для выжимок

**Выбор.** Публикация формируется только по сообществам выше отдельного порога, более высокого, чем порог для внутренних выжимок.

**Почему.** Внутренняя выжимка видна оператору; публикация видна всем и остаётся доступной. Обобщение из маленького сообщества позволяет узнать автора даже без имени — по характерной формулировке и контексту. Чем выше цена ошибки, тем выше порог.

**Следствие.** Часть сообществ, пригодных для внутренней работы, окажется непригодной для публикации. Это принимается сознательно.

### Решение 7. Instagram/Meta исключён из объёма каналов

**Выбор.** Публикация в Instagram в объём не входит. Ни официальный интерфейс площадки, ни извлечение содержимого не реализуются; конфигурация с каналом Meta отклоняется.

**Почему.** Основание — не способ доступа, а правовой статус площадки. Рамка относит Instagram/Meta к вне закона в РФ и выводит их из состава продукта (`full-enterprise-core-scope/proposal.md`), а задача 1.2 держит их в перечне недопустимых сервисов, конфигурации с которыми система обязана отклонять. Официальный API снимает возражение о правилах площадки, но не правовое: это разные возражения, и площадочное правовое не заменяет. Прежняя редакция этого решения отвечала только на первое и потому расходилась с рамкой.

**Рассмотренные альтернативы.** Публикация через официальный API профессионального аккаунта — отклонена: способ доступа здесь ни при чём, канал недопустим по статусу площадки. Извлечение содержимого и автоматизация сессии — отклонены отдельно и независимо: запрещённый класс при любом решении по каналу.

**Следствие.** Требования формата Instagram (профессиональный аккаунт, обязательная визуальная часть, двухшаговая публикация с ожиданием готовности, недействующие ссылки в подписи) выведены вместе с каналом и в объём не входят. Набор материалов выравнивается: три площадки дают три текстовых формата, отдельного инфраструктурного требования к публично доступному адресу медиа не возникает.

### Решение 8. Предел площадки — потолок, а не цель

**Выбор.** Суточный предел площадки по числу публикаций соблюдается как потолок: система остаётся ниже него и уведомляет о приближении.

**Почему.** Предел существует как ограничение площадки против массовой автоматизации. Достижение его означало бы, что канал превратился в конвейер, а это противоречит требованию ограничения частоты и запрету дублирования. Поэтому приближение к пределу приостанавливает публикации, а не ускоряет их.

## Risks / Trade-offs

- **[Ограничения площадок по автоматической публикации]** → Даже через официальный API избыточная и однотипная публикация отнесена к нарушениям. Смягчение: требование об ограничении частоты и запрете дублирования; частота задаётся ниже предела площадки.
- **[Публикация необратима]** → Отозвать материал нельзя. Смягчение: обязательное утверждение, проверка на персональные данные перед публикацией, запрет переноса цитат.
- **[Внешние предусловия не решаются кодом]** → Доступ к API Дзена выдаётся по заявке; для Дзена без доступа остаётся только импорт по RSS, который не даёт публиковать произвольно. Смягчение: требование о проверке готовности канала и честном сообщении о неготовности вместо имитации работы.
- **[Права на содержание]** → Материал строится из чужих сообщений. Смягчение: публикуются только производные формулировки, дословный перенос запрещён требованием.
- **[Расхождение формулировок в репозитории]** → BRD §7 при буквальном чтении запрещает публикацию в LinkedIn. Смягчение: уточнение формулировки входит в задачи, как это делалось для Telegram.
- **[Порог по сообществу сокращает пригодные источники]** → Часть сообществ не сможет быть источником публикаций. Принимается осознанно: цена публичной ошибки выше полноты охвата.
- **[Формулировки не должны становиться обещаниями]** → Публикация видна регулятору и любому читателю. Смягчение: запрет на сведения, отсутствующие в источнике, распространяется из других модулей на этот.

## Migration Plan

Миграция не требуется: кода нет.

**Порядок.**

1. Уточнение BRD §7 и таблицы Решения 9: разделить чтение LinkedIn и публикацию через официальный API. Предусловие, как правка рамки для Telegram: без него репозиторий противоречит себе.
2. Переоценка открытого вопроса BRD §8 под номером 7 в части публикации.
3. Внешние предусловия: заявка на доступ к API Дзена, OAuth-приложение LinkedIn, назначение бота администратором сообщества.
4. Реализация после `telegram-community-digest` и `linguistics`: модуль зависит от обоих.

**Откат.** Модуль изолирован и не связан с контуром персональных данных. Отключение затрагивает только публикации: ранее опубликованные материалы остаются на площадках, отозвать их нельзя — это свойство площадок, а не дефект модуля.

## Open Questions

Эти вопросы можно решить позже, не меняя спеки, подход и разбивку задач:

1. **Использовать ли импорт по RSS для Дзена** как резервный путь, пока нет доступа к API. Формат публикации при этом ограничен, но требование спеки (официальный путь) не нарушается.
2. **Значения частоты публикаций** по площадкам. Задаются ниже предела площадки; конкретные числа определяются опытным путём.
3. **Значение порога по размеру сообщества** для публикаций. Требование задаёт принцип «строже, чем для выжимок», а не число.
4. **Куда публиковать в Telegram** — канал или группа. Bot API поддерживает оба; требование о правке бота одинаково.
5. **Срок актуальности выжимки** перед публикацией. Операционное значение.
