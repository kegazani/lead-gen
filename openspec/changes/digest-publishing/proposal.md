## Why

Выжимка из сообществ Telegram сейчас живёт только внутри платформы: её видит оператор и никто больше. Ценность появляется, когда выжимка превращается в публикации на площадках, где сидит аудитория. Нужен модуль, который берёт выжимку, перерабатывает её в материал под формат площадки и публикует в Дзен, LinkedIn и сообщество Telegram.

Публикация — это иное действие, чем чтение. Рамка исключила движок LinkedIn (3.13) с обоснованием «парсинг под авторизацией»: речь шла о **чтении** данных под сессией. Публикация ничего не читает и не обходит защиту — она идёт через санкционированный канал, который сама площадка предоставляет: официальный API с OAuth. Разворот рамки не требуется, требуется провести различие в формулировке.

Различие это не косметическое, и оно задаёт границу всего изменения. Официальный API разрешён; браузерная автоматизация и неофициальные способы запрещены правилами площадок **даже на своём аккаунте**. Последнее — ровно тот класс, который рамка исключила, и он остаётся исключённым.

## What Changes

- **Добавляется capability `digest-publishing`.** Вход — выжимка из `telegram-community-digest`. Выход — опубликованный материал в Дзен, LinkedIn и сообществе Telegram.
- **Каналы публикации строятся только на официальных API.** Дзен — официальный API по OAuth (доступ выдаётся по заявке; резервный путь для обычных авторов — импорт по RSS). LinkedIn — официальный Posts API по OAuth. Telegram — бот, назначенный администратором сообщества. Автоматизация сессии, браузерная автоматизация и неофициальные библиотеки **не используются**.
- **Instagram/Meta исключён из объёма каналов.** Публикация от имени Meta недопустима по правовому основанию рамки (`full-enterprise-core-scope/proposal.md`, задача 1.2), а официальный API площадки этого основания не снимает: он отвечает на возражение о правилах площадки, а не на правовое. Канал, его требования формата и относящиеся к ним задачи из изменения выведены.
- **Публикуется от имени платформы.** Один набор учётных данных на канал: аккаунты Дзена, LinkedIn и Telegram принадлежат платформе, а не клиентам. Публикация от имени клиента не входит в объём.
- **Публикация — необратимое исходящее действие.** По Решению 3 каждый материал утверждается человеком до публикации. Автоматическая публикация без утверждения запрещена, включая публикацию по расписанию.
- **Выжимка перерабатывается, а не перепечатывается.** Материал собирается из тем, частот и повторяющихся запросов. Дословные цитаты участников сообществ в публикации не переносятся: приватная выжимка и публичная статья имеют разную цену ошибки.
- **Требуется уточнение в BRD §7 и в таблице Решения 9.** Формулировка «автоматизированный доступ нарушает условия использования» под запретом чтения описывает и публикацию. Различие между парсингом LinkedIn (исключён) и публикацией через официальный API (входит в объём) должно быть зафиксировано, иначе репозиторий будет противоречить себе так же, как это было с Telegram.
- **Вне объёма:** публикация от имени клиентов, закупка рекламы, продвижение публикаций, ответы на комментарии, аналитика охватов за пределами получаемой от API площадки.

## Capabilities

### New Capabilities

- `digest-publishing`: превращение выжимки из сообществ Telegram в публикации для Дзена, LinkedIn и сообщества Telegram. Охватывает: получение выжимки как входа; переработку под формат каждой площадки; формирование черновика публикации; утверждение оператором; публикацию через официальные API; учёт ограничений площадок по частоте и дублированию; фиксацию результата публикации.

### Modified Capabilities

Нет. `openspec/specs/` пуст, доставленных capability нет. Это изменение **переиспользует** существующие:

| Capability | Как используется |
|---|---|
| `telegram-community-digest` | источник: выжимка содержания сообществ |
| `linguistics` | переработка текста, тональность, язык публикации |
| `outreach-approval` | утверждение перед необратимым действием (по аналогии, для публикаций) |

Формулировка BRD §7 и таблица Решения 9 правятся как **уточнение**, а не как отмена: движок 3.13 остаётся исключённым для чтения.

## Impact

**Согласованность с рамкой.** Изменение не отменяет Решения 1-8. Решение 1 запрещает источники, требующие авторизации, — это правило о **чтении** данных. Публикация идёт через санкционированный канал и под это правило не подпадает. Решение 3 (утверждение перед необратимым действием) применяется полностью и без исключений.

**Требуется правка документов.** BRD §7 (абзац про LinkedIn) и таблица Решения 9 требуют уточнения: разделить чтение и публикацию. Открытый вопрос BRD §8 под номером 7 (LinkedIn) открывается заново в части публикации.

**Внешние предусловия, не решаемые кодом.**

- **Доступ к API Дзена** — выдаётся по заявке авторам и медиа. Без него остаётся только импорт по RSS, который не даёт публиковать произвольно.
- **OAuth-приложение LinkedIn** — для публикации в свой фид достаточно `w_member_social`; для страницы компании требуется одобрение Marketing Developer Platform.
- **Бот в сообществе Telegram** — должен быть назначен администратором; приглашение делает владелец сообщества.

**Риски.**

- **Ограничения площадок по массовой автоматической публикации.** Даже через официальный API избыточная и однотипная публикация запрещена: LinkedIn прямо относит к нарушениям «автоматическую публикацию, которая является спамной, повторяющейся или вводящей в заблуждение». Требование об ограничении частоты и запрете дублирования входит в объём.
- **Права на содержание.** Материал строится из чужих сообщений. Пересказ тем и запросов — производная работа; перенос цитат — копирование. Запрет на цитаты в публикациях зафиксирован требованием.
- **Раскрытие через цитату.** Даже без имени короткая фраза из малого сообщества позволяет узнать автора. Порог по размеру сообщества, действующий в `telegram-community-digest` для приватных выжимок, для публичных материалов ужесточается.
- **Расхождение форматов.** Один материал для трёх площадок публиковать нельзя: у Дзена статья, у LinkedIn пост, у Telegram сообщение. Требование о переработке под формат каждой площадки входит в объём.
