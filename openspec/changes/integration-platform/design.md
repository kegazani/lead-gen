## Context

См. `proposal.md` — Why. Ниже только состояние и ограничения, определяющие подход.

Доменные границы среза уже зафиксированы каталогом `architecture/domain-catalog.yaml` и не проектируются заново:

- owning context — `integration-platform` (класс `generic`), сервис `integration-platform`, роли `api, ingest, sender, worker, chains, schedule`;
- агрегат `adapter-registration` (AR; VO `manifest-version`; событие `adapter-registered`; политика `adapter-selection`; инварианты: возможности адаптера проверяются до вызова; секреты не входят в доменные события и ошибки);
- агрегат `integration-invocation` (AR; VO `correlation-ref`; события `integration-failed`, `integration-recovered`; политика `error-normalization`; инварианты: вызов идёт через provider port, а не через SDK поставщика; ответы и ошибки поставщика нормализуются до доменных значений);
- публикуемые контракты владельца: `provider-port` (command, `sync`/`http-json`), `adapter-capability`, `integration-error`; в каталоге семь связей `integrations-for-*`, все — `provider-port`;
- состояния агрегатов (`docs/system-map.md` §4): регистрация — «зарегистрирован; прошёл контрактные тесты / не допущен к поставке»; вызов — «выполнен / нормализованная ошибка; тайм-аут; отменён».

Требования среза — спека `migrate-platform-to-go/specs/provider-agnostic-integrations/spec.md`; она не меняется (`skip_specs: true`). Бизнес-кода контекста нет: сервис поднимается заглушкой `stubService` в `backend/cmd/lead-gen`, а механизмы `migrate-platform-to-go` §3 существуют только как задачи без кода. Каркас Go уже создан: модуль на контекст (`backend/contexts/outreach-orchestration` — эталон среза), `backend/platform`, `backend/cmd/lead-gen`, `contracts/<owner>`, связанные `go.work`; границы импортов проверяет `tools/importlint`, каталог — `tools/archlint`.

Ограничения, определяющие подход: драйвер PostgreSQL в проекте отсутствует — хранилища среза только in-memory (открытый вопрос 5 эталона `outreach-approval-slice`); SDK реальных поставщиков вне среза — проверка только на тестовых адаптерах; `docs/architecture.md` §6.5 (секреты не попадают в журналы, трассировки и сообщения об ошибках) и §11 (SDK только внутри адаптера) — обязательные границы.

## Goals / Non-Goals

**Goals:**

- Провести первый вертикальный срез контекста: домен → use case → порт → адаптер → сборка сервиса, до unit-тестов инвариантов обоих агрегатов.
- Закрепить границу «домен `integration-platform` ↔ технические примитивы `backend/platform`» так, чтобы манифест, выбор адаптера, нейтральные категории ошибок и нейтральные идентификаторы были доменными правилами, а реестр фабрик, валидация конфигурации и оболочка вызова — техническими механизмами без доменных терминов.
- Опубликовать контракты `provider-port`, `adapter-capability`, `integration-error` как артефакт (пакеты модуля `contracts/integration-platform`), который потребители могут импортировать без SDK.
- Доказать несущий инвариант продукта: внешняя работа идёт только через `provider-port`, с проверкой возможностей до вызова и нормализацией ошибок до доменных значений, — и это обеспечено ядром, а не адаптерами.
- Зафиксировать разметку задач §3 `migrate-platform-to-go` между этим изменением и платформенным каркасом без двойного владения.

**Non-Goals:**

- SDK и production-адаптеры реальных поставщиков — появляются с первым бизнес-сценарием каждого потребителя.
- Сетевой адаптер `provider-port` (`http-json`) — срез работает только в механизме `in-process`.
- PostgreSQL-адаптеры репозиториев — драйвер отсутствует, следующим шагом.
- Публикация доменных событий `integration-failed`/`integration-recovered` наружу контекста.
- Изменение каталога, `docs/*` и диаграмм: модель уже объявлена и реализуется как есть.

## Decisions

### Решение 1. Граница «домен `integration-platform` ↔ технические примитивы `backend/platform`»

Домен `backend/contexts/integration-platform/internal/domain` получает:

- типизированный manifest адаптера — стабильное имя адаптера, VO `manifest-version` и набор возможностей `adapter-capability`, без `map[string]any`; manifest — часть агрегата `adapter-registration`;
- нейтральные внутренние идентификаторы: `AdapterID` (регистрация) и `InvocationID` (вызов); привязка внешних идентификаторов — типизированная запись «тип интеграции + имя адаптера + внешний id» в результате вызова (`integration-invocation`), чтобы внешний id не подменял внутренний;
- нейтральные категории ошибок — доменные значения контракта `integration-error`; политика `error-normalization` работает только с категориями, а не с типами SDK;
- политики `adapter-selection` и `error-normalization` — чистые функции домена.

`backend/platform` получает технические примитивы **без доменных терминов** (не импортируют контексты и контракты):

- реестр фабрик адаптеров и ручную сборку зависимостей в composition root (задача §3.2 миграции) — предполагаемый пакет `backend/platform/registry`;
- предварительную проверку конфигурации: общая секция (имя адаптера, тайм-ауты, обязательные возможности) и специфическая секция выбранного адаптера; секреты — ссылками на защищённый источник (задача §3.3) — рядом с `backend/platform/deployment`;
- общую оболочку вызова порта: тайм-ауты, отмена, согласованная политика повторов и нормализованная телеметрия с метками `port`, `adapter`, `operation`, `outcome` (задача §3.6) — предполагаемый пакет `backend/platform/reliability`. Оболочка не знает категорий `integration-error`: она возвращает абстрактный исход вызова, а в категории нормализуют адаптер и домен.

Альтернатива — положить манифест и категории ошибок в `backend/platform`. Отклонена: платформенный примитив превратился бы в shared domain, а `docs/domain-model.md` («Реализация на Go») и `docs/system-map.md` §2.2 прямо запрещают общие библиотеки бизнес-правил и доменные термины в примитивах. Альтернатива — положить реестр, конфигурацию и оболочку в домен контекста. Отклонена: раздувает агрегаты техническими заботами и лишает другие контексты переиспользования механизма.

### Решение 2. Агрегат `adapter-registration`: manifest и проверка возможностей до вызова

Агрегат создаётся командой `RegisterAdapter` с нейтральным `AdapterID`, стабильным именем адаптера и неизменяемым manifest. Manifest типизирован: имя, VO `manifest-version` (валидируемая версия схемы возможностей) и набор возможностей `adapter-capability`. Возможности — значения с именами, а не строки на доверии; набор проверяется при создании.

Первый инвариант каталога — «возможности адаптера проверяются до вызова» — реализуется методом агрегата `Require(capability)`: регистрация отвечает, объявлена ли возможность в manifest, а app-слой обязан запросить эту проверку до вызова порта. Проверка живёт в агрегате, а не в прикладном коде: любой вызывающий путь, включая будущие, проходит через неё. Неизвестный адаптер или необъявленная обязательная возможность — диагностика с именем контракта и адаптера без секретов (спека, сценарий «Выбран неизвестный адаптер»).

Второй инвариант — «секреты не входят в доменные события и ошибки» — держится формой: событие `adapter-registered` несёт только идентификатор, имя, версию и возможности; доменные ошибки регистрации и выбора не имеют полей секретов; секреты передаются адаптеру исключительно механизмом конфигурации вне домена (`docs/architecture.md` §6.5).

Событие `adapter-registered` — domain event агрегата; политика `adapter-selection` — чистая функция «набор регистраций × обязательные возможности контракта → выбранный адаптер», без побочных эффектов и без доступа к хранилищу.

Альтернатива — проверять возможности в app-сервисе. Отклонена: проверку можно обойти любым другим вызывающим, а инвариант каталога обязан быть необходимым на уровне агрегата (тот же довод, что в Решении 1 эталона `outreach-approval-slice`).

### Решение 3. Агрегат `integration-invocation`: correlation-ref, порт вместо SDK, нормализация

Агрегат создаётся на каждый вызов внешней интеграции: `InvocationID`, VO `correlation-ref` (идентификатор, связывающий вызов со сквозным сценарием; заполняется из `correlation_id` envelope), тип интеграции, имя выбранного адаптера и состояние по `docs/system-map.md` §4 — «выполнен / нормализованная ошибка; тайм-аут; отменён». Результат успешного вызова хранит привязку внешнего идентификатора поставщика (тип интеграции, имя адаптера, внешний id) — спека, сценарий «Сохранение результата внешней операции»: внешний id не подменяет внутренний.

Второй инвариант — «вызов идёт через provider port, а не через SDK поставщика» — держится формой кода и проверяется инструментами: домен и app не импортируют SDK; вызов оформлен интерфейсом порта `ProviderPort` из `internal/ports`, реализации — только в `adapters`. Проверка: `tools/importlint`, отрицательные фикстуры и `go list -deps` доменного и прикладного слоёв.

Нормализация — политика `error-normalization`, чистая функция: ошибка, пришедшая от адаптера, отображается в доменную категорию контракта `integration-error` из набора §3.4 миграции — `temporarily-unavailable`, `rate-limited`, `authorization-denied`, `invalid-request`, `conflict`, `permanent-failure`. Категория — решение прикладной логики; диагностическая причина сохраняется для журналов и **не попадает в события** (инвариант о секретах). По исходу агрегат эмитит `integration-failed` (вызов завершился нормализованной ошибкой) или `integration-recovered` (успешный вызов, следующий за зафиксированной временной ошибкой в том же `correlation-ref`). События — доменные, наружу контекста в срезе не публикуются (Non-Goals).

Альтернатива — ветвить прикладную логику по ошибкам SDK. Отклонена: нарушает инвариант каталога и требование «SDK возвращает собственную ошибку → адаптер преобразует её в ошибку внутреннего контракта до передачи в прикладной слой».

### Решение 4. Форма контрактов: модуль `contracts/integration-platform`

Контракты публикуются отдельным Go-модулем `contracts/integration-platform`, пакет на контракт, по образцу `contracts/outreach-orchestration`:

- `providerport` — синхронный командный контракт `provider-port` (command, `sync`/`http-json`): интерфейс `Invoke(ctx, Request) (Result, error)`, типизированные DTO запроса и результата, envelope, имя и версия схемы, ключ идемпотентности; операции выражают возможности, объявленные `adapter-capability`;
- `adaptercapability` — типизированное объявление возможности (имя, версия схемы набора);
- `integrationerror` — категория ошибки закрытым набором значений, имя адаптера, тип контракта и диагностическая причина для журналов; полей секретов нет;
- `vector` — provider-port векторного хранилища (эмбеддинг + поиск по близости); потребляется `lead-management` (semantic-lead-search) и `request-fulfillment` (эмбеддинг оффера); введён change `semantic-lead-search`.

Пакеты зависят только от стандартной библиотеки: ни один не импортирует SDK, контексты или `backend/platform`. Поэтому потребитель импортирует контракт и не видит реализацию; связь сторон — in-process адаптер рядом с контрактом (Решение 8) или сетевой клиент — выбирается топологией, а не кодом потребителя.

Envelope — общий формат `docs/domain-model.md`: `event_id`, `occurred_at`, `tenant_id`, `correlation_id`, `causation_id`, имя и версия схемы; версии — semver, добавление опционального поля совместимо. Валидация возвращает все некорректные обязательные поля одним сообщением (как `approvedaction.Validate`).

Внутри контекста контракты реэкспортируются пакетом `internal/ports/contracts` — единственным определением wire-формы остаётся модуль `contracts/integration-platform`; там же сверка значений с доменными VO (как `ValidateApprovedAction` в эталоне).

Альтернатива — объявить контракты только внутри `internal/ports` контекста. Отклонена: потребители не смогли бы импортировать контракт, не импортируя модуль владельца, а межконтекстный доступ в проекте разрешён только через `contracts/<owner>` (правило `tools/importlint`). Альтернатива — один пакет на все три контракта. Отклонена: форма эталона — пакет на контракт, версионирование схем независимое.

### Решение 5. Слои и направление зависимостей

```text
backend/contexts/integration-platform/     # Go-модуль, корневой пакет — сборка сервиса
  internal/domain/    adapter-registration, integration-invocation (AR), VO manifest-version,
                      correlation-ref, domain events adapter-registered / integration-failed /
                      integration-recovered, политики adapter-selection, error-normalization
  internal/app/       use cases: RegisterAdapter, SelectAdapter, InvokeIntegration,
                      запросы состояния вызова
  internal/ports/     ProviderPort, AdapterRegistrationRepository, IntegrationInvocationRepository,
                      contracts/ (реэкспорт модуля contracts/integration-platform)
  internal/ports/contracttest/   общий contract suite портов
  internal/adapters/  repository (in-memory), provider (тестовый адаптер)
contracts/integration-platform/            # published language: providerport, adaptercapability,
                                           # integrationerror (+ inproc адаптер)
```

`domain` не импортирует `app`, `ports`, `adapters`, другие контексты и `backend/platform`. `app` видит только свой `domain`, свои `ports` и опубликованные контракты. `ports` видит контракты и свой `domain` (сверка значений с VO). SDK поставщиков и драйвер PostgreSQL допустимы только в `adapters` (и только SDK — в срезе его нет). Межконтекстная сборка — только в корневом пакете контекста и `backend/cmd/lead-gen`.

Эти границы проверяет `tools/importlint` (грамматика `lead-gen/backend/contexts/<ctx>/internal/<layer>` покрывает новый контекст автоматически; отрицательные фикстуры добавляются задачей среза), а не `tools/archlint`: archlint читает каталог, спеки и диаграммы, Go-импорты он не анализирует. Оба инструмента запускаются вместе.

Альтернатива — общие `internal/domain`, `internal/app`, `internal/ports`. Запрещена конфигурацией проекта (`migrate-platform-to-go` Решение 2, `docs/domain-model.md` «Реализация на Go»): она стёрла бы owning context и превратила бы домен в общий граф.

### Решение 6. Восстановление агрегатов через Snapshot/Rehydrate

Адаптер репозитория не имеет доступа к закрытым полям агрегатов: сохранение и загрузка идут через доменные функции в `domain/snapshot.go` — `Snapshot()` у обоих агрегатов отдаёт экспортированный снимок, а `RehydrateAdapterRegistration` / `RehydrateIntegrationInvocation` собирают агрегат. Восстановление проверяет инварианты (валидность manifest и версии, соответствие заявленных возможностей, согласованность состояния вызова с его результатом, отсутствие противоречий) и завершается доменной ошибкой при противоречивом снимке; события при восстановлении не эмитятся — восстановление не новый факт домена.

Знание об устройстве агрегатов остаётся в `domain`; `adapters` работают только с экспортированными снимками, сериализация снимка — забота адаптера (в срезе — in-memory, позднее — PostgreSQL тем же контрактом).

Альтернатива — репозиторий собирает агрегат напрямую из строк хранилища. Отклонена: адаптер получил бы доступ к внутреннему устройству агрегата, и инварианты пришлось бы дублировать вне домена (то же решение, что Решение 9 эталона).

### Решение 7. Идемпотентность и `correlation-ref`

Команды внешнего эффекта имеют стабильный ключ идемпотентности (политика «Idempotency» `docs/domain-model.md`). Ключ вызова — `(tenant_id, тип интеграции, операция, ключ команды)`; агрегат `integration-invocation` хранит ключ вместе с результатом. Повтор команды с тем же ключом возвращает сохранённый результат прежнего вызова и **не обращается к поставщику повторно** — внешний эффект не дублируется.

`correlation-ref` связывает вызов со сквозным сценарием: заполняется из `correlation_id` конверта входящей команды и передаётся в результат и события. Так вызов прослеживается от инициирующего бизнес-сценария потребителя (обогащение, отправка, CRM) без передачи домена потребителя в `integration-platform`.

Разграничение с платформенным примитивом: домен задаёт ключ и семантику «повтор не создаёт второго эффекта»; техническую дедупликацию команд на границе даёт примитив `platform` (`docs/system-map.md` §2.2), а механика хранения ключей — репозиторий агрегата. Оболочка вызова не владеет политикой повторов скрыто: согласованность повторов — её зона (Решение 1), но она не умножает эффекты — повторяются только идемпотентные вызовы по ключу.

Альтернатива — дедупликация только на границе примитивом `platform`. Отклонена: доменное правило «повтор вызова — тот же результат» обязано пережить смену транспорта и быть проверяемым тестами агрегата, а не зависеть от технического слоя.

### Решение 8. In-process адаптер при co-location; сетевой — позже

По образцу `contracts/outreach-orchestration/approvedaction/inproc`: пакет `contracts/integration-platform/providerport/inproc` связывает потребителя, держащего интерфейс `providerport.Port`, с реализацией владельца прямым вызовом в одном процессе. Адаптер обязан сохранять семантику контракта, чтобы переход к сетевому адаптеру не менял наблюдаемое поведение: принимает `context.Context`, соблюдает дедлайн и отмену (вызов прерывается по бюджету, даже если реализация не проверила контекст), проверяет контракт до вызова и дедуплицирует по ключу идемпотентности — повторная доставка того же ключа не вызывает владельца повторно.

Механизм связи задаёт топология: группы `deploy/services.yaml` в совмещённом деплое работают в `in-process`. Сетевой `http-json`-адаптер появится рядом с контрактом при разделении сервисов по процессам (вне среза) — форма контракта от этого не меняется.

Альтернатива — сразу писать сетевой адаптер. Отклонена: сетевой слой добавляет сериализацию, маршрутизацию и инфраструктуру, которых совмещённый деплой не требует; контракт и inproc-адаптер уже гарантируют, что смена транспорта не изменит семантику.

### Решение 9. Общий contract suite для портов

Владелец портов поставляет повторно используемый suite в `internal/ports/contracttest` — по образцу §5.1–5.3 миграции и спеки «Контрактная совместимость адаптеров». Suite запускается против любой реализации через фабрику и проверяет:

- успешный вызов с корректным результатом;
- каждую категорию `integration-error` (временная недоступность, rate limit, отказ авторизации, некорректный запрос, конфликт, окончательный отказ);
- тайм-аут и отмену `context.Context`;
- идемпотентность: повтор одного ключа не создаёт второго внешнего эффекта;
- отсутствие секретов в ошибках и диагностике (фикстуры API-ключей, токенов, адресов);
- для репозиториев — сохранение/загрузку через Snapshot/Rehydrate и различение «нет сущности».

Тот же suite гоняется против in-memory-реализаций и тестового адаптера провайдера; когда появится драйвер PostgreSQL, против него прогонится тот же набор (риск расхождения реализаций закрывается общим suite, как в эталоне). Unit-тест с mock не считается доказательством совместимости адаптера.

Альтернатива — тестировать каждый адаптер своими тестами. Отклонена: спека требует общий набор для каждого заменяемого контракта, и только он доказывает, что смена адаптера не меняет наблюдаемое поведение.

### Решение 10. Размежевание с задачами §3 `migrate-platform-to-go`

Двойного владения нет: каждая задача §3 получает ровно одного владельца.

| Задача §3 | Владение | Реализует |
|---|---|---|
| 3.1 типизированный manifest | домен (AR `adapter-registration`) | этот change, Решение 2 |
| 3.2 реестр фабрик и ручная сборка | `backend/platform` | платформенный каркас; срез потребляет |
| 3.3 предварительная проверка конфигурации | `backend/platform`; доменная часть (соответствие manifest обязательным возможностям) — политика `adapter-selection` | каркас + этот change |
| 3.4 нейтральные категории ошибок | домен (контракт `integration-error`, политика `error-normalization`); преобразование на границе — адаптеры среза | этот change |
| 3.5 нейтральные внутренние id и привязка внешних | домен (оба агрегата) | этот change, Решения 2–3 |
| 3.6 оболочка вызова (тайм-ауты, отмена, повторы, телеметрия) | `backend/platform` | платформенный каркас; срез потребляет |

Задачи 3.1, 3.4, 3.5 закрываются этим изменением; 3.2, 3.3, 3.6 остаются в платформенном каркасе и реализуются вне среза — срез лишь фиксирует их потребление. Разметка вносится в `openspec/changes/migrate-platform-to-go/tasks.md` задачей среза (раздел 6 задач) без переноса текстов спек. Задачи §5 миграции (контрактные тесты всех портов платформы) остаются за миграцией: suite среза — экземпляр их механизма, а не их замена.

## Risks / Trade-offs

- **[PostgreSQL-адаптер отсутствует, срез проверяется только на in-memory и тестовых адаптерах]** → Общий contract suite репозиториев и портов; тот же набор прогонится против PostgreSQL-реализации, когда драйвер появится (вопрос 1).
- **[Реальные SDK вне среза могут создать ложную уверенность в переносимости]** → Тестовый адаптер, эмулирующий все категории ошибок, тайм-аут и отмену; production-адаптер допускается только после прогона общего suite (спека, сценарий «Проверка адаптера перед включением»).
- **[Оболочка вызова в `backend/platform` может незаметно накопить доменные термины]** → Правило: пакеты `backend/platform` не импортируют контексты и контракты (проверяется `importlint`); оболочка работает с абстрактным исходом, нормализацию в категории выполняют адаптер и домен.
- **[Идемпотентность в in-memory теряется при перезапуске]** → В срезе допустимо (тесты и совмещённый деплой); устойчивое хранение ключей вернёт PostgreSQL-адаптер.
- **[События `integration-failed`/`integration-recovered` не публикуются наружу — риск потери фактов отказов для наблюдаемости]** → Факты фиксируются состоянием агрегата и нормализованными метками оболочки; публикация событий — отдельный шаг (вопрос 3).
- **[Замена `stubService` сборкой может разойтись с группами `deploy/services.yaml`]** → e2e-тест сборки сервисов в `backend/cmd/lead-gen`; роли, которых нет, честно логируются, а не притворяются работающими (как в эталоне).

## Migration Plan

Миграции данных нет: сервис был заглушкой, агрегаты существуют только в памяти. Порядок внутри среза: модуль и `domain` (инварианты) → `app` → контракты → адаптеры и suite → сборка сервиса и замена заглушки → разметка задач миграции → валидация.

Откат: вернуть ветку `stubService` для `integration-platform` в `backend/cmd/lead-gen` и убрать модули из `go.work`. Внешние эффекты отсутствуют, пока потребители не вызывают `provider-port`; доменные события наружу не публикуются.

## Open Questions

1. **Драйвер PostgreSQL.** Репозитории PostgreSQL заблокированы отсутствием драйвера: `go.mod` контекста не содержит зависимостей, добавление требует сетевого доступа и решения по зависимости (вопрос 5 эталона). До этого contract suite идёт только на in-memory-реализациях.
2. **Состав возможностей `adapter-capability` для реальных потребителей.** Срез несёт каркас `provider-port` и тестовую возможность; конкретные операции (OSINT-обогащение, отправка и т. д.) определяются сценариями потребителей. Не меняет форму контракта и разбиение задач.
3. **Публикация `integration-failed`/`integration-recovered` наружу.** Нужен ли публикуемый контракт событий для наблюдаемости или downstream-потребителей — отложено; в срезе события остаются доменными.
4. **Сетевой `http-json`-адаптер `provider-port`.** Появится при разделении сервисов по процессам; форма контракта и inproc-семантика уже совместимы.
5. **Параметры политики повторов оболочки `backend/platform`** (бюджеты, backoff, классы повторов). Детали — платформенный каркас (§3.6 миграции), домен от них не зависит: он видит только исход вызова.
