- [x] 1.5 Реализовать aggregate root `integration-invocation`: `InvocationID`, VO `correlation-ref`, тип интеграции, имя адаптера, состояния «выполнен / нормализованная ошибка / тайм-аут / отменён», результат с привязкой внешнего идентификатора (тип интеграции, имя адаптера, внешний id). - [x] 1.6 Реализовать политику `error-normalization`: отображение ошибки адаптера в категорию `integration-error` (`temporarily-unavailable`, `rate-limited`, `authorization-denied`, `invalid-request`, `conflict`, `permanent-failure`) с диагностической причиной только для журналов; domain events `integration-failed` и `integration-recovered` (успех после временной ошибки в том же `correlation-ref`). ## Отложено (вне среза)

- PostgreSQL-адаптеры `AdapterRegistrationRepository` и `IntegrationInvocationRepository` — заблокированы отсутствием драйвера (design.md, вопрос 1); contract suite уже готов и прогонится против них без изменений.
- Сетевой `http-json`-адаптер `provider-port` для разделённых по процессам сервисов (design.md, вопрос 4).
- Production-адаптеры SDK реальных поставщиков — с первым бизнес-сценарием каждого потребителя, только после общего contract suite.
- Публикация `integration-failed`/`integration-recovered` наружу контекста (design.md, вопрос 3).
- Конкретные операции `provider-port` для потребителей (OSINT-обогащение и др.) — состав возможностей определяется их сценариями (design.md, вопрос 2).
