## Context

`platform-governance` уже владеет командами решения по регистрации и профилю и
матрицей доступа консоли (`app.Section` / `app.Action` / `AuthorizeSection`).
Консоль `platform-governance` (`/console/**`) рисуется серверно, доступ
проверяется функцией `decideSection` по ролям актора из снимка `access-decision`.
Считанные команды (`ApproveRegistration` и т.п.) вызывают `app.Authorize` внутри
и требуют права `domain.RightManageTenants`, поэтому HTTP-слой не создаёт нового
права — он лишь предоставляет экран и действия.

Заявка на регистрацию не привязана к активному тенанту оператора: у тенанта
`pending` нет администратора-клиента, способного дать роль. Поэтому доступ к
разделу определяется признаком платформенного оператора
(`DecideAccess.IsOperator`), как уже сделано для списка тенантов без активного
тенанта.

## Goals / Non-Goals

- **Цель:** администратор платформы видит заявки на регистрацию и профили на
  согласовании и принимает решение (одобрить/отклонить с комментарием).
- **Цель:** решение проверяется на сервере, причина отклонения обязательна.
- **Не цель:** менять домен, команды, события, контракты и каталог.
- **Не цель:** живое обновление очереди (SSE) — экран статический, обновляется
  перезагрузкой; поток можно добавить отдельным change'ом.

## Decisions

### Решение 1. Новый раздел консоли `SectionRegistrations`

В `access_matrix.go` добавляется `SectionRegistrations`; `view`/`manage` требуют
`domain.RightManageTenants`. Экран — `GET /console/registrations`, действия —
`POST .../{tenantID}/approve|reject|profile/approve|profile/reject`. Пункт меню
добавляется в `consoleNav` (подпись из каталога сообщений).

### Решение 2. Доступ через признак платформенного оператора

Так как у заявки нет активного тенанта с ролями, раздел проверяется
`platformOperator(actor)` (тем же признаком, что и список тенантов без
`tenant_id`). Дополнительно команда сама проверяет право актора, поэтому неверный
актор получает отказ независимо от экрана.

### Решение 3. Расширение read-модели `TenantDirectory.List`

Список заявок требует идентифицирующих данных компании. Расширяется
`ports.TenantSummary` (`INN`, `CompanyEmail`, `Website`, `LegalData`,
`Description`, `RegistrationReason`, `CreatedAt`, `ProfileStatus`), а SQL-запрос
`selectTenantList` и обе реализации (`inmemory`, `postgres`) заполняют поля.
Пользователи (логины) в read-модель не добавляются: экран проверяет компанию, а
не её людей. Агрегат через список не восстанавливается.

### Решение 4. Причина отклонения регистрации обязательна

`POST .../reject` требует непустой `reason`; пустой ввод возвращает экран с
сообщением, а не «немой» отказ. Причина сохраняется доменом
(`RegistrationReason`) и остаётся доступной доменной модели. Отклонение профиля
(`RejectProfile`) причину не принимает — домен её не хранит, поэтому комментарий
для профиля не требуется (расширение причинами профиля — отдельный change).

## Risks / Trade-offs

- **[Расширение read-модели чужим кодом]** → Поля компании — не персональные
  данные пользователей; комментарий порта обновляется в том же change.
- **[Консоль без аутентификации]** → Срез полагается на проверенный `actor` из
  контура (dev) и `platformOperator`; команда повторно проверяет право. Граница
  аутентификации этим change'ом не меняется.
- **[Двойное решение по профилю]** → Обработчик проверяет `pending` в домене: из
  другого состояния команда отклоняется (`ErrProfileState`).

## Migration Plan

Миграций данных нет. Порядок: read-модель и запрос → матрица и сообщения →
маршруты, обработчики, шаблон → тесты → пересборка `platform` и живая проверка
(регистрация клиента → заявка в списке → одобрение → вход клиента).
