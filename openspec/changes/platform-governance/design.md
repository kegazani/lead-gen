## Context

См. `proposal.md` — Why. Ниже только состояние и ограничения, определяющие подход.

Доменные границы среза уже зафиксированы каталогом и не проектируются заново:

- owning context — `platform-governance` (класс `generic`, зелёная зона), агрегат `tenant-access` (`architecture/domain-catalog.yaml`);
- entities агрегата: `tenant`, `user-role`, `audit-record`; VO: `tenant-id`, `role-set`;
- инварианты каталога: роль принадлежит ровно одному тенанту; отключённый тенант не выдаёт новых решений доступа;
- domain events агрегата: `tenant-access-changed`, `audit-recorded`;
- policies: `tenant-isolation` (вход — контракт `tenant-context`, действие — `audit-recorded`), `least-privilege` (вход — контракт `access-decision`, действие — `tenant-access-changed`);
- публикуемые контракты — `access-decision`, `audit-recorded`, `tenant-context`; связь `platform-access-for-outreach` (policy, `async`/`amqp`) ведёт `access-decision` к `outreach-orchestration`.

Потребитель уже существует: порт `AccessDecision` в `backend/contexts/outreach-orchestration/internal/ports/access_decision.go` имеет форму `CanAct(ctx, actor, tenant) (bool, error)` — ошибка означает отказ инфраструктуры проверить право, а не отрицательное решение. Текущая реализация — `internal/adapters/access` — явная заглушка среза с пометкой «полная семантика RBAC — за `platform-governance`»; форма порта этим срезом не меняется.

Ограничения, заданные `docs/`: изменяющая команда внутреннего API идемпотентна по паре (тенант + клиентский идентификатор команды) (`docs/architecture.md` §6.1); аудит неизменяем, корректировка — только новой записью, фиксируются субъект, действие, объект, время, результат (§6.6); изменение агрегата и запись его события атомарны (transactional outbox), event неизменяем и несёт envelope `event_id`, `occurred_at`, `tenant_id`, `correlation_id`, `causation_id`, имя и версию схемы (`docs/domain-model.md`); при co-location синхронная связь идёт in-process адаптером контракта, выбор задаёт топология (`docs/architecture.md` §8).

Ограничение среза: в модуле `backend/contexts/platform-governance` драйвера PostgreSQL нет; добавление зависимости требует отдельного решения (тот же открытый вопрос 5 у `outreach-approval-slice`), поэтому хранилище среза — in-memory.

## Goals / Non-Goals

**Goals:**

- Провести первый вертикальный срез `platform-governance`: домен → use case → порт → адаптер → роли `api`/`worker`, до unit-тестов обоих инвариантов каталога.
- Доказать несущие инварианты продукта: изоляция тенантов и «отключённый тенант не выдаёт новых решений доступа» обеспечены ядром, а не интерфейсом.
- Зафиксировать форму контрактов `access-decision`, `tenant-context`, `audit-recorded` как артефакт в модуле `contracts/platform-governance`, не противореча форме существующего порта потребителя.
- Заложить структуру пакетов, которую проверяет `tools/importlint`, — без переделки на следующих срезах.

**Non-Goals:**

- Аутентификация (вход, сессии, учётные данные): срез работает с уже проверенным актором и не выдаёт заглушку аутентификации за готовую.
- Сетевой слой доступа для других сервисов (amqp-подписка на снимки, HTTP) — следующий шаг; сейчас связь идёт in-process адаптером.
- PostgreSQL-адаптер — следующим шагом, когда будет решение по драйверу.
- Архитектурные capability контекста (`domain-architecture`, `service-topology`, `service-topology-console`, `deployment-topology`) — реализованы инструментами и документацией либо принадлежат другим изменениям (консоль — ЭТАП 4) и в runtime-код среза не превращаются.
- Персональные данные: срез работает только с синтетическими данными.

## Decisions

### Решение 1. Инварианты доступа живут в aggregate root `tenant`, а не в app или интерфейсе

AR `tenant` — единственная точка, где защищаются оба инварианта каталога. Назначение и отзыв роли выполняются только методами агрегата, которые привязывают `user-role` к тенанту (роль ровно одного тенанта); решение доступа (`DecideAccess`) — метод агрегата, который отказывает, когда тенант отключён (отключённый тенант не выдаёт новых решений). `app`-слой только загружает агрегат, вызывает метод и сохраняет результат; HTTP-обработчик решений о допустимости не принимает.

Набор ролей — закрытый перечень, заданный политикой `least-privilege` (роль → права) как доменная константа: сущности «роль» в каталоге нет, поэтому реестр ролей — знание домена, а не данные. Расширение перечня — правка домена с тестами.

Альтернатива — проверки «отключён?», «есть ли роль?» в прикладном сервисе перед выдачей решения. Отклонена: требование говорит «ядро, а не интерфейс», и проверка в app обходится любым другим вызывающим. Инвариант обязан быть необходимым на уровне агрегата.

### Решение 2. Форма контрактов — новый модуль `contracts/platform-governance`

Контракты размещаются в отдельном модуле `contracts/platform-governance`, по пакету на контракт, по образцу `contracts/outreach-orchestration`: модуль зависит только от стандартной библиотеки, не импортирует контексты и `backend/platform`, поэтому потребитель видит только published language владельца. Внутренние порты владельца реэкспортируют типы контрактов (`internal/ports/contracts`), не повторяя wire-формат.

Все три контракта используют общий envelope по `docs/domain-model.md`: `event_id`, `occurred_at`, `tenant_id`, `correlation_id`, `causation_id`, имя и версия схемы; версионирование semver, `Validate` возвращает все некорректные обязательные поля одним сообщением (как в эталонном `approvedaction`).

- `access-decision` (policy): снимок правил тенанта — состояние тенанта (активен/отключён), версия снимка (монотонная), набор прав «актор → набор ролей». Публикуется как подписка на изменение правила: потребитель хранит снимок и применяет его локально, не воспроизводя RBAC. Ключ идемпотентности/версии — (`tenant_id`, `snapshot_version`). В том же пакете объявляется потребительский интерфейс `Decider` с методом `CanAct(ctx, actor, tenant) (bool, error)` — форма совпадает с существующим портом `ports.AccessDecision` контекста `outreach-orchestration`, поэтому порт потребителя не меняется, а его реализация переключается на контракт. Каталог фиксирует межпроцессный транспорт (`async`/`amqp`); при co-location та же семантика «применяй снимок локально» выполняется in-process адаптером (Решение 9) без сети.
- `tenant-context`: обязательный идентификатор тенанта, которым помечаются команды и сообщения; вход политики `tenant-isolation`. Команда без `tenant_id` контрактом не является.
- `audit-recorded` (event): неизменяемый факт — субъект (actor), действие, объект, время, результат; корректировка выражается новой записью со ссылкой на исходную. Ключ идемпотентности — (`tenant_id`, `audit_record_id`).

Альтернатива — держать контракты в `internal/ports/contracts` контекста. Отклонена: пакеты под `internal/` недоступны другим модулям, а `docs/domain-model.md` предписывает модуль `contracts/<owner>` как единственный межконтекстный язык.

### Решение 3. Transactional outbox для `audit-recorded` и изменений доступа

Изменение агрегата (тенант, роли, запись аудита) и запись его событий выполняются в одной транзакции; публикация `audit-recorded` и обновлений `access-decision` — после commit, с повторной доставкой. Вводятся независимые порты `TenantRepository`, `Outbox` и порт транзакции (unit-of-work), как в `outreach-approval-slice`: use case открывает транзакцию, в её контексте сохраняет агрегат и пишет события, затем коммитит; ни репозиторий, ни outbox не знают друг о друге.

Альтернатива — публиковать события из app сразу после сохранения. Отклонена: падение между commit и публикацией теряет факт аудита, а `audit-recorded` и изменения правил доступа — факты, чья потеря недопустима (`docs/domain-model.md`, «Transactional outbox»).

### Решение 4. Слои и направление зависимостей

```text
backend/contexts/platform-governance/   # корневой пакет — сборка сервиса (composition root)
  internal/domain/    tenant (AR), user-role, audit-record, VO tenant-id/role-set,
                      domain events, политики tenant-isolation и least-privilege
  internal/app/       command/{create_tenant,disable_tenant,assign_role,revoke_role,decide_access}
                      query/{audit_journal,tenant_context}
  internal/ports/     TenantRepository, Outbox, UnitOfWork (транзакция), Clock,
                      re-экспорт типов контрактов в ports/contracts
  internal/adapters/  repository (in-memory), outbox, http (api), access-decision
contracts/platform-governance/          published language владельца
```

`domain` не импортирует `app`, `ports`, `adapters` и другие контексты. `app` видит только свой `domain`, свои `ports` и контракты. Драйверы БД и типы внешних систем допустимы только в `adapters`. Межконтекстно — только через `contracts/<owner>`; сборка сервиса — публичный корневой пакет `backend/contexts/<context-id>`, а не общий `backend/platform/composition` (`docs/domain-model.md`, «Реализация на Go»).

Восстановление агрегата из хранилища выполняет сам домен через `Snapshot()`/`Rehydrate` (Решение 6), поэтому адаптер репозитория не имеет доступа к закрытым полям.

Эти границы проверяет `tools/importlint`, а не `tools/archlint`: `archlint` читает YAML-каталог, JSON-схему, имена capability в спеках и маркеры диаграмм, Go-импорты он не анализирует. Оба инструмента запускаются вместе.

Альтернатива — общие `internal/domain`, `internal/app`, `internal/ports`. Запрещена конфигурацией проекта и устаревшей процессной декомпозицией.

### Решение 5. `Clock` — порт

Время событий (`occurred_at`, время записи аудита) читается через порт `Clock`, чтобы тесты управляли временем. Composition подставляет системные часы по умолчанию; домен от источника времени не зависит.

Альтернатива — `time.Now()` прямо в домене. Отклонена: время становится неуправляемым в тестах аудита и дедупликации.

### Решение 6. Восстановление агрегата — часть домена, а не адаптера

Адаптер репозитория не имеет доступа к закрытым полям агрегата: `Tenant.Snapshot()` отдаёт экспортированное состояние (`TenantSnapshot`), а `RehydrateTenant` собирает из него агрегат. Восстановление проверяет инварианты (тенант и его роли согласованы, каждая роль принадлежит ровно этому тенанту, записи аудита непротиворечивы, дублей нет) и завершается доменной ошибкой `ErrInvalidSnapshot`, если сохранённое состояние противоречиво. События при восстановлении не эмитятся: восстановление — не новый факт домена.

Знание о внутреннем устройстве агрегата остаётся в `domain`; сериализация снимка в хранилище — забота адаптера (как Решение 9 эталона).

### Решение 7. Идемпотентность команд — (tenant_id, client command id)

Изменяющая команда внутреннего API идемпотентна по паре (идентификатор тенанта + клиентский идентификатор команды) — ключ предписан `docs/architecture.md` §6.1 и повторяет строку «Браузер → api» матрицы `docs/system-map.md` §3.3. Прикладной слой хранит применённые ключи команд (отдельный порт/хранилище, как `adapters/idempotency` эталона) и записывает ключ атомарно с эффектом команды — в той же транзакции, что и агрегат; повтор команды с тем же ключом эффекта не создаёт. Повтор с другим ключом — новая команда.

Альтернатива — идемпотентность по естественным ключам результата (например, по `tenant_id` при создании). Отклонена: не покрывает команды без естественного ключа (назначение/отзыв роли) и не совпадает с предписанным ключом §6.1.

### Решение 8. Аутентификация — вне среза

Срез принимает актора уже проверенным: `actor_id` приходит из контекста запроса, аутентификация (вход, сессии, учётные данные, проверка claims) не реализуется и не эмулируется. На границе HTTP-адаптера это явно помечено: заглушка «актор из запроса» не выдаётся за готовую аутентификацию — так же, как заглушка `AccessDecision` эталона не выдавалась за готовую авторизацию. Авторизация (решение о доступе) — в срезе; аутентификация — отдельное изменение.

Начальное состояние (первый тенант, первый актор с ролью управления платформой) задаёт вызывающий при сборке сервиса — флагами/конфигурацией процесса, как `GrantsFromStrings` эталона; composition не выдумывает стартовую политику и не выдаёт права сам себе.

Альтернатива — поднять учётные записи и вход в этом же срезе. Отклонена: расширяет срез за рамки proposal («Вне среза») и затягивает проверку несущих инвариантов доступа.

### Решение 9. In-process адаптер для `access-decision` при co-location

При co-location потребитель связывается с владельцем in-process адаптером, который живёт рядом с контрактом — `contracts/platform-governance/accessdecision/inproc`, по образцу `approvedaction/inproc`: связывает реализацию владельца с интерфейсом `Decider`, соблюдает дедлайн и отмену вызова, сам не подменяет транспорт. Потребительский порт `CanAct(actor, tenant)` остаётся в прежней форме; внутри адаптера запрос сверяется с актуальным снимком правил владельца — это то же «локальное применение снимка», что и в межпроцессном варианте, только снимок обновляется напрямую, а не через брокер.

Сетевой адаптер (amqp-подписка на снимки) появится при разделении сервисов по процессам; выбор способа связи задаёт топология (`deploy/services.yaml`, механизм группы процессов), а не код потребителя (`docs/architecture.md` §8).

Альтернатива — сразу реализовать сетевую подписку. Отклонена: брокера вне процесса в совмещённом деплое нет, а семантика контракта от способа связи не зависит; сетевой слой добавляется без изменения порта потребителя и формы снимка.

## Risks / Trade-offs

- **[Агрегат `tenant-access` включает все записи аудита тенанта; при большом журнале загрузка агрегата станет узким местом]** → Граница агрегата задана каталогом. В срезе журнал ограничен синтетикой; до роста объёма проверить, требуется ли пересмотр границы агрегата (отдельное изменение каталога, а не правка внутри среза). Не маскировать нарушением границы.
- **[Снимок правил у потребителя может отставать (eventual consistency)]** → Снимок несёт монотонную версию и время; при co-location in-process адаптер читает актуальный снимок напрямую, при сетевом слое интерфейсы показывают freshness там, где это влияет на решение (`docs/domain-model.md`, «Eventual consistency»).
- **[Заглушка аутентификации может создать ложное чувство безопасности]** → Явно пометить в коде и дизайне, что актор приходит проверенным и срез аутентификацию не реализует; аутентификация — отдельное изменение (Решение 8).
- **[Ключи идемпотентности команд хранятся in-memory и теряются при рестарте]** → В срезе вызывающий — оператор через `api`, хранилище in-memory (как у эталона); при появлении PostgreSQL-адаптера ключи переезжают в хранилище в той же транзакции.
- **[Срез проверяется на in-memory адаптере, а PostgreSQL-адаптер появится позже, и расхождение может всплыть]** → Общий contract suite для `TenantRepository` сначала прогоняется против in-memory, затем против PostgreSQL-реализации.

## Migration Plan

Миграции данных нет: сервис `platform-governance` был заглушкой (`stubService` в `backend/cmd/lead-gen/runners.go`), состояния переносить нечего.

Порядок внутри среза: домен и тесты инвариантов → app use cases → порты и модуль `contracts/platform-governance` → адаптеры → сборка сервиса (замена `stubService`) → сквозная валидация. Каталог и карты обновлены на этапе планирования (capability `platform-access`), поэтому `archlint` зелёный на протяжении всего изменения.

Откат — вернуть ветку `default` в `buildService` (заглушку) и отключить роли сервиса: агрегат самодостаточен и на другие контексты не влияет, пока `access-decision` и `audit-recorded` не публикуются в реальную очередь. Потребительский порт `AccessDecision` в `outreach-orchestration` сохраняет форму, поэтому откат его реализации к заглушке среза ничего не ломает.

## Open Questions

1. **Драйвер PostgreSQL.** PostgreSQL-адаптер `TenantRepository` заблокирован отсутствием драйвера в модуле `backend/contexts/platform-governance`: добавление `pgx` требует сетевого доступа и решения по зависимости (тот же открытый вопрос 5 у `outreach-approval-slice`). До этого contract suite идёт только на in-memory-реализации.
2. **Сетевой слой `access-decision` и `audit-recorded`.** Amqp-подписка на снимки правил и доставка `audit-recorded` потребителям появятся при разделении сервисов по процессам; форма снимка и порт потребителя не меняются, поэтому решение не влияет на спеки и разбивку задач этого среза.
3. **Аутентификация.** Как проверенный актор передаётся на границу `api` (токен, подпись запроса) — отдельное изменение; в срезе `actor_id` берётся из контекста запроса и проверенным не выдаётся за свой результат.
4. **Перечисления.** `TenantRepository` умеет только загрузку по идентификатору и сохранение; перечисление тенантов, пользователей и журнала аудита за пределами одного тенанта требует отдельного read-порта или проекции — решение отложено, в срезе запросы адресованы по `tenant_id` (как открытый вопрос 3 эталона).
5. **Начальная синхронизация снимка правил.** Для сетевых потребителей нужен initial sync/backfill снимка при старте; in-process адаптеру он не требуется, вопрос решается вместе с открытым вопросом 2.
