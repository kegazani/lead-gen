# Проверка качества контактов demo

## Наблюдаемый дефект

Пользователь показал четыре телефона из статьи dom.ria.com/articles:
173525620, 249375288, 249376288 и 9032007. Прежний regex принимал числовые
последовательности из 7–15 цифр с пробелом/дефисом. Поиск из заявки сохранял
название и домен даже без пригодного контакта и не выполнял оценку отдельного
поискового задания; общая витрина накладывала последнюю оценку заданий и
показывала новые компании как «Не оценено».

В облачном demo у Linear обнаружены шесть прежних числовых записей, в том числе
13-значная 7510913015200. Длины недостаточно для доказательства телефона.

## Изменение задачи 15

- Общая витрина показывает контакты и источник без глобальных групп и вердиктов.
  Оценка соответствия сохраняется в контексте отдельного задания.
- Телефон требует полного номера из 10–15 цифр и явного tel/телефонного контекста
  либо международного формата. URL, код, даты, ID/цены не служат контактами.
- Новая компания обоих путей crawl сохраняется и считается найденной только
  с пригодным именем/доменом и подтверждённым страницей контактом. Статьи,
  новости и блоги не становятся компанией издателя.
- Structured extract проверяется по содержимому страницы, включая явную
  обфускацию адреса. Предположенные email/телефоны отвергаются.
- Phone provenance сохраняет необязательное Evidence в существующем JSONB.
  Старые телефоны без свидетельства не считаются пригодными по длине. Они
  доступны отдельно с причиной; данные автоматически не удаляются.
- Повторный обход подтверждает существующий контакт без дубля, сохраняя его ID,
  createdAt и не найденные заново поля. Подбор пула и email-выгрузки используют
  пригодные контакты. Наличие контакта не является проверкой доставки.

## Проверки

Полные тесты lead-management и request-fulfillment, build и vet прошли.
Регрессии покрывают четыре числа dom.ria, длинное старое число Linear, URL,
даты, цены, код, границы номера, tel-ссылки, международные номера, реальный email,
подтверждённую обфускацию и выдуманный extract. Оба пути проверяются на отсутствие
сохранения/found для отвергнутой страницы. Повторное подтверждение сохраняет
произвольный старый ID контакта, время создания и роль. В HTTP проверены поля
каталога, отсутствие глобальных оценок и отдельная доступность старых значений.

В интеграционном тесте сборки подтверждено, что при запрете Extract бюджетной
обёрткой страница без контакта даёт found=0, сохраняя запрет сетевого Extract.
Строгая валидация change прошла. Общий make check останавливается на прежних
secret-file тестах cloud; archlint отдельно сообщает прежнее отсутствие
content-production в OpenSpec. Задача по общему гейту остаётся открытой.

## Реальная интеграция

В том же demo tenant через клиентский портал создана новая заявка на Рарус,
оператор нажал «Взять на проверку» и «Одобрить и начать поиск» с целью 1.
Request req-b0a0a88df1fe97c99268477144bd38a0 прошёл searching → drafting → fulfilled.
API подтвердил found=1, target=1, from_pool=0, crawled=1, drafted=1,
sources_known=true: результат получен новым Firecrawl обходом и реальным LLM.

PostgreSQL содержит компанию rarus.ru, семь email и шесть телефонов из страницы
компании. Пример адреса: 1c@rarus.ru. У телефонов сохранены Evidence из tel-ссылок,
например 74952312245 / tel:+74952312245. Ключи провайдеров в отчёт не включены.
Числа взяты из реальных источников; тестовыми двойниками интеграция не заменена.

Открытая общая витрина обновилась с трёх до четырёх компаний без ручной загрузки,
сохранила вид «Строки» и игнорировала старый localStorage выбор fits. Ошибок
JavaScript не обнаружено. SMTP не запускался.

Ранее в этом же прогоне другая заявка на Норбит дала from_pool=0, crawled=1,
drafted=1 и пригодный email info@norbit.ru. После введения Evidence прежние
телефоны без этого поля честно требуют повторного подтверждения.

Локальная БД пользователя не проверялась этим прогоном. Старые счётчики уже
завершённых заявок не пересчитываются; качество нового поиска проверяется
новой заявкой после обновления demo.

На окончательной сборке Chromium подтвердил четыре сохранённые компании,
пригодные email/телефон Рарус и отсутствие старого короткого числа Linear
в рабочей таблице. В отдельном раскрытом блоке Linear доступны все шесть
исходных значений и причины, включая отсутствие телефонного контекста у
длинного числа. Общая карточка не содержит секции оценки соответствия.
Браузерный тест обновления с тестовым fetch временно показал пятую карточку,
сохранив «Строки», затем вернулся к четырём реальным данным. Тестовый ответ не
создавал запись в БД и не использовался на продуктовом пути. JavaScript errors=0.
