# Исследовательский runtime: проверка 2026-10-15

Change: `intelligent-lead-research`; ветка: `concept/intelligent-lead-research`.
Это проверка написанного исследовательского контура, а не приёмка всей программы
REQ-01…REQ-36. Задачи закрываются только после полного соответствия их критериям.

## Что соединено в приложении

- `researchplan`: человеческие offer/ICP, версия критериев, страны/языки,
  выбранные количество и единица; bounded LLM portfolio и явные состояния отказа.
- `researchmission`: постоянная очередь действий PostgreSQL, leases/CAS,
  сохранение receipts до анализа, восстановление без повторного платного вызова,
  pause/resume/cancel, раздельные saved/accepted/contact counters.
- `researchmemory`: tenant+purpose, компании без контактов, версии документов,
  точные фрагменты, утверждения/достоверность/свежесть, поздние контакты,
  подтверждённые идентификаторы и отзыв оснований.
- Human identity decisions: link/reject/revoke, проверка ревизии и доказательств,
  обратимая каноническая проекция без удаления исходных наблюдений.
- `researchacquisition`: Firecrawl Search/Fetch с постоянным account/grant учётом,
  неизвестным расходом и replay; альтернативный технический адаптер SearXNG.
- Request UI: одобрение и выбранный режим атомарно сохраняются у владельца
  заявки; серверная проверка роли/tenant, CSRF, прогресс, досье и ручная identity
  проверка. Старый и новый обход одной заявки взаимоисключены.
- Владелец заявки отдельным worker переводит её в processing/fulfilled/failed/
  cancelled по проверенному исходу исследования. GET не меняет состояние.
- Контактная цель получает приоритет доказанных переходов к контактам;
  отложенные результаты сохраняются в receipts и возвращаются в очередь в
  пределах общего технического лимита. Отсечение видно в диагностике.

Точка сборки — `backend/cmd/lead-gen/research_runtime.go`.
Запуск — [deploy/research/README.md](../../deploy/research/README.md).

## Реальные внешние проверки

Проверены пользовательские Firecrawl и DeepSeek: API доступны, модель
`deepseek-flash` присутствует. Значения ключей не записаны в репозиторий.
Использован настоящий PostgreSQL 17.6, а не in-memory замена.

Первый сквозной прогон обнаружил обрезание JSON ответа модели: reasoning
исчерпывал предел ответа при большом количестве субъектов на странице.
Для DeepSeek extraction явно отключено reasoning, добавлен отдельный отказ
при `finish_reason=length`, извлечение ограничено четырьмя субъектами с видимой
диагностикой неполного просмотра. Проверки цитат и принадлежности не ослаблялись.
Повторный разбор сохранённой страницы занял 6,18 с: четыре наблюдения, одно
подтверждение критериев, три кандидата с неизвестным рынком.

Повтор полного `TestResearchLiveProviders`: **36,03 с, PASS**. Человеческая
тестовая заявка выбрала две компании; сохранено восемь кандидатов, зачтены две
различные компании («Поревит», «МАПЕИ»), итог `goal-reached`. Использовано шесть
Firecrawl credits, неизвестный расход нулевой. Контактов не найдено; этот прогон
подтверждает единицу «компания», не поиск достаточного количества контактов.
Учтённые credits рассчитаны тарифной функцией адаптера. Это не индивидуальная
выписка provider usage; общий баланс проверяется отдельным запросом.

Первый настоящий UI/Chromium прогон подтвердил создание/одобрение, polling,
открытие досье и отказ 403 чужому tenant. Визуальная проверка обнаружила два
зачёта «Поревит» с разными entity ID. Этот прогон **не подтверждает различимость
результатов**: добавлен отдельный hold `identity-review-required` для спорных
дублей. Исторический результат первой миссии не переписывается как будто она
прошла проверку; read-only пересчёт подтвердил один зачёт вместо двух.

Повторный UI/Chromium прогон после исправления: **68 с, PASS**. Сохранено 16
кандидатов, зачтены две разные компании («Поревит», «Группа ЛСР ПАО»),
`goal-reached`, владелец заявки автоматически установил `fulfilled`.
Учтено 13 Firecrawl credits, неизвестный расход — ноль. Последующее чтение
с новым экземпляром production ACL и PostgreSQL прошло без платных запросов:
четыре экрана, чужой tenant получает 403, ошибок JS и горизонтального
переполнения нет. [Скриншот](intelligent-research-ui-2026-10-15.png),
[отчёт браузера](intelligent-research-browser-2026-10-15.json).

Проверка единицы «компания с контактом» пока **не принята**. Два реальных
прогона закончились partial: первый сохранил 18 компаний без контактов;
после исправления очереди — 25 без зачёта контактной цели. Первый выявил
вытеснение контактных переходов широкими search hits. Во втором depth2 уже
выполнялся, но большинство страниц были каталогами/ассоциациями; email
издателя не присваивался производителю. Сохранённая страница производителя
подтвердила дефект проверки пустых строк между полями реквизитов. После
исправления настоящий DeepSeek replay и PostgreSQL сохранили email и полный
телефон; короткий номер отклонён, неизвестный ICP не повышен до подтверждённого.
[Доказательства и ограничения](research-legal-contact-replay-2026-10-15.md).
Эти результаты не подменяют полноценную приёмку поиска контактной цели.

Официальная закреплённая сборка SearXNG запущена, `/healthz` и JSON API
отвечают. Внешние поиски DuckDuckGo/Brave заблокированы текущим облачным proxy
(`CONNECT 403` к `html.duckduckgo.com` и `search.brave.com`). Адаптер показывает
недоступность источников, а не успешную пустую выдачу. Реальная внешняя выдача
SearXNG пока не принята; Firecrawl остаётся доступным источником.

## Проверки и оставшаяся приёмка

Адресные suites памяти, миссий и acquisition прошли с реальным PostgreSQL и
`-race`. Проверены конкурентный остаток Firecrawl, tenant isolation, crash после
provider/owner commit, отсутствие сети внутри транзакции, отмена с поздним
receipt, отзыв источника и восстановление по подтверждённому идентификатору.
HTTP/JS проверки включают stale snapshot, 401/503, CSRF и forged actor.
`make check` прошёл build/test/vet/importlint/archlint и остановился на
`openspec validate --all --strict`: 30 исходных specs/changes получают strict
отказ из-за длинных требований. Сравнение с исходным HEAD `364c858` дало те же
30 отказов (45 passed / 30 failed). Новых ошибок этой проверки нет;
`openspec validate intelligent-lead-research --strict` проходит. Общий гейт
не объявляется зелёным, checkboxes задач остаются открытыми.

Secure-file тестам требуется обычная файловая среда: в облачном host namespace
корень принадлежит UID 65534. Они проходят в штатном контейнере Go 1.27.2 с
временными `/root` и TMPDIR, read-only checkout/cache, без ослабления проверок.
Отдельный исходный PostgreSQL provisioning тест G2 воспроизводит потерю ACL
предыдущего поколения; он не исправляется под видом настройки среды.

Остаются обязательными: независимые корпуса и метрики качества, полный отзыв
производных оснований, обучаемый планировщик, MarketStudy, собственный crawler,
browser/OCR, полноценный индекс, связь нового досье с материалами и exact
approval, формы, inbound mailbox/переписка и весь итоговый сценарий раздела 12.
Новые досье пока показываются в исследовании заявки; прежний каталог лидов
и генератор писем используют старые контракты. Это не объявляется завершённой
миграцией демо или готовностью полной программы к production.

Все 94 задачи проверены отдельно: [аудит покрытия](intelligent-research-task-coverage-2026-10-15.md)
содержит ссылки на код и конкретные недостающие результаты. Наличие
работающего среза не означает выполнения всех критериев целого task.
