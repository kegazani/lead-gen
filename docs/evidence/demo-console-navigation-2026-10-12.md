# Проверка навигации локального демо

Изменение: `customer-demo-request-to-emails`, задача 11. Проверялся отдельный
`lead-gen-demo` с сохранёнными данными предыдущего реального Firecrawl/LLM прогона.
Доставка писем не запускалась.

## Наблюдаемые причины

- Lead API хранил операторские сессии в собственной lead DB, тогда как админка
  и заявки использовали support DB. Переход требовал повторного входа.
- Проверка доступа к списку компаний зависела от активного tenant. Устаревший
  адрес или cookie давали 404, не оставляя возможности сменить выбор.
- Очередь без выбранной компании выглядела пустой.
- В demo Compose отсутствовали analytics и маршрут `/reporting`.

## Результат проверки

- Проверены адресные тесты трёх затронутых контекстов, тесты сборки сервисов,
  `go vet` и сборка служебного бинарника. `openspec validate
  customer-demo-request-to-emails --strict` прошёл.
- Обновлённые app/demand и новый reports запущены со старыми demo volumes.
  Nginx перезапущен для перечитывания bind-mounted конфигурации.
- В Chromium выполнен один вход admin и переход по ссылкам меню: «Заявки» →
  «Исполнение» → «Лиды» → «Пользователи» → «Регистрации» → «Интеграции» →
  «Аудит» → «Топология» → «Операции» → «Отчёты» → «Заявки». Все страницы
  ответили 200, сохраняли компанию и не требовали нового входа.
- Адрес выбора с отсутствующим tenant ответил 200; после выбора существующей
  компании показаны её пользователь и сохранённая завершённая заявка.
- В карточках через вкладку «Не оценено» виден лид из реального crawl.
- HTML-выгрузка отчёта принята с CSRF общей сессии и открыла страницу прогресса.
  Ошибок JavaScript в этом браузерном сценарии нет.

## Границы результата

Отчётность отражает существующую аналитическую проекцию. В демо без доставки
показатели доставки могут быть пустыми. Топология без Prometheus продолжает
показывать неизвестные метрики. Полная продуктовая готовность не заявляется.

Общий `make check` остановился на прежних тестах владельца/прав secret files
в облачном окружении. Отдельные lint-проверки также нашли прежние проблемы:
`archlint` — отсутствие capability `content-production` в OpenSpec;
`importlint` — импорт outbox adapter из теста app в `message-delivery`.
Эти файлы не менялись. Задачи изменения не отмечены выполненными, поскольку
полный гейт AGENTS.md пока не зелёный.

## Проверка поиска и открытой карточки исполнения

Дополнительно проверена задача 12. Через клиентский портал подана заявка с
аудиторией Sentry и целью 1. После одобрения оператором workflow без второй
кнопки прошёл `searching (found=0)` → `drafting (found=1)` →
`fulfilled (found=1, drafted=1)`. Запрос `/lead-search` выполнил реальный
Firecrawl обход; фаза поиска заняла около 108 секунд, генерация письма —
около 9 секунд. Часть сайтов дала таймауты и диагностические предупреждения;
они не выдавались за найденные лиды. Нулевой счётчик во время searching
отражал отсутствие завершённого раунда, а не неработающий запуск.

После исправления интерфейса другая заявка с целью 1 использовала существующий
пул Linear и реальную генерацию письма. В Chromium открытая карточка без
перезагрузки обновилась из drafting в fulfilled, показала письмо и сохранила
цель. При тестовом HTTP 503 на запросе обновления появились сообщение об
ошибке и сохранённые до сбоя данные. Ошибок JavaScript не обнаружено.
Полный набор тестов request-fulfillment, сборка, vet и строгая проверка change
прошли; прежние ограничения общего гейта остаются указанными выше.

## Детали исполнения и источники лидов

Задача 13 добавляет чтение метаданных активных шагов из Temporal Describe:
состояние, попытку, время старта/heartbeat/следующей попытки и безопасную категорию
ошибки. Текст ошибок и payload не передаются. Workflow сохраняет источники только
уникальных refs, поэтому лид из нового crawl не считается второй раз как пуловый
в следующем раунде. Для старых результатов без происхождения источники неизвестны.

Проверены тесты уникальных источников в трёх раундах, старых результатов, ожидания
повторной попытки при восьми лидах, закрытого времени исполнения и готового письма
при ещё нулевом итоговом Drafted activity. Полные тесты workflow platform и
request-fulfillment, build, vet и строгая проверка change прошли. make check и
archlint сохранили прежние ограничения, перечисленные выше; задачи не закрыты.

В Chromium старое исполнение показало сохранённое письмо и неизвестные источники.
Новое исполнение на существующем пуле Linear показало во время drafting:
«Раунд 1 / максимум 3», «Из существующей базы: 1», «Добавлено новым обходом: 0»,
выполняемую подготовку писем, попытку 1 и предел попытки 10 минут. После завершения
без перезагрузки появились фактический счётчик одного сохранённого письма и его
тема/текст. API подтвердил sources_known=true, from_pool=1, crawled=0. Ошибок
JavaScript не было. Заявка пользователя с восемью лидами находится на его локальном
сервере и по этому прогону не диагностирована; новый экран позволяет увидеть её
состояние и ожидания после обновления контейнеров.

## Видимость сохранённых лидов

По обращению «найдено 17/25, в обоих списках только 6» проверена задача 14.
Найдены три проблемы интерфейса: таблица исключала компании без email, карточки
по умолчанию показывали только подходящие, открытый список не обновлялся во время
обхода. Таблица теперь показывает все сохранённые компании, карточки имеют группу
«Все» и действие возврата ко всем результатам, оба списка обновляются каждые
5 секунд. Email-экспорты сохраняют прежний состав.

В облачном demo PostgreSQL до и после пересоздания контейнеров сохранены две
компании одного tenant (linear.app и docs.sentry.io), обе visible и без email.
В Chromium после одного входа admin обе видны в таблице и карточках. Ссылка из
таблицы сохраняет tenant и открывает карточку с HTTP 200. Проверены пустая группа
«Подходят», возврат ко всем результатам и выбор «Не оценено»/строк.

Для проверки обновления только браузерный fetch перехвачен тестовым ответом с
третьей карточкой: счётчик и список обновились без навигации, группа и вид
сохранились. После снятия перехвата вернулись две реальные записи PostgreSQL.
Тестовый HTTP 503 показал ошибку обновления, сохранив обе карточки. Эти ответы
использовались только в тесте, новые компании в БД не создавались. Ошибок
JavaScript нет.

Полные тесты lead-management, vet, сборка и строгая проверка change прошли.
Тест tenant-изоляции проверяет отсутствие чужой компании и открытие карточки
без email; существующие тесты экспортов подтверждают email-фильтр. Общий
make check снова остановился на прежних secret-file тестах; archlint сохраняет
прежний отказ по content-production. Задача остаётся открытой по общему гейту.

Локальную базу пользователя этот прогон не проверяет. Конкретное расхождение
17 против 6 пока не объяснено: запрошены адрес заявки и read-only подсчёт
lead_profile по tenant. Исправление фильтров не является доказательством
сохранения всех 17 компаний на его компьютере.
