# 3. LLM, долговечное исполнение и память

## 3.1. Распределение ответственности

В проекте уже есть `agent-orchestration`, реестр блоков, версии pipeline, `agent-run` и Temporal. Их следует использовать. Программный супервизор контролирует жизненный цикл и полномочия; LLM выбирает исследовательские действия внутри разрешённого блока. Модель не публикует себе новый pipeline и не становится владельцем предметной истины.

До установления компании работает `research-mission` по исходной гипотезе. После появления подтверждённой сущности миссия может создать/связать существующий персональный company-agent для последующих зарегистрированных блоков. Незавершённая гипотеза не требует фиктивного domain-based CompanyID.

### Логические роли

| Роль | Вход | Выход | Что проверяет система |
|---|---|---|---|
| Интерпретатор поручения | Оффер, аудитория, страны, ограничения | Структурированные критерии и неизвестности | Разделение фактов клиента и предположений |
| Планировщик исследования | Пробелы dossier, доступные инструменты, история | Следующее действие и ожидаемая польза | Бюджет, область, допустимые аргументы |
| Извлекатель | Ограниченный документ/фрагмент | Наблюдения с субъектом и locator | Значения действительно присутствуют в источнике |
| Аналитик тождества | Кандидатные пары и свидетельства | Гипотеза связи, конфликт, нужная проверка | Юрисдикция, сильные ID, версия policy |
| Исследователь рынков | Оффер и ограниченный набор стран | Рекомендации с основаниями | Независимость источников и смысл метрик |
| Автор материала | Разрешённый снимок фактов и sender offer | Версия текста на нужном языке | Фактическая персонализация и адресат |
| Проверяющий | Текст, evidence refs, критерии | Список нарушений/неподтверждённых тезисов | Формальные проверки и человеческое решение |

Это роли одного/нескольких LLM-профилей, а не требование запускать автономную группу моделей. В первой версии достаточно планировщика, извлечения и автора с отдельными промптами и бюджетами. «Проверка другой моделью» не даёт независимого фактического подтверждения.

## 3.2. Цикл одного исследовательского шага

1. Загрузить разрешённый контекст миссии и нужной сущности.
2. Определить конкретный пробел: идентичность, домен, принадлежность контакта, роль, актуальность или соответствие рынку.
3. Получить от LLM структурированное предложение действия и короткое основание.
4. Проверить схему, зарегистрированный инструмент, входные refs и области доступа.
5. Зарезервировать максимальную стоимость действия и проверить лимиты.
6. Зафиксировать action ID, версию плана и параметры.
7. Исполнить инструмент как activity, вне открытой предметной DB-транзакции.
8. Сохранить артефакт/наблюдение и фактическую стоимость.
9. Детерминированно проверить значения и применить правила свидетельств; при необходимости вызвать отдельного извлекателя.
10. Обновить память, дефицит и доступные действия; затем остановиться или продолжить.

Результат может быть полезным отрицательным наблюдением: «в реестре по этому номеру запись не найдена данным способом». Это не ошибка провайдера и не глобальное опровержение существования организации.

## 3.3. Словарь инструментов

Предлагаемые tool names и владельцы, не готовый API:

| Инструмент | Владелец | Назначение |
|---|---|---|
| `search_web` | integration-platform | Получить candidate URLs в нужной географии и языке |
| `lookup_registry` | integration-platform | Типизированный поиск по конкретному реестру |
| `acquire_url` | integration-platform | Получить документ с разрешёнными возможностями |
| `extract_document` | lead-management | Выделить субъекты, поля и свидетельства |
| `inspect_entity` | lead-management | Прочитать разрешённый dossier и пробелы |
| `find_related_entities` | lead-management | Найти ограниченный набор candidate relations |
| `propose_identity_link` | lead-management | Зарегистрировать гипотезу связи |
| `verify_contact_link` | lead-management | Проверить принадлежность endpoint субъекту |
| `check_endpoint` | lead-management | Отдельно запросить доступную проверку адреса/номера |
| `retrieve_research_memory` | lead-management | Вернуть контекст по refs, времени и scope |
| `request_human_review` | Владелец соответствующего решения | Создать понятную задачу проверки |
| `finish_research` | agent-orchestration | Зафиксировать результат и причину остановки |

LLM не получает свободный SQL, возможность произвольного HTTP с секретами, доступ ко всему хранилищу или инструмент `send_any_email`. Fetch ограничивается публичными адресами и действующими политиками источников; переходы проверяются после redirect и разрешения адреса.

## 3.4. Пример предложения действия

```json
{
  "mission_ref": "mission-fixture-1",
  "scope_version": 3,
  "entity_ref": "entity-fixture-a",
  "question": "Какой сайт принадлежит подтверждённому юрлицу?",
  "tool": "search_web",
  "arguments": {
    "query_template": "registry_number_exact_plus_legal_name",
    "input_refs": ["assertion-registry-number", "assertion-legal-name"],
    "target_market": "DE",
    "search_language": "de",
    "serp_country": "DE",
    "max_results": 5
  },
  "expected_observation": "candidate_official_website",
  "brief_reason": "В памяти подтверждён субъект, но отсутствует связь с сайтом.",
  "max_cost_ref": "reserved-action-budget-1"
}
```

Ключи и лимиты задаёт приложение. Модель не может поднять `max_results`, `max_cost` или поменять tenant на основании текста страницы. Готовая поисковая строка строится из проверенных полей; при свободной генерации всё равно применяются лимиты длины, языков, фильтров и источников.

## 3.5. Выбор следующего действия

Можно ранжировать действия по ожидаемой полезности:

`priority = expected_information_gain * task_value * success_estimate / estimated_total_cost`.

Это политика выбора, а не вероятность истинности факта. В первой версии используются понятные уровни: «подтвердить юридическую личность» важнее «найти ещё один похожий сайт»; «устранить сильное противоречие» важнее «написать более персональное письмо».

Полезность зависит от цели: для email-ready нужно найти и подтвердить email, для телефонной кампании — номер/роль и разрешённый канал. Избыток данных о выручке или сотрудниках не должен бесконечно откладывать готовый результат.

Дополнительные механизмы:

- best-first frontier по пробелам и вероятной полезности ссылок;
- query expansion по локальному имени, торговому имени и регистрационному номеру;
- остановка повторов по нормализованной цели и параметрам страны/языка;
- ограниченная альтернатива после отказа источника;
- приоритет свежих проверок существенных полей перед отправкой;
- запрос человеку, если продолжение дороже принятого порога или требует решения о конфликте.

Адаптивный crawl по coverage полезен для выбора страниц ([S04](08-research.md#s04)). Coverage слов не определяет, правильно ли установлен субъект. Условие успеха миссии проверяет предметный результат.

## 3.6. Устройство памяти

| Слой | Что хранит | Пример | Как используется |
|---|---|---|---|
| Рабочий контекст | Текущий вопрос и нужные refs | «Нет связи email с филиалом DE» | Только один/несколько шагов |
| Наблюдения/доказательства | Источники, spans, версии | Строка legal page с номером | Проверка утверждений |
| Предметная память | Типизированные факты и отношения | Домен обслуживает юрлицо A | Сборка dossier |
| Эпизодическая память | Действия и исходы | Поиск DE/de дал 3 URLs | Не повторять попытки, считать стоимость |
| Отрицательные результаты | Ограниченная неудача и TTL | Поиск email на этой версии сайта пуст | Планировать альтернативы |
| Процедурная память | Версионируемые рецепты источника | Для registry X искать номер по country profile | Ускорять повторимые шаги |
| Резюме | Сжатое представление с refs | Известная идентичность и два пробела | Экономить контекст LLM |
| Контекст заявки | Критерии, рынки и решения клиента | Нужен офис DE, исключены посредники | Оценка только данной миссии |

Извлечённое резюме и embedding перестраиваются из доступных исходных утверждений. Они не становятся самостоятельной копией истины без зависимостей и механизма отзыва.

## 3.7. Как извлекать контекст

Порядок retrieval:

1. Проверить tenant, actor, purpose и доступ к сущности.
2. Загрузить точные идентификаторы, свежие подтверждённые факты и текущие конфликты.
3. Прочитать соседние связи ограниченного типа и глубины.
4. Найти релевантные evidence spans по полнотекстовому и, при наличии, векторному индексу.
5. Убрать зависимые копии, явно устаревшие/отозванные источники и лишние персональные поля.
6. Сформировать ограниченный context package: известное, спорное, неизвестное, выполненные попытки, допустимые действия.

Доступ фильтруется до поиска и после разрешения refs. Запись из соседнего tenant не должна попасть в top-k, резюме, кеш или объяснение «почему отказано». Все кеш-ключи включают scope и версии.

## 3.8. Стек памяти и графа

Для первого этапа: PostgreSQL с таблицами entities, identifiers, assertions, evidence, relation edges, attempts и decisions; полнотекстовый поиск; существующий vector port для дополнительного recall. Метаданные и индексы сохраняют контекст владельца.

Graphiti показывает полезную модель временных фактов, episodes и hybrid retrieval ([S09](08-research.md#s09)). Принимать автоматически созданные им связи как предметную истину нельзя. Возможен отдельный spike на наших кейсах.

GraphRAG полезен для обзора большого корпуса и тематических связей ([S10](08-research.md#s10)); это не готовый валидатор ИНН или принадлежности телефона. Массовое построение graph summaries нужно только после оценки стоимости и необходимости.

Mem0/Letta полезны как источники идей о слоях памяти и контекстных блоках ([S13](08-research.md#s13), [S32](08-research.md#s32)). Наши доказательные факты должны оставаться в предметном хранилище с собственной политикой. Не нужно внедрять все frameworks одновременно.

## 3.9. Время, кеш и обновление

TTL задаётся типом отношения, источником и предполагаемым действием. Начальные интервалы для пилота подбираются измерением; единый TTL «30 дней для всего» непригоден.

- Юридическая идентичность обычно стабильнее роли сотрудника.
- Статус компании может измениться между поиском и отправкой.
- Отсутствие email в одной версии сайта имеет короткий срок полезности.
- Bounce и отписка требуют немедленного обновления разрешённости контакта.
- Заблокированный источник — состояние доступности, а не отрицательный факт о компании.

При конфликте старого и нового наблюдений используются время, роль источника и проверка предметного правила. Новейшая страница автоматически не побеждает официальный реестр по юридическому статусу.

## 3.10. Долговечное исполнение и бюджет

LLM-вызовы и внешние инструменты исполняются activities; replay использует сохранённые решения. Продолжение не должно повторно спрашивать модель «о чём мы думали» и получать другую траекторию без версии.

Для действия сохраняются idempotency key, input refs/version, state, result ref, reserved cost, actual cost и error category. Внешний вызов не удерживает долгую транзакцию entity dossier. Результат применяется отдельной идемпотентной операцией.

Бюджет включает деньги/кредиты, model tokens, поисковые запросы, страницы, browser-seconds, proxy traffic, wall time и предел человеческих review. Раздельные лимиты нужны на миссию, страну, компанию, источник и действие.

При лимите остаются уже собранные данные, понятный stop reason и предложение полезного продолжения. Отмена предотвращает новые действия; уже завершённые внешние эффекты не скрываются из истории.

## 3.11. Проверяемость LLM

Для оценки сохраняются версия модели/промпта, схема результата, разрешённые input refs и короткое предметное основание. Секреты и полный персональный контекст не копируются в общий telemetry.

Набор проверок: неправильный tool name, несуществующий evidence ID, чужой tenant, расширение рынка, несоответствие цитаты источнику, ложная уверенность, повтор платного действия, инструкция внутри страницы и попытка отправки без решения.

Цена, latency и фактическая результативность ролей измеряются отдельно. Более дорогая модель применяется к сложным конфликтам/планированию по policy; простое извлечение и форматные проверки выполняются дешёвыми инструментами и кодом.

## 3.12. Политика следующего шага

Первому прототипу достаточно упорядоченных классов действий; формула expected information gain из §3.5 остаётся будущей оптимизацией по накопленным исходам. Модель выбирает внутри доступного класса, а приложение задаёт приоритеты.

| Приоритет | Условие | Следующий полезный вопрос | Ограничение |
|---|---|---|---|
| P0 | Отзыв/противоречие затрагивает используемый контакт | Можно ли продолжать использовать этот результат? | Приостановить зависимое действие до проверки |
| P1 | Субъект неизвестен или неоднозначен | Как различить одноимённые компании? | Реестр/локальные реквизиты, без выдуманного ID |
| P2 | Субъект различён, контакта нет | Где опубликован канал этого субъекта? | Legal/contact pages, карточки, документы |
| P3 | Контакт найден, принадлежность не доказана | В чьём блоке он расположен и чем связан? | Scope/locator/сильные признаки, не количество совпадений |
| P4 | Связь доказана, но качество/актуальность недостаточны | Как проверить конкретный пробел? | Страновая нормализация, другой способ чтения, свежий источник |
| P5 | Единица результата готова | Нужно ли ещё действие для цели миссии? | Засчитать и перейти к следующему seed; лишнее обогащение не обязательно |

Источники выбираются по проверяемому вопросу. После найденного ИНН полезен точный lookup/поиск номера; очередной общий запрос «строительные компании» не исправит принадлежность уже найденного email. Дополнительные поля вроде выручки собираются только при связи с критериями поручения.

Порядок инструментов: разрешённая свежая память → точный registry lookup → проверяемый известный URL → regional discovery → ограниченный browser/document/OCR режим. Source recipe может сразу направить скан в OCR или JS-карточку в браузер; не требуется сначала оплачивать заведомо неподходящие способы.

Для каждого предложения сохраняются `question_ref`, версия dossier, `expected_observation`, ограниченные входные refs и `reason_short`. Исполнитель возвращает один из содержательных исходов: новый факт, подтверждённая связь, новый кандидат, проверяемое отрицательное наблюдение, конфликт, недоступность, ошибка либо неоднозначный внешний исход. «HTTP 200» — transport outcome, а не исследовательский успех.

## 3.13. Повторы, полезность и распределение внимания

Ключ попытки строится по смыслу: tenant/purpose, миссия и критерии, субъект/seed, вопрос, инструмент/источник, нормализованные параметры страны/языка и версия известного evidence. Перестановка слов не создаёт автоматически новую полезную цель.

Новая попытка оправдана изменением источника/локали/данных, истечением применимого negative TTL или исправлением конкретной ошибки. Замена одного синонима без нового основания считается повтором стратегии и учитывается в её лимите.

Предлагаемые стартовые настройки пилота: до трёх поисковых уточнений на вопрос, одно активное внешнее действие на субъект, ограниченный общий deadline и отдельные пределы страниц/browser/OCR. Это параметры эксперимента, не достигнутые показатели. Конкретные денежные ceilings задаёт человек/настройка tenant; документ не назначает фиктивные тарифы.

Если два последовательных допустимых действия не уменьшили известный пробел, seed временно уступает очередь другому. Причина park сохраняется: исчерпана стратегия, источник недоступен, нужен review или остался только дорогой инструмент. Миссия может вернуться к seed при изменении условия. Park не равен «компания не подходит».

Нужен предел одновременно исследуемых субъектов и справедливая очередь. Иначе один трудный сайт съест весь бюджет заявки на 25 компаний. Параллелизм не отменяет source-wide host limits; резерв стоимости/места в целевом наборе применяется атомарно.

## 3.14. Жизненный цикл миссии

Состояние исполнения, фаза и результат — отдельные поля будущей проекции. Они не добавляются скрыто в enum существующей клиентской заявки.

| Состояние миссии | Значение | Допустимый переход |
|---|---|---|
| `queued` | Поручение устойчиво принято, ещё нет выполняемого шага | running / paused / cancelled |
| `running` | Планирование либо конкретное действие исполняется | running / paused / completed / failed / cancelled |
| `paused` | Продолжение требует внешнего условия/решения | queued по разрешённому resume / cancelled |
| `completed` | Исследовательский цикл остановлен с устойчивым результатом | Новый явно связанный run для продолжения |
| `failed` | Невозможно устойчиво продолжать из-за терминальной ошибки | Новый run после исправления причины |
| `cancelled` | Поручение отменено | Новый run только по новому разрешённому действию |

У `completed` есть отдельный outcome: `target-reached`, `partial` или `no-results`, и stop reason: цель/бюджет/deadline/исчерпание стратегий. Лимит бюджета с восемью сохранёнными результатами не выдаётся за полную цель. Для `paused` нужны reason, ответственная сторона и условие продолжения; таймер backoff хранит `next_attempt_at`, а не бесконечный статус «в работе».

Фаза: identity / discover-sources / acquire / extract / verify-link / persist / review. Heartbeat означает, что исполнитель жив, но не доказывает появление фактов. Поэтому отдельно показываются время последнего heartbeat и последнего содержательного результата.

Терминальное решение фиксируется после принятия уже завершённых receipts и классификации оставшихся in-flight действий. Новый внешний шаг после закрытия планирования не стартует. Поздний результат допускается как объяснимое дополнение dossier с собственным временем; исторический снимок завершения миссии не переписывается молча.

Согласование in-flight ограничено отдельным сроком: неответившие вызовы остаются в reconciliation с неизвестным внешним исходом, а не удерживают миссию бесконечно. Возможная стоимость такого вызова не считается нулём; резерв не освобождается как неиспользованный без достаточного основания.

Resume не поднимает бюджет и не снимает policy block. Для изменения критериев/рынков/лимита создаётся новая версия человеческого поручения и связанный run. Технический retry в той же области имеет явную попытку и учёт стоимости.

## 3.15. Когда прекращать исследование

1. Есть принятые и устойчиво сохранённые целевые единицы в требуемом количестве — остановить новые discovery, сохранить итог и завершить миссию.
2. Цели нет, но доступно полезное действие в бюджете — продолжить по очереди.
3. Не хватает человеческого решения или обязательного источника — pause с конкретной причиной/условием.
4. Остались только запрещённые/неподдержанные инструменты либо исчерпаны стратегии — завершить partial/no-results с перечнем пробелов.
5. Budget/deadline исчерпан — сохранить частичное и прекратить новые вызовы.

Если пришёл другой результат от ещё работающего provider, он не должен потеряться. Повторный worker не может повторно засчитать ту же компанию. Актуальный зачёт, membership результата и доступная ёмкость цели — согласованная проекция aggregate `research-mission`, не сумма локальных counters workers.

Результат исследования потребляет `request-fulfillment`; финальный статус клиентской заявки зависит также от её текущей версии условий и других фаз. В первом исследовательском прототипе миссия не присваивает сама `fulfilled`: UI показывает отдельно результат миссии и статус заявки. Переход всего fulfillment на новый путь требует отдельной проверенной проводки у владельца заявки, без одновременного запуска старого и нового поиска по одному intent.

## 3.16. Открытые потребности и событийное дообогащение

`OpenNeed` — предлагаемая долговечная модель пробела знаний у владельца `lead-management`. Это не клиентская заявка и не самостоятельно исполняющийся агент. Пример: «для entity A нужен email отдела продаж с подтверждённой принадлежностью». Она переживает завершение запуска и позволяет связать позднее разрешённое наблюдение с прежним исследованием.

Минимальные поля: tenant/purpose, entity_ref, тип недостающего отношения/значения, требуемые критерии, refs исходных поручений/версий, состояние и причина, refs попыток, evidence/assertion revision, next_review_at и условие повторной оценки. Повторяющиеся потребности можно объединять только при совпадающем scope и совместимых критериях; зачёт и пределы каждой миссии остаются раздельными.

| Состояние потребности | Смысл |
|---|---|
| open | Есть применимый пробел, подходящее основание пока не найдено |
| satisfied | Требуемый контакт/факт принят с конкретными версиями оснований |
| blocked | Пересмотр требует данных/решения либо сталкивается с конфликтом; причина видна |
| dormant | Потребность сохранена, активного разрешённого исполнения сейчас нет |
| obsolete | Требование более не применимо, отменено или истёк разрешённый scope; дальнейшее хранение определяется policy |

Эти состояния предлагаются для будущей модели. Они не добавляют enum существующей клиентской заявки. Истечение negative-memory TTL позволяет заново оценить полезность попытки; оно не запускает внешний вызов само по себе.

Событийный цикл будущего исполнения:

1. Владелец сохраняет evidence и предметные изменения, затем устойчивое событие с tenant/purpose и ссылками на версии.
2. Индекс зависимостей находит подходящие entities, открытые потребности и производные выводы. Точное совпадение ID проверяется по типу, юрисдикции и субъекту; семантический поиск лишь предлагает кандидата.
3. Обработчик идемпотентно проверяет новую версию, конфликты и оставшиеся достаточные основания. Запоздалое событие не откатывает актуальную проекцию; при несовпадении версии читается текущее состояние владельца.
4. В разрешённом scope обновляются утверждение/потребность, досье, индексы и резюме. Изменение допуска передаётся владельцу канала; активная миссия отдельно пересчитывает свой результат по действующим критериям.
5. UI получает объяснимое изменение: когда компания обнаружена, когда появился контакт, что подтвердилось/устарело, какие проверки ещё нужны.

`evidence-recorded`, изменение assertion, merge/split, invalidation и окончание применимости являются основаниями пересмотра. Необходимость внешнего действия оценивается отдельно. Для активной миссии проверка допускается только при действующих полномочиях, остатке бюджета, сроке и выбранных рынках. Для терминального run обновляются текущее досье и уведомление, исходный completion snapshot сохраняется. Продолжение внешнего исследования требует явно разрешённого связанного run; LLM не создаёт новую человеческую заявку и не открывает новый бюджет.

Контрольный кейс: перезапуск между T0 и T2 не теряет компанию/потребность; поздний контакт привязывается один раз; дубликат события не увеличивает зачёт; отзыв единственного основания вновь показывает пробел; другое независимое достаточное основание сохраняет допустимый вывод; чужой tenant не получает ни факт, ни уведомление, ни контекст для LLM.
