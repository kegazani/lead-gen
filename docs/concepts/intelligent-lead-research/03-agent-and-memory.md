# 3. LLM, долговечное исполнение и память

## 3.1. Распределение ответственности

В проекте уже есть `agent-orchestration`, реестр блоков, версии pipeline, `agent-run` и Temporal. Их следует использовать. Программный супервизор контролирует жизненный цикл и полномочия; LLM предлагает ограниченный набор действий внутри разрешённого блока, а приложение выбирает и исполняет допущенные действия. Модель не публикует себе новый pipeline и не становится владельцем предметной истины.

Главный пользовательский приоритет — поиск и краулинг лидов от оффера и описания целевой аудитории. До установления компании работает `research-mission` по сохраняемому `SearchBrief` и портфелю стратегий; исходного company seed может не быть. После появления подтверждённой сущности миссия может создать/связать существующий персональный company-agent для последующих зарегистрированных блоков. Незавершённая гипотеза не требует фиктивного domain-based CompanyID.

### Логические роли

| Роль | Вход | Выход | Что проверяет система |
|---|---|---|---|
| Интерпретатор поручения | Оффер, аудитория, страны, ограничения | Структурированные критерии и неизвестности | Разделение фактов клиента и предположений |
| Планировщик исследования | Пробелы dossier, доступные инструменты, история | Следующее действие и ожидаемая польза | Область, технические пределы; Firecrawl credits только для его операций |
| Извлекатель | Ограниченный документ/фрагмент | Наблюдения с субъектом и locator | Значения действительно присутствуют в источнике |
| Аналитик тождества | Кандидатные пары и свидетельства | Гипотеза связи, конфликт, нужная проверка | Юрисдикция, сильные ID, версия policy |
| Исследователь рынков | Оффер и ограниченный набор стран | Рекомендации с основаниями | Независимость источников и смысл метрик |
| Автор материала | Разрешённый снимок фактов и sender offer | Версия текста на нужном языке | Фактическая персонализация и адресат |
| Проверяющий | Текст, evidence refs, критерии | Список нарушений/неподтверждённых тезисов | Формальные проверки и человеческое решение |

Это роли одного/нескольких LLM-профилей, а не требование запускать автономную группу моделей. В первой версии достаточно планировщика, извлечения и автора с отдельными промптами и техническими пределами. По явному уточнению пользователя общий прикладной денежный/кредитный бюджет применяется только к Firecrawl; LLM и остальные proxy-инструменты не получают второй денежный резерв или отказ. «Проверка другой моделью» не даёт независимого фактического подтверждения.

## 3.2. Цикл одного исследовательского шага

1. Загрузить версию поручения, `SearchBrief`, стратегии, разрешённую память и текущий дефицит.
2. Выбрать вопрос обнаружения новых компаний либо конкретный пробел известного субъекта; выполнить доступную локальную проверку.
3. Использовать проверенный source recipe либо запросить у LLM ограниченное число структурированных предложений с кратким основанием.
4. Проверить схему, зарегистрированный инструмент, ссылки, страну и технические пределы; ограничить исправления невалидных предложений.
5. Сохранить intent/attempt/outbox с устойчивым action ID, версией плана и параметрами. Модель не запускает свой скрытый цикл инструментов.
6. Только для Firecrawl получить идемпотентный резерв у владельца общего account/grant и зафиксировать receipt допуска к выполнению. Прочие proxy-вызовы не требуют денежного резерва.
7. Исполнить инструмент как activity вне открытой предметной DB-транзакции.
8. Сохранить provider receipt/artifact и получить устойчивый receipt записи от владельца evidence; Firecrawl credits урегулировать у владельца бюджета, proxy usage сохранить при наличии.
9. Проверить значения, субъект, критерии поручения и применимость свидетельств; ошибки получения, извлечения и записи различать.
10. Обновить память, состав принятых результатов и стратегии; затем продолжить или объяснимо остановиться.

Отрицательное наблюдение «в реестре по этому номеру запись не найдена данным способом» может закрыть конкретную попытку. Оно не означает ошибку провайдера или глобальное отсутствие компании. HTTP 200 не означает исследовательский успех.

## 3.3. Словарь инструментов

Предлагаемые tool names и владельцы, не готовый API:

| Инструмент | Владелец | Назначение |
|---|---|---|

| `lookup_registry` | integration-platform | Типизированный поиск по конкретному реестру |
| `acquire_url` | integration-platform | Получить документ с разрешёнными возможностями |
| `extract_document` | lead-management | Выделить субъекты, поля и свидетельства |
| `inspect_entity` | lead-management | Прочитать разрешённый dossier и пробелы |
| `find_related_entities` | lead-management | Найти ограниченный набор candidate relations |
| `propose_identity_link` | lead-management | Зарегистрировать гипотезу связи |
| `verify_contact_link` | lead-management | Проверить принадлежность endpoint субъекту |
| `check_endpoint` | lead-management | Отдельно запросить доступную проверку адреса/номера |
| `retrieve_research_memory` | lead-management | Вернуть контекст по refs, времени и scope |
| `request_human_review` | Владелец соответствующего решения | Создать понятную задачу проверки |
| `finish_research` | agent-orchestration | Зафиксировать результат и причину остановки |

LLM не получает свободный SQL, возможность произвольного HTTP с секретами, доступ ко всему хранилищу или инструмент `send_any_email`. Fetch ограничивается публичными адресами и действующими политиками источников; переходы проверяются после redirect и разрешения адреса.

## 3.4. Пример предложения действия

```json
{
  "mission_ref": "mission-fixture-1",
  "scope_version": 3,
  "entity_ref": "entity-fixture-a",
  "question": "Какой сайт принадлежит подтверждённому юрлицу?",
  "tool": "search_web",
  "arguments": {
    "query_template": "registry_number_exact_plus_legal_name",
    "input_refs": ["assertion-registry-number", "assertion-legal-name"],
    "target_market": "DE",
    "search_language": "de",
    "serp_country": "DE",
    "max_results": 5
  },
  "expected_observation": "candidate_official_website",
  "brief_reason": "В памяти подтверждён субъект, но отсутствует связь с сайтом.",
  "technical_limits_ref": "mission-technical-limits-v1"
}
```

Ключи и технические пределы задаёт приложение. Модель не может поднять `max_results`, поменять tenant или Firecrawl grant на основании текста страницы. Firecrawl reservation создаётся исполнителем после допуска действия, а не моделью; для другого backend денежный reserve отсутствует. Готовая поисковая строка строится из проверенных полей; при свободной генерации всё равно применяются лимиты длины, языков, фильтров и источников.

## 3.5. Выбор следующего действия

Приоритет определяется общей целью: получить принятые по текущим критериям компании и нужные контакты. Поиск балансирует **обнаружение новых кандидатов** и **закрытие пробелов известных компаний**. Портфель и очередь описаны в §3.17–3.18; фиксированная доводка каждой компании до идеала может оставить остальные без исследования.

Начальная policy: допустимость → существенный конфликт используемого факта → дефицит рынков/целевой единицы → справедливая очередь → проверенный source recipe → наблюдаемая результативность. Число новых URL, слов или сырых emails не заменяет целевой результат. Соответствие аудитории проверяется по этой заявке; глобальная «подходящесть компании» не вводится.

Формула expected information gain из прежнего плана — гипотеза оптимизации, а не заданный алгоритм или вероятность истинности. После измерений можно сравнивать ожидаемый прирост принятых единиц и закрытие значимого пробела с технической задержкой/числом попыток; для Firecrawl отдельно учитывать расход credits. Самооценка LLM не задаёт probability success. Нельзя складывать credits, токены и секунды либо вводить денежный gate для proxy-инструментов.

Адаптивное покрытие текста полезно для выбора страниц ([S04](08-research.md#s04)), но не доказывает правильную идентичность или принадлежность контакта. Дополнительная персонализация после достижения нужной единицы допускается только при связи с человеческими критериями.

## 3.6. Устройство памяти

| Слой | Что хранит | Пример | Как используется |
|---|---|---|---|
| Рабочий контекст | Текущий вопрос и нужные refs | «Нет связи email с филиалом DE» | Только один/несколько шагов |
| Наблюдения/доказательства | Источники, spans, версии | Строка legal page с номером | Проверка утверждений |
| Предметная память | Типизированные факты и отношения | Домен обслуживает юрлицо A | Сборка dossier |
| Эпизодическая память | Действия и исходы | Поиск DE/de дал 3 URLs | Не повторять попытки, связывать Firecrawl credits и доступную proxy usage |
| Отрицательные результаты | Ограниченная неудача и TTL | Поиск email на этой версии сайта пуст | Планировать альтернативы |
| Процедурная память | Версионируемые рецепты источника | Для registry X искать номер по country profile | Ускорять повторимые шаги |
| Резюме | Сжатое представление с refs | Известная идентичность и два пробела | Экономить контекст LLM |
| Контекст заявки | Критерии, рынки и решения клиента | Нужен офис DE, исключены посредники | Оценка только данной миссии |

Извлечённое резюме и embedding перестраиваются из доступных исходных утверждений. Они не становятся самостоятельной копией истины без зависимостей и механизма отзыва.

## 3.7. Как извлекать контекст

Порядок retrieval:

1. Проверить tenant, actor, purpose и доступ к сущности.
2. Загрузить точные идентификаторы, свежие подтверждённые факты и текущие конфликты.
3. Прочитать соседние связи ограниченного типа и глубины.
4. Найти релевантные evidence spans по полнотекстовому и, при наличии, векторному индексу.
5. Убрать зависимые копии, явно устаревшие/отозванные источники и лишние персональные поля.
6. Сформировать ограниченный context package: известное, спорное, неизвестное, выполненные попытки, допустимые действия.

Доступ фильтруется до поиска и после разрешения refs. Запись из соседнего tenant не должна попасть в top-k, резюме, кеш или объяснение «почему отказано». Все кеш-ключи включают scope и версии.

## 3.8. Стек памяти и графа

Для первого этапа **предлагаются** PostgreSQL таблицы entities/identifiers/assertions/evidence/typed edges/attempts/decisions и полнотекстовый поиск у владельцев контекстов. Это будущая предметная модель, а не готовая схема baseline.

Существующий vector adapter `backend/contexts/integration-platform/internal/adapters/vector/postgres/store.go` хранит `double precision[]` и перебирает строки, вычисляя cosine similarity в Go. Это **не pgvector/ANN**; нынешний `vector_document` не имеет готового tenant/purpose-scoped evidence retrieval и удаления производных данных. Переиспользование контракта возможно после расширения scope, версий и invalidation; semantic recall не блокирует exact/lexical первый срез.

Raw artifacts/контакты/переписка должны оставаться в клиентской red области по предлагаемой модели. Переиспользуемый runtime object-storage contract/adapter для этих evidence в просмотренном baseline не обнаружен; наличие инфраструктурного типа `object-storage` не означает готовое хранилище. Artifact put/get/retention/delete, metadata/locator версии и доступ необходимо реализовать и принять отдельно.

Graphiti предлагает идеи временных фактов/episodes/hybrid retrieval ([S09](08-research.md#s09)); автоматически созданные связи не принимаются предметной истиной. GraphRAG помогает обзору корпуса ([S10](08-research.md#s10)), но не валидирует ИНН или принадлежность телефона. Mem0/Letta полезны для организации контекста ([S13](08-research.md#s13), [S32](08-research.md#s32)). Их использование требует измеримой пользы; одновременно внедрять несколько систем памяти не требуется.

## 3.9. Время, кеш и обновление

TTL задаётся типом отношения, источником и предполагаемым действием. Начальные интервалы для пилота подбираются измерением; единый TTL «30 дней для всего» непригоден.

- Юридическая идентичность обычно стабильнее роли сотрудника.
- Статус компании может измениться между поиском и отправкой.
- Отсутствие email в одной версии сайта имеет короткий срок полезности.
- Bounce и отписка требуют немедленного обновления разрешённости контакта.
- Заблокированный источник — состояние доступности, а не отрицательный факт о компании.

При конфликте старого и нового наблюдений используются время, роль источника и проверка предметного правила. Новейшая страница автоматически не побеждает официальный реестр по юридическому статусу.

## 3.10. Долговечное исполнение и бюджет Firecrawl

Общий прикладной денежный/кредитный бюджет относится **только к Firecrawl Search/Crawl/Extract**, включая все раунды/refinement одного человеческого intent. LLM, собственные search/crawler/browser/OCR и другие инструменты идут через предусмотренный proxy/adapter путь без второго application monetary reserve/deny. Их usage сохраняется, если proxy её возвращает; отсутствие тарифа или usage не блокирует вызов/завершение.

`integration-platform` — предлагаемый единственный владелец Firecrawl account policy, grants и operation ledger. Grant миссии или человеческого `MarketStudy` intent является разрешённой областью расхода из того же account. Account и grant проверяют одну operation reservation; они не создают две кассы/списания. `agent-orchestration` хранит opaque `grant_ref` и проекцию состояния. Текущий Firecrawl Registry process-local; durable ledger и контракт ещё предстоит реализовать.

Предлагаемая saga:

1. Короткая agent Tx сохраняет action/attempt/outbox; Firecrawl action получает `awaiting_fc_reservation`, остальные — обычный технический допуск.
2. Владелец Firecrawl выполняет идемпотентный `ReserveForAction(account, grant, action, attempt)`: одна Tx проверяет account/grant и сохраняет одну reservation.
3. Reservation receipt переводит action через CAS в ready; затем worker claim/fencing generation, dispatch commit и внешний activity.
4. Provider receipt и owner persistence receipt сохраняются независимо от успеха критериев. `Settle`/`MarkUnknown` идут владельцу Firecrawl идемпотентно; mission читает проекцию.
5. Crash после reserve до agent acknowledgement восстанавливается `GetReservation(action, attempt)`, без повторного резерва. Межконтекстной общей DB-транзакции нет.

Все действия имеют stable ID, input/schema/policy versions, attempt, result refs и error category. Lease expiry не доказывает отсутствие внешнего эффекта. Если результат provider неизвестен, используются его idempotency/job lookup; Firecrawl credits удерживаются до точного доказательства, а общий account balance не заменяет attribution операции. Для proxy-инструментов неизвестный исход ограничивается retry/attempt policy без нового денежного ledger.

Технические пределы отдельно ограничивают deadline, concurrency, host rate, page/depth/bytes, retries и длительность browser/OCR; они не показываются как исчерпание денег. Firecrawl exhausted исключает только его новые действия. Разрешённый полезный memory/proxy/self-hosted путь продолжает работу.

LLM и сетевые вызовы — activities; replay использует сохранённые решения. Workflow/prompt/model/schema/policy versions фиксируются, mutable model alias не выдаётся за воспроизводимую генерацию. Изменения workflow требуют versioning/replay проверки; bounded history/ContinueAsNew сохраняет business mission ID и grant refs. Старый RunStep вызывает executor внутри UoW — новый длительный research loop этот паттерн не наследует.

Текущий fulfillment top-up меняет query и Firecrawl scope, а RunSearch имеет собственный refine loop. Для нового пути `StartResearchMission` выполняется один раз на execution intent; дальнейшие действия читают/сигналят ту же миссию. Legacy top-up не оборачивает новый loop и не сбрасывает общий Firecrawl бюджет.

## 3.11. Проверяемость LLM

Для оценки сохраняются версия модели/промпта, схема результата, разрешённые input refs и короткое предметное основание. Секреты и полный персональный контекст не копируются в общий telemetry.

Набор проверок: неправильный tool name, несуществующий evidence ID, чужой tenant, расширение рынка, несоответствие цитаты источнику, ложная уверенность, повтор платного действия, инструкция внутри страницы и попытка отправки без решения.

Latency, корректность и полезный результат ролей измеряются отдельно; proxy usage/cost — необязательная диагностика. Выбор модели опирается на нужные возможности и измеренное качество. Простой разбор и форматные проверки выполняются кодом; application monetary cap на LLM не вводится.

## 3.12. Политика следующего шага

Первому прототипу достаточно упорядоченных классов действий; числовая utility из §3.5 проверяется отдельно. До работы с конкретным субъектом нужен discovery portfolio (§3.17). Приложение выбирает между discovery и обогащением, модель предлагает допустимые шаги внутри выбранного вопроса.

| Приоритет | Условие | Следующий полезный вопрос | Ограничение |
|---|---|---|---|
| P0 | Отзыв/противоречие затрагивает используемый контакт | Можно ли продолжать использовать этот результат? | Приостановить зависимое действие до проверки |
| P1 | Субъект неизвестен или неоднозначен | Как различить одноимённые компании? | Реестр/локальные реквизиты, без выдуманного ID |
| P2 | Субъект различён, контакта нет | Где опубликован канал этого субъекта? | Legal/contact pages, карточки, документы |
| P3 | Контакт найден, принадлежность не доказана | В чьём блоке он расположен и чем связан? | Scope/locator/сильные признаки, не количество совпадений |
| P4 | Связь доказана, но качество/актуальность недостаточны | Как проверить конкретный пробел? | Страновая нормализация, другой способ чтения, свежий источник |
| P5 | Единица результата готова | Нужно ли ещё действие для цели миссии? | Засчитать и перейти к следующему seed; лишнее обогащение не обязательно |

Источники выбираются по проверяемому вопросу. После найденного ИНН полезен точный lookup/поиск номера; очередной общий запрос «строительные компании» не исправит принадлежность уже найденного email. Дополнительные поля вроде выручки собираются только при связи с критериями поручения.

Для обогащения известного субъекта предлагаемый порядок: свежая память → точный registry lookup при наличии ID → проверяемый известный URL → regional discovery → нужный browser/document/OCR режим. Для поиска с нуля сначала выбираются источники из портфеля, а не выдумывается registry ID. Source recipe может сразу направить скан в OCR или JS-карточку в браузер; не требуется сначала оплачивать заведомо неподходящие способы.

Для каждого предложения сохраняются `question_ref`, версия dossier, `expected_observation`, ограниченные входные refs и `reason_short`. Исполнитель возвращает один из содержательных исходов: новый факт, подтверждённая связь, новый кандидат, проверяемое отрицательное наблюдение, конфликт, недоступность, ошибка либо неоднозначный внешний исход. «HTTP 200» — transport outcome, а не исследовательский успех.

## 3.13. Повторы, полезность и распределение внимания

План и история попыток сохраняются, а не восстанавливаются из свободного пересказа модели. Семантический ключ включает tenant/purpose, версию критерия, subject/StrategyCell, вопрос, QueryFamily/template version, источник, типизированные slots страны/языка и evidence revision. Physical dispatch имеет отдельный action/attempt ID. Перестановка слов не открывает новый лимит; новый источник, локаль, применимый TTL или изменённое evidence могут обосновать повтор.

Предлагаемые **экспериментальные** настройки: до трёх уточнений вопроса, одно активное внешнее действие на субъект, park после двух действий без уменьшения пробела. Доля exploration новых источников — технические dispatch opportunities, не новый денежный budget. Значения выбираются сравнением с round-robin по сохранённым целевым единицам, качеству связей, latency и Firecrawl credits; модель не сама назначает оптимальные пороги.

Park сохраняет причину и условие возвращения: новый evidence, истёкшая применимость negative result, восстановленный источник, human review. Он не означает «компания не подходит». Справедливая очередь поддерживает discovery и известные субъекты; country quota не переносятся без решения человека. Если весь полезный остаток требует исчерпанного Firecrawl, миссия объяснимо завершает partial; другие допустимые пути продолжаются.

Один источник с HTTP 200 и дубликатами не даёт прогресса только из-за числа ответов. Stage yield различает discovery hits → сохранённые кандидаты → критерии/identity → подтверждённый контакт → credited unit. Общие источники/копии не превращают один субъект в несколько результатов.

## 3.14. Жизненный цикл миссии

Состояние исполнения, фаза и результат — отдельные поля будущей проекции. Они не добавляются скрыто в enum существующей клиентской заявки.

| Состояние миссии | Значение | Допустимый переход |
|---|---|---|
| `queued` | Поручение устойчиво принято, ещё нет выполняемого шага | running / paused / cancelled |
| `running` | Планирование либо конкретное действие исполняется | running / paused / completed / failed / cancelled |
| `paused` | Продолжение требует внешнего условия/решения | queued по разрешённому resume / cancelled |
| `completed` | Исследовательский цикл остановлен с устойчивым результатом | Новый явно связанный run для продолжения |
| `failed` | Невозможно устойчиво продолжать из-за терминальной ошибки | Новый run после исправления причины |
| `cancelled` | Поручение отменено | Новый run только по новому разрешённому действию |

У `completed` есть отдельный outcome: `target-reached`, `partial` или `no-results`, и stop reason: цель/Firecrawl budget-exhausted/deadline/исчерпание стратегий. Недобор после исчерпания полезных допустимых действий не выдаётся за полную цель; Firecrawl budget-exhausted становится общей stop reason только когда оставшиеся полезные действия требуют Firecrawl. Для `paused` нужны reason, ответственная сторона и условие продолжения; таймер backoff хранит `next_attempt_at`, а не бесконечный статус «в работе».

Фаза: identity / discover-sources / acquire / extract / verify-link / persist / review. Heartbeat означает, что исполнитель жив, но не доказывает появление фактов. Поэтому отдельно показываются время последнего heartbeat и последнего содержательного результата.

Терминальное решение фиксируется после принятия уже завершённых receipts и классификации оставшихся in-flight действий. Новый внешний шаг после закрытия планирования не стартует. Поздний результат допускается как объяснимое дополнение dossier с собственным временем; исторический снимок завершения миссии не переписывается молча.

Согласование in-flight ограничено отдельным сроком: неответившие вызовы остаются в reconciliation с неизвестным исходом. Для Firecrawl owner удерживает неизвестные credits; поздний settlement имеет отдельную финансовую ревизию. Для других инструментов нет app monetary hold, отсутствие proxy usage не мешает завершению. Snapshot фиксирует canonical/criteria/evidence revisions и обработанный event watermark; более поздний пересмотр меняет current dossier, не исторический состав.

Resume не повышает Firecrawl grant/технические пределы и не снимает policy block. Изменение критериев/рынков/предела требует разрешённой версии поручения/связанного run; оно не сбрасывает общий account cap. Retry имеет явную попытку; Firecrawl расход учитывается владельцем, proxy usage необязательна.

## 3.15. Когда прекращать исследование

1. Принятые и устойчиво сохранённые единицы достигли цели и квот — закрыть новые discovery/actions и завершить после bounded finalization.
2. Цели нет, но осталось полезное допустимое действие — продолжить. Firecrawl cap применяется только к Firecrawl, deadline/технические caps — по своему scope.
3. Обязательное человеческое решение или глобальное внешнее условие мешает продолжать — pause с owner/reason/deadline/условием resume. Недоступность одного источника обычно оставляет другие пути.
4. Полезные разрешённые стратегии исчерпаны, либо истёк deadline/общий технический предел — completed partial/no-results с пробелами и причинами. Firecrawl-budget-exhausted указывается, если необходимый остаток требует его вызовов.
5. Cancel прекращает новые действия и сохраняет известные результаты/неопределённые effects; terminal storage failure отличается от честного недобора.

Membership, canonical dedup и доступная ёмкость цели согласованы у `research-mission`. Receipt от provider не доказывает сохранение entity: зачёт требует owner persistence receipt и criteria/unit decision. Конкурентный последний слот занимает один canonical subject; surplus evidence остаётся в памяти. Отзыв/merge до завершения пересчитывает дефицит, после — отображается отдельно от исторического снимка.

`request-fulfillment` потребляет итог исследования и сам определяет статус клиентской заявки вместе с другими фазами. Миссия не присваивает `fulfilled`. Новый маршрут не запускает старый и новый поиск одновременно по одному intent.

## 3.16. Открытые потребности и событийное дообогащение

`OpenNeed` — предлагаемая долговечная модель пробела знаний у владельца `lead-management`. Это не клиентская заявка и не самостоятельно исполняющийся агент. Пример: «для entity A нужен email отдела продаж с подтверждённой принадлежностью». Она переживает завершение запуска и позволяет связать позднее разрешённое наблюдение с прежним исследованием.

Минимальные поля: tenant/purpose, entity_ref, тип недостающего отношения/значения, требуемые критерии, refs исходных поручений/версий, состояние и причина, refs попыток, evidence/assertion revision, next_review_at и условие повторной оценки. Повторяющиеся потребности можно объединять только при совпадающем scope и совместимых критериях; зачёт и пределы каждой миссии остаются раздельными.

| Состояние потребности | Смысл |
|---|---|
| open | Есть применимый пробел, подходящее основание пока не найдено |
| satisfied | Требуемый контакт/факт принят с конкретными версиями оснований |
| blocked | Пересмотр требует данных/решения либо сталкивается с конфликтом; причина видна |
| dormant | Потребность сохранена, активного разрешённого исполнения сейчас нет |
| obsolete | Требование более не применимо, отменено или истёк разрешённый scope; дальнейшее хранение определяется policy |

Эти состояния предлагаются для будущей модели. Они не добавляют enum существующей клиентской заявки. Истечение negative-memory TTL позволяет заново оценить полезность попытки; оно не запускает внешний вызов само по себе.

Событийный цикл будущего исполнения:

1. Владелец сохраняет evidence и предметные изменения, затем устойчивое событие с tenant/purpose и ссылками на версии.
2. Индекс зависимостей находит подходящие entities, открытые потребности и производные выводы. Точное совпадение ID проверяется по типу, юрисдикции и субъекту; семантический поиск лишь предлагает кандидата.
3. Обработчик идемпотентно проверяет новую версию, конфликты и оставшиеся достаточные основания. Запоздалое событие не откатывает актуальную проекцию; при несовпадении версии читается текущее состояние владельца.
4. В разрешённом scope обновляются утверждение/потребность, досье, индексы и резюме. Изменение допуска передаётся владельцу канала; активная миссия отдельно пересчитывает свой результат по действующим критериям.
5. UI получает объяснимое изменение: когда компания обнаружена, когда появился контакт, что подтвердилось/устарело, какие проверки ещё нужны.

`evidence-recorded`, изменение assertion, merge/split, invalidation и окончание применимости являются основаниями пересмотра. Необходимость внешнего действия оценивается отдельно. Для активной миссии проверка допускается в действующих рынках/полномочиях/технических пределах; доступный Firecrawl grant требуется только для его операций. Для терминального run обновляются текущее досье и уведомление, исходный completion snapshot сохраняется. Продолжение внешнего исследования требует явно разрешённого связанного run; LLM не создаёт новую человеческую заявку и не открывает новый Firecrawl grant.

Контрольный кейс: перезапуск между T0 и T2 не теряет компанию/потребность; поздний контакт привязывается один раз; дубликат события не увеличивает зачёт; отзыв единственного основания вновь показывает пробел; другое независимое достаточное основание сохраняет допустимый вывод; чужой tenant не получает ни факт, ни уведомление, ни контекст для LLM.

## 3.17. SearchBrief, стратегии и семейства запросов

`SearchBrief` — предлагаемая сохраняемая модель плана у `agent-orchestration`, связанная с утверждёнными OfferVersion/TargetAudience/CriteriaVersion. Она разделяет наш оффер и признаки покупателя, must/should/exclude, неизвестности, result unit, countries/quotas, язык, технические пределы и Firecrawl grant_ref. Целевой объём берётся из конкретной человеческой заявки; фиксированного общего количества лидов нет. Human facts и LLM inference имеют разное происхождение. «Внедряем CRM генподрядчикам» задаёт поиск генподрядчиков, а не агентств CRM.

`StrategyCell` описывает `(country, segment, source family, language, question, policy version)`. Полное произведение вариантов не запускается: небольшая стартовая волна расширяется по покрытию и результатам. `QueryFamily` хранит смысл/шаблон/типизированные slots; конкретная строка — вариант для backend. Изменение порядка слов не новая стратегия.

| Источник | Что ищем | Что не следует автоматически |
|---|---|---|
| Известный corpus/открытые потребности | Применимые факты и прежние попытки | Оценка другой заявки не наследуется |
| Реестры/лицензии | Идентификаторы, разрешённые отраслевые/региональные фильтры | Код деятельности сам не подтверждает ICP |
| Каталоги/ассоциации/участники выставок | Компании и их роли | Контакты издателя не принадлежат участникам |
| Закупки/проекты/новости | Названные компании и evidence деятельности | Владелец статьи не её субъект |
| Официальные сайты | Услуги, реквизиты, контакты | TLD/язык не юридическая страна |
| Другой сайт с точным ID | Поздние связи/контакты прежней entity | Одинаковое имя без основания не merge |

Query families: локальная категория+услуга+город; списки участников; проект/отраслевое событие; registry query по поддерживаемым фильтрам; exact-ID/имя+адрес для identity/contact gap. LLM предлагает местные синонимы, country profile различает неоднозначные смыслы. `DiscoveryHit` сохраняет source/document/locator/strategy/action и предложенного субъекта до принятия identity. Страница без email и статья допустимы как источник candidate discovery.

Каждая попытка даёт lineage `human intent → brief version → cell/query family → action/attempt → document receipt → entity/assertion → criterion decision → membership`. Поздний контакт связывается с прежней entity и OpenNeed; прежний terminal snapshot сохраняется. Подробная последовательность реализации — [поисковый blueprint](11-search-implementation-blueprint.md).

## 3.18. Один владелец каждой очереди

У `agent-orchestration` один сохраняемый исследовательский план с двумя классами работы: discovery новых кандидатов и gaps известных entities. Он владеет вопросами, попытками и допуском действий. `integration-platform` владеет acquisition frontier для конкретного bounded action: канонические URLs, host limits, leases, retries и receipts. Очередь выбранного crawler runtime исполняет эти work items и не начинает отдельную независимую миссию.

Стабильный action/work-item ID проходит через все уровни. Передача ownership/lease сохраняется явно; повтор dispatch восстанавливает тот же item либо явно новую попытку. Нельзя отдельно обходить весь сайт в runtime и одновременно переоткрывать те же URLs бесконечным mission planner. Source recipe может делегировать ограниченный обход с depth/page/time caps; результаты возвращаются с полной lineage.

Scheduler сначала применяет уже устойчивые receipts и пересчитывает цель, затем выбирает bottleneck: мало целевых кандидатов — discovery, достаточно почти готовых — закрытие gaps, дефицит конкретного рынка — соответствующие cells. Детерминированные проверки и рецепты обходятся без planner call; сложный вопрос получает bounded LLM proposals. Dispatch ограничивается host/source capacities, cancellation и текущими версиями. При отсутствии допустимой работы видны причина, срок ожидания либо terminal shortfall; heartbeat сам не поддерживает ложный статус прогресса.
