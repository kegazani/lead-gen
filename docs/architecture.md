# Архитектура платформы

> Реализует функциональный бэклог `docs/business-requirements.md` в границах рамки продукта — `openspec/changes/full-enterprise-core-scope/` (`design.md`, Решение 9). При расхождении действует рамка.
> Целевой рынок и юрисдикция не зафиксированы — см. открытый вопрос 6 в `design.md`. Запреты рамки действуют независимо от ответа на него.
> **Архитектура не зависит от выбранного стека.** Границы сервисов, модель данных и механизмы устойчивости отделены от технологий: стек предложен в разделе 11 и может быть заменён без переписывания остального.
> **Канонические доменные границы заданы в `architecture/domain-catalog.yaml`, а объяснены в `docs/domain-model.md`.** `docs/system-map.md` проецирует их на процессы развёртывания. Здесь остаются принципы, механизмы, эксплуатационная архитектура и стек.

## 1. Принципы

1. **Асинхронно всё, что может быть асинхронным.** Синхронными остаются только операции, где пользователь ждёт ответа на экране.
2. **Каждый движок — отдельный обработчик с явным контрактом** входа и выхода. Движки не вызывают друг друга напрямую через код; связь идёт через очередь и хранилище.
3. **Идемпотентность на всех точках приёма извне.** Повторная доставка вебхука, повторная загрузка файла, повторный запуск задания не создают дублей.
4. **Изоляция внешних сервисов.** Недоступность Firecrawl, провайдера отправки или CRM не останавливает остальной конвейер.
5. **Изоляция данных тенанта на уровне хранилища**, а не только в коде приложения.
6. **Прослеживаемость.** Для каждого атрибута контакта хранится источник и дата получения; для каждого действия, влияющего на отправку — запись аудита.
7. **Лимиты и объёмы — настройка, а не код.** Ставки, пороги, ограничения частоты и расписания меняются без выпуска новой версии.
8. **Context first.** Код, данные и контракты сначала относятся к bounded context и агрегату, и только затем — к процессу, движку или адаптеру. Чужая доменная модель напрямую не импортируется.

## 2. Доменная и компонентная архитектура

Архитектура имеет три независимые проекции:

| Проекция | Граница | Ответственность |
|---|---|---|
| Доменная | bounded context → aggregate → aggregate root/entity/value object | язык, инварианты, владение состоянием, domain events и policies |
| Прикладная | use case и опубликованный контракт | оркестрация одного сценария без передачи чужих доменных типов |
| Эксплуатационная | процесс (`api`, `worker`, `sender` и другие) | запуск, масштабирование, изоляция отказов и composition root |

Канонический список контекстов, агрегатов, сущностей и связей находится в `architecture/domain-catalog.yaml`; Markdown и PlantUML — его читаемые представления. У каждой сущности и aggregate root ровно один owning context. Межконтекстное взаимодействие идёт через command/query/event/policy contract; прямой импорт `domain` другого контекста запрещён.

Целевая структура Go-модуля — context-first:

```text
internal/
  contexts/<context-id>/
    domain/      # агрегаты, entity, value object, domain event, policy
    app/         # use cases и транзакционные границы
    ports/       # контракты, нужные этому контексту
    adapters/    # реализации портов этого контекста
  composition/   # сборка контекстов в процессы
  platform/      # технические примитивы без бизнес-терминов
cmd/<process>/
```

Общие `internal/domain`, `internal/app` и `internal/ports` не создаются: они стирают владельца модели. Повторяемый технический код допускается в `internal/platform`, но доменные правила не выносятся туда только ради переиспользования.

**Эксплуатационные слои и их ответственность**

| Слой | Ответственность | Не делает |
|---|---|---|
| Веб-интерфейс | Интерфейс, очередь утверждений, отчёты | Бизнес-логику |
| API-сервис | Аутентификация, права, CRUD, запуск заданий | Долгие операции |
| Очередь | Надёжная доставка заданий, повторные попытки, DLQ | Хранение состояния сущностей |
| Воркеры движков | Размещение application services нескольких контекстов | Владение общей доменной моделью |
| Оркестратор цепочек | Состояние и шаги последовательностей | Отправку писем напрямую |
| Хранилища | Данные, события, файлы | Логику |
| Приём событий | Публичные эндпоинты трекинга и вебхуки | Обработку (передаёт в очередь) |

## 3. Синхронное и асинхронное

| Операция | Тип | Почему |
|---|---|---|
| Просмотр списков и карточек | Синхронно | Пользователь ждёт; данные в реляционной БД |
| Поиск и фильтрация | Синхронно | Индексированные запросы |
| Загрузка файла импорта | Асинхронно | Разбор до 1 млн строк; отдаётся идентификатор задания |
| Генерация контента | Асинхронно | Внешняя LLM, секунды; лимит 30 с на документ |
| Рендеринг PDF | Асинхронно | Пул браузеров; лимит 30 с |
| Верификация адресов | Асинхронно, пакетно | Сетевые пробы; лимит 5 с на адрес |
| Отправка письма | Асинхронно, через очередь | Ограничения частоты, прогрев домена |
| Верификация расчёта и утверждение | Синхронно | Действие человека, требует немедленного ответа |
| Трекинг перехода по ссылке | Синхронно (ответ < 100 мс) | Пользователь ждёт загрузки страницы после перехода |
| Синхронизация CRM | Асинхронно, двусторонне | Внешний сервис, возможны конфликты |
| Отчёты | Асинхронно при больших периодах | Тяжёлые агрегаты |
| Сбор данных (scraping) | Асинхронно, длительные задания | Внешний сервис, минуты и часы |

## 4. Карта движков

| Движок | Исполнение | Хранилище | Особенность |
|---|---|---|---|
| 3.1 Сбор данных | Воркер, только по запросу человека | Зелёная зона | Внешний Firecrawl; фоновый сбор и кеш результатов запрещены |
| 3.2 Импорт | Воркер, потоковая обработка | Красная зона (контур клиента) | Крупные файлы; идемпотентность по хешу файла |
| 3.3 Обогащение | Воркер, только по запросу | Зелёная зона, результат не хранится | Зависит от 3.1; профили ЛПР не кешируются |
| 3.4 Дедупликация и скоринг | Синхронно (единично) + воркер (пакет) | Красная зона | Блокировки по ключу дедупликации |
| 3.5 Сегментация | Синхронные запросы + пересчёт по расписанию | Красная зона | Представления для динамических сегментов |
| 3.6 Генерация контента | Воркер | Зелёная зона | Внешняя LLM; персональные данные не передаются; версионирование |
| 3.7 Рендеринг PDF | Воркер, пул браузеров | Объектное | Детерминированный рендеринг |
| 3.8 Отправка | Отдельный сервис отправки | Реляционная + очередь | **Изолирован**; исполняет только утверждённые черновики |
| 3.9 Трекинг | Публичный эндпоинт + воркер | Аналитическое | **Только переходы**; пиксели не используются; без идентифицирующих данных |
| 3.10 Цепочки | Оркестратор состояний | Реляционная | Долгие задержки, ветвления; порождает черновики, не отправляет |
| 3.11 Синхронизация почты | — | — | **Исключён:** чтение ящиков помещает переписку и учётные данные в контур платформы |
| 3.12 Чтение сообществ Telegram | MTProto-клиент под пользовательским аккаунтом + пул аккаунтов | Красная зона (авторы, состав) + зелёная (выжимка) | **В объёме** (`design.md`, Решение 10): непрерывное чтение по расписанию; выжимка содержания без авторов; сессии изолированы |
| 3.13 LinkedIn | — | — | **Исключён:** парсинг под авторизацией, ст. 272 УК РФ |
| 3.14 CRM | Воркер + приём вебхуков | Красная зона | Twenty CRM в собственной инсталляции платформы; идемпотентность обязательна |
| 3.15 Отчётность | Read-модели | Аналитическое | Отчёты только по обезличенным агрегатам |
| 3.16 Доступ и аудит | Middleware API + запись аудита | Реляционная | Аудит неизменяем; решения оператора фиксируются |
| 3.17 Размер компании | Воркер, по запросу | Зелёная зона | Stateless-обогащение; внешний сервис оценки трафика |
| 3.18 Верификация адресов | Воркер, пакетно | Реляционная | **Отдельный исходящий IP**, не отправляющий |

## 5. Модель данных

Тактическая DDD-модель — aggregates, aggregate roots, entities, value objects, domain events и policies — зафиксирована в `architecture/domain-catalog.yaml` и объяснена в `docs/domain-model.md`. Таблица ниже остаётся обзором данных, а не назначением владельцев. Транзакционный invariant защищает aggregate root; межконтекстная согласованность достигается опубликованными событиями и policies, но это не означает обязательный event sourcing.

**Основные сущности**

| Сущность | Содержание | Ключевые связи |
|---|---|---|
| Тенант | Клиент платформы; граница изоляции | Владеет всеми сущностями |
| Пользователь | Учётная запись, роль | Принадлежит тенанту |
| Компания | Организация-цель | Много контактов |
| Контакт (красная зона, контур клиента) | Человек: имя, адрес, телефон, профили. На стороне платформы не хранится | Принадлежит компании; доступ платформы — только в рамках поручения |
| Происхождение атрибута | Источник и дата для каждого поля контакта | К контакту |
| Основание обработки | Согласие или иное основание, дата, версия документа | К контакту |
| Стоп-лист | Отписавшиеся, жалобы, жёсткие отказы | К контакту |
| Верификация | Статус, причина, дата, источник пробы | К контакту |
| Скоринг | Оценка соответствия профилю ICP | К контакту и компании |
| Сегмент | Статический или динамический, условия | Много контактов |
| Кампания | Цель, сегмент, шаблон, настройки | Много сообщений |
| Цепочка | Последовательность шагов с условиями | Много шагов |
| Сообщение | Конкретное письмо: тело, вложения, состояние | К контакту и кампании |
| Событие | Доставлено, переход по ссылке, отказ, ответ. Открытий нет | К сообщению |
| Черновик действия | Предложенное исходящее действие: предмет, состояние, срок | К лиду, кампании, тенанту |
| Решение оператора | Кто, когда, что решил, какие правки внёс | К черновику |
| Файл | PDF, вложение, исходный импорт | Объектное хранилище |
| Запись аудита | Кто, что, когда, результат | К тенанту |

**Требования к модели**

- **Разделение зон — на уровне хранилищ, а не прав.** Зелёная зона (платформа): агрегаты, статистика, данные юрлиц из открытых реестров. Красная зона (контур клиента): персональные данные физлиц, пул лидов, состояние сделки. Это разные хранилища с разными потоками записи (`design.md`, Решение 1); попытка записи персональных данных в зелёную зону завершается ошибкой.
- **Утверждение — часть модели, а не интерфейса.** Исходящее действие существует в системе только как черновик с состоянием и связанным решением оператора. Исполнение без записи решения невозможно (`design.md`, Решение 3).
- **Происхождение атрибутов.** Каждое поле контакта хранит источник и дату. Требование BRD 3.3 о приоритете источников реализуется на уровне данных, а не логикой импорта.
- **Разделение ролей.** Контакт имеет признак «потребитель или партнёр» — для метрик и для политик обработки.
- **Мультитенантность.** Идентификатор тенанта присутствует во всех таблицах и участвует в политике доступа хранилища.
- **События отделены от сущностей.** События трекинга пишутся в аналитическое хранилище: объём на порядки выше, чем у сущностей.
- **Хранение и удаление.** Сроки хранения задаются по типам данных; удаление контакта выполняется каскадно с сохранением обезличенной записи аудита.

## 6. Сквозные механизмы

### 6.1 Идемпотентность

| Точка | Ключ идемпотентности |
|---|---|
| Изменяющая команда внутреннего API | Идентификатор тенанта + клиентский идентификатор команды |
| Загрузка файла импорта | Хеш содержимого файла |
| Вебхук провайдера отправки | Идентификатор события провайдера |
| Вебхук CRM | Идентификатор записи и версия изменения |
| Событие трекинга | Идентификатор сообщения + тип + временное окно |
| Выбор слота на публичной странице | Источник + внешний идентификатор события |
| Сообщение Telegram | Идентификатор сообщества + идентификатор сообщения |
| Исполнение шага цепочки или напоминания | Идентификатор выполнения + шаг |
| Отправка утверждённого черновика | Идентификатор утверждённого черновика |
| Публикация материала | Идентификатор публикации + версия |
| Запуск задания по расписанию | Идентификатор окна расписания |

### 6.2 Очереди, повторные попытки, отказы

- Каждый движок имеет собственную очередь: сбой одного не блокирует остальные.
- Повторные попытки с нарастающей задержкой; предел попыток задаётся настройкой.
- Исчерпавшие попытки задания попадают в очередь необработанных (DLQ) и видны администратору.
- **Требование.** Потеря задания при перезапуске воркера не допускается: очередь надёжная, задание подтверждается только после успешной обработки.

### 6.3 Ограничение частоты

| Уровень | Ограничение |
|---|---|
| Домен отправки | Писем в час и в сутки; отдельно для прогрева |
| Провайдер | Лимиты API провайдера |
| Получатель | Не более заданного числа касаний за период |
| Внешние API | Firecrawl, LLM, CRM, сервис верификации |
| Пробы верификации | Обращений к одному домену в единицу времени |

**Требование.** Счётчики частоты хранятся в общем хранилище, а не в памяти процесса: при масштабировании воркеров лимиты не должны умножаться на число реплик.

### 6.4 Мультитенантность

- Изоляция обеспечивается политикой доступа хранилища, а не только фильтром в запросах.
- Тяжёлые задания одного тенанта не должны исчерпывать общие ресурсы: отдельные лимиты на тенанта.
- Секреты интеграций хранятся отдельно по тенанту.

### 6.5 Секреты

- API-ключи внешних сервисов и учётные данные интеграций хранятся в защищённом хранилище секретов в зашифрованном виде. Учётные данные почтовых ящиков менеджеров платформа не хранит: движок 3.11 исключён из объёма.
- Секреты не попадают в журналы, трассировки и сообщения об ошибках.
- Доступ к секрету — только у сервиса, которому он нужен.

### 6.6 Аудит

- Записи аудита неизменяемы: корректировка только новой записью.
- Фиксируется: субъект, действие, объект, время, результат.
- Аудит административных действий обязателен по BRD 3.16.

### 6.7 Планирование

- Расписания: пересчёт сегментов, повторная верификация, отчёты, контроль сроков утверждения. Фоновый сбор данных по расписанию не выполняется: сбор и обогащение инициируются человеком (`design.md`, Решение 2).
- Учёт часового пояса получателя при отправке по расписанию.
- Запуск по расписанию идемпотентен: пропущенное окно не приводит к двойной обработке.

## 7. Сквозные сценарии

### 7.1 Основной конвейер

```
Импорт/сбор ──> нормализация ──> дедупликация ──> верификация адресов
     ──> скоринг ──> сегмент ──> генерация контента ──> PDF
     ──> очередь утверждений (обязательно) ──> отправка
     ──> события доставки ──> CRM ──> отчётность
```

**Контрольные точки.** Подтверждение на каждом переходе: запись состояния на сущности. Сбой на любом шаге не теряет данные: задание возвращается в очередь.

### 7.2 Обработка отказа

```
Провайдер/сервер получателя ──> вебхук отказа ──> очередь ──> воркер 3.18
   ├── жёсткий отказ ──> стоп-лист, статус invalid, исключение из кампаний
   └── мягкий отказ  ──> повторная попытка, при исчерпании ──> понижение статуса
```

**Требование.** Отказ, полученный асинхронно, изменяет статус адреса до следующей кампании (BRD 3.18).

### 7.3 Обработка ответа

```
Ответ ──> вебхук провайдера или ручная фиксация ──> определение контакта по адресу
      ──> привязка к карточке ──> приостановка цепочки (3.10) ──> уведомление владельцу
      ──> возобновление цепочки только решением человека
```

### 7.4 Генерация one-pager

```
Данные лида + образец + брендкомплект ──> генерация (3.6) ──> предпросмотр
   ──> рендеринг PDF (3.7) ──> объектное хранилище ──> вложение в отправку
```

**Требование.** Рендеринг детерминирован: одинаковый вход даёт одинаковый файл, что делает возможным повторную генерацию и сравнение версий.

## 8. Развёртывание и масштабирование

| Аспект | Решение |
|---|---|
| Упаковка | Контейнеры; одинаковый образ для API и воркеров, разное назначение |
| Миграции схемы | Обратно совместимые; откат предусмотрен |
| Горизонтальное масштабирование | Воркеры масштабируются по длине очереди |
| Отдельный контур отправки | Сервис отправки масштабируется независимо: объём писем не влияет на API |
| Отдельный контур трекинга | Публичные эндпоинты на отдельном домене и отдельном масштабировании |
| Управляемые сервисы | База, кэш, объектное хранилище — управляемые: SLA 99,9 % недостижим на самообслуживании |
| Резервное копирование | Регулярное; проверка восстановления по расписанию |

**Пропускная способность отправки.** Требование к скорости не задаётся (BRD §5): ограничение находится не в платформе, а в репутации домена и графике прогрева. Кампания в 50 000 писем рассчитана на растяжение по дням и неделям. Пропускная способность задаётся провайдером отправки и состоянием прогрева домена, а не горизонтальным масштабированием сервиса отправки. Прежнее требование «не менее 5 000 писем в минуту» относилось к автономному режиму, исключённому из объёма, и снято.

## 11. Стек

Стек не является частью архитектуры: замена любой строки не требует пересмотра разделов 1–10. Основа — язык **Go** и его стандартная библиотека, прежде всего `net/http` для HTTP. Внешние системы (PostgreSQL, Valkey, RabbitMQ, Temporal, S3-совместимое объектное хранилище, провайдеры отправки, CRM, MTProto-клиент и прочие) подключаются через внутренние порты и отдельные адаптеры (раздел 2): SDK поставщика живёт только внутри адаптера и не становится контрактом домена. Конкретные продукты ниже — **текущий эксплуатационный вариант**, заменяемый сменой конфигурации; обязательными они не являются.

**Язык реализации — Go** (изменение `migrate-platform-to-go`): прежний выбор C++20 и зависимый от языка стек (`userver`, CMake, Inja, GoogleTest, TDLib, AWS SDK for C++) — **историческое решение** изменения `system-map-and-cpp-baseline`, снятое без пересмотра разделов 1–10. Проверки наличия и версий через brew выполнялись только для прежнего C++-стека; для Go-варианта такая проверка ещё не проводилась.

| Слой | Выбор | Обоснование |
|---|---|---|
| Язык и API | **Go + стандартная библиотека (`net/http`)** | Серверные процессы собираются из одного Go-модуля. HTTP-слой начинается со стандартного `net/http`; дополнительные библиотеки допускаются локально, если не становятся контрактом домена. | Сборка | **`go build` + `go.mod`** | Стандартный toolchain вместо внешнего сборщика и менеджера пакетов. Один образ на все процессы, разное назначение (§8) |
| Интерфейс | **HTMX + серверные шаблоны на `html/template`** | Серверный рендеринг. Очередь утверждений — внутренний инструмент, полноценный SPA не оправдан (§2) |
| Хранилище зелёной зоны | **PostgreSQL**, отдельный инстанс — текущий вариант адаптера репозиториев | Агрегаты и обезличенные данные |
| Хранилище красной зоны | **PostgreSQL**, отдельный инстанс и учётные данные | Физическое разделение зон (Решение 1). Перекрёстные запросы невозможны |
| Мультитенантность | **Row-level security** | Изоляция по тенанту без отдельной схемы на клиента |
| Доступ к данным | **SQL через драйвер внутри адаптера репозитория**, без ORM | Модель данных задана, запросы сложнее генерируемых. RLS и разделение зон остаются на стороне PostgreSQL; миграции — SQL-файлы, обратно совместимые (§8). Драйвер и SQL-типы не выходят за границу адаптера |

| Очередь | **RabbitMQ** через порт очередей | Подтверждения и DLQ |
| Долгие процессы | **Temporal** через порт планирования долгих процессов | Цепочки живут днями и ждут утверждения человеком. Соответствует Решению 3; при непригодности — собственный durable-планировщик поверх очереди и БД отдельным решением |
| Объектное хранилище | **S3-совместимое хранилище** через порт объектного хранения | PDF, изображения, архивы лендингов, вложения. Конкретный облачный провайдер (включая AWS S3) не обязателен: подключение — адаптер, замена — сменой конфигурации |
| Рендеринг | **headless Chromium по CDP** | Один движок на два модуля: `presentation-generator` (слайды → PDF) и `landing-page-generator` (HTML → страница). Chromium управляется по DevTools Protocol. **Проверено (Chrome 153.0.8010.48):** сам рендеринг детерминирован, но PDF не байт-идентичен «из коробки» — Chromium пишет дату создания и модификации и добавляет авто-колонтитул со временем печати. ## 13. Открытые вопросы

Закрыты выбором стека (раздел 11): брокер очередей, движок оркестрации цепочек, схема мультитенантности. Вопрос о лимите 5 000 писем в минуту снят вместе с самим требованием (BRD §5).

**Язык и рантайм пересмотрен:** платформа реализуется на **Go** (изменение `migrate-platform-to-go`), прежний выбор C++20 снят; C++ остаётся только как **явно помеченная история** изменения `system-map-and-cpp-baseline`. Более ранний выбор Python 3.12 + FastAPI был снят ещё до этого. **Проверки Go-варианта не проводились:** версия Go и выбранные библиотеки фиксируются и проверяются задачами раздела 2 изменения `migrate-platform-to-go` при первом сервисе. **Остаётся проверить:** выбор MTProto-клиента и библиотек экспорта документов, запись PPTX, пригодность Temporal для долгих процессов. Прежние проверки toolchain C++20 (Apple clang 21.0.0, CMake 4.4.3, Ninja 1.13.2), тринадцати библиотек через brew и сборки `userver` относятся к снятому C++-выбору и для Go недействительны.

Закрыты отдельно: управляемые сервисы (2), трекинговые домены (3), хранение событий трекинга (5). Порог перехода на собственный MTA (4) отложен осознанно с trigger-условием.

**Открытыми остаются два вопроса, и оба требуют твоего решения: они определяют правовой режим, а не технические параметры.**

1. **Юрисдикция хостинга** — определяет требования к хранению данных и доступности сервисов. Это выбор правового режима, а не технический параметр.
2. ~~**Управляемые сервисы или собственные**~~ — **закрыт: управляемые.** База, кэш и объектное хранилище — управляемые сервисы. Раздел 8 сам фиксирует: SLA 99,9 % на самообслуживании недостижим. Собственная эксплуатация допускается только там, где для неё есть причина, и обосновывается отдельно.
3. ~~**Трекинговые домены**~~ — **закрыт: общий домен платформы в первой версии.** Отдельный домен на тенанта умножает управление DNS и сертификатами без выигрыша, пока этого не требует клиент. При требовании со стороны клиента выделяется отдельный домен без пересмотра архитектуры: контур трекинга уже вынесен на отдельный домен (раздел 8).
4. ~~**Порог перехода на собственный MTA**~~ — **решение отложено осознанно.** Порог определяется не объёмом, а сравнением полной стоимости: расходы управляемого провайдера отправки против стоимости собственного MTA **включая эксплуатацию**. До накопления объёма сравнение не имеет данных, и назвать число сейчас значило бы выдумать его. Trigger-условие: пересмотр при приближении расходов на отправку к стоимости содержания собственного MTA с обслуживанием.
5. ~~**Хранение событий трекинга**~~ — **закрыт: сырые события 90 дней, агрегаты бессрочно.** Сырые события нужны для разбора инцидентов и проверки расхождений; дальше они занимают объём без пользы. Агрегаты хранятся бессрочно: они основа отчётности и динамики, а объём агрегатов на порядки меньше.
6. **География продукта** — целевой рынок и юрисдикция, для которой рамка обязательна. Влияет на требования к хранению и доступности, но не на архитектуру обработки.
