# archlint

Проверяет канонический каталог доменной архитектуры, его соответствие JSON Schema, владение сущностями, покрытие OpenSpec capability, направленные связи, обязательные PlantUML-диаграммы и сервисную границу (единица сервиса — bounded context).

Запуск из корня репозитория:

```bash
go -C tools/archlint run .
```

При согласованном каталоге команда печатает краткую сводку и завершается кодом 0:

```
archlint: OK — контекстов: 14, агрегатов: 14, сущностей: 47, capability: ..., связей: 28
```

При любом нарушении команда завершается ненулевым кодом и перечисляет **все** найденные нарушения за один прогон:

```
archlint: найдено ошибок: N
- <нарушение>
- <нарушение>
```

Unit-тесты и статический анализ:

```bash
go -C tools/archlint test ./...
go -C tools/archlint vet ./...
```

Сетевой доступ и внешние Go-модули не требуются: используется только стандартная библиотека. `domain-catalog.yaml` использует JSON-синтаксис, допустимый в YAML 1.2. `deploy/services.yaml` разбирается встроенным минимальным YAML-парсером (вложенные списки, flow-списки вида `[a, b]`, скаляры, комментарии).

## Проверки

### Каталог (JSON Schema и межобъектные инварианты)

- **Схема:** каталог соответствует `architecture/domain-catalog.schema.json` (типы, перечисления, обязательные поля, неизвестные поля).
- **Владение сущностями:** у сущности один owning context и один aggregate; `root_entity` и члены aggregate принадлежат тому же контексту; идентификаторы value objects / domain events / policies уникальны в каталоге.
- **Покрытие capability:** каждая capability из OpenSpec имеет ровно один primary context; каждая capability каталога объявлена в OpenSpec.
- **Связи:** ссылки на существующие контексты, запрет self-loop и повторов, контракт объявлен upstream-контекстом.
- **Диаграммы:** обязательные PlantUML-диаграммы существуют, содержат маркеры `CTX:<context>` для объявленных контекстов и не содержат неизвестных маркеров.

### Сервисная граница (единица сервиса — bounded context)

1. **Один сервис на контекст** — `validateServicePerContext`. Поле `service` обязательно, равно `id` контекста и уникально; сервисов ровно столько, сколько контекстов.
2. **Роли корректны** — `validateContextRoles`. `roles` непусты, содержат только значения `api`/`ingest`/`sender`/`worker`/`chains`/`schedule` и не дублируются. Роль `sender` разрешена только контекстам-источникам отправки (явный список `senderContexts`: `message-delivery` владеет агрегатом `message`, `integration-platform` исполняет отправку как транспортный адаптер).
3. **Транспорт объявлен и согласован** — `validateRelationshipTransports`. У каждой связи есть `transport` и `mechanism`; `command`/`query` → `sync` + `http-json`, `event`/`policy` → `async` + `amqp`. Пропуск или расхождение — ошибка с идентификатором связи.
4. **Деплой не спорит с моделью** — `validateDeploy` читает `deploy/services.yaml` (`processes` → `services` → `id`/`roles`/`mechanism`). Каждый сервис существует в каталоге, объявлен ровно в одной группе, роли группы ⊆ ролей сервиса, `mechanism` группы совпадает с режимом роли. `mechanism` может быть задан на уровне группы или сервиса (сервис уточняет групповой); `in-process` — совмещённый первый деплой и совместим с любой ролью, `http-json` — только с `api`/`ingest`, `amqp` — только с `sender`/`worker`/`chains`/`schedule`.
